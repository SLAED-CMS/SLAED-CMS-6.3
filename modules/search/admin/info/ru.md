# Модуль «Поиск»

> [!NOTE]
> Модуль `Search` — это комплексное решение, которое отвечает сразу за две связанные задачи: предоставление удобного frontend-поиска по разделам сайта для посетителей и детализированный сбор поисковой (SEO) статистики для администраторов.

## Описание
В текущей реализации система поиска не сводится к одной простой форме. Модуль работает как интеллектуальный агрегатор, способный выполнять поиск как по стандартным контент-модулям, так и по специализированным компонентам системы.

**Ключевые возможности модуля:**
- Единая frontend-форма поиска с возможностью выбора целевого раздела (модуля).
- Автоматический сбор и сохранение статистики запросов пользователей.
- Поддержка отдельных поисковых обработчиков для сложных (special) модулей.
- Панель администратора с подробной аналитикой, топом популярных запросов и ручными инструментами очистки.
- Уникальная система аудита совместимости, позволяющая подключать новые модули к глобальному поиску буквально в один клик.

---

## Пользовательская часть (Frontend)

Публичный поиск доступен по адресу: `index.php?name=search`.

Интерфейс поиска позволяет пользователю:
- Искать текстовые совпадения сразу по всей базе данных сайта (во всех включенных модулях по умолчанию).
- Сузить область поиска до конкретного модуля (например, только в «Статьях», «Форуме» или «Новостях»).
- **Интеллектуальная подсветка (Highlighting):** При выводе результатов поиска, а также при переходе на конкретную страницу (например, просмотр файла), целевые поисковые слова, переданные через URL-параметр `&word=...`, автоматически подсвечиваются ярким фоном в заголовках и тексте для быстрого визуального ориентирования.
- Для сложных модулей (например, `media`) предусмотрен расширенный фильтр по свойствам: название, описание, режиссер, роли, год выпуска.

> [!IMPORTANT]
> При каждом поиске система проверяет минимальную длину введенной строки (задается в Конфигурациях). Если анализатор запросов включен, искомая фраза фиксируется в таблице `sport_search`, формируя аналитическую базу интересов.

## Панель администратора (Admin)

Административная часть расположена в панели управления.

Она разделена на 5 логических экранов:

### 1. Главная (Журнал запросов)
Показывает сырой хронологический лог всех поисковых запросов пользователей в таблице `sport_search`. 
Для каждой записи фиксируется текст фразы (word), целевой модуль (modul), количество вводов (score) и дата последней активности (time). Поддерживается фильтрация по модулям и поиск по тексту фразы для быстрого нахождения нужных ключей.

### 2. Топ запросов
Агрегированная аналитическая сводка. В отличие от сырого лога, группирует все одинаковые запросы в единый «хит-парад». Экран позволяет понять, что именно чаще всего ищут ваши посетители. Эти данные бесценны для корректировки контент-плана или структуры навигации на сайте.

### 3. Конфигурации
Единый центр управления поведением поиска:
- Включение/отключение участвующих в поиске модулей.
- Настройка лимита выводимых результатов.
- Управление анализатором (записью) статистики.
- **Аудит совместимости**, который в реальном времени сканирует структуру таблиц доступных модулей CMS и предлагает добавить их к глобальному поиску одним нажатием (Auto-discover).

### 4. Очистка (Удалить)
Гибкий инструмент обслуживания и оптимизации базы данных поиска. Поддерживает массовое удаление старых поисковых логов (например, старше X суток), возможность чистить пустые запросы или сбрасывать лог выборочно для конкретных модулей, чтобы не перегружать БД `sport_search`.

### 5. Информация
Встроенная справочная система (текущий документ).

## Опции конфигурации

Настройки модуля физически хранятся в файле `config/search.php`.

| Параметр | Описание |
|---|---|
| **Поиск в модулях** | Список frontend-модулей, по которым в данный момент разрешен поиск. |
| **Минимум символов** | Минимальная длина поисковой строки. |
| **Максимум символов** | Верхний лимит поисковой строки для защиты базы от переполнения и обрезки SQL-запроса. |
| **Результатов на странице** | Общее количество результатов, отдаваемое на страницу поисковой выдачи на frontend. |
| **Страниц в навигации** | Размер блока кнопок постраничной навигации в публичной части сайта. |
| **Результатов в админке** | Количество строк в разделах `Главная` и `Топ запросов`. |
| **Страниц в админке** | Вывод кнопок пагинации в админке. |
| **Анализатор запросов** | Глобальный переключатель, запускающий запись поисковых фраз в таблицу `sport_search`. |

> [!WARNING]
> Значение параметра **«Минимум символов»** критически важно для безопасности и производительности. Слишком короткие слова (например, 1-2 буквы) сильно нагружают SQL-сервер при поиске по большим таблицам `LIKE %text%` и выдают много нерелевантного «мусора». Рекомендуемый минимум: 3 символа.

## Архитектура и совместимость модулей

В SLAED CMS используется гибридная архитектура поисковых алгоритмов. Модуль `search` не имеет жестко прошитого монолитного кода. Он умеет автоматически подхватывать типовые таблицы (simple-модули) и использовать изолированные обработчики для многоуровневых структур (special-модули).

### 1. Auto-совместимость (Минимальные требования)
Для того чтобы любой новый контентный модуль можно было автоматически добавить в поиск через аудит в разделе «Конфигурации», его главная таблица в БД обязана содержать минимальный набор полей.

**Обязательные поля:**
1. `id` (Уникальный числовой идентификатор записи)
2. `title` (Заголовок объекта)
3. Хотя бы одно текстовое поле поиска: `intro`, `body` или `url`.

> [!TIP]
> **Рекомендация для разработчиков:** Если вы создаете новый модуль (например, Каталог или Блог) и хотите, чтобы он легко интегрировался в поиск CMS «в один клик», желательно добавьте в свою таблицу также поля: `time` (дата публикации записи), `status` (статус активности), `cid` (категория) и `uid` (автор). 
Причина проста: если эти поля есть, подсистема поиска сможет автоматически отсеивать отключенные (`status = 0`) записи, корректно проводить сортировку по дате и выводить точное имя автора в выдаче, избегая безопасной деградации (когда дата берется текущая, а автор неизвестен).

### 2. Специальные модули (Special-handlers)
Для сложных компонентов системы авто-схема не подходит. Специальные обработчики-заглушки для поиска пишутся вручную, если модуль:
- Хранит рабочие данные не в одной типовой таблице, а просит сложных `JOIN` связей.
- Формирует специфический публичный URL в выдаче (как, например, в интернет-магазинах).
- Включает нестандартные или множественные поля поиска (мульти-теги, мета характеристики).

В SLAED CMS такими встроенными модулями-исключениями традиционно являются: `forum`, `media`, `shop`, `auto_links`. В admin-аудите поиска они помечаются как `Специальный`.

## Оптимизация и Производительность механизма

Таблица статистики поисковых фраз (`sport_search`) использует интеллектуальный счетчик весов (колонка `score`). 
При самом первом поиске слова создается уникальная запись со `score = 1`. Если другой или этот же пользователь ищет данное слово повторно в этом же целевом модуле, система не дублирует записи! Она просто обновляет время использования строки (`time`) и инкрементит `score + 1`. Таким образом таблица остается компактной.

> [!CAUTION]
> **Контроль нагрузки:** При гигантской базе данных контента поиск по текстовым полям (`intro` и `body`) без использования нативных полнотекстовых индексов (FULLTEXT) может вызывать замедление СУБД из-за сканирования (Full Table Scan). Если сайт очень большой (десятки тысяч статей), старайтесь ограничивать количество одновременно включенных в поиск простых модулей и вовремя использовать вкладку «Удалить» для сброса поисковых логов.
