# Поиск

Модуль `Search` отвечает сразу за две связанные задачи:

1. поиск на сайте по выбранным frontend-модулям;
2. администрирование поисковой статистики в панели управления.

В текущей реализации модуль уже не сводится только к одной форме поиска. Он включает:

- frontend-форму поиска с выбором модуля;
- сохранение статистики поисковых запросов в таблицу `sport_search`;
- отдельные поисковые обработчики для стандартных и специальных модулей;
- административную статистику запросов;
- топ популярных запросов;
- конфигурацию поиска;
- очистку статистики;
- аудит совместимости модулей для автоматического подключения к поиску.

## Что делает frontend-часть

Публичный поиск работает через `index.php?name=search`.

Пользователь может:

- выбрать конкретный модуль;
- искать сразу по всем разрешённым модулям;
- для модуля `media` дополнительно выбрать область поиска:
  - название;
  - описание;
  - режиссёр;
  - роли;
  - год.

При выполнении поиска модуль:

- валидирует минимальную длину строки;
- определяет набор разрешённых модулей из конфигурации;
- пишет статистику запроса в `sport_search`, если включён анализатор запросов;
- выполняет поиск по каждому подходящему модулю;
- собирает результаты в единый список;
- выводит результаты постранично.

## Что делает admin-часть

Административная часть доступна по адресу:

`admin.php?name=search`

В ней есть 5 основных экранов:

1. `Главная`
2. `Топ запросы`
3. `Конфигурации`
4. `Удалить`
5. `Информация`

### Главная

Показывает журнал поисковых запросов из таблицы `sport_search`.

Для каждой записи доступны:

- текст запроса;
- модуль;
- число входов;
- дата последнего обновления;
- действия:
  - редактирование;
  - удаление.

Поддерживаются:

- сортировка;
- фильтр по модулю;
- поиск по тексту запроса;
- подсветка совпадений;
- summary-блок со статистикой.

### Топ запросы

Показывает агрегированную статистику:

- группировку по слову;
- количество входов;
- последний момент использования слова;
- модуль, связанный с последней записью;
- действия для перехода к редактированию и очистке конкретной записи.

Это аналитический экран, а не просто raw-лог.

### Конфигурации

Позволяет:

- включать и отключать поиск по модулям;
- задавать лимиты вывода;
- включать или отключать запись статистики;
- анализировать совместимость модулей с поиском;
- автоматически подключать совместимые модули в один клик.

### Удалить

Поддерживает несколько режимов очистки статистики:

- удалить всё;
- удалить по модулю;
- удалить старше указанного количества суток;
- удалить пустые записи.

### Информация

Используется как встроенная документация по модулю.

## Настройки

Конфигурация хранится в:

`config/search.php`

Основные параметры:

| Параметр | Описание |
|---|---|
| **Поиск в модулях** | Список frontend-модулей, по которым разрешён поиск |
| **Минимум символов** | Минимальная длина поисковой строки |
| **Результатов на странице** | Количество результатов на frontend-странице поиска |
| **Страниц в навигации** | Размер блока постраничной навигации на frontend |
| **Результатов в админке** | Количество строк в `Главная` и `Топ запросы` в admin |
| **Страниц в админке** | Размер блока пагинации в admin |
| **Максимум символов** | Верхний лимит поисковой строки для SQL-поиска |
| **Анализатор запросов** | Включает запись поисковых запросов в `sport_search` |

## Таблица статистики

Для статистики используется таблица:

`sport_search`

В ней хранятся:

- `id`
- `word`
- `modul`
- `time`
- `score`

Смысл полей:

- `word` — поисковая строка;
- `modul` — модуль, в контексте которого выполнялся поиск;
- `time` — время последнего использования;
- `score` — счётчик использования запроса.

В текущей логике:

- новая запись создаётся со `score = 1`;
- повторный поиск увеличивает `score` на `1`;
- статистика больше не опирается на старое поведение с `score = 0`.

## Как работает совместимость модулей

Модуль умеет подключать к поиску не только жёстко прошитые модули, но и совместимые структуры таблиц автоматически.

Сейчас используется облегчённая модель совместимости.

### Минимальная совместимость

Для автоподключения модуль должен иметь:

1. поле `id`;
2. поле `title`;
3. хотя бы одно из полей:
   - `intro`
   - `body`
   - `url`

Этого достаточно, чтобы модуль считался `Авто-совместимым`.

### Необязательные поля

Если они есть, поиск использует их дополнительно:

- `name`
- `time`
- `cid`
- `uid`
- `status`

Если этих полей нет:

- модуль всё равно может быть подключён к поиску;
- просто часть возможностей деградирует безопасно:
  - дата берётся как `NOW()`;
  - категория не подтягивается;
  - автор не подтягивается;
  - фильтр по статусу не применяется.

### Специальные модули

Некоторые модули работают через отдельные поисковые обработчики и не попадают под простую auto-схему:

- `auto_links`
- `forum`
- `media`
- `shop`

В admin-аудите они отображаются как `Специальный`.

## Аудит совместимости в admin

В `Конфигурации` модуль показывает 3 группы:

### Уже подключены

Модули, которые уже включены в `config/search.php`.

Для них выводятся:

- имя модуля;
- тип;
- таблица;
- поисковые поля;
- маршрут редактирования.

### Доступны для подключения

Модули, которые:

- активны;
- имеют `modules/<mod>/index.php`;
- проходят проверку минимальной совместимости;
- ещё не включены в конфиг поиска.

Для них доступны:

- выбор checkbox;
- `Добавить выбранные`;
- `Добавить все совместимые`.

### Несовместимы

Для несовместимых модулей показывается причина. Например:

- таблица не найдена;
- нужны поля: `id`, `title`;
- нужно одно из полей: `intro`, `body`, `url`.

## Маршрут редактирования

В admin-аудите выводится колонка `Маршрут`.

Она показывает, какой admin-route используется для перехода к полному редактированию найденного объекта.

Примеры:

- `news_add`
- `page_add`
- `content_add`
- `shop_products_add`

Это диагностическое поле. Оно полезно при подключении новых модулей и проверке того, куда ведёт moder-меню.

## Встроенные поисковые режимы

Сейчас модуль использует 2 класса поисковых обработчиков.

### 1. Обычные simple-модули

Это модули с типовой структурой данных.

Для них поиск строится автоматически:

- определяется список поисковых полей;
- собирается SQL;
- при наличии поля `status` применяется фильтр активности;
- при наличии поля `time` используется сортировка по времени;
- при наличии `cid` и `uid` подтягиваются категория и автор.

### 2. Special-модули

Для них используются отдельные обработчики:

- `forum`
- `media`
- `shop`
- `auto_links`

Причины:

- особая структура таблиц;
- нестандартные поля;
- отдельные правила URL;
- дополнительные фильтры;
- нет прямого соответствия типовой схеме.

## Что важно при подключении новых модулей

Если новый модуль должен автоматически участвовать в поиске, лучше сразу проектировать таблицу так, чтобы она содержала:

- `id`
- `title`
- `intro` или `body` или `url`

Желательно также:

- `time`
- `status`
- `cid`
- `uid`
- `name`

Тогда модуль:

- быстрее проходит auto-аудит;
- корректнее отображается во frontend-результатах;
- лучше интегрируется с категориями и авторами;
- проще сопровождается без новых custom-веток в коде.

## Практическая рекомендация по структуре новых модулей

Для новых контентных модулей лучше использовать схему, близкую к `news/pages/files/faq/links`.

Это даёт:

- совместимость с поиском;
- совместимость с категориями;
- корректный вывод даты;
- возможность полноценного moder-редактирования;
- меньше специальных исключений в коде.

## Ограничения

Нужно учитывать несколько особенностей текущей реализации:

1. Поиск агрегирует результаты из разных модулей в один массив, а затем режет его пагинацией.
2. Для специальных модулей используются отдельные SQL-ветки.
3. Для auto-совместимых модулей используется облегчённая схема и безопасные fallback-значения.
4. Не каждый активный модуль сайта имеет физическую таблицу.
5. Совместимость в admin и фактический frontend-поиск должны оставаться синхронными.

## Когда стоит делать отдельный special-handler

Авто-совместимости достаточно не всегда.

Отдельный special-handler нужен, если модуль:

- хранит данные не в одной типовой таблице;
- требует сложных JOIN;
- имеет особый публичный URL;
- использует нестандартные поля поиска;
- должен искать по специфическим сущностям, как `media`.

## Производительность

При большом количестве контента стоит контролировать:

- длину поисковой строки;
- список включённых модулей;
- размер `slimit`;
- объём таблицы `sport_search`;
- индексацию полей `title`, `intro`, `body`, `url`, если база очень большая.

## Важно

> [!IMPORTANT]
> Значение **Минимум символов** влияет на frontend-поиск и на любые места, где используется тот же порог длины для поисковых строк.

> [!NOTE]
> Автоподключение модуля в `Конфигурации` не означает, что модуль автоматически идеален по UX. Это означает только, что его структура уже достаточно совместима для участия в поиске без написания нового special-handler.

> [!TIP]
> Если новый модуль должен подключаться «в один клик», проектируйте таблицу минимум с полями `id`, `title` и одним из `intro/body/url`. Если нужен качественный вывод даты, категории, автора и фильтра активности — добавляйте также `time`, `cid`, `uid`, `status`, `name`.
