# Мастер обновлений

Модуль **«Мастер»** работает только на slaed.net. Он раздаёт сайтам выпуски SLAED, принимает от них короткую ежедневную сводку и даёт владельцу пульт: какой выпуск подавать, какой доле сайтов, когда остановить выкатку. Сайты обращаются к мастеру только через API: `GET /api/v1/master/check` раз в сутки и `GET /api/v1/master/file` при скачивании архива. Страницы сайта у модуля нет.

> [!IMPORTANT]
> Мастер ничего не подписывает и не может подписать. Каждый выпуск, каждое оповещение и каждое заявление о ключах подписаны офлайн на машине владельца. Мастер только проверяет подписи тем же кодом, что и сайты (класс `Update` ядра), и подаёт уже подписанное. Взлом slaed.net позволяет придержать или переключить подписанные выпуски, но не подменить их.

---

## 1. Установка модуля

1. Папка `modules/master/` в архив выпуска не входит (`export-ignore`), поэтому на slaed.net её кладут по SFTP вместе с остальным кодом из репозитория. Так же — модуль `modules/changelog/` и его шаблоны `changelog*.html` из `public/templates/admin` и `public/templates/lite` (`fragments/` и `partials/`): их в выпуске тоже нет. Обновление slaed.net из панели их не трогает — файлов нет в списке поставки, а названия обоих модулей лежат в их собственных языковых файлах.
2. **Модули** → строка `master` → **Опции** → **Установка таблиц базы**: создаются таблицы `_master_site`, `_master_stat`, `_master_release`, `_master_note`.
3. Там же — **Активировать**. Пока модуль выключен, API отвечает на `master/…` кодом 404, а задачи мастера в планировщике отвечают «Отключено».
4. **Мастер → Настройки → Сохранить изменения**: создаётся `config/master.php`, и в планировщик этого сайта один раз добавляются задачи `masterclean` и `masterwatch` (раздел 9). Объявлены они в `modules/master/scheduler.php`; ядро их имён не знает и запускает, пока модуль активен. В поставочном планировщике этих задач нет: на обычных сайтах мастера нет.

Файлы мастера лежат вне веб-корня, в `storage/update/master/`:

| Папка | Что там |
| --- | --- |
| `inbox/<версия>/` | выпуск, присланный `tools/release.php publish` и ещё не принятый: оба архива, `manifest-beta.json`, `manifest-stable.json` и их подписи `.sig` |
| `inbox/notes/` | подписанные оповещения `<id>.json` и `<id>.sig`, ещё не принятые |
| `inbox/keys/` | заявления о ключах `<kseq>.json`, `.sig` и при замене ключа восстановления `.psig`; приёма они не требуют (раздел 7) |
| `<версия>/` | принятый выпуск: архивы, оба манифеста и подписи |

## 2. Путь выпуска

Всё, кроме последних трёх шагов, делается на машине владельца, в папке репозитория; полное устройство — в `docs/UPDATE.md`, раздел «Releasing».

**Что нужно на машине владельца.** PHP CLI с расширением `sodium` (`php -m` должен его назвать), `git`, `gh` со входом в аккаунт GitHub проекта, системный `sftp` со входом на slaed.net по SSH-ключу и флешка с основным ключом (раздел 7). Настройки — в файле `tools/.env`, его нет в git:

| Строка | Что значит |
| --- | --- |
| `SLAED_KEY=H:/slaed/primary.key` | путь к файлу основного ключа; без строки `sign.php` ждёт `--key=<файл>` |
| `SLAED_SFTP=user@slaed.net:22` | вход SFTP на slaed.net |
| `SLAED_SFTP_PATH=/путь/к/storage/update/master` | папка мастера на сервере; в неё `publish` кладёт `inbox/` |

| Шаг | Команда | Что видно на вкладке «Выпуски» |
| --- | --- | --- |
| Тег | `git tag v8.0.1` | ничего |
| Сборка | `php tools/release.php build v8.0.1` | ничего: архивы и манифесты лежат в `storage/release/8.0.1/` у владельца |
| Подпись | `php tools/sign.php 8.0.1` | ничего |
| Репетиция | `php tools/rehearse.php v8.0.1` | ничего |
| Публикация | `php tools/release.php publish v8.0.1` | строка `8.0.1` в таблице «Ждёт в inbox/» |
| Приём | **Принять** | выпуск в таблице выпусков в состоянии **Ждёт**; сайтам он ещё не подаётся |
| Бета | **В beta** | выпуск подаётся сайтам канала `beta` |
| Стабильный | **В stable** через несколько дней | выпуск подаётся всем сайтам: и `stable`, и `beta` |

**Репетиция** ставит прошлый выпуск начисто во временную папку и одноразовую базу, обновляет его через панель полным архивом и дельтой и возвращает назад, а новый выпуск ставит и начисто; схема после обновления должна совпасть со схемой чистой установки. Зелёная репетиция пишет `storage/release/8.0.1/rehearsal.json` с SHA-256 архивов, и `publish` без такой записи для тех же архивов отказывает. Красная номер версии не сжигает: исправить, собрать, подписать и репетировать заново под тем же номером.

**Принять** проверяет обе подписи манифестов ключом в силе, что оба манифеста называют эту версию и свой канал, что срок манифеста не истёк и что каждый архив совпадает с подписанным размером и SHA-256. Только после этого папка `inbox/<версия>/` переезжает в `<версия>/`. Отказ называет причину, а файлы остаются в `inbox/`:

| Сообщение | Причина | Что делать |
| --- | --- | --- |
| подпись не сходится с ключом в силе | манифест подписан не основным ключом в силе, например ключом восстановления или старым ключом | подписать заново `sign.php` нужным ключом и опубликовать |
| срок манифеста истёк | `expires` манифеста уже прошёл | `php tools/sign.php --refresh 8.0.1`, затем `publish` и **Принять** |
| архив не совпадает с подписанным размером или SHA-256 | архив повреждён или заменён при передаче | повторить `publish` |
| манифест неполон или другого формата, версии или канала | нет файла подписи, в папке чужая версия, манифест испорчен | собрать, подписать и опубликовать заново |
| файлов нет | папки нет в `inbox/` | проверить `SLAED_SFTP_PATH` в `tools/.env` |

Повторный **Принять** для уже принятой версии (после `--refresh`) заменяет манифесты и архивы и сохраняет состояние и долю выпуска.

### Подготовка новой версии

До тега в репозитории должно быть всё, что едет в выпуске, закоммиченное и отправленное на GitHub:

1. **Тесты зелёные** — полный `phpunit`.
2. **Номер версии** — `SL_VERSION` в `core/version.php`, строго `X.Y.Z` и выше прошлого выпуска; кодовое имя — `SL_CODENAME`. Номер в `config/global.php` не хранится.
3. **Описание** — запись в `docs/VERSIONS.md` и, если меняется что-то для чужого кода, в `UPGRADING.md`.
4. **Шаг базы данных**, если меняется схема: файл `storage/update/step/<версия>.sql` (префикс таблиц — `{prefix}`, движок — `{engine}`), при необходимости `<версия>.php` для данных и переименования опций. Та же правка схемы — в `storage/update/sql/table.sql`: новая установка ставит схему из него и сразу отмечает шаги своей версии выполненными. Репетиция сверяет обе схемы и без этой правки красная.
5. **Новая опция настроек** — в файле поставки `config/<имя>.php`; установка допишет её сайтам сама. Код читает её с запасным значением (`$conf['раздел']['опция'] ?? …`), потому что сайт, обновлённый вручную, её не получит.
6. **Первым после 8.0 идёт пустой 8.0.1** — меняется только номер; сначала beta, потом stable. Он проверяет всю цепочку на настоящих сайтах, пока их мало.

### Сборка, подпись, репетиция, публикация

```
git tag v8.0.1
php tools/release.php build v8.0.1
php tools/sign.php 8.0.1
php tools/rehearse.php v8.0.1
php tools/release.php publish v8.0.1
```

**Сборка** берёт дерево тега через `git archive` — без того, что сайту для работы не нужно: тестов, инструментов, документов, стендов и файлов разработки (список — `export-ignore` в `.gitattributes`), — кладёт в него список файлов `storage/update/files.json` и пишет в `storage/release/8.0.1/` полный архив, дельту от прошлой версии и два манифеста — beta и stable. Параметры:

| Параметр | Что задаёт |
| --- | --- |
| `--from=v8.0.0` | от какой версии собрать дельту; по умолчанию — прошлый тег |
| `--min=8.0.0` | с какой версии сайт может обновиться на этот выпуск; по умолчанию — первый выпуск с обновлятором |
| `--expires=45` | срок жизни манифеста в днях |
| `--max=<МБ>` | подтверждает размер полного архива, выросший больше чем на 20 % против прошлого; для самого первого выпуска обязателен |
| `--security` | выпуск исправляет уязвимости: плашка на сайтах красная |

Сборка отказывает, если тега нет, дерево не чистое, номер в `core/version.php` не равен тегу или не выше прошлого, в архиве есть символическая ссылка или папка вне поставки, или полный архив вырос больше чем на 20 % без `--max`. Пересборка под тем же номером сначала стирает `storage/release/8.0.1/` вместе со старыми подписями.

**Подпись** показывает версию, SHA-256 обоих архивов и коммит, спрашивает «y» и пароль основного ключа и подписывает оба манифеста. Пока выпуск не опубликован, подписи никто не видит.

**Публикация** отказывает без зелёной репетиции тех же архивов, если вшитые в ядро заводские ключи — тестовые или их отпечатков нет в README, и если `origin` репозитория указывает не на `github.com/SLAED-CMS/SLAED` — туда ведут ссылки «Доступна версия …» на всех сайтах. Затем она отправляет тег на GitHub, создаёт страницу выпуска с обоими архивами (для людей и для «Загрузить архив») и текстом, где сказано, какой архив ставит сайт, какой обновляет, их SHA-256 и что «Source code», которые GitHub добавляет сам, — исходники для разработчиков, а не выпуск, кладёт выпуск в `inbox/` мастера по SFTP через временное имя и переименование, скачивает каждый файл обратно и сверяет SHA-256.

**Красная репетиция или ошибка до публикации** номер не сжигают: тег пока только у вас. Удалите его (`git tag -d v8.0.1`), исправьте и закоммитьте, поставьте тег заново и повторите сборку, подпись и репетицию.

Первый выпуск с обновлятором (8.0.0) прошлого выпуска не имеет: репетиция ставит его только начисто.

## 3. Вкладка «Выпуски»

Таблица принятых выпусков, старшие сверху.

* **Статус** — `Ждёт`, `beta`, `stable` или **Пауза** с пометкой, кто её поставил: *поставил владелец* или *автопауза: N срывов, M удачных* — цифры, на которых сработала задача `masterwatch`.
* **Доля выкатки** — какой доле сайтов подаётся выпуск, от 0 до 100. Сайт попадает в долю по правилу `crc32(sid.'|'.версия) % 100 < доля`: у каждого выпуска своя первая когорта, а не одни и те же сайты каждый раз. Сайт вне доли получает следующий младший выпуск, который ему подходит, или ничего.
* **Принят**, **Изменён** — время приёма и последней смены состояния или доли.
* **Манифест истекает** — срок подаваемого манифеста (`expires`, по умолчанию 45 дней от подписи).
* **Опции**: **В beta**, **В stable**, **Пауза**, **Доля выкатки** (отдельная форма с числом).

Какой манифест получает сайт: из выпусков в `beta` и `stable` берётся старший выше версии сайта, если канал сайта его принимает (`stable`-сайт — только выпуски в `stable`, `beta`-сайт — оба), сайт входит в его долю и версия сайта не ниже `min` манифеста. Выпуск в `stable` подаётся своим `manifest-stable.json`, выпуск в `beta` — `manifest-beta.json`.

> [!WARNING]
> Над таблицей появляется оранжевое предупреждение за 10 дней до `expires` подаваемого манифеста. Истёкший манифест сайты не принимают: обновление им просто не предлагается, сайты не ломаются. Раз в месяц владелец переподписывает поданные манифесты: `php tools/sign.php --refresh 8.0.1`, `php tools/release.php publish v8.0.1`, затем **Принять**.

### Пауза

**Пауза** снимает выпуск с подачи сразу: следующая проверка сайта получает ответ без него, и плашка «Доступна …» на сайтах гаснет. `master/file` для выпуска на паузе отвечает 404, поэтому его не поставить и ручной загрузкой архива. Назад сайты не откатываются; исправление идёт следующей версией.

Чтобы сайтам ниже приостановленного выпуска снова подавался предыдущий, его манифест переподписывают (`sign.php --refresh`) и принимают заново: сайт, видевший более свежий манифест, старый по полю `time` отклонил бы. Ручную паузу отметьте и на странице выпуска GitHub (`gh release edit v8.0.2 --notes "Paused"`); автопауза GitHub не трогает, доступа к нему у сервера нет.

Снять паузу — **В beta** или **В stable**.

## 4. Вкладка «Сайты»

Последнее состояние каждого сайта, который проверял обновления; сверху недавние. Список служит поддержке, наружу не выводится и не выгружается.

* **Домен** — хост сайта, если сайт его сообщает; иначе *не сообщён*. Значок `(i)` открывает идентификатор (`sid`), `kseq`, последний срыв установки (версия, шаг, время) и готовую команду личного оповещения: `php tools/release.php note --level info --sid <sid>`.
* **Версия**, **Канал**, **PHP**, **База данных** (MySQL или MariaDB и версия), **Расширения** (`sodium`, `zip`, `phar` с `zlib`), **Ошибки PHP / базы** — число ошибок с прошлой проверки, без текста.
* **Первый визит**, **Последний визит**.

Поиск — по части домена. Список *Молчат больше 7 дней* показывает сайты, которые давно не проверяли обновления. Сайты, молчащие дольше срока из «Настроек», удаляет задача `masterclean`.

Домен — заявление сайта, а не доказательство: под случайным `sid` можно прислать чужой.

## 5. Вкладка «Статистика»

* Выбор дня и таблица дневного итога: канал, версия, PHP (`X.Y`), база (`mariadb 10.11`), число сайтов, сколько из них без `sodium` и без `zip`, сумма ошибок, сорванные установки за сутки. Итог за день пишет задача `masterclean` по сайтам, проверявшим обновления в последние сутки.
* **Сорванные установки по версии и шагу** — по всем сайтам: на какой версии и на каком из девяти шагов установки случился последний откат. Рост ошибок или срывов на одной версии — сигнал остановить её выкатку.

## 6. Вкладка «Оповещения»

Оповещение — короткий подписанный текст на русском и английском, который сайты показывают плашкой в панели.

* **Общее** — всем сайтам или диапазону версий: `php tools/release.php note --level warn --ver "<8.0.2" --until 2026-12-31`.
* **Личное** — одному сайту: `php tools/release.php note --level info --sid <sid>`; `sid` подписан внутри оповещения, переслать его другому сайту нельзя.

Затем `php tools/sign.php --note <id>` и `php tools/release.php publish --note=<id>` — оповещение появляется в таблице «Ждёт в inbox/». **Принять** проверяет подпись основным ключом в силе и формат и переносит его в базу; файлы из `inbox/notes/` удаляются. Неверная подпись — отказ, файлы остаются.

В таблице: уровень (`info`, `warn`, `danger`), адресат (`sid` или *все сайты*), диапазон версий, срок, начало русского текста, статус. **Деактивировать** снимает оповещение: оно исчезает с сайтов при их следующей проверке. Истёкшее по сроку перестаёт подаваться само.

## 7. Вкладка «Ключи»

Только чтение.

* Отпечатки (SHA-256 открытого ключа) заводских ключей, вшитых в ядро, и ключей в силе — основного и восстановления, и `kseq` последнего заявления.
* Заявления о ключах из `inbox/keys/` в порядке `kseq`. Заявление в силе, если оно подписано ключом восстановления в силе и его `kseq` выше прежнего; замена самого ключа восстановления требует ещё подписи основного ключа. Приёма заявления не требуют: подпись и есть доказательство. Сайт с меньшим `kseq` получает недостающие заявления при следующей проверке.
* Если заявление не прошло проверку, на каждой вкладке мастера стоит красное предупреждение с причиной: в силе остаются ключи до этого заявления, а выпуски, подписанные новым ключом, мастер не примет. Неверный файл нужно убрать из `inbox/keys/` и опубликовать заявление заново.

Отпечатки заводских ключей на этой вкладке должны совпадать с таблицей «Updates and Release Keys» в README репозитория.

### Два ключа

* **Основной** подписывает выпуски и оповещения. Нужен на каждом выпуске и раз в месяц для `--refresh`.
* **Ключ восстановления** подписывает только заявления о смене ключей. Нужен, только когда основной ключ меняют.

Открытые половины обоих вшиты в ядро (`Update::PRIMARY`, `Update::RECOVERY` в `core/classes/update.php`) и опубликованы отпечатками в README. Закрытые никогда не попадают в репозиторий, на сервер и в CI: каждая — файл, зашифрованный паролем.

### Создание ключей

Церемония проводится один раз, перед первым выпуском, в своём окне консоли на машине владельца — не через удалённый доступ и не через программу, которая записывает сеанс:

```
php tools/sign.php --keys new primary  H:/slaed/primary.key
php tools/sign.php --keys new recovery G:/slaed/recovery.key
```

* Файла по указанному пути ещё не должно быть. Пароль спрашивается дважды, не короче 10 символов, у двух ключей — разные.
* Каждая команда печатает `public` (открытый ключ) и `fingerprint` (отпечаток). `public` основного ключа встаёт в `Update::PRIMARY`, ключа восстановления — в `Update::RECOVERY`, оба отпечатка — в README; это коммит перед первым выпуском.
* Ключ восстановления один раз показывает `seed for paper` — 64 шестнадцатеричных символа группами по 8. Перепишите его на бумагу и проверьте бумагу: `php tools/sign.php --keys new recovery <временный файл> --seed` с seed с бумаги должна напечатать тот же `public`; временный файл затем удалите.
* В `tools/.env` — строка `SLAED_KEY=` с путём к основному ключу.

### Хранение

* Основной ключ — флешка и копия файла в менеджере паролей; пароль — отдельно от файла.
* Ключ восстановления — **другая** флешка и бумага с seed, вместе в сейфе, отдельно от основного ключа. Одна потеря или кража не должна уносить оба ключа: только ключ восстановления может заменить основной.

### Смена основного ключа

Нужна, если основной ключ украден, потерян или его пароль известен постороннему.

```
php tools/sign.php --keys new primary H:/slaed/primary-2.key
php tools/sign.php --keys change --primary=H:/slaed/primary-2.key --with=G:/slaed/recovery.key
php tools/release.php publish --keys=<kseq>
```

Вторая команда показывает заявление, спрашивает «y» и пароль ключа восстановления, пишет `storage/release/keys/<kseq>.json` с подписью и печатает номер заявления `kseq` для третьей; третья кладёт его в `inbox/keys/`. Сразу после этого переподпишите новым ключом всё, что мастер подаёт (предупреждение ниже), и замените `SLAED_KEY` в `tools/.env`. Прежний основной ключ уходит в отозванные и вернуться не может.

### Смена ключа восстановления

```
php tools/sign.php --keys new recovery G:/slaed/recovery-2.key
php tools/sign.php --keys change --recovery=G:/slaed/recovery-2.key --with=G:/slaed/recovery.key --key=H:/slaed/primary.key
php tools/release.php publish --keys=<kseq>
```

Такое заявление подписывают оба ключа в силе: прежний ключ восстановления и основной; новый ключ восстановления — на новую флешку и новую бумагу. Ключ восстановления, потерянный совсем, заменить нельзя: любое заявление о ключах требует его подписи. Храните две его копии, флешку и бумагу; потерянную флешку восстанавливает бумага (`--keys new recovery <файл> --seed`).

> [!WARNING]
> Сайт, получивший заявление о новом основном ключе, перестаёт принимать подписанное прежним: поданный выпуск он отклоняет с причиной `sign`, оповещение молча отбрасывает. Поэтому вместе с заявлением (`php tools/release.php publish --keys=<kseq>`) переподпишите новым ключом каждый поданный выпуск — `php tools/sign.php --refresh 8.0.1`, `publish`, **Принять** — и каждое действующее оповещение — `php tools/sign.php --note <id>`, `publish --note=<id>`, **Принять**. Принимайте их сразу, как только заявление легло в `inbox/keys/`: до этого сайты, уже взявшие заявление, видят причину `sign`.

## 8. Вкладка «Настройки»

* **Хранить молчащие сайты, дней** — по умолчанию 180.
* **Хранить дневные итоги, дней** — по умолчанию 730.
* **Порог автопаузы** — доля сорванных установок в процентах, по умолчанию 5.

Сохранение пишет `config/master.php` и один раз добавляет задачи мастера в планировщик.

## 9. Задачи планировщика

| Задача | Расписание | Что делает |
| --- | --- | --- |
| `masterclean` | раз в сутки, 04:20 | пишет дневной итог на вкладку «Статистика», удаляет сайты, молчащие дольше срока, и итоги старше срока |
| `masterwatch` | раз в час | автопауза выпусков |

### Автопауза

По каждому выпуску в `beta` или `stable` задача `masterwatch` считает с момента его приёма:

* **сорванные установки** — сайты, у которых последний срыв случился на этой версии и которые всё ещё сообщают версию ниже неё;
* **удачные** — сайты, которые сообщают эту версию. Сайт, сорвавшийся и потом поставивший выпуск, считается только удачей.

Если сорванных не меньше 5 и их доля от суммы выше порога из «Настроек», выпуск уходит в паузу с пометкой *автопауза* и цифрами, на `adminmail` slaed.net уходит письмо с версией, цифрами и самыми частыми шагами срыва, а в журнал панели ложится запись `master autopause`. Минимум в 5 срывов защищает от ложной паузы на малой выборке.

Сама задача паузу не снимает. Разберитесь по вкладкам «Сайты» и «Статистика» (на каком шаге срываются, на каких PHP и базах), выпустите исправление следующей версией или, если причина вне выпуска, переведите выпуск обратно **В beta** или **В stable**.

## 11. Приватность

* Мастер хранит только то, что сайт сам присылает в `master/check`: идентификатор, версию, канал, `kseq`, версии PHP и базы, наличие расширений, число ошибок PHP и базы, последний срыв установки и домен, если сайт его не выключил. Сайт, выключивший отправку домена, присылает пустое значение, и мастер стирает сохранённый домен при этой же проверке.
* IP-адрес в базу мастера не пишется. API считает частоту запросов по ключевому хешу адреса в файловом кэше с коротким сроком (IPv6 — по префиксу /64).
* Строку запроса `master/check` с доменом веб-сервер записал бы в журнал доступа рядом с IP. Поэтому для `/api/v1/master/` журнал nginx на slaed.net ведётся без строки запроса и без Referer. Образец для контекста `http`:

```nginx
map $uri $slaed_master {
    ~^/api/v1/master/ 1;
    default 0;
}
map $slaed_master $slaed_other {
    1 0;
    default 1;
}
log_format slaed_path '$remote_addr - $remote_user [$time_local] "$request_method $uri $server_protocol" '
                      '$status $body_bytes_sent "-" "$http_user_agent"';
```

и в блоке `server` сайта вместо прежней строки `access_log`:

```nginx
access_log /var/log/nginx/slaed.net.access.log combined if=$slaed_other;
access_log /var/log/nginx/slaed.net.access.log slaed_path if=$slaed_master;
```

* Список доменов с версиями — цель для атакующего: держите панель slaed.net под сильным паролем и ограничьте `admin.php` по IP на хостинге.
* Раз домен собирается, на slaed.net должна стоять короткая заметка о приватности службы обновлений: что сайт присылает и зачем, сколько это хранится и как удалить. Её текст на английском — в `docs/UPDATE.md`, раздел «Statistics and Privacy»; опубликуйте его на русском и английском.
