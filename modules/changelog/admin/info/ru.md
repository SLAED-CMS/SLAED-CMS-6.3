# Журнал изменений (Changelog)

Раздел **«Журнал изменений»** — это специализированная консоль мониторинга для разработчиков и администраторов. Модуль агрегирует данные из систем контроля версий, позволяя отслеживать все правки, внесённые в код проекта, прямо из панели управления сайтом.

---

## 1. Источники данных

Система SLAED CMS 8.0 Phoenix поддерживает два способа получения истории коммитов:
1. **Локальный Git:** Чтение данных непосредственно из Git-репозитория, в котором развёрнут проект на вашем сервере (требуется установленный Git на хостинге). Фильтрация выполняется силами `git log` на стороне сервера.
2. **GitHub API:** Получение истории из удалённого репозитория на GitHub с умным инкрементальным кешированием (см. раздел 4).

---

## 2. Управление журналом (Главная)

На главной странице правки идут таблицей, как и другие списки панели: одна строка — один коммит, новейшие сверху. Колонки:
* **Коммит:** Короткий хеш коммита.
* **Заголовок:** Краткая суть изменений. Значок «i» перед ним открывает описание коммита (его тело), E-Mail автора и, при включённых «Статистике» и «Показывать файлы» (только для локального Git), список изменённых файлов с числом добавленных и удалённых строк.
* **Автор:** Имя разработчика; при наведении — его E-Mail.
* **Изменения и Файл(ы):** Сколько строк добавлено (`+`) и удалено (`-`) и сколько файлов затронуто. Колонки видны при включённой «Статистике» и только для локального Git.
* **Дата:** Когда сделан коммит, относительно текущего момента; точное время — при наведении.

Таблица сортируется по любой колонке щелчком по заголовку, переключатель вида над ней меняет вид строк («Стандартный», «Полный», «Компактный», «Карточки»), а клавиши J и K проходят по строкам.

### Фильтрация и поиск
Панель фильтра стоит над вкладками:
* **Поиск:** По тексту коммита — ищет одновременно в **заголовке и теле** сообщения (регистронезависимо). Найденное подсвечивается в заголовке и описании. Клавиша «/» ставит курсор в это поле.
* **Автор:** Фильтр по разработчику — совпадение по **имени или E-Mail** (регистронезависимо).
* **Файл:** Поиск коммитов, затрагивающих конкретный файл. **Только для локального Git.** В режиме GitHub это поле скрыто, так как API списка коммитов не возвращает состав файлов.
* **Период:** Фильтрация по датам «Дата с» и «Дата по» (по дате коммита).

Фильтр остаётся в адресе страницы вместе с её номером. Если под фильтр не попал ни один коммит, список говорит «Ничего не найдено» и предлагает кнопку «Сбросить фильтр»; если коммиты не удалось загрузить, вместо списка выводится причина (например, не настроен репозиторий GitHub).

### Счётчик и страницы
Над таблицей и под ней стоит строка страниц: номер страницы, число коммитов под фильтром («Всего») и отметка «Показаны 1–10». Щелчок по отметке выбирает, сколько строк показывать на странице; без выбора действует общее число строк панели из «Конфигураций» (раздел «Пагинация»).

> [!NOTE]
> В режиме GitHub поиск и фильтры работают **в памяти по уже загруженному окну** (последние N коммитов), а не по всей истории репозитория. Это мгновенно и не расходует лимит запросов к GitHub.
> **Практический вывод:** чтобы поиск охватывал всю историю, значение «Количество коммитов» должно быть **не меньше числа коммитов в репозитории** — тогда окно совпадает со всей историей. Ограничение проявляется только если коммитов в репозитории больше, чем `limit`.

## 3. Настройки и производительность

Вкладка **«Конфигурации»** определяет технические параметры взаимодействия с репозиторием.

### Параметры GitHub API
Источник данных, владельца, репозиторий и токен видит и меняет только главный администратор: сайт обращается к указанному репозиторию с этим токеном. Когда настройки сохраняет другой администратор раздела, эти значения остаются прежними, а сохранение, в котором они всё же пришли, отклоняется с сообщением «Доступ запрещен».

* **GitHub Owner & Repository:** Имя владельца и название репозитория на GitHub.
* **GitHub Token:** Персональный токен доступа.

> [!IMPORTANT]
> GitHub Token — использование токена увеличивает лимит запросов к GitHub API с **60 до 5000 в час**. Каждые 100 коммитов = 1 запрос, поэтому для крупных репозиториев или частых обновлений токен критичен.

### Параметры отображения и кеширования
* **Количество коммитов (`limit`):** Размер **рабочего окна** — сколько последних коммитов загружать и держать в кеше (от **10 до 2000**). Это не «сколько докачивать за раз», а общий объём окна (см. раздел 5).
* **Записей на странице сайта (`rows`):** Сколько коммитов показывать на одной странице сайта. Пустое поле берёт число из «Конфигураций» (раздел «Пагинация»), оно видно в поле серым. На объём загрузки и кеш не влияет — это только разбивка показа.
* **Номеров страниц в пагинаторе сайта (`span`):** Сколько номеров страниц показывает пагинатор на сайте; пустое поле так же берёт общее число.
* **Кеширование (Cache TTL):** Время жизни кеша в секундах (по умолчанию 900 сек / 15 минут). По истечении TTL выполняется лёгкая проверка обновлений (см. раздел 4).
* **Группировать по дате:** Делит список коммитов на сайте полосами по периодам («Сегодня», «Вчера», «Эта неделя»). Таблица панели сортируется по колонкам и полос не показывает.

> [!IMPORTANT]
> Поле «Количество коммитов»: предел **2000** проверяется при сохранении конфигурации из админки — значения выше не сохраняются. Чем больше лимит, тем дольше идёт **первичная** загрузка (каждые 100 коммитов = 1 запрос) и тем тяжелее кеш-файл, поэтому без необходимости рекомендуется умеренное значение (100–300).

## 4. Архитектура кеширования (режим GitHub)

Модуль использует **инкрементальное кеширование**, чтобы не перекачивать всю историю при каждом обновлении.

* **Хранение:** кеш лежит в `storage/cache/changelog/<хэш>.json`. Один файл на рабочее окно. Очищается кнопкой «Очистить кеш» в админке или вместе с общим сбросом кеша.
* **Первичная загрузка (холодный старт):** когда кеша нет, окно строится **за один проход** — постранично по 100 коммитов, пока не наберётся `limit` или не закончится история. Этот запрос синхронный, поэтому при большом лимите первый показ страницы может занять несколько секунд.
* **Свежий кеш (в пределах TTL):** отдаётся из файла, **без обращений к GitHub**.
* **Устаревший кеш (после TTL):** выполняется **условный запрос** с заголовком `If-None-Match` (ETag):
  * **304 Not Modified** — на GitHub ничего не изменилось → отдаётся существующий кеш, TTL продлевается. Такой ответ **не расходует** лимит запросов.
  * **200 OK** — есть новые коммиты → докачиваются **только новые** (сверху, до первого уже известного коммита), затем добавляются в начало окна.

Таким образом обычное обновление раз в час обходится **одним лёгким запросом** (часто 304), а не полной перекачкой.

> [!NOTE]
> Локальный Git инкрементальное кеширование не использует — `git log` локален и дёшев. Там кеш строится на каждый набор фильтров отдельно, с тем же TTL.

---

## 5. Семантика рабочего окна (скользящее окно)

Параметр «Количество коммитов» (`limit`) задаёт **скользящее окно** последних N коммитов:

* В кеше всегда хранятся **самые свежие** `limit` коммитов.
* Пока история репозитория **меньше** `limit` — окно просто накапливается, ничего не теряется.
* Когда история **превышает** `limit` — каждый новый коммит вытесняет **самый старый** (хвост окна отбрасывается).

**Пример** (`limit = 100`, 20 коммитов в день): окно = ~5 дней истории. Каждый час докачиваются новые коммиты сверху, самые старые за пределами сотни выпадают. Большая глубина окна задаётся увеличением `limit`.

## 6. Экспорт данных

Если в настройках включена опция **«Экспорт»**, на панели навигации появляются две дополнительные вкладки:
* **Export TXT:** Формирование текстового отчёта по истории изменений.
* **Export Markdown:** Генерация истории в формате Markdown для документации проекта (например, файлов `CHANGELOG.md`).

---

## 7. Нюансы и крайние случаи

* **Поиск ограничен окном (GitHub).** Фильтры применяются к загруженным `limit` коммитам, а не ко всей истории на GitHub — ради скорости и экономии лимита запросов. *Пример:* при `limit = 500` коммит с нужным словом на позиции №650 не найдётся, так как он вне окна. Для поиска по всей истории значение `limit` должно быть **не меньше числа коммитов в репозитории** (пока оно влезает в потолок 2000).
* **Локальный Git ищет по всей истории.** `git log --grep` сканирует все коммиты и возвращает до `limit` совпадений — ограничение окном это специфика именно GitHub-режима.
* **Фильтр по файлу — только Git.** В режиме GitHub поле «Файл» скрыто (нет данных о файлах в списке коммитов API).
* **Force-push / rebase.** Если знакомые коммиты исчезли с GitHub (переписана история), кеш самовосстанавливается: не найдя известный коммит, модуль перестроит окно заново.
* **Сбой сети / ошибка API.** При недоступности GitHub в момент обновления отдаётся имеющийся (устаревший) кеш — журнал не «обнуляется».
* **Смена лимита.** При изменении `limit` создаётся новое окно-кеш (старый файл с прежним лимитом перестаёт использоваться и удаляется при сбросе кеша).

> [!WARNING]
> Статистика добавленных и удалённых строк (`Show statistics`) и список файлов доступны только при источнике **«Локальный Git»**. GitHub API не предоставляет эти данные в рамках стандартного запроса списка коммитов.
