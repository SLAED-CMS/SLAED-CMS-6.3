# Журнал изменений (Changelog)

Раздел **«Журнал изменений»** — это специализированная консоль мониторинга для разработчиков и администраторов. Модуль агрегирует данные из систем контроля версий, позволяя отслеживать все правки, внесённые в код проекта, прямо из панели управления сайтом.

---

## 1. Источники данных

Система SLAED CMS 6.3 Phoenix поддерживает два способа получения истории коммитов:
1. **Локальный Git:** Чтение данных непосредственно из Git-репозитория, в котором развёрнут проект на вашем сервере (требуется установленный Git на хостинге). Фильтрация выполняется силами `git log` на стороне сервера.
2. **GitHub API:** Получение истории из удалённого репозитория на GitHub с умным инкрементальным кэшированием (см. раздел 4).

---

## 2. Управление журналом (Главная)

На главной странице выводится хронологический список правок (новейшие сверху). Каждая запись содержит:
* **Заголовок и Хеш:** Краткая суть изменений и уникальный идентификатор коммита.
* **Автор:** Имя и E-Mail разработчика, внёсшего изменения.
* **Статистика:** Количество добавленных (`+`) и удалённых (`-`) строк кода (только для локального Git).
* **Список файлов:** Перечень изменённых файлов в рамках коммита (только для локального Git).

### Фильтрация и поиск
Для быстрого анализа доступны фильтры:
* **Поиск:** По тексту коммита — ищет одновременно в **заголовке и теле** сообщения (регистронезависимо).
* **Автор:** Фильтр по разработчику — совпадение по **имени или E-Mail** (регистронезависимо).
* **Файл:** Поиск коммитов, затрагивающих конкретный файл. **Только для локального Git.** В режиме GitHub это поле скрыто, так как API списка коммитов не возвращает состав файлов.
* **Период:** Фильтрация по датам «С» и «По» (по дате коммита).

### Счётчик результатов
Под фильтрами выводятся два числа:
* **«Всего»** — сколько коммитов загружено в рабочее окно (см. раздел 5).
* **«Отфильтровано»** — сколько из них попало под текущие фильтры.

> [!NOTE]
> В режиме GitHub поиск и фильтры работают **в памяти по уже загруженному окну** (последние N коммитов), а не по всей истории репозитория. Это мгновенно и не расходует лимит запросов к GitHub.
> **Практический вывод:** чтобы поиск охватывал всю историю, значение «Количество коммитов» должно быть **не меньше числа коммитов в репозитории** — тогда окно совпадает со всей историей. Ограничение проявляется только если коммитов в репозитории больше, чем `limit`.

## 3. Настройки и производительность

Вкладка **«Конфигурации»** определяет технические параметры взаимодействия с репозиторием.

### Параметры GitHub API
* **GitHub Owner & Repository:** Имя владельца и название репозитория на GitHub.
* **GitHub Token:** Персональный токен доступа.
  > [!IMPORTANT]
  > Использование токена увеличивает лимит запросов к GitHub API с **60 до 5000 в час**. Каждые 100 коммитов = 1 запрос, поэтому для крупных репозиториев или частых обновлений токен критичен.

### Параметры отображения и кэширования
* **Количество коммитов (`limit`):** Размер **рабочего окна** — сколько последних коммитов загружать и держать в кэше (от **10 до 2000**). Это не «сколько докачивать за раз», а общий объём окна (см. раздел 5).
  > [!IMPORTANT]
  > Предел **2000** проверяется при сохранении конфигурации из админки: значения выше не сохраняются. Чем больше лимит, тем дольше идёт **первичная** загрузка (каждые 100 коммитов = 1 запрос) и тем тяжелее кэш-файл, поэтому без необходимости рекомендуется умеренное значение (100–300).
* **На страницу (`perpage`):** Сколько коммитов показывать на одной странице пагинации (от 5 до 50). На объём загрузки и кэш не влияет — это только разбивка показа.
* **Кэширование (Cache TTL):** Время жизни кэша в секундах (по умолчанию 900 сек / 15 минут). По истечении TTL выполняется лёгкая проверка обновлений (см. раздел 4).
* **Группировка:** Опция группировки коммитов по временным периодам («Сегодня», «Вчера», «На этой неделе»).

---

## 4. Архитектура кэширования (режим GitHub)

Модуль использует **инкрементальное кэширование**, чтобы не перекачивать всю историю при каждом обновлении.

* **Хранение:** кэш лежит в `storage/cache/changelog/<хэш>.json`. Один файл на рабочее окно. Очищается кнопкой «Очистить кэш» в админке или вместе с общим сбросом кэша.
* **Первичная загрузка (холодный старт):** когда кэша нет, окно строится **за один проход** — постранично по 100 коммитов, пока не наберётся `limit` или не закончится история. Этот запрос синхронный, поэтому при большом лимите первый показ страницы может занять несколько секунд.
* **Свежий кэш (в пределах TTL):** отдаётся из файла, **без обращений к GitHub**.
* **Устаревший кэш (после TTL):** выполняется **условный запрос** с заголовком `If-None-Match` (ETag):
  * **304 Not Modified** — на GitHub ничего не изменилось → отдаётся существующий кэш, TTL продлевается. Такой ответ **не расходует** лимит запросов.
  * **200 OK** — есть новые коммиты → докачиваются **только новые** (сверху, до первого уже известного коммита), затем добавляются в начало окна.

Таким образом обычное обновление раз в час обходится **одним лёгким запросом** (часто 304), а не полной перекачкой.

> [!NOTE]
> Локальный Git инкрементальное кэширование не использует — `git log` локален и дёшев. Там кэш строится на каждый набор фильтров отдельно, с тем же TTL.

---

## 5. Семантика рабочего окна (скользящее окно)

Параметр «Количество коммитов» (`limit`) задаёт **скользящее окно** последних N коммитов:

* В кэше всегда хранятся **самые свежие** `limit` коммитов.
* Пока история репозитория **меньше** `limit` — окно просто накапливается, ничего не теряется.
* Когда история **превышает** `limit` — каждый новый коммит вытесняет **самый старый** (хвост окна отбрасывается).

**Пример** (`limit = 100`, 20 коммитов в день): окно = ~5 дней истории. Каждый час докачиваются новые коммиты сверху, самые старые за пределами сотни выпадают. Большая глубина окна задаётся увеличением `limit`.

## 6. Экспорт данных

Если в настройках включена опция **«Экспорт»**, на панели навигации появляются две дополнительные вкладки:
* **Export TXT:** Формирование текстового отчёта по истории изменений.
* **Export Markdown:** Генерация истории в формате Markdown для документации проекта (например, файлов `CHANGELOG.md`).

---

## 7. Нюансы и крайние случаи

* **Поиск ограничен окном (GitHub).** Фильтры применяются к загруженным `limit` коммитам, а не ко всей истории на GitHub — ради скорости и экономии лимита запросов. *Пример:* при `limit = 500` коммит с нужным словом на позиции №650 не найдётся, так как он вне окна. Для поиска по всей истории значение `limit` должно быть **не меньше числа коммитов в репозитории** (пока оно влезает в потолок 2000).
* **Локальный Git ищет по всей истории.** `git log --grep` сканирует все коммиты и возвращает до `limit` совпадений — ограничение окном это специфика именно GitHub-режима.
* **Фильтр по файлу — только Git.** В режиме GitHub поле «Файл» скрыто (нет данных о файлах в списке коммитов API).
* **Force-push / rebase.** Если знакомые коммиты исчезли с GitHub (переписана история), кэш самовосстанавливается: не найдя известный коммит, модуль перестроит окно заново.
* **Сбой сети / ошибка API.** При недоступности GitHub в момент обновления отдаётся имеющийся (устаревший) кэш — журнал не «обнуляется».
* **Смена лимита.** При изменении `limit` создаётся новое окно-кэш (старый файл с прежним лимитом перестаёт использоваться и удаляется при сбросе кэша).
