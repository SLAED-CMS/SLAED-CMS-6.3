# Интеграции Node с SLAED

Статус: проектирование завершено; реализация и её проверки выполняются по 13-testing.md и 14-roadmap.md.

## Цель

Подключить `node` к существующим глобальным подсистемам без их дублирования и без жёстких списков конкретных типов.

## Подсистемы

Для каждой интеграции необходимо зафиксировать целевой контракт, необходимые изменения, ошибки и проверку.

Настройки поиска, RSS, sitemap, блоков и SEO принадлежат `config/node.php → types → <name> → integrations`; общий код не содержит список имён типов. Раздел содержит только логические `search`, `rss`, `sitemap`, `blocks` и строковый `seo` со значением `website`, `article` или `news`. Все четыре включателя по умолчанию равны `false`, а `seo` — `website`.

## Размер синхронизации

`config/node.php → limits.syncbatch = 500` ограничивает только количество ID материалов, которое Node передаёт одной глобальной подсистеме за один проход. Например, очистка данных `1200` материалов в комментариях, рейтинге или избранном выполняется как `500 + 500 + 200`. Входные ID сначала приводятся к положительным целым значениям и удаляются повторы.

- Одиночная запись материала и её синхронные побочные действия остаются одной транзакцией и не превращаются в фоновую задачу.
- Массовая операция делится до вызова интеграции; одна интеграция не получает более `syncbatch` ID и не выполняет запрос на каждый материал.
- Долгий последовательный обход использует курсор `id > <последний ID> ORDER BY id ASC LIMIT 500`, а не `OFFSET`. Успешная партия фиксируется целиком; после ошибки повтор начинается с последнего подтверждённого курсора.
- Для sitemap Node читает минимальную проекцию по `500` строк, а общий генератор сразу записывает результат и делит XML по существующему пределу `50000` URL, не собирая все материалы Node в памяти.
- Интерактивный поиск сохраняет собственный `search.slimit`, RSS — `rss.max`, а доставка почты — `mail.batch`; Node не дублирует и не подменяет их настройки.
- Отдельные пределы для файловых и сетевых расширений не создаются. Если расширение выполняет внешнюю синхронизацию, размер и повтор определяет его собственный подтверждённый контракт.

## Порядок подключения

Интеграции подключаются по фактическим зависимостям, а не одним завершающим пакетом:

1. Категории и сборка `NodeContext` входят в основу чтения и записи до базового CRUD.
2. CRUD и жизненный цикл материала стабилизируют глобальный ID, состояния и транзакционные границы.
3. До первой целевой подсистемы утверждается единый контракт регистрации и разрешения цели Node.
4. Одновременно заранее фиксируются события, получатель, уникальность и момент начисления или возврата баллов.
5. Уведомления подключаются после успешной фиксации соответствующего изменения материала.
6. Комментарии подключаются вместе с разрешением цели, `comnum` и относящимися к ним баллами.
7. Рейтинг подключается вместе с `score`, `ratings`, защитой повторного голоса.
8. Избранное подключается через тот же контракт цели вместе со своими баллами.
9. Поиск, блоки и главная используют уже стабильное публичное чтение.
10. RSS, sitemap и SEO подключаются после окончательных публичных маршрутов и правил видимости.

Пользовательская личность и уведомления не считаются одной интеграцией: первая является входной зависимостью `NodeContext`, вторые — побочным действием завершённого жизненного цикла. Баллы могут включаться поэтапно вместе с владельцем события, но их общий контракт утверждается до комментариев и избранного, чтобы эти подсистемы не переделывались повторно.

## Единая регистрация типа

Node не регистрирует каждый тип отдельно в комментариях, рейтинге, избранном, поиске, RSS, sitemap или блоках. Единственный реестр образуют `_node_types` и `config/node.php`; глобальные подсистемы разрешают его через публичный API `NodeQuery`.

- В колонке `modul` существующих глобальных таблиц хранится неизменяемое публичное имя типа, например `news` или `docs`.
- В `cid`, `mid` или `fid` хранится глобальный `_nodes.id`; локальный ID типа и составной идентификатор не создаются.
- Активность типа, существование и видимость материала проверяются одним предикатом Node, а включённая возможность — по полученному `NodeType`.
- Перед изменением `comment`, `rate`, `favorite`, `asset` или `report` зарегистрированное расширение дополнительно вызывается через `checkNodeAction()` и может только сузить уже полученное разрешение.
- После успешного фактического изменения та же транзакция вызывает `updateNodeAction()`. Метод не выполняет глобальное действие повторно и может изменить только собственную строку расширения; его ошибка откатывает обе части.
- Административная модерация динамического типа использует право `node-<name>` из `NodeContext`, а не значение `modul` как самостоятельное право старого модуля.
- Имя типа неизменяемо после создания, поэтому сохранённые глобальные ссылки не требуют каскадного переименования.
- Фиксированные цели, которые не принадлежат Node, остаются ответственностью своей подсистемы; они не копируются в конфигурацию Node.
- Для одиночных и пакетных потребителей Node предоставляет `getNodeTarget()` и `getNodeTargetList()` с объектами `NodeTarget`, без загрузки текста, полей, категорий, связей и ресурсов.

Отдельные `Registry`, `Provider`, таблица регистраций и список имён Node в каждой подсистеме не создаются. Неизвестное, отключённое или недоступное имя разрешается как отсутствующая цель без раскрытия внутренней причины.

### Категории

Динамическая регистрация типа вместо фиксированных списков модулей, сохранение дерева, языков и прав. `_nodes.cid` хранит одну основную категорию и определяет язык и основной маршрут; `_node_categories` хранит только дополнительные связи. Список категории объединяет оба индексируемых источника и возвращает материал один раз. Строковые списки по образцу старого `news.assoc` не используются.

### Комментарии

Динамический resolver цели вместо фиксированной карты таблиц, сохранение веток, модерации и счётчиков.

Для Node действие считается завершённым при первой фактической видимости комментария: немедленно при открытом режиме либо при последующем одобрении модератором. Тогда вызывается `updateNodeAction(..., 'comment')`; редактирование, скрытие и удаление уже учтённого комментария повторный вызов не создают. `NodeSupport` использует этот вызов, чтобы атомарно обновить сторону ожидания, `activity` и `version` без собственной таблицы ответов.

### Рейтинг

Полный контракт: [ratings.md](ratings.md). Scope node.<name> разрешается через NodeQuery/NodeService и расширение. Прямой SQL глобальных обработчиков к _nodes запрещён; Point не участвует.

### Избранное

Глобальный ID материала и его тип.

### Поиск

Единая выборка опубликованных типов с `integrations.search = true`, индексируемые поля и формат результата. Поиск выполняется во время запроса и ограничивается существующим `search.slimit`; отдельный индекс, перестроение и пакет Node первой версии не создаются.

### RSS и sitemap

Получение материалов типов с соответствующими `integrations.rss` и `integrations.sitemap` через публичный read API и устойчивые маршруты. RSS использует существующий `rss.max`. Sitemap получает минимальные строки Node последовательными партиями `syncbatch` и записывает XML потоково в файлы не более `50000` URL.

Интеграции и архивные блоки ограничивают публикацию через `NodeQuery::setNodePublished()` с включённой нижней и исключённой верхней границей. Свободное имя колонки или неоднозначный период в API не передаются.

### Блоки и главная

Тип с `integrations.blocks = true` можно выбрать в общих блоках. Блок использует `NodeQuery` без собственного SQL к таблицам Node.

### Пользователи и уведомления

Авторство, права, административные уведомления и пользовательские публикации.

Расширение `support` не создаёт свою очередь уведомлений и использует существующий `Mail`. Единственная логическая настройка `ext.mail`, по умолчанию включённая профилем `help`, управляет всей почтой Ticket System:

- новое обращение уведомляет подписанных через `_admins.smail` администраторов с правом `node-help`, включая главного администратора;
- ответ владельца уведомляет назначенного и подписанного администратора; при `aid = 0`, отсутствующем администраторе или отключённой его подписке уведомление получают остальные подписанные модераторы типа;
- ответ администратора уведомляет зарегистрированного владельца обращения, если у его учётной записи есть адрес;
- отправитель никогда не получает уведомление о собственном действии, а закрытие, повторное открытие, назначение и смена приоритета отдельного письма не создают;
- письмо содержит название сайта, безопасный заголовок обращения, имя стороны и контролируемую ссылку, но не копирует приватный текст ответа;
- строка существующей почтовой очереди создаётся только после успешного фактического события. Ошибка постановки письма журналируется, но не откатывает уже сохранённое обращение или комментарий; физическая доставка остаётся задачей штатного обработчика Mail.

При `ext.mail = false` не создаётся ни одно письмо поддержки. Раздельные переключатели нового обращения и ответа, пользовательская подписка на один тикет, собственная таблица уведомлений и новый почтовый сервис первой версии не создаются.

### Баллы

Point получает доверенный источник успешного действия и работает до COMMIT владельца. API, суммы, источники, компенсация и ошибки: [points.md](points.md). Rating не создаёт событий Point. Подключение общих владельцев — S04, Node — S16.

### Право привязки редакторских вложений

По NOD-198 при создании и содержательном изменении `NodeService` получает точный набор имён из `Parser::getAttachList()` для новых `intro/body`. Для обновления отдельно извлекается набор из сохранённого текста этого же материала; клиент не передаёт доверенный список прежних вложений.

- Имя, уже присутствовавшее в этом материале, может остаться после правки другим редактором с правом изменения материала. Присутствие в чужом материале, соседнем поле формы или клиентском списке не даёт такого права.
- Каждое впервые добавленное имя требует существования файла, разрешённого пути и проверки владельца. Используются штатные `getUploadTakenFile()`, `getEditorFileOwner()` и `FileManager::getFileOwner()`; второе хранилище владельцев Node не создаётся.
- Пользователь может привязать свою загрузку, гость — загрузку текущей сессии. Исключение владения возможно для модератора только при подтверждённом праве на файловую область данного типа; управление конфигурацией само по себе его не даёт.
- Повторная проверка допустимого имени, расширения и границ каталога обязательна и для прежнего вложения. Смена `intro` на `body` внутри того же материала не считается привязкой чужого файла. Разрешение чтения чужого материала не означает право копировать его вложения.
- Для структурированного ресурса новый локальный `src` проходит ту же проверку; прежний `id` должен принадлежать этому материалу. Замена `src` проверяется как новая привязка, даже если сохранён ID строки.
- Проверки выполняются при `preview` и повторно при сохранении. Отказ не записывает материал, связи или ресурсы; неизвестные имена не принимаются на основании одной строки `[attach]`.



### Файловый менеджер

Единственным интерфейсом выбора структурированного ресурса является существующий `getFileManagerField()` (`docs/WINDOW.md`) со штатным местом `<type>.attach`. `node` принимает результат выбора, повторно проверяет файл, путь или внешний адрес на сервере и сохраняет одну строку `_node_assets`; для нескольких ресурсов поле повторяется с уникальным ID без второго загрузчика.

Каждый тип использует стандартную область `uploads/<type>`, как отдельный модуль SLAED. Файлы `[attach]` редактора и локальные структурированные ресурсы `_node_assets` находятся в её корне, а уменьшенные копии изображений редактора — в `thumb`. Контекст редактора передаёт публичное имя текущего типа как `mod`, поэтому `getTplTextarea()` сам выбирает `$conf['uploads'][<type>]`, `<type>.attach` и правильный каталог.

Единственная адаптация общего файлового слоя касается модерации динамического типа. `getUploadPlaceRule()` сохраняет `mod = <type>` для конфигурации и пути, но разрешает административные файловые действия по существующему ключу `_admins.modules = node-<type>`; `checkEditorUploadAccess()`, `getEditorFileOwner()` и `getUploadFileArea()` используют полученное сервером право, а не значение из формы. Отдельная ACL, Node-загрузчик и параллельная проверка доступа не создаются.

Парсер использует уже существующее разрешение `[attach]` относительно `uploads/<mod>` и `uploads/<mod>/thumb`; отдельная схема пути Node ему не требуется. В контролируемом режиме он формирует `op=attach&id=<nid>&key=<name>` и добавляет `thumb=1` только для существующей уменьшенной копии; в прямом режиме сохраняет стандартный физический URL. Сигнатуры `Parser::filterContent()` и `Parser::filterDoc()` получают последний совместимый параметр `int $nid = 0`, который Node передаёт при выводе сохранённого материала и включает контролируемые адреса. Ключ внутреннего кеша парсера учитывает `nid`; старые вызовы не меняются.

`Parser::getAttachList(string $src): array` возвращает уникальные безопасные имена вложений в порядке появления и использует ту же грамматику, что закрытый `filterAttach()`. Маршрут проверяет объединение списков исходных `intro` и `body`; отдельный регулярный шаблон в модуле Node не создаётся. Дополнительные поля первой версии не являются местом `[attach]`, а структурированные файлы принадлежат `_node_assets`.

`Upload` назначает безопасное имя один раз. Multipart-файл формы сохраняется существующим `getUploadService()`, а выбранный существующий путь проверяется существующим `getUploadTakenFile()`. Node не переименовывает файл повторно, не копирует его в `storage/node`, не создаёт собственного закрытого хранилища, `temp` или `public`. Единые правила веб-сервера запрещают выполнение PHP во всём дереве `uploads`.

Ресурс наследует состояние материала, право чтения его основной категории и дополнительные ограничения расширения; собственные `access` и `groups` у роли отсутствуют. Возможность `report` сохраняет `reported` и `ruid` первой жалобы в конкретной строке `_node_assets`, а не меняет состояние материала. Разбор блокирует и повторно проверяет эту строку; начисление за полезную жалобу и очистка выполняются одной транзакцией. Способ отдачи не настраивается: тип с категориями или расширением автоматически закрывает сервером весь `uploads/<type>` и отдаёт файлы через Node без отдельного каталога и копирования.

### Отдача ресурсов

Адрес `index.php?name=<type>&op=asset&id=<id>` проверяет совпадение типа маршрута с типом ресурса, материал, основную категорию и ограничения расширения. При прямой отдаче режим `download` атомарно увеличивает `_node_assets.hits` и перенаправляет на разрешённый локальный или внешний URL; при контролируемой отдаче этот же адрес обслуживает локальный ресурс.

- Локальные `image`, `gallery`, `poster` и `player` в прямом режиме используют URL из `uploads/<type>` и не проходят через PHP.
- В прямом режиме веб-сервер самостоятельно обслуживает MIME, длину, кеширование и диапазоны для плеера и продолжения скачивания; существующие правила `mod_expires` не дублируются в Node.
- В контролируемом режиме прямой доступ запрещён ко всему дереву типа, включая корень редакторских файлов и `thumb`; структурированные ресурсы обслуживает `asset`, а редакторские файлы — утверждённый маршрут `attach`.
- Внешний URL передаётся клиенту только после проверки допустимой схемы; сервер его не скачивает, не измеряет и не проксирует.
- `none` не создаёт автоматическую ссылку.
- `hits` означает одно разрешённое начало скачивания через Node, а не количество частей файла или всех HTTP-запросов. `HEAD`, повторный `Range` и прямое отображение изображения счётчик не увеличивают.
- `HEAD`, отказ и отсутствующий файл не увеличивают `hits`.
- Изменение `hits` не меняет `_nodes.version`, `_nodes.updated` и `_node_assets.updated`.
- Чтение ресурса выполняет `NodeQuery::getNodeAsset()`, а изменение `hits`, `reported` и `ruid` — три утверждённых метода `NodeService`; контроллеры и интеграции не пишут в `_node_assets` напрямую.
- Простому типу без категорий и расширения общий файловый ответ для визуальных ресурсов не требуется. Тип с категориями или расширением использует утверждённый общий файловый ответ.

Точная совместимая сигнатура существующей функции:

```php
function getFileStream(
    string $path,
    string $name,
    string $mime = 'application/octet-stream',
    bool $inline = false,
    bool $cached = false,
    ?callable $start = null
): void
```

- Первые два аргумента и их поведение сохраняются для всех существующих вызовов: по умолчанию это вложение `application/octet-stream` без хранения в кеше.
- `mime` передаётся только из проверенных серверных метаданных; значение запроса не используется. Неизвестное значение заменяется на `application/octet-stream`.
- `inline = true` действует только для закрытого реестра безопасных растровых изображений, аудио и видео. SVG, HTML, XML, PDF и неизвестные активные форматы принудительно становятся вложением.
- `cached = true` вызывает `Cache::setPrivateHeaders()` и включает частное хранение браузером с обязательной повторной проверкой; серверную копию файла функция не создаёт.
- `$start` вызывается после успешного открытия и разбора условий, но до отправки заголовков и тела, только для полного ответа или диапазона с нулевого байта. Callback отсутствует у прежних вызовов и у режимов, которым не нужен счётчик.
- Полная отдача и один диапазон используют один открытый файловый дескриптор, `fseek()` и ограниченные блоки чтения; размер файла не влияет на память PHP, а разрыв соединения прекращает цикл.
- Диапазоны используют исходные байты без динамического сжатия и с `no-transform`; `Accept-Ranges`, `Content-Length`, `Content-Range`, `Content-Disposition` и безопасное имя формируются централизованно.

Существующий класс кеша расширяется без изменения прежних вызовов:

```php
public static function setPrivateHeaders(string $type, int $mtime, string $etag): void
public static function checkNotModified(int $mtime, string $etag = ''): bool
```

- `setPrivateHeaders()` выдаёт общие защитные заголовки SLAED, `Last-Modified`, `ETag` и `Cache-Control: private, no-cache, must-revalidate, no-transform`; cookie не удаляются.
- `checkNotModified()` сначала проверяет точное совпадение `If-None-Match`, а при отсутствии этого заголовка — `If-Modified-Since`; старый вызов только с датой остаётся совместимым.
- Валидатор строится без чтения всего файла из его канонического пути, размера и времени изменения. Случайное имя, назначаемое `Upload`, не переиспользуется для другого содержимого.
- Глобальный `cache_b` остаётся настройкой HTML-страниц и не управляет файлами; каталог `storage/cache` не получает байты ресурсов.

## Критерии готовности

- Ни одна интеграция не содержит список имён мигрированных типов в общем коде.
- Другие модули не обращаются напрямую к таблицам `node`.
- Удаление и изменение статуса синхронно обновляют связанные глобальные данные.
- Составные операции участвуют в одной транзакции или имеют явно описанную компенсацию.
- Ни одна интеграция не получает больше `limits.syncbatch` ID за вызов и не создаёт N+1.
- Обход более `syncbatch` строк использует проверяемый курсор, а не `OFFSET`.

## Опрос материала и оставшиеся владельцы ограничений

poll — целый ID существующего опроса общей подсистемы; 0 означает отсутствие связи, как в _nodes и NodeInput. При назначении проверяются существование, доступность и features.poll; произвольный ID из формы не считается правом. Отображение повторно проверяет доступность опроса, голос передаётся существующему обработчику опросов с его серверными правами, методом и CSRF. Отключение features.poll скрывает блок и запрещает новое назначение, сохраняя прежнюю связь. Удаление материала убирает только ссылку Node, не общий опрос; удаление опроса очищает ссылки через NodeService в транзакции владельца, без удаления материалов.

В целевой первой версии временная _rating остаётся хранилищем ограничений опросов с modul=voting. Это окончательная граница данной работы, не fallback нового Rating. Очистка истёкших ограничений ограничивается voting; новая история рейтинга из трёх таблиц не участвует. Награда poll использует ID опроса как source, visit в остающемся auto_links — ID ссылки; один uid/action/scope/source вознаграждается один раз за жизнь цели независимо от повторных переходов и срока ограничения. Нулевая награда не создаёт строку Point. Счётчик outs обновляется по собственному контракту перехода; он не зависит от успеха баллов. Старый addPointsAction() удаляется после замены всех остающихся вызовов, без обёртки.
