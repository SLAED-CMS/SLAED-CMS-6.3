# Point — класс системы баллов

Действующий контракт. Класс — S01, подключение — S04 в [дорожной карте](14-roadmap.md). Rating и Node не являются зависимостями.

## Граница первого окна

Создать core/classes/point.php, config/points.php, DDL _points в setup/sql/table.sql и тесты на изолированной MariaDB. Использовать существующий Database. Рабочие обработчики и старые балансы переключаются только на S04; HTTP и setConfigFile классу не нужны. Реализуется полный API, без заглушек и runtime-совместимости.

## API

`final class Point` из `core/classes/point.php` обслуживает Node и остальные владельцы событий через минимальный API:

```php
public function __construct(Database $db, array $conf)
public function addEvent(string $action, string $scope, string $source, int $uid, array $data = []): bool
public function getEventId(string $action, string $scope, string $source, int $uid): int|false
```

Конструктор получает только проверенную область `$conf['points']`, а не всю глобальную конфигурацию. Источником области является `config/points.php`, штатно объединяемый в `config/local.php`.

- Владелец исходного события передаёт утверждённое действие, контекст, серверный уникальный источник и получателя. Необязательный `data` принимает только `mid`, `aid`, `rid`, `note` и `points`; неизвестный ключ отклоняется.
- `mid`, `aid` и `rid` являются положительными целыми либо `0`. `note` содержит простой текст не длиннее 255 символов.
- Обычное действие не принимает `data.points`: его сумма всегда определяется конфигурацией. Явное ненулевое `points` разрешено только действию `adjust`, только при `aid > 0` и с непустым `note`.
- `Point` берёт единую глобальную сумму действия из системной конфигурации. Для обычного начисления нулевая сумма и отключённая система являются успешной операцией без SQL. Компенсация по rid и административный adjust проверяются раньше этого выхода: они работают с уже существующим балансом независимо от текущей суммы действия и active.
- Ненулевое событие блокирует строку пользователя, одной транзакцией добавляется в `_points` и изменяет быстрый агрегат `_users.points`; фактически применённая сумма не допускает отрицательного итога и именно она попадает в журнал.
- Достигнутый временной limit возвращает true без начисления и строки журнала; это успешное пропускание награды, не ошибка основного действия. Неизвестный исход SQL этим результатом не маскируется.

- Уникальность конкретного события обеспечивает сочетание получателя, действия, контекста и источника. Повтор является успешной пустой операцией, а не ошибкой и не повторным начислением.
- При `rid > 0` метод блокирует исходную запись, проверяет совпадение получателя, действия и контекста и создаёт единственную компенсирующую строку. Исходная строка обязана иметь `rid IS NULL`, положительные `points` и действие, отличное от `adjust`; компенсацию и ручную корректировку повторно компенсировать нельзя. Вызывающая сторона передаёт серверный `source` вида `reverse:<rid>`, а сумма получается из исходной строки и не принимается извне. Даже нулевая фактическая отмена записывается, чтобы её нельзя было повторить после будущего пополнения.
- Неизвестное действие, неверный uid, недопустимый контекст или восстановимая ошибка SQL возвращают `false`; произвольные действия из админки не регистрируются.
- Отдельные методы добавления и вычитания, класс `NodePoint`, таблица баллов Node и передача имени обработчика из конфигурации не создаются.

Получение исходного начисления для компенсации: getEventId() принимает тот же доверенный ключ, что addEvent(), и возвращает положительный ID исходной положительной строки без rid, 0 при подтверждённом отсутствии и false при ошибке/неверном ключе. Метод требует открытую транзакцию владельца, блокирует сначала пользователя, затем исходную строку текущим чтением; блокировки сохраняются до завершения внешней транзакции. Он работает при отключённых начислениях. При 0 компенсация не нужна; false журналируется как ошибка баллов, не как отсутствие. При ID > 0 владелец вызывает addEvent() с rid и source=reverse:<rid> в той же транзакции. Повтор проверяется уникальностью rid; параллельное начисление по тому же ключу сериализовано пользователем. API используется публикациями, комментариями, заказами и жалобами согласно их жизненному циклу. Rating и его контроллеры этот метод не вызывают.

По NOD-191 баллы полностью отделены от рейтинга: голосование и аннулирование не вызывают Point. Закрытый начальный словарь состоит из 15 действий:

| Действие | Назначение |
|---|---|
| `publish` | публикация материала или темы |
| `comment` | комментарий или ответ |
| `view` | засчитанный просмотр |
| `download` | засчитанное скачивание |
| `visit` | засчитанный переход по внешней ссылке |
| `poll` | голос в опросе |
| `order` | подтверждённый или оплаченный заказ |
| `favorite` | добавление в избранное |
| `message` | сообщение или обращение |
| `recommend` | рекомендация или публикация ссылки |
| `register` | регистрация пользователя |
| `login` | засчитанный вход |
| `report` | подтверждённая полезная жалоба |
| `moderate` | завершённое действие модератора |
| `adjust` | ручная корректировка администратором |

Контекст не меняет смысл и стоимость действия и хранится только в журнале: например, `comment` с `node.news`, `account` или `forum.topic`. Он служит для аудита, группировки, связи с целью и уникальности события. Удаление или отмена результата не являются новыми действиями.

### Конфигурация Point

`config/points.php` возвращает одну область с точными корневыми ключами `active` и `actions`:

```php
return [
    'points' => [
        'active' => '1',
        'actions' => [
            'publish' => ['points' => '10', 'period' => '86400', 'limit' => '10'],
            'comment' => ['points' => '5', 'period' => '86400', 'limit' => '30'],
            'view' => ['points' => '0', 'period' => '86400', 'limit' => '50'],
            'download' => ['points' => '3', 'period' => '86400', 'limit' => '20'],
            'visit' => ['points' => '0', 'period' => '86400', 'limit' => '20'],
            'poll' => ['points' => '3', 'period' => '86400', 'limit' => '10'],
            'order' => ['points' => '10', 'period' => '0', 'limit' => '0'],
            'favorite' => ['points' => '0', 'period' => '86400', 'limit' => '20'],
            'message' => ['points' => '0', 'period' => '86400', 'limit' => '20'],
            'recommend' => ['points' => '0', 'period' => '86400', 'limit' => '5'],
            'register' => ['points' => '0', 'period' => '0', 'limit' => '0'],
            'login' => ['points' => '0', 'period' => '86400', 'limit' => '1'],
            'report' => ['points' => '3', 'period' => '86400', 'limit' => '5'],
            'moderate' => ['points' => '0', 'period' => '86400', 'limit' => '100'],
            'adjust' => ['points' => '0', 'period' => '0', 'limit' => '0'],
        ],
    ],
];
```

- `active`, `points`, `period` и `limit` хранятся каноническими десятичными строками, совместимыми с существующей `setConfigFile()`: только `'0'` или `'1'` для `active`, только `'0'` либо положительная запись без знака и ведущих нулей для остальных значений. `Point` один раз строго проверяет полный набор и преобразует его во внутренние `bool` и `int`; нативные числа, логические значения, знаки, пробелы и частичная нормализация не принимаются.
- `active = '0'` отключает только обычные начисления без SQL; компенсации по rid и административный adjust продолжают работать. `actions` содержит ровно 15 утверждённых действий; неизвестный или отсутствующий ключ делает сохраняемую конфигурацию неверной.
- Обычное `points` принимает значения от `0` до `1000`. Отрицательные настройки действий запрещены; списание выполняют только отмена и административный `adjust`.
- `period` измеряется в секундах, а `limit` задаёт число успешно начисленных событий одного `action` получателю `uid` за скользящий период. Контекст не разделяет предел между модулями или типами.
- `period` и `limit` либо оба равны `0`, либо оба являются положительными. Положительный `period` находится в диапазоне от `60` до `31536000`, положительный `limit` — от `1` до `10000`; уникальность одного источника действует независимо от них.
- Предел считает только исходные успешно начисленные события. Компенсации и `adjust` в него не входят.
- `adjust` присутствует среди 15 правил с нулевой суммой и без временного ограничения. Его фактическую ненулевую сумму от `-1000000` до `1000000` задаёт только авторизованный администратор через разрешённый ключ `data.points`.
- Ручное повреждение runtime-конфигурации безопасно отключает `Point` и записывает техническую ошибку в системный журнал; частично пригодные правила не применяются.
- Существующая `setConfigFile()` получает возвращаемый `bool`: `true` только после успешной записи источника и пересборки `config/local.php`, `false` без удаления рабочего кеша при ошибке. Старые вызовы могут игнорировать результат, а экран баллов обязан проверить его и после POST показать фактически перечитанные значения.

### Жизненный цикл баллов

- Получатель `uid` является исполнителем обычного пользовательского действия. Чужое сообщение или комментарий меняют профильную статистику цели, но не её баланс.
- publish вызывается при фактической публикации с устойчивым source материала. По ответу G1, если раньше записи начисления не было из-за нулевой суммы, отключения, лимита или восстановимой ошибки, последующая публикация может начислить баллы впервые. Если исходное событие уже записано, повтор — пустая операция, в том числе после его компенсации. Отдельный признак первого события не создаётся. По ответу G2 отложенная публикация начисляется не при сохранении Published, а после наступления pubdate первым успешным запуском планировщика. Немедленная публикация вызывает Point в своей транзакции; восстановление только до Disabled и обычное редактирование не создают событие. Доставка будущего события Node описана в 03/05.
- `comment` начисляется, когда комментарий впервые становится видимым; премодерируемая запись ждёт одобрения.
- `order` начисляется после подтверждения или оплаты, `report` — после признания жалобы полезной, `register` — после активации учётной записи. Остальные действия начисляются после своего успешного завершения.
- Один серверный `source` обозначает один факт и никогда не принимается из пользовательского запроса. Материал, комментарий, ресурс, опрос и заказ используют устойчивый ID владельца события; вход получает source=day:YYYYMMDD по UTC; скользящий период login дополнительно проверяется журналом и не сбрасывается на границе даты. Голосование в рейтинге не является событием Point (NOD-191).
- Физическое удаление вознаграждённого материала или комментария, отмена или возврат заказа и отмена признанной полезной жалобы создают единственную компенсацию через `rid`. Просмотр, переход, сообщение и вход не отменяются.
- Владелец изменяющего действия вызывает `Point` до своего `COMMIT`. При уже открытой транзакции `Point` изолирует журнал и баланс через SQL `SAVEPOINT`; при автономном вызове открывает собственную транзакцию. Успешное начисление фиксируется вместе с основным действием, аварийное завершение не оставляет окно между ними, а восстановимая ошибка участка баллов откатывается до точки сохранения, журналируется с `source` и не отменяет основное пользовательское действие. Ошибка `adjust` откатывает его собственную транзакцию, показывается администратору и не считается успешной корректировкой.
- Баллы не сгорают, не передаются и не расходуются. Пользователь видит только итоговый баланс; журнал, независимые фильтры по пользователю, действию и дате и не более 50 строк одной страницы доступны администраторам на существующем экране баллов.
- В административной форме пользователя баланс доступен только для чтения, а изменение задаётся знаковой разницей через `adjust` с обязательной причиной. Контроллер читает её как текст и принимает только строгую десятичную запись с необязательным начальным минусом; `getVar(..., 'num')` для неё запрещён.
- Общий сброс создаёт в административной сессии серверный случайный ID операции и хранит там подтверждённый курсор пользователя. Запросы читают `id > cursor ORDER BY id ASC LIMIT 500`, обрабатывают каждого пользователя отдельной транзакцией и при необходимости делят списание одного баланса на части до `1000000`. Источник `reset:<operation>:<uid>:<part>` устойчив для безопасного повтора партии; после завершения состояние операции удаляется из сессии.

## Хранение

`_points` не принадлежит Node и обслуживает все подсистемы через общий `Point`. Источником текущего быстрого баланса остаётся `_users.points`, а журнал хранит новую историю, уникальность и отмены. Восстановление старого аккаунта требует начального баланса из снимка перехода плюс новые записи; один новый журнал не восстанавливает неизвестную прошлую историю.

```sql
CREATE TABLE `{prefix}_points` (
  `id` BIGINT UNSIGNED NOT NULL AUTO_INCREMENT,
  `uid` INT UNSIGNED NOT NULL,
  `aid` INT UNSIGNED NOT NULL DEFAULT 0,
  `action` VARCHAR(16) CHARACTER SET ascii COLLATE ascii_bin NOT NULL,
  `scope` VARCHAR(50) CHARACTER SET ascii COLLATE ascii_bin NOT NULL,
  `mid` INT UNSIGNED NOT NULL DEFAULT 0,
  `source` VARCHAR(64) CHARACTER SET ascii COLLATE ascii_bin NOT NULL,
  `points` INT NOT NULL,
  `rid` BIGINT UNSIGNED DEFAULT NULL,
  `note` VARCHAR(255) NOT NULL DEFAULT '',
  `created` DATETIME NOT NULL DEFAULT CURRENT_TIMESTAMP,
  PRIMARY KEY (`id`),
  UNIQUE KEY `event` (`uid`, `action`, `scope`, `source`),
  UNIQUE KEY `rid` (`rid`),
  KEY `uid_created` (`uid`, `created`),
  KEY `uid_action_created` (`uid`, `action`, `created`),
  KEY `action_created` (`action`, `created`),
  KEY `created` (`created`),
  KEY `target` (`scope`, `mid`),
  CONSTRAINT `{prefix}_fk_points_rid` FOREIGN KEY (`rid`) REFERENCES `{prefix}_points` (`id`) ON DELETE RESTRICT,
  CONSTRAINT `{prefix}_chk_points_uid` CHECK (`uid` > 0)
) ENGINE={engine} DEFAULT CHARSET={charset} COLLATE={collate};
```

- `id` и `rid` используют `BIGINT`, потому что журнал растёт быстрее таблиц содержимого; остальные идентификаторы сохраняют общесистемный `INT`.
- `uid` является получателем баллов и для обычного пользовательского действия одновременно его исполнителем. `aid` хранит администратора, если событие создано административным действием; `0` означает автоматическое событие.
- `action` принимает только 15 закрытых имён из реестра `Point`; SQL `ENUM` и ограничение со списком не используются, чтобы добавление утверждённого действия не требовало DDL.
- `scope` содержит точный контекст вроде `node.news`, `account` или `forum.topic`; он не является именем PHP-класса, таблицы или обработчика.
- `mid` хранит связанный материал или другой объект для ссылки и пакетной отмены. Значение `0` допустимо для действия без объекта.
- `source` является созданным сервером устойчивым ключом конкретного факта, например `node:1050`, `comment:8451` или `day:20260904`. Уникальность `event` не позволяет повторно начислить одно действие одному получателю.
- По NOD-191 Rating не создаёт событий в `_points` и не хранит ссылок на них; таблицы голосов и баллов независимы.
- `points` хранит фактически применённую знаковую разницу. Если списание упирается в нулевой баланс, журнал получает только реально применённое значение, поэтому начальный баланс плюс сумма новых строк даёт тот же агрегат.
- Обычное настроенное действие начисляет от `0` до `1000` баллов. Отрицательная строка появляется только как компенсирующая отмена или административный `adjust` в диапазоне от `-1000000` до `1000000`, кроме `0`.
- `rid` заполняется только у компенсирующей записи и уникально ссылается на исходное положительное начисление с `rid IS NULL` и `action != 'adjust'`. Компенсацию и `adjust` компенсировать через `rid` запрещено. Отмена записывается даже при фактически применённом `0`, чтобы её нельзя было повторить после будущего пополнения; исходная строка не изменяется и не удаляется.
- `note` пуст у автоматических событий и обязателен для `adjust`; HTML в нём запрещён.
- `updated`, `status`, IP и универсальный JSON отсутствуют. Автоматический сборщик мусора и использование `_rating` для журнала не допускаются.
- Внешние ключи к пользователям и администраторам не создаются: удаление учётной записи не должно уничтожать историю или блокироваться журналом. Ссылка `rid` остаётся внутренне строгой.
- Обычное чтение профиля, групп и прав не обращается к `_points`. Оно использует `_users.points`; журнал и агрегат изменяются одной транзакцией.
- Прямое изменение `_users.points` вне `Point` запрещено. Административная корректировка и общий сброс создают строки `adjust`; сброс обрабатывает по 500 пользователей, каждого пользователя — отдельной транзакцией, а баланс свыше `1000000` делит на несколько допустимых операций.
- Баллы не сгорают, не передаются между пользователями и не расходуются. При попытке превысить диапазон `_users.points` событие отклоняется и журналируется без изменения агрегата.
- Административный журнал читает не более 50 строк за запрос в порядке `created DESC, id DESC`. Индексы `uid_created`, `uid_action_created`, `action_created` и `created` обслуживают независимые фильтры пользователя, действия и периода без полного просмотра неизменяемого журнала.

## Приёмка S01 — класс

- Точные конструктор/addEvent/getEventId; 15 действий, закрытые ключи данных и ASCII scope/source; полная строковая конфигурация. Проверить границы сумм/периодов/лимитов и соседние недопустимые значения, неизвестные/пропущенные ключи.
- Нулевая/выключенная обычная награда: 0 SQL. Ненулевое событие: общий предел uid/action, постоянная уникальность источника, параллельная запись и переполнение баланса.
- Компенсация: ID/0/false, порядок пользователь→исходная запись, один rid, невозможность отменить adjust/компенсацию, нулевой фактический остаток. active=0 не мешает компенсации/adjust.
- SAVEPOINT сохраняет внешнее действие только при подтверждённом локальном откате; потеря внешней транзакции/неизвестный COMMIT дают фатальную ошибку владельца. Проверить постоянный результат отдельным соединением.
- Рейтинг/Point не импортируют друг друга, rate отсутствует. Класс работает без Node, HTTP и административной формы.

## Ошибки транзакции

Обычный SQL-отказ Point возвращает false только если подтверждены локальный ROLLBACK TO SAVEPOINT и сохранность внешней транзакции. При deadlock, потере соединения/внешней транзакции или неудаче отката Point выбрасывает RuntimeException; владелец прекращает всю операцию и не сообщает об успехе. Повтор возможен только целиком с прежним источником. Собственный неизвестный COMMIT также не считается доказанным откатом. NodeService переводит исключение в NodeException::STORAGE. На S01 проверить оба случая: восстановимый локальный отказ и потерянную внешнюю транзакцию с уже записанным основным действием.

Использовать текущие Database::setSqlBegin(), checkSqlActive(), setSqlCommit(), setSqlRollback(); их false проверяется явно. SAVEPOINT выполняется на том же соединении через параметризуемый слой SQL, имя — доверенный фиксированный идентификатор, без клиентского ввода.

scope: 1..50 ASCII, грамматика ^[a-z][a-z0-9.:-]{0,49}$. source: 1..64 ASCII, грамматика ^[A-Za-z0-9][A-Za-z0-9:._-]{0,63}$. Синтаксическая валидация выполняется и при выключенной награде; существование пользователя проверяется под lock только при фактической записи/чтении журнала, не скрытым SQL в нулевой операции; эти строки не являются SQL-идентификаторами.

## Заметки реализации S01

- Окно period считается только часами БД: created заполняет CURRENT_TIMESTAMP, а граница окна вычисляется в том же SQL через NOW() того же соединения. Время PHP в сравнение не подмешивается: зона PHP задаётся gtime, зона соединения синхронизируется лишь при db.sync, а probe-соединения тестов её не синхронизируют.
- Database хранит текст последней ошибки и после следующего успешного запроса: getSqlError() читается только сразу после результата false и не служит признаком неудачи сам по себе.
- _points вводит первые в схеме FOREIGN KEY и CHECK. CHECK исполняется начиная с MariaDB 10.2.1 и MySQL 8.0.16; S01 меняет строку совместимости в заголовке setup/sql/table.sql на эти версии. Проверка версии сервера и InnoDB при обновлении — preflight S04.
- Оба ограничения именованы с `{prefix}_`, как ограничения Node в 03: имя внешнего ключа уникально в пределах базы, а в одной базе допустимы две установки с разными префиксами.
- После S01 таблица _points есть в table.sql и в изолированной тестовой БД, но не на стенде: стенд получает её штатным обновлением на S04. Расхождение стенда с table.sql между S01 и S04 ожидаемо и не исправляется вручную.
- Класс строится как `new Point($db, $conf['points'])`; core/system.php его не подключает и не создаёт — это S04. Тесты: tests/Unit/PointTest.php запускает tests/Support/point_probe.php, который поднимает реальное ядро в отдельном процессе, создаёт одноразовую схему из DDL `_users` и `_points` файла table.sql и удаляет её; конкуренция проверяется настоящими процессами.
- Сломанная конфигурация выключает класс целиком: addEvent и getEventId возвращают false также для компенсации и adjust. Ошибка пишется в site-журнал один раз при создании объекта.
- adjust, который фактически ничего не применил (списание с нулевого баланса), возвращает true без строки журнала: нулевая строка adjust запрещена хранением, а его source остаётся свободным.
- Компенсация записывает mid, aid и note из data своего вызова; из исходной строки берутся только сумма и проверка получателя, действия и контекста. Исходная строка ищется по rid, уже существующая компенсация — по ключу события с source=reverse:<rid>.
- Отсутствующая учётная запись: addEvent с фактической записью возвращает false, getEventId возвращает 0. Нулевая и выключенная обычная награда учётную запись не проверяет.
- note — валидный UTF-8 не длиннее 255 символов без управляющих символов, который не меняется от strip_tags; для adjust после trim он непуст. mid, aid и rid принимаются только как int.
- Класс сам пишет в site-журнал четыре случая: сломанную конфигурацию, отклонённое переполнение баланса, неоткрывшуюся собственную транзакцию и SQL-отказ участка баллов — с action, scope, source, uid и кодом ошибки сервера. Отказ валидации ключа и данных не журналируется: это ошибка вызывающего кода, он получает false.
- Коды сервера 1213 (deadlock) и 1020 (запись изменилась после снимка) всегда дают RuntimeException, в том числе в собственной транзакции класса: сервер в обоих случаях откатывает транзакцию целиком. Превышение ожидания блокировки 1205 — восстановимый отказ: false после подтверждённого отката. В getEventId сохранность транзакции владельца после отказа подтверждается обращением к серверу (`DO 1`), потому что состояние транзакции соединение узнаёт только из ответа сервера.
- Устаревший снимок владельца. Транзакция владельца могла взять снимок REPEATABLE READ раньше, чем параллельный запрос того же пользователя закоммитил своё событие. При включённом innodb_snapshot_isolation (по умолчанию с MariaDB 11.6.2, стенд — 11.7) блокирующее чтение строки пользователя даёт 1020, сервер откатывает всю транзакцию владельца, Point выбрасывает RuntimeException, владелец повторяет действие целиком с прежним source. Без этого режима (MySQL 8, MariaDB до 11.6) проверка повтора читает снимок и не видит строку соперника; вставку останавливает уникальный ключ, код 1062 после подтверждённого отката участка возвращает true как обычный повтор, транзакция владельца цела.
- Лимит в транзакции владельца считается неблокирующим чтением, то есть из снимка владельца (решение пользователя 2026-09-19). На серверах без innodb_snapshot_isolation N параллельных запросов одного пользователя могут получить до N−1 наград сверх limit; дублей события и расхождения баланса с журналом при этом нет. Блокирующий подсчёт отклонён: его gap-блокировки на индексе журнала дают deadlock между соседними по индексу пользователями, и падает действие постороннего владельца. В собственной транзакции класса снимок берётся после блокировки пользователя, и лимит точен.
- Префикс source `reverse:` зарезервирован за компенсацией: событие без rid с таким source отклоняется, getEventId по такому ключу возвращает false. Иначе обычное событие могло бы занять ключ будущей компенсации, и она молча стала бы «повтором».
