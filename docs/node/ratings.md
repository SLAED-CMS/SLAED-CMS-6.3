# Rating — класс системы оценок

Действующий контракт. Класс — S02, HTTP/обновление — S05, цель Node — S16 в [дорожной карте](14-roadmap.md).

## Граница первого окна

Создать core/classes/rating.php, три таблицы в setup/sql/table.sql и тесты на изолированной MariaDB. Вместе с классом реализовать необходимые методы существующего Cache по разделу «Завершённый протокол HTML-кеша» в 11-security-performance.md. Это минимальная зависимость работающего Rating; остальная инфраструктура следует на S03. Конфигурация и read/write передаются конструктору; Point, Node, HTTP и getRatingService классу не нужны. Рабочие обработчики/данные переключаются на S05.

## Правила

| Условие | Решение |
|---|---|
| Шкала | Звёзды 1..5, палец вверх 5, вниз 1; сумма/число/среднее. 5+1 → 6/2 → 3, 60%. Без голосов среднего нет. |
| Аккаунт | u:<uid> из серверной сессии; IP, устройство и cookie не меняют срок. |
| Гость | При guests=1, g:<нормализованный IP>; отсутствие адреса и 0.0.0.0 не принимаются. |
| Вход/выход | Гость и аккаунт независимы, сроки/голоса не переносятся и не обнуляются. |
| Повтор | Новый голос добавляется при now-last >= действующий period. При 0 ожидания нет. last сохраняется при любом интервале. |
| Собственный голос | Запрещён своему профилю и известному автору Node/форума без дополнительного SQL. В _products автора пользователя нет; новую связь не создавать. uid=0 не доказывает гостевое авторство. |
| Отмена | Пользователь не изменяет и не удаляет голос. Super аннулирует новый голос с причиной без сброса last. |
| Серверная проверка | Доступ, active, guests, value, автор, срок; Node также проверяет features.rating, даты, категорию и расширение. detail управляет местом показа, не доступом. |
| Point | Голос/повтор/аннулирование не создаёт баллов, компенсации или обращения к Point через посредника. |

## API

`Rating` находится в `core/classes/rating.php` и не зависит от Point. Публичный API:

```php
public function __construct(Database $db, array $conf, array $actor, Closure $read, Closure $write)
public function getRating(string $scope, int $id): array
public function addRating(string $scope, int $id, int $value, string $request): array
public function deleteRating(int $vote, string $reason): array
public function getRatingList(string $scope = '', int $id = 0, int $after = 0, int $limit = 50): array
```

`$conf` — только валидированные правила ratings. Доверенный actor содержит ровно `uid:int`, `ip:string`, `aid:int`, `super:bool`; его создаёт серверный адаптер из текущей сессии. super требует положительного aid. IP нужен только гостю и нормализуется штатной функцией; 0.0.0.0 и отсутствие достоверного адреса не идентифицируют гостя. Клиентские uid/ip/aid/super не читаются как actor.

Callback read имеет контракт `(string $scope, int $id, array $actor, bool $lock): ?array` и возвращает только доступную цель с `owner:int`, `score:int`, `ratings:int`, `enabled:bool`. При lock=true он повторяет актуальные права и блокирует строку владельца; для Node сначала блокируется тип, затем материал. Callback write имеет контракт `(string $scope, int $id, int $score, int $ratings): bool` и записывает проверенный итог в уже заблокированную цель без собственного COMMIT; callback также выполняет предусмотренную реакцию расширения, поэтому Rating не зависит от классов Node.

Обе функции задаются единожды доверенным bootstrap-кодом, используются публичным и административным обработчиками и не передаются из запроса/конфига. Закрытая карта имеет account/users, forum и shop/products; `node.<name>` разрешается через общий NodeQuery/NodeService. Никакое значение scope не превращается в SQL-таблицу или путь. Отдельные callbacks в конфигурации типов и второй обработчик голосования не создаются.

Результат getRating/addRating/deleteRating содержит ровно `ok:bool`, `code:string`, `vote:int`, `score:int`, `ratings:int`, `average:?string`, `wait:int`, `duplicate:bool`, canvote:bool. Нулевой vote означает отсутствие созданного голоса, average=null — отсутствие оценок. При отказе недоступной цели счётчики не раскрываются. Коды: `ok`, `invalid`, `denied`, `unavailable`, `interval`, `conflict`, `storage`. wait задаёт оставшиеся секунды без отрицательного значения; точность производной строки среднего определена в уточнениях результата ниже, целые агрегаты не округляются.

getRating читает состояние без записи. Для доступной цели возвращается агрегат даже при запрете собственного голоса, active=0, guests=0 или ожидании: ok=true, code=ok, canvote=false. Ненулевой wait отражает только интервал. Недоступная цель не раскрывает счётчики. После add/delete canvote относится к новому голосу в полученном состоянии и не заменяет серверную проверку. addRating принимает 1..5, проверяет текущую настройку, гостя, владельца и право цели. request — 32 маленьких hex-символа идентификатора доставки, не секрет и не разрешение голоса. Новый намеренный клик получает новый ключ, сетевой повтор — прежний. Совпадение участника/цели/request возвращает прежний vote и duplicate=true; другой value с тем же ключом даёт conflict. Проверка интервала не заменяется уникальностью request.

deleteRating требует super, положительный ID и непустую причину до 255 символов. Он исключает ровно сохранённый вклад, фиксирует aid/причину/время аннулирования и не меняет время участия. Повтор — успешная пустая операция. При физически отсутствующей цели операция возвращает unavailable и не подделывает изменение агрегата; история сохраняется. getRatingList доступен только super, использует курсор id>after, лимит 1..100, возвращает сохранённые строки голосов с причиной и состоянием. Публичного просмотра чужих участников нет.

Rating владеет своей транзакцией; вызов add/delete внутри чужой незавершённой транзакции отклоняется до изменений. Внутри используются одно соединение, порядок блокировок из схемы и обязательная проверка каждого SQL-результата. При подтверждённом ROLLBACK все части откатываются вместе. Неизвестный исход COMMIT возвращает storage без обещания отката; повтор request выясняет результат идемпотентно. Point в транзакции отсутствует.

## Результаты

getRatingList возвращает ровно ok:bool, code:string, rows:array, next:int. rows содержит сохранённые колонки _rating_votes только для главного администратора; next — последний выданный ID, 0 при пустом результате. Для продолжения допустима пустая следующая страница, дополнительный COUNT не нужен. id>0 требует непустой валидный scope; after>=0, limit=1..100, неверный набор даёт invalid, отсутствие права — denied, ошибка чтения — storage и пустые rows. getRating получает vote=0 и duplicate=false; deleteRating возвращает ID аннулируемой строки. average — десятичная строка с точностью до шести дробных знаков, без незначащих конечных нулей; источник истины — целые score/ratings, округлённая строка обратно не сохраняется.

Служебное аннулирование не требует включённого голосования, гостевого разрешения или истёкшего интервала. Административный callback разрешает существующую цель в контексте super, включая отключённый материал; физическое отсутствие остаётся unavailable. Запрет собственной оценки применяется к addRating, а не ремонту агрегата. При неизвестном исходе COMMIT обработчик не обещает откат; storage вместе с прежним request позволяет безопасно повторить addRating, а повтор deleteRating идемпотентен. Cache guard остаётся до гарантированной инвалидации.

## Настройки

В config/ratings.php область ratings содержит правила с ключами account, forum, shop и node.<name>. Каждое правило имеет ровно active, period, detail, guests. На диске active/detail/guests — строки «0» или «1», period — каноническая строка неотрицательного целого числа секунд. Rating проверяет весь набор и преобразует его один раз; произвольное приведение truthy запрещено. detail сохраняет смысл нынешнего места показа, а не шкалы. Новое правило: active=1, period=2592000, detail=1, guests=1. Форма принимает целое число суток; 0 означает отсутствие ожидания. Перевод в секунды проверяет переполнение до умножения, максимальное число суток — intdiv(PHP_INT_MAX, 86400). При обновлении старое значение, не кратное суткам, останавливает preflight с отчётом, без округления. Проверка срока использует now-last >= period, исключая сложение с переполнением; будущий last является ошибкой данных, не разрешением голоса.

Пропущенный ключ или неверное правило блокирует соответствующий рейтинг с диагностикой, не включает умолчание при каждом запросе. Явные запреты сохраняются. Общая форма Node передаёт полное правило через NodeTypeInput.rating и ожидаемую version в NodeService; остальные три области сохраняются общим setConfigFile() под той же блокировкой конфигурации. Создание/клонирование/удаление типа изменяет только node.<name>; удаление не касается фиксированных правил. В NodeType.rating находится проверенный снимок, а не вторая конфигурация.

## Хранение и транзакции

Rating использует три самостоятельные таблицы InnoDB; старая `_rating` остаётся таблицей других потребителей до их перехода. Все scope/actor/request имеют ASCII с бинарным сравнением. Внешних ключей к полиморфным целям нет.

| Таблица | Колонки и ограничения |
|---|---|
| `_rating_targets` | scope VARCHAR(50), mid INT UNSIGNED, base BIGINT UNSIGNED, votes BIGINT UNSIGNED, created BIGINT UNSIGNED; PRIMARY KEY(scope,mid). base/votes — однократные начальные сумма/количество |
| `_rating_actors` | scope VARCHAR(50), mid INT UNSIGNED, actor VARCHAR(50), last BIGINT UNSIGNED; PRIMARY KEY(scope,mid,actor) |
| `_rating_votes` | id BIGINT UNSIGNED AUTO_INCREMENT PRIMARY KEY, scope VARCHAR(50), mid INT UNSIGNED, actor VARCHAR(50), uid INT UNSIGNED, value TINYINT UNSIGNED, request CHAR(32), created BIGINT UNSIGNED, annulled BIGINT UNSIGNED DEFAULT 0, aid INT UNSIGNED DEFAULT 0, reason VARCHAR(255) DEFAULT ''; UNIQUE(scope,mid,actor,request), KEY target(scope,mid,id), KEY scope(scope,id), CHECK(value BETWEEN 1 AND 5) |

Индекс target обслуживает журнал одной цели; scope(scope,id) — журнал типа/подсистемы при id=0 с курсором по голосам. Обязательные колонки NOT NULL. Времена — Unix-секунды UTC; пустое last не выдумывается: строки участника нет до достоверного участия. actor формируется сервером как u:<uid> или g:<нормализованный IP>; uid=0 у гостя. IP зарегистрированного участника в историю не копируется. История и последнее время не удаляются при истечении интервала или аннулировании. request идентифицирует доставку, а id — созданный сервером голос.

Порядок записи: Cache guard → BEGIN → блокировка актуальной цели через адаптер (для Node тип, затем материал) → строка rating_targets → строка rating_actors → поиск/блокировка request либо голоса → изменение голоса и агрегата → реакция расширения Node → COMMIT → Cache::addEpoch(true) → снятие guard. Ошибка кеша после подтверждённого COMMIT журналируется, guard сохраняется для восстановления; голос считается записанным. Новая пустая цель создаёт targets с нулевым остатком. Ненулевой старый агрегат без отметки перехода не считается новой целью. Параллельное создание строк защищается уникальными ключами и повторной проверкой под блокировкой цели.

При повторе доставки сначала проверяется сохранённый request; новый ключ при period>0 проверяет now-last>=period, а при period=0 проходит без ожидания. last обновляется только после принятия нового голоса, отказ его не продлевает. До COMMIT проверяются неотрицательные итоговые сумма/количество и вместимость колонок конкретной цели. Аннулирование вычитает value и 1, помечает голос и оставляет last неизменным.

Администратор сначала читает принадлежность vote без блокировки, затем захватывает блокировки в том же порядке и перечитывает голос. Это предотвращает инверсию vote→target. Оценка аккаунта блокирует только оцениваемого пользователя, а не аккаунт голосующего; взаимные оценки не вводят пару пользовательских блокировок Point.

Пересчёт цели использует base + сумму неаннулированных value и votes + их количество. Удалённая цель не восстанавливается из истории. При штатном обновлении targets/actors заполняются однократно по протоколу миграции; отдельные старые голоса не создаются.

## HTTP общего рейтинга

Сохраняется `POST index.php?go=1&op=getRatingView`. Только go/op остаются в адресе; тело содержит `mod` (account/forum/shop либо node.<name>), `id`, `rate`, `request` и `token`. Представление `typ` берётся из закрытого набора звёзды/пальцы и не определяет математику или доступ. Старые изменяющие query-параметры не читаются как fallback. CSRF проверяется штатным checkSiteToken, метод — до выполнения действия; GET даёт 405 с Allow: POST.

Фронтенд создаёт request из 16 криптографически случайных байт на новый клик и сохраняет его при сетевом повторе. Ключ не является полномочием и не отменяет положительный интервал. Общий обработчик получает Rating через `getRatingService(): Rating`; эта же сборка используется админкой и содержит единственную карту целей и callbacks.

Успех отвечает 200 с обновлённым штатным фрагментом рейтинга; no-store обязателен. Неверная форма — 422, CSRF/участник — 403, недоступная цель — 404, тот же request с другим значением — 409, действующий интервал — 429 с Retry-After, сбой хранения — 500. Отказ не заменяется успешным фрагментом, скрывающим ошибку.

Служебный журнал: `GET admin.php?name=ratings&op=votes`; аннулирование: `POST admin.php?name=ratings&op=annul` с vote/reason/token. Оба входа требуют главного администратора, сервис повторяет полномочия. Операции пользователей для замены/отмены голоса отсутствуют.

## Переход накопленных рейтингов

Статус: политика NOD-189/NOD-190 конкретизирована физической схемой в 03-database.md и протоколом ниже. Протокол относится только к остающимся целям; материалы девяти старых модулей не импортируются.

### Источники начального остатка

| Цель | Существующее количество | Существующая сумма | Сохраняемая идентичность |
|---|---|---|---|
| Пользователь | `_users.votes` | `_users.tvotes` | `account` и ID пользователя |
| Тема форума | `_forum.ratings` | `_forum.score` | `forum` и ID темы |
| Товар | `_products.votes` | `_products.tvotes` | `shop` и ID товара |

По NOD-189 обе величины каждой цели сохраняются как начальный остаток, отдельно от новых индивидуальных голосов. Отдельная запись об остатке не является вымышленным голосом или событием Point. После перехода агрегат восстанавливается как начальное количество плюс число действующих новых голосов и начальная сумма плюс их значения. Аннулированные новые голоса исключаются из обеих добавок. Точные значения старой отдельной оценки неизвестны, поэтому по начальному остатку нельзя выполнять индивидуальное аннулирование или вычислять историческую награду.

Начальный остаток не заменяет текущий агрегат при каждом запуске и не добавляется повторно. Например, при начальных сумме `37` и количестве `10` переход сохраняет среднюю `3.7`; новый голос `5` даёт сумму `42` и количество `11`, а его аннулирование возвращает `37` и `10`. Повторное обновление после этого нового голоса не должно записать `42/11` как новый остаток поверх той же истории. Для новых целей, включая Node без импорта старых материалов, начальный остаток равен нулю.

### Последовательность обновления

1. Закрыть изменяющие запросы затрагиваемых подсистем на время перехода. Сохранить согласованный снимок кода, схемы, конфигурации, исходных агрегатов и `_rating`; зафиксировать момент перехода. Это будущий этап обновления, не действие текущей работы над планом.
2. Проверить существование целей, целочисленность и неотрицательность агрегатов, вместимость целевых колонок. Для пустого количества сумма должна быть нулевой; для непустого сумма должна лежать между количеством и его пятикратным значением. Ошибки перечислить по таблице и ID и остановить переход до решения; не обнулять и не нормализовать их автоматически.
3. Однократно зафиксировать сумму и количество для каждой остающейся цели в _rating_targets. Повтор проверяется manifest и штатной версией обновления по разделу «Фиксация перехода Rating»; текущий агрегат после появления новых голосов не принимается за новый остаток.
4. Из сохранившихся строк `_rating` только для этих целей восстановить достоверное последнее время по новым логическим ключам: для положительного `uid` — максимум времени по аккаунту и цели, для `uid = 0` — максимум по нормализованному IP и цели. Достоверные сохранившиеся строки учитываются и после окончания старого интервала; они не превращаются в голоса с придуманным значением. Гостевые и пользовательские ограничения не объединяются по IP.
5. Проверить формат времени и ссылок; повреждённые значения не заменять моментом обновления. Строки отсутствующих целей, опросов, иных событий и исключаемых модулей отдельно учесть в отчёте и не смешивать с новым Rating. Данные опросов сохраняются до их собственного перехода.
6. Если достоверного времени нет, по NOD-190 искусственный запрет не создаётся: первый допустимый новый голос принимается по текущим настройкам и начинает достоверную историю участника. До его принятия начальный агрегат не меняется. Отсутствие старой строки не отменяет проверки доступа, собственного автора или разрешения гостей; повреждённая имеющаяся строка не приравнивается к отсутствию данных и обрабатывается диагностикой шага 5.
7. Преобразовать проверенные настройки по NOD-186, сохранив старые три значения и добавив разрешение гостей. Новый Rating получает единственный целевой формат; runtime-чтение старой и новой модели одновременно не создаётся.
8. До открытия записи сверить все начальные агрегаты, восстановленные ограничения, отсутствие вымышленных голосов и событий Point, изоляцию опросов и повторный запуск этапа. Отметка завершения фиксируется только после успешной проверки. Принудительный сбой в середине должен либо откатить переход, либо оставить проверяемое состояние для продолжения без повторного добавления остатка.
9. Открыть запись после завершения проверки. При неудаче до открытия восстановить согласованный снимок, а не отдельный конфигурационный файл. Возврат после принятия новых голосов требует отдельного протокола сохранения этих данных и не выполняется простым повтором первоначального обновления.

Приёмка S05: неизменность суммы/количества и средней оценки на переходе; точный новый голос поверх остатка; аннулирование только нового вклада; сохранение реального последнего времени; явно выбранное поведение при отсутствии времени; независимость гостя и аккаунта; сохранение строк `voting`; повторное обновление и остановка на повреждённых данных. Проверка выполняется на изолированной копии, не подменяет будущий штатный протокол на стенде.

## Фиксация перехода Rating

При остановленной записи создать три таблицы из 03-database.md. Для каждой остающейся цели записать _rating_targets(scope,mid,base,votes,created), не изменяя агрегат владельца. Начальный остаток может быть нулевым. Восстановленные сроки записать в _rating_actors; _rating_votes остаётся пустой. Проверить диапазоны, отсутствие сирот и согласованность суммы/числа (нулевое число требует нулевой суммы, иначе votes <= base <= 5*votes); повреждённые данные останавливают preflight с перечнем ID.

Обновление использует защищённый manifest в storage/backup с хешами исходных агрегатов, нормализованных сроков, перечнем целей и версией преобразования. Каждая партия записывается транзакционно; при повторе существующий начальный остаток и срок обязаны совпасть с manifest, иначе остановка. Успешное окончание фиксируется штатной версией обновления только после сравнения всех целей/сроков с manifest и публикации настроек. До этой отметки новые обработчики не допускаются к записи. После переключения новый голос никогда не принимается за старый остаток; повтор завершённого обновления проверяет отметку и не повторяет преобразование. Строки voting и старый баланс Point сохраняются. Переключение кода, настроек и версии выполняется в закрытом для записи режиме; откат до открытия восстанавливает согласованный снимок, после открытия требует отдельного сохранения новых голосов.
