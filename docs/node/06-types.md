# Типы, поля и настройки Node

Статус: проектирование завершено; реализация и её проверки выполняются по 13-testing.md и 14-roadmap.md.

## Цель

Описать создание и жизненный цикл типов, стандартные возможности, дополнительные поля, настройки и ограничения административного конструктора.

## Утверждённые принципы

- Один установленный `node` обслуживает несколько типов одновременно.
- Искусственного лимита количества типов нет.
- Простой тип создаётся из административной панели без PHP-кода.
- Тип использует общую схему данных по умолчанию.
- Новое специальное поведение требует зарегистрированного расширения.
- Серверные пути и пределы безопасности нельзя расширять настройкой типа.
- Отдельных прав просмотра типа нет: стандартный доступ определяется существующими правами категорий.

## Базовое описание типа

`_node_types` хранит только идентичность и состояние типа:

`id`, `name`, `title`, `intro`, `ext`, `active`, `sort`, `version`, `created`, `updated`.

- `name` одновременно является техническим ключом и публичным маршрутом, например `news`, `faq` или `files`.
- `name` неизменяемо после создания типа, потому что связывает маршрут, настройки, поля, категории и глобальные интеграции.
- `title` и `intro` предназначены для понятного отображения типа в администрировании.
- `ext` связывает тип с зарегистрированным расширением; обычный тип оставляет его пустым.
- `name` и `ext` хранятся в ASCII с бинарным сравнением; регистр и допустимый формат проверяет сервис типа.
- `active` по умолчанию равен `0`; активация выполняется явно после настройки типа.
- Отключение типа не изменяет состояния его материалов.
- `sort` задаёт устойчивый порядок типов в административных списках.
- `version` защищает данные и конфигурацию типа от перезаписи устаревшей административной формой.
- Изменяемые параметры типа не раздувают эту таблицу и хранятся в `config/node.php`.
- Внешний ключ `_nodes.tid` запрещает удаление типа с материалами.

Тип читается только через `NodeQuery::getNodeType()` или `getNodeTypeList()`. Эти методы объединяют строку `_node_types`, одноимённый раздел `config/node.php` и определения `config/fields.php` в один `final readonly NodeType`; контроллеры, интеграции и расширения не собирают его самостоятельно. Объект содержит метаданные базы, полные эффективные `settings` после применения `defaults` и проверенные `fields` конкретного типа.

Административный ввод типа после нормализации представлен отдельным `final readonly NodeTypeInput`. Он содержит только публичные типизированные свойства `title`, `intro`, `ext`, `sort`, `settings`, `fields`, `uploads` и `rating`, создаётся одним конструктором и не имеет геттеров, сеттеров, фабрики или наследования. Публичное `name` передаётся операции создания отдельно и после создания не входит ни в один изменяемый объект. Ожидаемая `version` передаётся изменяющей операции отдельно; `id`, `active`, `version`, `created` и `updated` всегда определяются системой.

Типами управляют только `NodeService::addNodeType()`, `updateNodeType()`, `updateNodeTypeStatus()` и `deleteNodeType()`. Создание всегда заканчивается отключённым типом с версией `1`; остальные операции требуют ожидаемую версию. Изменение не может заменить имя; ключ `ext` можно изменить только у отключённого типа без материалов. Активация выполняет полную проверку актуального состояния, а физическое удаление запрещено при наличии материалов, категорий или пользовательских файлов и не удаляет файловый каталог типа (NOD-196).

## Имя и удаление типа

По NOD-195 `name` содержит 1–20 символов ASCII: первую маленькую латинскую букву и затем маленькие латинские буквы или цифры (`^[a-z][a-z0-9]{0,19}$`). Префикс `node-` вместе с именем помещается в существующие 25 символов права модерации. Системные и занятые имена запрещены; полный реестр резервирования и правила девяти штатных замен определены в 02-naming.md.

По NOD-196 физическое удаление требует отсутствия материалов во всех состояниях, категорий типа и пользовательских файлов. Проверяется фактическое содержимое каталога, а не только строки ресурсов: несвязанный пользовательский файл также блокирует удаление. Штатные служебные файлы защиты не считаются пользовательскими. Администратор предварительно освобождает тип отдельными операциями; удаление типа не выполняет каскадной очистки этих данных. Проверки должны исключать конкурентную загрузку или создание категории во время удаления; защита каталога не снимается автоматически.

## Каталог нового типа и сбой конфигурации

По NOD-200 создание типа не присваивает файлы существующего одноимённого каталога. Предварительная проверка обходит каталог, включая `thumb` и вложенные каталоги: наличие любого пользовательского файла блокирует создание, включая файлы прежнего модуля. Штатные файлы защиты не считаются пользовательскими; небезопасная ссылка или недоступная для проверки область не считается пустой. Сначала каталог освобождается отдельной явной операцией. Правило относится и к девяти штатным заменам; оно не разрешает удаление их данных при установке Node.

По NOD-201 при неподтверждённой согласованности после аварии тип временно недоступен для публичного чтения и записи. Админка показывает причину и предоставляет восстановление последнего согласованного состояния. Произвольная смесь БД, исходников и `local.php` не объявляется рабочей конфигурацией. Точный журнал операции, обнаружение рассогласования и безопасное восстановление всех общих областей входят в D1–D3; пользовательская политика отказа уже принята.



## Настройки

`config/node.php` является единственным хранилищем настроек Node:

- глобальные значения задают безопасные пределы и значения по умолчанию;
- настройки типа находятся по его публичному имени;
- настройки зарегистрированного расширения находятся внутри соответствующего типа;
- административное сохранение инвалидирует и пересобирает общий `config/local.php`;
- база не содержит таблицу настроек и не выполняет отдельный запрос при чтении типа;
- принимаются только зарегистрированные ключи с известным типом и валидатором.

Определения полей остаются в `config/fields.php`, загрузки — в `config/uploads.php`, рейтинг — в `config/ratings.php`. По NOD-213 операции используют актуальные области, прочитанные под одной общей блокировкой. Подготовленный до блокировки полный файл не является входом обновления общего источника.

```php
function setConfigFile(string|array|Closure $fp, array $arr = [], array $act = []): bool
```

Строковый и массивный вызовы сохраняются для существующих независимых источников. Все писатели общих node/fields/uploads/ratings переходят на режим Closure; замыкание задаётся только серверным кодом. Функция захватывает один глобальный файловый lock, проверяет отсутствие незавершённого журнала и перечитывает исходники с актуальным OPcache-состоянием. Замыкание получает `array $base` без корневых обёрток по именам файлов и `Closure $save`. Оно возвращает только `committed`, `aborted` или `uncertain`; это результат операции владельца, а не пользовательский параметр.

`$save(array $package, array $proof = []): bool` доступен только внутри вызова, вызывается не более одного раза и принимает полный пакет, собранный из `$base` с изменениями только принадлежащих операции областей. Он валидирует типы и сериализацию, сохраняет защищённые старый/новый снимки и журнал, затем заменяет исходники. Замыкания, объекты, ресурсы и float не сериализуются. Для Node proof содержит имя, ID и ожидаемые старую/новую версии типа и вид операции; SQL и имена произвольных PHP-обработчиков в журнал не помещаются.

Для чисто конфигурационной операции возврат committed следует за успешным save. Для Node внутри того же замыкания открывается транзакция БД, блокируется тип, проверяются права и версия, выполняется SQL, вызывается save, затем COMMIT. Глобальная файловая блокировка удерживается на всём протяжении. При подтверждённом ROLLBACK возвращается aborted; при неизвестном исходе COMMIT — uncertain. Писатель не вызывает setConfigFile повторно из замыкания и не получает глобальный lock после захвата строки типа.

Только после committed функция собирает временный `local.php` из полного нового снимка, проверяет его и атомарно заменяет рабочий файл с инвалидированием OPcache. Старый local.php не удаляется заранее. После проверки согласованности и инвалидации кеша завершённый журнал снимается. `true` означает законченный согласованный результат; `false` сообщает отказ и не обещает автоматически прежнюю БД при неопределённом COMMIT.

Полные node/fields/uploads/ratings участвуют в одной операции создания/удаления типа; редактирование меняет только необходимые области. Для Node общие экраны полей, загрузок и рейтинга передают ожидаемую версию в NodeService, а не обходят его прямой записью. `NodeTypeInput` включает собственные `uploads` и `rating` рядом с settings/fields; в NodeType эти массивы доступны отдельно и не дублируются внутри settings. NodeService сохраняет изменения через существующие четыре операции типов. В `node.types[name].version` хранится номер, совпадающий с `_node_types.version`; это метаданные согласованности, не пользовательская настройка.

Чтение NodeType сверяет номер БД и конфигурации. Запрос со старым снимком после конкурентного изменения один раз перечитывает общий конфиг и тип; при повторном несовпадении отвечает отказом, а не смешивает версии. Получение основного конфига не выполняет SQL для каждого типа; проверка БД остаётся в чтении конкретного типа.

### Аварийное восстановление конфигурации

Журнал операции и оба снимка хранятся в закрытой области `storage/backup/config/<operation>`, вне публичной выдачи и вне набора загружаемых PHP-конфигов. Небольшой маркер незавершённой операции создаётся и сбрасывается на диск до замены первого источника; он содержит затронутые типы/файлы и хеши. Это журнал восстановления, а не второй runtime-кеш. Незаписанный журнал запрещает начинать замену.

До завершения getConfig использует последний целый local.php и не пересобирает его из промежуточных исходников. Bootstrap проверяет маркер до HTML-кеша и запрещает публичное обслуживание затронутых типов. Остальные типы используют последний согласованный снимок. Новые записи конфигурации отклоняются до восстановления, чтобы не затереть последующие изменения восстановлением полного снимка.

Восстановление доступно главному администратору через POST+CSRF в управлении Node; диагностический экран доступен и при невалидном типе. Под глобальной блокировкой сверяются журнал, хеши и фактическая версия БД независимым чтением: старая версия означает восстановление старых исходников; новая — завершение нового снимка. Для создания/удаления дополнительно проверяются идентичность записи и ожидаемое наличие/отсутствие. Иной результат, повреждённая резервная копия или неизвестный исход не заменяются догадкой: тип остаётся недоступным с отчётом.

После восстановления пересобирается local.php, инвалидируется OPcache и HTML-кеш, повторно сверяются версии и только затем удаляется маркер. Операция повторяема. Принудительные сбои проверяются после каждого сохранённого шага, включая окно после COMMIT и перед сменой local.php. Настройки другого типа или области восстанавливаются только из снимка, относительно которого после маркера не было разрешено новых конфигурационных записей.


Тип можно активировать только после успешного сохранения, проверки его конфигурации и создания стандартной файловой области:

```text
uploads/<type>/
├── thumb/    уменьшенные копии изображений редактора `[attach]`
└── <files>   файлы редактора и структурированные ресурсы `_node_assets`
```

- `<type>` равен неизменяемому `_node_types.name`, совпадает с модулем в штатном файловом месте `<type>.attach` и поэтому сохраняет обычную структуру `uploads/<module>`.
- Корень типа является общей файловой областью существующих `Upload` и `FileManager`; различие редакторского `[attach]` и структурированной строки `_node_assets` хранится в тексте и базе, а не в параллельных каталогах.
- При создании типа создаётся только `uploads/<type>` и его стандартная серверная защита. `thumb` создаётся существующим Parser по необходимости; `temp`, `public` и специальное дерево `uploads/node` не создаются.
- Начальное правило `$conf['uploads'][<type>]` копируется из существующего `$conf['uploads']['all']` и сохраняется существующим `setUploadRuleData()`; числовые пределы и расширения в Node не дублируются. После создания правило автоматически появляется на штатном экране `admin.php?name=uploads&op=config` и изменяется там.
- Удаление типа не удаляет его каталог автоматически: физические файлы требуют отдельного подтверждённого административного действия.
- `Upload` сразу назначает безопасное имя; повторное переименование, копирование в `storage/node` и отдельное закрытое хранилище Node не создаются.
- Запрет выполнения PHP во всём `uploads` обеспечивается единым правилом веб-сервера для всех типов.
- По NOD-206 каждый тип получает контролируемую отдачу всего дерева, независимо от категорий и расширения; отдельного переключателя нет.
- Прямой доступ веб-сервера к локальным файлам и уменьшенным копиям всех типов Node закрыт. Обычное чтение идёт через `asset` или `attach`, новая загрузка — через защищённый preview.

Перед активацией сервис типа одним полным проходом проверяет:

- структуру и типы всех настроек;
- зависимости включённых возможностей и глобальных интеграций;
- определения дополнительных полей и ролей ресурсов;
- наличие и доступность файловой области типа;
- регистрацию, совместимость и настройки расширения;
- непревышение системных пределов.

Ошибка любой проверки оставляет тип отключённым и возвращает точную причину. Частично работоспособный тип активировать нельзя.

### Структура конфигурации

```php
'node' => [
    'version' => '1',
    'limits' => [
        'maxassets' => 100,
        'maxlist' => 100,
        'syncbatch' => 500,
    ],
    'support' => [
        'state' => [
            'staff' => 0,
            'author' => 1,
            'closed' => 2,
        ],
        'prio' => [
            'low' => 0,
            'normal' => 1,
            'high' => 2,
            'urgent' => 3,
        ],
    ],
    'defaults' => [
        'list' => [
            'orders' => ['published'],
            'order' => 'published',
            'dir' => 'desc',
            'limit' => 10,
            'alpha' => false,
            'show' => ['category', 'author', 'date', 'views'],
        ],
        'view' => [
            'mode' => 'default',
        ],
        'form' => [],
        'workflow' => [
            'access' => 'user',
            'groups' => [],
            'publish' => [],
            'notify' => [
                'pending' => true,
                'result' => true,
            ],
        ],
        'admin' => [],
        'features' => [],
        'assets' => [],
        'integrations' => [
            'search' => false,
            'rss' => false,
            'sitemap' => false,
            'blocks' => false,
            'seo' => 'website',
        ],
    ],
    'types' => [
        'news' => [
            'version' => 1,
            'list' => [],
            'view' => [
                'mode' => 'article',
            ],
            'form' => [],
            'workflow' => [],
            'admin' => [],
            'features' => [],
            'assets' => [],
            'integrations' => [],
            'ext' => [],
        ],
    ],
],
```

- `version` определяет общий формат `config/node.php`, включая форму настроек расширений, а не версию SLAED или отдельной схемы расширения.
- `limits` содержит непревышаемые системные пределы: `maxassets = 100` ограничивает общее количество строк ресурсов одного материала, `maxlist = 100` — размер одной страницы списка, а `syncbatch = 500` — число ID материалов в одном проходе синхронизации с глобальной подсистемой.
- `support.state` и `support.prio` являются единственным источником допустимых значений и подписанных ключей Ticket System. `NodeSupport` читает их из `$conf['node']`; отдельные `STATE_*`, `PRIO_*` и дублирующие массивы в классе не создаются.
- `syncbatch` является общим пределом Node и не переопределяется типом. Он не ограничивает общее количество материалов, размер публичной страницы, ресурсы материала, поиск, RSS или почтовую очередь.
- `defaults` содержит общие значения для типов.
- `types` содержит номер `version` как метаданные согласованности с БД и отличия настроек от `defaults`; номер не входит в пользовательские settings.
- `list`, `view`, `form` и `admin` управляют своими участками без передачи шаблонных путей или CSS-классов.
- `view` является разделом отображения и не содержит прав доступа.
- `view.mode` задаёт единый комплект публичных представлений типа. Он содержит только безопасное короткое имя, например `article`, `faq`, `docs`, `files` или `media`; путь к шаблону в настройку не передаётся.
- `workflow` управляет доступом к публичной отправке, прямой публикацией и уведомлениями, но не дублирует права чтения категории и права администратора-модератора.
- Администратор с ключом `node-<name>` модерирует только соответствующий тип, право `node` управляет подсистемой и типами, а главный администратор имеет оба права; эти значения преобразуются в `NodeContext` на границе запроса.
- Для списка этих существующих прав `_admins.modules` использует `TEXT NOT NULL`; формат остаётся общесистемным, а отдельная ACL-таблица Node не создаётся.
- `features` включает стандартные возможности Node.
- `assets` определяет роли структурированных ресурсов типа.
- `integrations` настраивает поиск, RSS, sitemap, блоки и SEO. Баллы являются глобальной политикой действий и не дублируются в настройках типа.
- `ext` содержит только настройки расширения; его ключ хранится один раз в `_node_types.ext` и в конфигурации не повторяется.
- Ассоциативные настройки объединяются с `defaults`, а списки заменяются целиком и не сливаются по числовым индексам.
- Тип может только ужесточить относящиеся к его материалам пределы, например `maxassets`; служебный предел `syncbatch` принадлежит всей подсистеме и в настройках типа отсутствует.

### Интеграции типа

Раздел имеет закрытый точный состав:

```php
'integrations' => [
    'search' => false,
    'rss' => false,
    'sitemap' => false,
    'blocks' => false,
    'seo' => 'website',
],
```

- `search`, `rss`, `sitemap` и `blocks` принимают только нативные логические значения.
- `seo` принимает только `website`, `article` или `news` и напрямую соответствует существующему аргументу `kind` функции `setHead()`; на внутренней странице `website` создаёт `WebPage`.
- Все внешние публикации нового типа по умолчанию выключены. Администратор включает каждую интеграцию явно.
- После объединения с `defaults` эффективный раздел обязан иметь все пять ключей и не иметь неизвестных; неверный тип или состав не позволяет активировать тип. В записи конкретного типа разрешён пустой массив или только отличия.
- `home`, комментарии, рейтинг, избранное, опросы, уведомления и баллы здесь не повторяются: они управляются своими утверждёнными разделами и глобальными подсистемами.
- Настройки не создают таблицу регистраций, отдельный кеш или классы интеграций; потребители читают проверенный `NodeType` через `NodeQuery`.

### Граница настроек материала

Произвольного переопределения конфигурации типа на уровне материала нет. Материал хранит только собственное содержимое и состояние: категории, текст, дополнительные поля, опрос, признаки главной страницы, комментариев и закрепления, даты публикации, связи, ресурсы и состояние жизненного цикла.

Режим отображения, права, процесс модерации, настройки списка, интеграции, правила ресурсов, расширение и системные пределы всегда определяются типом. Универсальный JSON настроек материала, исключения по ID и объединение конфигурации типа с данными материала не создаются.

`NodeService` связывает допустимые значения с возможностями типа:

- без `categories` допустимы только `cid = 0` и пустой `cids`;
- без `comments` допустим только `CommentMode::Disabled`, а без `home` и `pinned` соответствующие логические значения обязаны быть `false`;
- без `poll` допустим только `poll = 0`;
- без `related` и `tree` запрещены соответствующие виды связей;
- без `schedule` нельзя назначить будущий `published` или непустой `expires`.

Контроллер не показывает недоступный элемент формы, но сервис независимо отклоняет подделанный запрос с непустым запрещённым значением. Пустые значения принимаются, потому что входят в полную форму `NodeInput`.

### Публичная отправка и модерация

```php
'workflow' => [
    'access' => 'user',
    'groups' => [],
    'publish' => [],
    'notify' => [
        'pending' => true,
        'result' => true,
    ],
],
```

- `features.submit = false` полностью отключает публичную форму независимо от `workflow`.
- `access` принимает только `all`, `user` или `group`: соответственно все посетители, любой зарегистрированный пользователь либо пользователь хотя бы одной группы из `groups`.
- `groups` и `publish` содержат уникальные положительные ID существующих глобальных групп. При `access = group` список `publish` обязан быть подмножеством `groups`.
- При включённой `features.moderation` публичная отправка создаёт `Pending`; зарегистрированный пользователь из `publish` может сразу создать `Published`.
- При отключённой `features.moderation` разрешённая публичная отправка создаёт `Published`. Комбинация `access = all` сознательно разрешает прямую публикацию гостям и должна явно подтверждаться в административной форме.
- Публичная форма не создаёт `Draft`; черновик доступен административному созданию.
- `notify.pending` включает существующее административное уведомление о новом `Pending`, а `notify.result` — существующее уведомление зарегистрированного автора после решения. Для анонимного автора уведомление о результате не создаётся.
- Модерация выполняется только главным администратором или администратором с `node-<name>`. Право `node` управляет системой и типами, но само по себе не даёт права модерировать материалы.
- Пользовательские группы не получают действий модерации, отдельной пользовательской панели и новой ACL-таблицы нет.
- Старые сочетания `add`, `addquest` и `addmail` заменяются этой схемой; нелогичный режим «гость может отправить, зарегистрированный пользователь не может» не поддерживается.

### Права чтения

- Разделы `access`, `view` в значении ACL и `group` в настройках типа не создаются.
- Основная категория из `_nodes.cid` определяет стандартное право чтения материала через существующее `pread`; её `pview` управляет видимостью самой категории.
- Дополнительные категории дают материалу дополнительные места показа, но не могут предоставить право, которого нет у основной категории.
- Список дополнительной категории одновременно проверяет право на эту категорию и право чтения основной категории материала.
- Для опубликованного материала без категории стандартное чтение открыто с учётом `published`, `expires` и состояния.
- Зарегистрированное расширение может только дополнительно сузить доступ, например до владельца обращения и модератора поддержки.
- Одна общая проверка доступа применяется в просмотре, списках, поиске, RSS, sitemap, блоках и отдаче защищённых файлов.

## Поля

Дополнительные поля принадлежат глобальной системе SLAED:

- существующий `admin/modules/fields.php` является единым административным менеджером полей и получает динамические области вместо фиксированного списка модулей;
- определения находятся в `config/fields.php` как структурированные массивы;
- область `node` и публичное имя типа выбирают нужный набор;
- значения материала находятся в `_nodes.field` как JSON-объект по устойчивым именам;
- тип поля определяет форму, нормализацию, валидацию и вывод;
- список допустимых типов закрыт и расширяется только зарегистрированным PHP-компонентом;
- отдельные таблицы полей и значений для `node` не создаются;
- порядок определения влияет только на форму и не меняет соответствие сохранённых значений.

Один набор содержит не более 256 полей. Один `select` содержит не более 256 вариантов и не более 64 выбранных значений в режиме `multi`. Верхние длины: `text` — 4096, `textarea` — 262144, `email` — 254, `url` — 2048 Unicode-символов. После нормализации весь JSON значений не превышает 1048576 байт. Эти пределы принадлежат `Field`, не настраиваются и могут быть только уменьшены параметром `max` конкретного определения.

Старый позиционный формат с разделителями `|` и `||`, числовые типы и лимит десяти полей в целевом контракте отсутствуют. Общий механизм строит форму, нормализует, проверяет и готовит значения для вывода; Node не повторяет эту логику. Автоматическое создание полей из профиля и импорт типа вызывают тот же общий механизм, а не второй путь сохранения.

Этот механизм реализует один глобальный `final class Field` из `core/classes/field.php`. Административный модуль остаётся контроллером, а отдельные классы для Node или каждого типа поля не создаются.

Проверка определений является атомарной: `filterFieldList()` возвращает весь канонический набор или бросает `InvalidArgumentException` с техническим путём первой ошибки для журнала. Node преобразует его в `NodeException::INVALID`; повреждённый сохранённый набор делает тип невалидным. Частичная нормализация и специальный класс ошибки полей отсутствуют.

Проверка значений возвращает не текст, а один первый машинный код на поле: `required`, `type`, `format`, `choice`, `min` или `max`. Неизвестные входные имена отбрасываются при нормализации. Общая форма локализует эти коды одинаково для Node и остальных потребителей.

Поля не участвуют в SQL-фильтрации и сортировке. Такое требование переводит значение в базовую колонку или индексируемые данные расширения.

### Формат определения

```php
'source' => [
    'title' => '_SOURCE',
    'intro' => '',
    'type' => 'url',
    'default' => '',
    'options' => [],
    'req' => false,
    'multi' => false,
    'active' => true,
    'sort' => 10,
],
```

| Ключ | Назначение |
|---|---|
| `title` | подпись поля или имя языковой константы |
| `intro` | необязательная подсказка или имя языковой константы |
| `type` | ключ зарегистрированного типа поля |
| `default` | начальное значение новой сущности |
| `options` | разрешённые выбранным типом параметры и варианты |
| `req` | обязательность значения |
| `multi` | разрешение нескольких значений |
| `active` | участие поля в формах и выводе без уничтожения сохранённого значения |
| `sort` | порядок поля в форме и стандартном выводе |

`title`, `intro` и `type` являются строками, `options` — массивом, `req`, `multi` и `active` — логическими значениями, `sort` — целым числом. `default` обязан соответствовать базовому типу и признаку `multi`. Строковые представления логических значений и чисел, включая `'0'`, `'1'` и `'10'`, не преобразуются и считаются ошибкой определения.

`title` обязателен и содержит до 255 Unicode-символов, `intro` необязателен и содержит до 1000. Разрешены простой текст без HTML или имя существующей языковой константы. Начальный `_` всегда означает константу, поэтому неизвестное имя отклоняется; пустой `intro` канонически хранится как `''`. Подпись варианта `select` использует тот же контракт `title`.

Для Node полный путь определения имеет вид `$conf['fields']['node'][$name][$field]`, где `$name` — публичное имя типа, а `$field` — устойчивое имя дополнительного поля. Другие потребители используют собственную область и набор в той же структуре.

### Начальный реестр типов

| Тип | Значение |
|---|---|
| `text` | короткий текст |
| `textarea` | многострочный текст |
| `select` | одно или несколько значений из закрытого списка |
| `bool` | логическое значение |
| `int` | целое число |
| `decimal` | десятичное число заданной точности |
| `date` | календарная дата без времени |
| `datetime` | календарная дата и точное время |
| `email` | адрес электронной почты |
| `url` | абсолютный или разрешённый относительный адрес |

Старые числовые типы `1`–`5` в новом контракте не используются. Их функциональные соответствия: `text`, `textarea`, `select`, `datetime` и `date`.

Каждый элемент единого реестра содержит только имя языковой константы `title`, закрытый ключ элемента формы `control`, поддержку множественного значения `multi` и список допустимых параметров `options`. `text`, `textarea`, `email` и `url` принимают `min`, `max`; `int`, `date` и `datetime` — `min`, `max`; `decimal` — `min`, `max`, `scale`; `select` — `items`, `min`, `max`; `bool` не принимает параметров. Только `select` поддерживает `multi = true` в первой версии.

`min` и `max` включительны. Строковые типы считают Unicode-символы, числовые используют точные числовые границы, даты — канонические календарные значения, множественный `select` — количество элементов. Для одиночного `select` границы запрещены. `decimal` требует `scale` от `1` до `18`, хранит фиксированное количество знаков после точки и сравнивается без `float`; нулевая точность дублировала бы `int` и не поддерживается. Общая точность ограничена 65 цифрами без учёта знака и десятичной точки и не увеличивается определением поля.

Точные подписи типов: `text` — `_FIELDINPUT`, `textarea` — `_FIELDAREA`, `select` — `_FIELDSELECT`, `bool` — `_FIELD_BOOL`, `int` — `_FIELD_INT`, `decimal` — `_FIELD_DECIMAL`, `date` — `_FIELDDATE`, `datetime` — `_FIELDTIME`, `email` — `_EMAIL`, `url` — `_URL`. Только `_FIELD_BOOL`, `_FIELD_INT` и `_FIELD_DECIMAL` являются новыми и добавляются во все шесть файлов `admin/lang`; остальные существующие общие константы не дублируются.

Административная форма не регистрирует исполняемое поведение. Новый технический тип добавляется только кодом в `Field` вместе с тестами; произвольные классы, callback, SQL, пути шаблонов и CSS в реестре запрещены.

`select.options.items` является ассоциативным массивом по устойчивому сохраняемому ключу варианта. Значение содержит только строковый `title`, логический `active` и целочисленный `sort`. Отключённый вариант нельзя выбрать заново, но его подпись продолжает отображаться у ранее сохранённого значения. Порядок определяется `sort`, затем ключом; отдельный ID, таблица вариантов и физическое удаление используемого ключа не требуются.

Имя поля и ключ варианта используют один шаблон `^[a-z][a-z0-9_]{0,31}$`. Чисто цифровой ключ запрещён, поэтому PHP не превращает сохраняемое строковое значение в целое; отдельные правила регистра, алфавита и длины для вариантов не создаются.

Самостоятельный файл, изображение, аудио, видео и связь с другим материалом не являются дополнительными полями: они принадлежат ресурсам и связям Node. Вложение `[attach=...]` внутри текста остаётся содержимым редактора и не регистрируется как ресурс автоматически.

## Ресурсы типа

Раздел `assets` является реестром ролей конкретного типа. Ключ роли записывается в `_node_assets.role`, например `cover`, `gallery`, `download`, `source` или `poster`. Отдельная таблица и глобальный список имён ролей не создаются.

Полный раскрытый контракт роли:

```php
'cover' => [
    'title' => '_COVER',
    'intro' => '',
    'kinds' => ['image'],
    'extensions' => [],
    'maxbytes' => null,
    'min' => 0,
    'max' => 1,
    'canlink' => false,
    'report' => false,
    'mode' => 'image',
    'active' => true,
    'sort' => 10,
],
```

| Ключ | Тип | Значение по умолчанию | Назначение |
|---|---|---|---|
| `title` | `string` | нет | подпись роли или имя языковой константы |
| `intro` | `string` | `''` | необязательная подсказка или имя языковой константы |
| `kinds` | `list<string>` | `[]` | дополнительное ограничение допустимых видов ресурсов |
| `extensions` | `list<string>` | `[]` | дополнительное ограничение расширений локальных файлов |
| `maxbytes` | `int|null` | `null` | собственный предел размера либо предел штатного правила `<type>.attach` |
| `min` | `int` | `0` | минимальное количество ресурсов роли |
| `max` | `int` | нет | максимальное количество ресурсов роли |
| `canlink` | `bool` | `false` | разрешение внешнего URL |
| `report` | `bool` | `false` | разрешение сообщить о нерабочем ресурсе |
| `mode` | `string` | нет | ключ зарегистрированного режима отображения |
| `active` | `bool` | `true` | участие роли в форме и стандартном выводе без удаления данных |
| `sort` | `int` | `0` | порядок роли в форме и стандартном выводе |

- `title`, `mode` и `max` обязательны; остальные ключи записываются только при отличии от значений по умолчанию.
- Значения ролей используют нативные PHP-типы; строки `'0'` и `'1'` вместо чисел и логических значений не принимаются.
- `min` заменяет отдельный признак обязательности: `0` означает необязательную роль, значение от `1` задаёт минимальное количество.
- `max` должен быть не меньше `min` и не может превышать глобальный предел количества ресурсов одной роли.
- `max` проверяется при каждом сохранении; `min` допускает неполный черновик, но проверяется перед отправкой на модерацию и публикацией.
- `kinds` может содержать только `file`, `image`, `audio`, `video`; пустой список использует все виды, совместимые с выбранным `mode`.
- `extensions` и `maxbytes` могут только сужать штатное правило места `<type>.attach`; пустой список и `null` используют ограничения `$conf['uploads'][<type>]`.
- `extensions` и `maxbytes` применяются к локальному файлу; внешний URL не скачивается и не опрашивается для определения размера во время сохранения или публичного просмотра.
- `report` выводит действие только для доступного ресурса; жалоба выполняется через `POST`, проверяет CSRF и ограничение частоты, после чего идемпотентно устанавливает `_node_assets.reported` и автора первой жалобы `_node_assets.ruid`. Повтор не меняет первого автора.
- Роль ресурса не определяет собственные права и группы: ресурс наследует состояние материала, `pread` основной категории и ограничения расширения. Смешанный режим «публичный материал, закрытая роль ресурса» в первой версии не поддерживается.
- Роли сортируются по `sort`, затем по устойчивому имени.
- Имя роли использует строчные ASCII-буквы, цифры и `_`, задаётся при создании и не изменяется после появления связанных ресурсов.
- Отключение роли сохраняет строки `_node_assets`, но запрещает добавление и исключает роль из стандартного автоматического вывода.
- Физически удалить определение роли можно только при отсутствии связанных ресурсов; произвольные классы, обработчики и пути шаблонов в определении запрещены.

Начальная совместимость режимов и видов:

| `mode` | Допустимые `kind` |
|---|---|
| `image` | `image` |
| `gallery` | `image` |
| `download` | `file`, `image`, `audio`, `video` |
| `player` | `audio`, `video` |
| `none` | `file`, `image`, `audio`, `video` |
| `link` | `file`; только внешний HTTP/HTTPS |

Ядро сначала получает допустимые виды режима, затем пересекает их с `kinds` роли. Пустое пересечение является ошибкой конфигурации и не позволяет активировать тип.

### Режим внешнего перехода `link`

Для NOD-202 закрытый реестр ресурсов дополняется режимом `link`: вид `file`, только абсолютный HTTP/HTTPS `src`, `canlink = true`, `max = 1`. В одном типе допускается не более одной роли этого режима; локальный файл несовместим с ним. Роль получает обычные `hits` и `report`, но называет действие переходом, а не скачиванием. Правило принадлежит режиму, а не условию `name == links`.

Уникальность адреса обеспечивает общий `NodeService` в транзакции сохранения, а не Field. Он сначала блокирует строку типа, затем проверяет текущие адреса его ролей режима `link` и сохраняет ресурс; все писатели и изменения конфигурации такой роли используют тот же порядок. Изменение режима/роли не может активировать уже существующие дубликаты. Прямой SQL контроллера, отдельная таблица ссылок и `NodeLinks` не создаются.


### Стандартные назначения ресурсов

Первая версия предоставляет пять готовых определений, которые административный конструктор копирует в настройки создаваемого типа. Рабочий код не содержит проверок по имени назначения: после создания это обычные записи раздела `assets`.

| `role` | `mode` | `kinds` | Назначение |
|---|---|---|---|
| `cover` | `image` | `image` | главное изображение материала |
| `gallery` | `gallery` | `image` | упорядоченный набор изображений |
| `download` | `download` | `file`, `image`, `audio`, `video` | один или несколько файлов для скачивания |
| `source` | `player` | `audio`, `video` | один или несколько источников воспроизведения |
| `poster` | `none` | `image` | заставка, которую использует плеер |

Это готовые назначения, а не закрытый глобальный список. Администратор может создать другое безопасное имя, например `manual`, `screenshots` или `documents`, и связать его с одним из зарегистрированных режимов.

Начальные настройки ресурсов типов:

| Тип и назначение | `min` | `max` | `canlink` |
|---|---:|---:|---:|
| `news.cover` | `0` | `1` | `false` |
| `news.gallery` | `0` | `20` | `false` |
| `pages.download` | `0` | `10` | `true` |
| `faq.download` | `0` | `10` | `true` |
| `help.gallery` | `0` | `30` | `false` |
| `help.download` | `0` | `10` | `true` |
| `links.cover` | `0` | `1` | `false` |
| `links.link` | `1` | `1` | `true` |
| `files.cover` | `0` | `1` | `false` |
| `files.download` | `1` | `10` | `true` |
| `media.poster` | `0` | `1` | `false` |
| `media.source` | `1` | `10` | `true` |
| `media.gallery` | `0` | `30` | `false` |
| `media.download` | `0` | `10` | `true` |
| `gallery.gallery` | `1` | `100` | `false` |

Тип `jokes` не получает раздел ресурсов. Неуказанные `maxbytes = null` и `extensions = []` используют ограничения места `<type>.attach` без дополнительного ослабления.

- Настройка является стартовым значением административного конструктора, а не условием по имени типа в ядре.
- В галерее первое изображение назначения `gallery` по `sort`, затем по `_node_assets.id`, используется как обложка; отдельный `cover` добавляется только при необходимости.
- Одно и то же назначение можно настроить по-разному в разных типах.
- Точные `min`, `max`, `maxbytes`, `canlink` и ограничения расширений принадлежат настройке типа и не зашиваются в определение имени назначения.
- `limits.maxassets` считает все строки `_node_assets` материала независимо от назначения и активности его определения.
- Предел назначения и `limits.maxassets` действуют одновременно: добавление запрещается при достижении любого из них, но сумма настроенных `max` разных назначений может превышать общий предел.
- `max` назначения считает все связанные с ним строки; отключение назначения не освобождает лимит и не скрывает факт наличия сохранённых ресурсов в администрировании.

### Значения

- Строковые типы сохраняются строкой, `bool` — логическим значением, `int` — целым числом.
- `decimal` сохраняется нормализованной строкой с обязательным `scale` от `1` до `18`, чтобы JSON и PHP не теряли точность.
- `date` использует `YYYY-MM-DD`, `datetime` — `YYYY-MM-DD HH:MM:SS`.
- При `multi = true` сохраняется массив значений базового типа.
- Пустая строка и пустой массив отсутствуют в JSON; `false`, `0` и `'0.00'` не считаются пустыми.
- `default` применяется только при создании активного поля и отсутствии переданного значения; чтение и редактирование его не используют.
- `default` множественного `select` является массивом уникальных активных ключей; отключённый вариант не может быть выбран по умолчанию.
- Отключённое поле не выводится и не редактируется, но его сохранённое значение остаётся в JSON; `active = false` несовместимо с `req = true`.
- `req` проверяется для `Pending` и `Published`, но не препятствует сохранению незавершённого `Draft` или `Disabled`.
- Форма изменения передаёт полный набор только активных редактируемых полей; сервис сохраняет прежние неактивные значения, полностью заменяет активные и удаляет отсутствующее необязательное активное значение.
- Неизвестное имя из формы игнорируется, а сохранённое имя без определения удаляется при следующем изменении содержимого; смена одного состояния JSON не переписывает.
- `text` обрезает края и запрещает переносы строк; `textarea` нормализует окончания строк в `LF`, но сохраняет остальные отступы.
- Множественный `select` удаляет повторы и следует порядку определения; `bool` принимает только логические значения и их точные формы `1`, `0`, `'1'`, `'0'`.
- `int` ограничен знаковым 64-битным диапазоном, `decimal` не принимает экспоненту и запятую, даты проверяются строго без автоматического исправления календаря.
- `email` сохраняет регистр локальной части и нормализует домен, `url` разрешает только `http`, `https` и путь от корня; протокол-независимый URL, учётные данные и опасные схемы запрещены.
- Сервис сортирует ключи по имени перед кодированием.

## Возможности

Раздел `features` содержит только утверждённые логические возможности типа:

```php
'features' => [
    'categories' => true,
    'comments' => true,
    'rating' => true,
    'favorites' => true,
    'poll' => false,
    'home' => false,
    'pinned' => false,
    'submit' => false,
    'moderation' => false,
    'schedule' => false,
    'related' => false,
    'tree' => false,
],
```

- `categories` разрешает основную и дополнительные категории; язык материала определяется основной категорией.
- `comments`, `rating` и `favorites` подключают существующие глобальные подсистемы. При включённых комментариях материал выбирает существующий `CommentMode`: `Disabled`, `Moderated` или `Open`.
- `poll`, `home` и `pinned` используют одноимённые базовые данные материала.
- `submit`, `moderation` и `schedule` включают соответствующие части общего жизненного цикла; доступ к отправке, группы прямой публикации и уведомления находятся в `workflow`.
- Права административной модерации определяются `NodeContext::$mods` и `super`, а не конфигурацией типа.
- `schedule` использует состояние `Published` вместе с будущим `published` и не добавляет отдельное состояние материала.
- `related` использует связь материала `related`, а `tree` — иерархическую связь `parent`.
- `views` не является переключателем и учитывается для всех опубликованных материалов.
- Дополнительные параметры возможности не дублируются в `features`, а находятся в принадлежащем им разделе конфигурации.

## Стандартные настройки списка

Раздел `list` определяет разрешённые способы сортировки, сортировку по умолчанию, алфавитный указатель, размер страницы и показ категории, автора, даты и просмотров. Все значения выбираются из закрытых реестров; произвольное имя SQL-колонки или выражение из конфигурации запрещено.

- `orders` содержит разрешённое подмножество `published`, `updated`, `title`, `views`, `rating` без повторов.
- `order` обязан входить в `orders`, а `dir` равен `asc` или `desc`.
- `limit` является положительным целым от `1` до системного `limits.maxlist`; начальное значение равно `10`.
- `alpha` является логическим значением и разрешает фильтр `let` по первой Unicode-букве или цифре заголовка.
- `show` является упорядоченным подмножеством закрытых имён `category`, `author`, `date`, `views` без повторов; отсутствие имени скрывает метаданные только в стандартном отображении и не меняет SQL-доступность базового значения.
- Отсутствующие параметры публичного запроса используют `order` и `dir` типа; запрос не может включить запрещённую типом сортировку.
- Возможность `pinned` автоматически ставит закреплённые материалы первыми и не добавляет отдельного ключа сортировки.
- Пользовательские подписи «Новые», «Старые», «Популярные» и «Лучшие» принадлежат интерфейсу; ключи `new`, `old`, `popular` и `best` в конфигурации и API отсутствуют.

Один и тот же контракт обслуживает обычный список, категорию и административный предпросмотр. Имена ключей и закрытые значения сортировки утверждаются вместе с контрактом `NodeQuery`.

## Профили создания типа

Административный конструктор первой версии предоставляет десять профилей: `news`, `pages`, `faq`, `help`, `jokes`, `content`, `links`, `files`, `media` и дополнительный `docs`. Штатный экземпляр профиля поддержки получает публичное имя `help`, расширение `support`, режим представления `support` и настройку расширения `mail = true`. Профиль копирует обычные настройки, поля, роли ресурсов и ключ зарегистрированного расширения в новый отключённый тип; после создания профиль не является runtime-зависимостью.

Состав принят решением NOD-175. `news`, `docs`, `files` служат эталонами ядра. Ниже определены все десять штатных профилей, включая `pages`, `faq`, `jokes` и `content` по NOD-210/NOD-211. Для `content` уже выбран `sync`. По NOD-202/NOD-203 ссылки и медиа используют общие материалы и ресурсы без отдельной таблицы или расширения.

- Профиль не создаёт PHP-код, таблицу типа или особую ветку в ядре.
- Тип можно клонировать в новый тип с новым неизменяемым `name`.
- Определение типа можно экспортировать и импортировать после проверки версии формата, допустимых ключей и зависимостей.
- Секреты, локальные абсолютные пути, данные материалов и физические файлы в профиль и экспорт не входят.

### Профили `pages`, `faq`, `jokes`

По NOD-210 каждый профиль получает полный набор `list/features/workflow/integrations` эталона `news` с заменой `features.poll = false`, `integrations.seo = article` и перечисленными ниже отличиями. Настройки копируются в новый отключённый тип; runtime-наследования профилей нет. Общие категории, комментарии, рейтинг и избранное включены; публичная отправка зарегистрированного пользователя создаёт Pending, оба уведомления включены. Дополнительные поля отсутствуют, `ext` пуст.

| Профиль | view.mode | Содержание | Ресурсы вместо ресурсов news |
|---|---|---|---|
| pages | article | Заголовок, вступление и тело обычной статьи | Необязательный download: min 0, max 10, canlink true, report true, все допустимые виды |
| faq | faq | title — вопрос, intro/body — краткий/полный ответ | Такой же необязательный download |
| jokes | default | Заголовок и текст короткой записи | Пустой набор структурированных ресурсов |

Общие редакторские вложения разрешаются штатными настройками загрузок. Отдельная таблица ответов FAQ, собственный каталог файлов шуток и ветвление ядра по имени профиля не создаются.

### Профиль `content`

По NOD-211 `ext = sync`, `view.mode = article`. Базовые list/features/workflow/integrations копируются из news с `features.submit = false`, `features.moderation = false`, `features.poll = false`, `features.home = false`, `integrations.seo = article`. Дополнительные поля и структурированные ресурсы отсутствуют. Создание/настройка выполняются администратором с правом типа.

Материал использует ровно одну строку NodeSync с `url` и `refresh`. Пользовательский title и intro сохраняются; body принадлежит Feed и не принимается из административной формы как ручное содержимое. У нового материала до первого успешного обновления body пустое. Новый адрес очищает валидаторы; прежнее успешное тело сохраняется до получения нового, без сети в запросе сохранения или просмотра. Ошибка и 304 не стирают последнее тело. Ручной запуск и расписание используют ранее утверждённые NodeSync/планировщик, публичная отправка выключена.


### Профили каталогов `links` и `media`

По NOD-202/NOD-203 оба профиля используют полные `list`, `features`, `workflow` и `integrations` эталона `files`. Конструктор копирует значения, а не создаёт runtime-наследование профилей. `ext` пуст; `assets` и `fields` полностью заменяются приведёнными ниже наборами. Рейтинг независимо от профиля получает собственное правило по NOD-193.

#### `links`

`view.mode = default`, `integrations.seo = website`. Материал содержит заголовок сайта, вступление и описание; специальных дополнительных полей нет.

| Роль | Режим | Вид | min/max | Внешний URL | Жалоба |
|---|---|---|---|---|---|
| `cover` | `image` | `image` | 0/1 | нет | нет |
| `link` | `link` | `file` | 1/1 | обязателен, HTTP/HTTPS | да |

Основной адрес хранится только в `_node_assets.src`; дополнительное поле `site` его не дублирует. Незавершённый черновик может не иметь ссылки; отправка и публикация требуют одну. Переход идёт через `asset`, проверяет доступ, увеличивает счётчик переходов и выполняет `302`. Жалоба использует общий `report`.

Один нормализованный URL не повторяется внутри типа среди ролей режима `link`, включая материалы в корзине и черновики. Собственное неизменённое значение не считается дубликатом. Другой тип имеет независимое пространство адресов. `http` и `https`, разные пути и параметры не объявляются одним сайтом по догадке; сравнивается точный результат общей проверки `src`.

#### `media`

`view.mode = media`; описание хранится в `intro/body`, а характеристики — в Field. Все перечисленные поля необязательные, активные, одиночные, без подставляемого значения; порядок задаётся шагом 10 по строкам таблицы. Подписи локализуются штатными языковыми средствами.

| Ключ | Подпись | Тип | Ограничения |
|---|---|---|---|
| `subtitle` | Дополнительное название | `text` | max 100 |
| `year` | Год | `int` | 1..9999; отсутствие вместо неизвестного 0 |
| `director` | Режиссёр | `text` | max 100 |
| `cast` | Участники | `text` | max 255 |
| `creator` | Создатель | `text` | max 100 |
| `runtime` | Продолжительность | `text` | max 100 |
| `language` | Язык произведения | `text` | max 100 |
| `notes` | Примечания | `textarea` | max 262144 |
| `format` | Формат | `text` | max 100 |
| `quality` | Качество | `text` | max 100 |
| `filesize` | Заявленный размер | `text` | max 100 |
| `release` | Выпуск | `text` | max 100 |

Это отображаемые характеристики, а не SQL-фильтры; `language` не заменяет язык/права категории, `creator` не заменяет автора аккаунта. Метаданные фактического файла остаются в ресурсе и не подменяются текстом характеристик.

| Роль | Режим | Виды | min/max | canlink | report |
|---|---|---|---|---|---|
| `poster` | `none` | `image` | 0/1 | false | false |
| `source` | `player` | `audio, video` | 1/10 | true | false |
| `gallery` | `gallery` | `image` | 0/30 | false | false |
| `download` | `download` | `file, image, audio, video` | 0/10 | true | true |

Пределы локальных файлов наследуются от штатного правила загрузок. Источники плеера — допустимые локальные файлы или прямые HTTP/HTTPS-медиаресурсы; произвольная HTML-вставка и скачивание внешнего файла сервером при просмотре не создаются. По NOD-204 `ed2k` и прочие схемы вне HTTP/HTTPS отклоняются, автоматического преобразования в иной адрес нет. Владелец может вручную заменить адрес; импорта старого каталога в этом проекте нет.


### Профиль `help`

Приватная Ticket System использует точный профиль:

```php
'list' => [
    'orders' => ['published'],
    'order' => 'published',
    'dir' => 'desc',
    'limit' => 20,
    'alpha' => false,
    'show' => ['category', 'date'],
],
'view' => [
    'mode' => 'support',
],
'features' => [
    'categories' => true,
    'comments' => true,
    'rating' => false,
    'favorites' => false,
    'poll' => false,
    'home' => false,
    'pinned' => false,
    'submit' => true,
    'moderation' => false,
    'schedule' => false,
    'related' => false,
    'tree' => false,
],
'integrations' => [
    'search' => false,
    'rss' => false,
    'sitemap' => false,
    'blocks' => false,
    'seo' => 'website',
],
'workflow' => [
    'access' => 'user',
    'groups' => [],
    'publish' => [],
    'notify' => [
        'pending' => false,
        'result' => false,
    ],
],
'ext' => [
    'mail' => true,
],
```

Профиль создаётся с публичным именем `help` и ключом расширения `support`. Только зарегистрированный пользователь может создать обращение; оно сразу получает `Published`, но `NodeSupport` ограничивает чтение владельцем и модераторами типа с сохранением прав основной категории. Все материалы этого расширения обязаны иметь `CommentMode::Open`: закрытие новых ответов выполняет только `_node_support.state`, поэтому параллельного режима закрытия или премодерации комментариев нет. `addNodeData()` и `updateNodeData()` отклоняют другой режим независимо от формы.

Выключенные интеграции не допускают тикеты в поиск, RSS, sitemap и блоки. Обязательное значение `seo = website` используется только как полный валидный контракт конфигурации; приватный список, просмотр, формы и служебные маршруты всегда получают `noindex` и не попадают в HTML-кеш.

Профиль не создаёт ролей `_node_assets`. Файлы и изображения обращения добавляются штатным файловым окном текстового редактора и остаются ссылками `[attach]` внутри `intro` или `body`; существующий `Upload`, каталог `uploads/help` и контролируемый маршрут Node обеспечивают их загрузку и доступ. Начальных дополнительных полей, опросов, связей и отдельной таблицы вложений профиль не создаёт.

## Экспорт и импорт типа

Определение переносится между установками одним UTF-8 JSON-файлом `node-<name>.json` размером не более 1 МиБ:

```json
{
  "format": "slaed.node",
  "version": 1,
  "type": {
    "name": "news",
    "title": "Новости",
    "intro": "",
    "ext": "",
    "sort": 10,
    "settings": {},
    "fields": {},
    "uploads": {},
    "rating": {"active": "1", "period": "2592000", "detail": "1", "guests": "1"}
  }
}
```

Пример выше показывает оболочку формата: пустые settings/uploads не являются готовым профилем и заменяются полными проверенными значениями при реальном экспорте.

- `version` относится только к формату экспорта, а не к версии SLAED, строки `_node_types` или расширения.
- Экспорт содержит ровно `name`, `title`, `intro`, `ext`, `sort`, `settings`, `fields`, `uploads` и `rating`; `id`, `active`, версия записи, даты, материалы, ресурсы, секреты и пути отсутствуют.
- Импорт всегда создаёт новый отключённый тип. Имя из файла предлагается в форме, но администратор может заменить его до создания; существующий тип никогда не перезаписывается импортом.
- Весь файл декодируется и проверяется до записи: формат, версия, точный набор ключей, предел размера, имя, настройки, определения полей, режимы, роли ресурсов и зарегистрированное расширение.
- Зависимости вычисляются из содержимого и не дублируются отдельным разделом файла. Ошибка любой зависимости отменяет создание целиком.
- PHP-массивы, `serialize()`, исполняемый код, подпись и контрольная сумма не используются. После проверки импорт вызывает тот же путь создания типа, что административный конструктор.

## Ограничения административного конструктора

- Уникальное и безопасное `name`, одновременно являющееся публичным маршрутом типа.
- Запрет удаления типа с существующими материалами, категориями или пользовательскими файлами (NOD-196).
- Ограничение разумной сложности формы и размера сохранённого JSON без искусственного лимита количества полей.
- Только зарегистрированные типы полей и расширения.
- Никакого PHP, SQL, include-пути или имени произвольного класса в базе.

## Критерии готовности

- Описан полный жизненный цикл типа.
- Утверждена схема каждого стандартного поля.
- Настройки имеют тип, значение по умолчанию и валидатор.
- Определение типа можно экспортировать и повторно импортировать без кода.
- Отключение типа с расширением не уничтожает его материалы и данные расширения.

## Дополнение восстановления общих источников

Чисто конфигурационная операция без proof БД записывает в журнал фазу committed после успешного возврата callback и до замены local.php. Сбой до этой долговечной отметки восстанавливает старый снимок; после неё завершает новый. Node-операция разрешается по proof БД, а не по отсутствующей файловой отметке после COMMIT. Независимая проверка использует текущее блокирующее чтение строки/уникального имени типа на новом соединении, дожидаясь завершения прежней транзакции; обычный SELECT из старого снимка не доказывает ROLLBACK. Таймаут сохраняет блокировку обслуживания и журнал, не выбирает старую версию наугад.

Порядок файлового lock, Cache guard и SQL определён в 11-security-performance.md: Node callback получает lock каталога до BEGIN; публикация/восстановление удерживают те же locks до финальной проверки. Если local.php отсутствовал на чистой установке, запросы до первого согласованного снимка получают служебную недоступность; смешанный снимок не строится.
