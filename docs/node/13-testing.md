# Тестирование Node

Статус: проектирование завершено; реализация и её проверки выполняются по 13-testing.md и 14-roadmap.md.

## Цель

Определить проверяемые контракты каждого слоя и условия, при которых этап реализации считается завершённым.

## Уровни тестирования

### Самопроверка профилей и контрактов до реализации

Каждый штатный профиль рассматривается как вход обычного конструктора типа и должен удовлетворять тем же определениям, пределам и правилам резервирования, что пользовательский ввод. В профиле `files` версия распространяемого файла имеет ключ `release` с пределом 100 символов; дополнительное поле `version` отклоняется, поскольку это имя базовой колонки. Проверяется весь профиль, а не отдельный вручную упрощённый набор.

Утверждение дизайна не означает, что PHP, DDL или HTTP-сценарии уже реализованы. ER и спецификация колонок проверяются при планировании; исполняемый DDL, обновление и результаты конкретных MySQL/MariaDB фиксируются только после этапа схемы по `03-database.md`.

### Модели и правила

Статусы `Draft`, `Pending`, `Published`, `Disabled`, `Deleted`, типы, поля, настройки, права, связи и переходы жизненного цикла.

Проверки Rating разделены на класс S02, HTTP/обновление S05 и Node S16 в [ratings.md](ratings.md).

### Принятые уточнения NOD-192–NOD-197

| Сценарий | Ожидаемый результат |
|---|---|
| Тип Node создан, клонирован или удалён | Его правило автоматически появляется либо удаляется в едином экране рейтингов; настройки других целей не перезаписываются |
| Рейтинг разрешён глобальным правилом, но выключена возможность типа | Голос отклоняется; обойти `features.rating` настройкой Rating нельзя |
| Интервал 0, два разных намеренных голоса подряд | Оба голоса учитываются; ожидания нет, остальные права проверяются |
| Интервал 0, повторная или конкурентная доставка одного запроса | Один голос и один вклад; протокол request проверяется по 05/07 |
| При нуле оставлен голос, затем включён положительный интервал | Ожидание считается от последнего принятого голоса |
| Положительный интервал заменён нулём | Ожидание прекращается без удаления истории и без изменения рейтинга |
| Введён отрицательный, дробный или переполняющий преобразование интервал | Настройка отклоняется; ноль не заменяется 30 днями |
| Имя длиной 1 или 20, первая буква и допустимые остальные символы | Грамматика пройдена, затем проверяются резервирование и занятость |
| Имя длиной 21, первая цифра, верхний регистр, кириллица, дефис или подчёркивание | Отказ без создания типа и его настроек |
| Имя системное или уже занято | Отказ; обход через регистр или файловую систему не допускается |
| В удаляемом типе есть только материал в корзине, категория либо несвязанный пользовательский файл | Удаление отклоняется; состояние и защита файлов сохраняются |
| Все пользовательские данные типа явно удалены, остались лишь служебные файлы защиты | Удаление типа допускается после повторной проверки; каталог автоматически не удаляется |
| Основную категорию использует непубличный материал или материал в корзине | Удаление категории отклоняется; `cid` не обнуляется |
| Материал явно перенесён в другую основную категорию | Права проверены, видимость и язык определяются новой категорией; кеш прежней доступности не используется |

Конкурентное назначение категории, загрузка файла и создание материала во время удаления проверяются после утверждения единого порядка блокировок C6/D4/E3.



### Приёмка пакета NOD-198–NOD-205

| Сценарий | Ожидаемый результат |
|---|---|
| В собственный текст впервые подставлено имя чужого файла | Preview и сохранение отклонены; чтение чужого материала не даёт права новой привязки |
| Другой уполномоченный редактор сохраняет прежнее вложение того же материала | Ссылка сохраняется без требования владения новым редактором |
| Сохранён ID ресурса, но локальный src заменён чужим файлом | Замена отклонена как новая привязка |
| Новую загрузку открывает владелец, другой аккаунт или другая гостевая сессия | Владелец получает файл после проверки; остальные получают общий 404 |
| Preview открыт до сохранения материала | Нет временного материала/ресурса в БД, нет счётчиков; ответ private, no-store |
| В запросе preview подставлены id, uid, путь с выходом из каталога или чужой thumb | Ни один параметр не даёт дополнительного доступа |
| Каталог нового типа содержит старый файл или файл только внутри thumb | Создание отклонено без присвоения/удаления данных |
| После удаления типа остались служебные файлы защиты | Они не раскрывают каталог и не считаются пользовательскими файлами |
| Процесс завершён между записями частей конфигурации | Рассогласованный тип не обслуживает публичные запросы; доступно диагностируемое восстановление |
| Два соединения переносят B → C и D → A при A → B и C → D | Один перенос проходит, другой перечитывает дерево и отклоняет цикл |
| Первый перенос откатывается | Второй проверяет актуальное дерево и может завершиться; блокировка не остаётся захваченной |
| Обычный запрос читает дерево во время переноса | Он не получает блокировку записи типа и видит согласованное состояние своего снимка |
| Две конкурентные публикации одной ссылки внутри типа | Одно сохранение проходит; второе получает ошибку дубликата |
| Два URL совпадают только в первых 191 символах | Префикс индекса не даёт ложного дубликата; сравнивается полный адрес |
| Ссылка повторена в другом типе или оставлена без изменения в своём материале | Другой тип независим; собственный неизменённый адрес допустим |
| Выполнен GET/HEAD внешней ссылки | GET учитывает переход перед 302, HEAD не меняет hits и баллы |
| Администратор меняет роль в link при уже существующих дубликатах | Изменение не активирует неверный набор данных |
| Профиль media загружен через обычный конструктор | Все 12 полей валидны, роли имеют утверждённые пределы; отдельной таблицы/расширения нет |
| В media переданы ed2k, javascript, file или иной неразрешённый адрес | Адрес отклоняется; локальные файлы проходят только штатный путь выбора Upload/FileManager |
| Просматривается media с прямым HTTP/HTTPS-источником | Сервер не скачивает внешний ресурс ради метаданных, плеер получает только проверенный URL |

Защита прямого URL новой загрузки проверяется для всех типов по NOD-206. Проверка аварийного восстановления связывается с точным журналом и блокировками D1–D3, а не считается выполненной по наличию этой таблицы.


### Хранение

CRUD, фильтры, сортировка, пагинация, индексы, транзакции и конкурентные изменения.

Схема чистой установки и результат штатного обновления сравниваются структурно. Тест отдельно подтверждает отсутствие второй копии DDL в `modules/node/sql/`.

### Расширения

Регистрация, валидация, дополнительные таблицы, откат и отключение. Проверяется точное расположение `NodeExtension`, закрытая карта `core/classes/node/ext/load.php`, отсутствие построения пути из `_node_types.ext`, единственное расширение типа и загрузка `NodeSupport` или `NodeSync` только по зарегистрированному ключу. Интерфейс содержит ровно девять утверждённых методов; отдельные manager, registry, событие и набор мелких интерфейсов отсутствуют.

Для расширения проверяются канонизация конфигурации и `NodeInput::$ext`, обязательный пустой массив стандартного типа, точный состав `join`, `where`, `params`, параметризация значений и применение ограничения до количества и пагинации. Создание, изменение, смена состояния и удаление подтверждают утверждённый порядок, одну общую транзакцию и полный откат при ошибке каждого хука. `getNodeData()` получает всю страницу одним вызовом, возвращает карту по ID без N+1, готового HTML и изменения массива `NodeView`.

`checkNodeAction()` принимает только `comment`, `rate`, `favorite`, `asset`, `report`, вызывается после успешного чтения цели и не выполняет само действие. Для каждого имени проверяется возможность дополнительного запрета, невозможность расширить базовое разрешение и отказ неизвестной строки; закрытый тикет остаётся читаемым, но серверно не принимает новый комментарий.

Для `NodeSync` проверяются точный вход `url, refresh`, одна строка на материал, каскадное удаление, индексированная очередь `due, id`, ручной режим `refresh = 0`, очистка валидаторов при смене URL и сохранение их при смене периода. `updateNodeSyncList()` не принимает предел вне `1..50`, не использует `syncbatch`, не выполняет N+1 SQL для подготовки очереди и возвращает точные счётчики результата.

Успешные ответы `200`, `304` и совпадающее тело проверяются отдельно. Новое тело проходит предел `node.body`, одним условным SQL меняет только `body`, `version`, `updated` и инвалидирует HTML-кеш; `304` и совпадение меняют только служебное состояние. Ошибка HTTP, XML, размера или безопасности оставляет прежний текст, увеличивает `fails` и назначает ограниченный повтор, а конкурентная смена URL или версии не допускает запись устаревшего ответа. Тест отдельно доказывает отсутствие вызова обычного CRUD в цикле, циклической зависимости `NodeService` и сохранения частичного результата.

`FeedTest.php` проверяет RSS и Atom, условные заголовки, окончательный HTTP-код, три перенаправления, предел ответа, тайм-аут, запрет внешних XML-сущностей, частных и зарезервированных адресов, DNS rebinding и безопасную ошибку. Сеть подменяется тестовыми швами класса; PHPUnit не зависит от доступности внешнего сайта.

### Интеграции

Категории, комментарии, рейтинг, избранное, поиск, RSS, sitemap и блоки.

Для категорий проверяются одна основная и несколько дополнительных связей, запрет повторной пары `(nid, cid)`, отсутствие основной категории среди дополнительных, замена полного набора в одной транзакции, выборка материала из каждой категории без дублей, отказ категории другого типа и каскадная очистка при физическом удалении материала.

### HTTP

Публичные списки и просмотр, административное создание и изменение, права, CSRF, загрузки, редиректы и сохранение результата в базе.

Для `NodeQuery::getNode()` проверяются глобальный ID, обязательное совпадение `NodeType`, активность типа, все состояния и даты, `pread` основной категории, ограничения расширения и одинаковый `null` для отсутствующей и недоступной записи. `getNodeContent()` повторяет те же проверки одним основным SQL, возвращает `body`, оставляет `fields`, `cids`, `rels`, `assets` равными `null` и не получает свободный параметр проекции.

Для `final readonly Node` проверяются точный конструктор, неизменяемость, преобразование состояния в `NodeStatus`, режима комментариев в существующий `CommentMode`, JSON `field` в массив `fields` и `published` в `pubdate`. Полное чтение возвращает строковый `body` и массивы `fields`, `cids`, `rels`, `assets`; список использует `null` только для незагруженных тяжёлых значений, отличает его от пустого значения и не запускает ленивый SQL. `ip` доступен только разрешённому административному контексту и равен `null` для остальных. Последние свойства `uname` и `ctitle` получают актуальные значения через соединения основного запроса только по требованиям представления; они не заменяют сохранённое `aname` и не создают отдельного SQL.

Загруженные связи являются только `NodeRelation[]`, ресурсы — только `NodeAsset[]`, категории — `int[]`; необработанные строки PDO и массивы с произвольными ключами из API чтения не возвращаются. Отдельный `NodeCategory` отсутствует.

Для `final readonly NodeRelation` проверяются точный конструктор, типы и порядок `id`, `nid`, `rid`, `type`, `sort`, `created`, неизменяемость и отсутствие вложенного материала. Входной элемент разрешает только `rid`, `type`, `sort`; сервис отклоняет повтор, самого себя, незарегистрированный вид, чужой или отсутствующий материал и цикл `parent` до SQL.

Для `final readonly NodeAsset` проверяются точный конструктор, типы и порядок всех 19 колонок `_node_assets`, неизменяемость, nullable-метаданные и канонические даты. Объект не выполняет вычисление пути, файловый или сетевой ввод-вывод, выбор режима отдачи и не содержит вычисляемые дубли сохранённых значений.

Для элемента `NodeInput::$assets` проверяется закрытый набор обязательных ключей `id`, `kind`, `role`, `src`, `name`, `title`, `intro`, `sort`. `null` создаёт ресурс, положительный ID обновляет только ресурс текущего материала, а ноль, повтор, чужой ID, неизвестный ключ, запрещённый вид, роль или путь отклоняются до транзакции. Служебные метаданные не принимаются, сервер пересчитывает их сам, а удаление элемента из полного набора не удаляет физический файл.

Для базового списка проверяются цепочка `setNodeType()`, `setNodeCategory()`, `setNodeLetter()`, `setNodePage()`, результаты `getNodeList()` и `getNodeCount()`, отсутствие дублей при основной и дополнительной категории, одинаковые фильтры списка и количества, игнорирование пагинации в количестве и отказ от произвольных SQL-ключей. Буквенный фильтр принимает пустую строку либо одну Unicode-букву или цифру, работает без учёта регистра только при `list.alpha = true`, экранирует шаблон `LIKE` и использует индекс `title`. Требуемые представлением поля, категории, связи и ресурсы догружаются пакетно для страницы без N+1; отдельный `NodeItem` отсутствует.

Для дополнительных фильтров проверяются `setNodeAuthor()`, `setNodeLetter()`, типизированный `setNodeStatus()` и закрытый реестр `setNodeOrder()`; пользовательский контекст не может запросом состояния расширить собственный доступ. Конфигурация списка принимает `limit` в границах `1..limits.maxlist`, логический `alpha` и уникальное подмножество `show` из `category`, `author`, `date`, `views`.

`setNodePublished()` принимает канонические nullable-границы `from` и `until`, применяет интервал `[from, until)` только к `_nodes.published` и использует существующий составной индекс типа и состояния. Проверяются каждая одиночная граница, точные значения на краях, неверная дата, обе границы `null`, равенство и обратный порядок. Свободный выбор колонки, `setNodePeriod()` и публичные параметры периода отсутствуют.

Для типов проверяются точные сигнатуры `getNodeType()` и `getNodeTypeList()`, точный конструктор и неизменяемость `final readonly NodeType`, объединение метаданных базы с эффективными настройками и полями, канонический формат дат, публичное исключение отключённых и повреждённых типов, административное чтение валидных отключённых типов, один SQL для списка и отсутствие повторной загрузки одного имени в экземпляре `NodeQuery`. Отдельно подтверждается, что `final readonly NodeTypeInput` принимает только `title`, `intro`, `ext`, `sort`, `settings` и `fields`, не изменяется после создания, а `name`, `id`, `active`, `version`, `created`, `updated` и неизвестные свойства назначить через него нельзя. `NodeService` отклоняет неизвестные ключи и неподдерживаемые вложенные значения массивов.

Тесты передают настройки через штатный глобальный `$conf` и подтверждают, что Node читает только области `node`, `fields.node` и правило `uploads.<type>` уже разрешённого типа, не изменяет их и не обращается к пользовательским глобальным данным вместо `NodeContext`. Класс `NodeConfig` и параметры конфигурации в конструкторах отсутствуют; `NodeQuery` и `NodeService` получают один общий `Field`.

Для `final readonly NodeContext` проверяются точный конструктор, неизменяемость, `uid`, эффективные `groups`, отдельный `aid`, нормализованные имена `mods`, `manage`, `super`, `ip` и `lang`. `super` подразумевает управление и все типы, а `manage`, модерация или `super` невозможны без положительного `aid`. Адаптер преобразует существующие ключи `node` и `node-<name>` из `_admins.modules`, отвергает имя типа из запроса как источник права и не смешивает ID пользователя с ID администратора.

Проверка прав подтверждает: модератор одного типа не изменяет другой, `manage` не возникает из права типа, пользовательская группа может только отправить или непосредственно опубликовать материал по `workflow`, а обычные права чтения основной категории применяются независимо от модерации.

Для `workflow` проверяются только значения `all`, `user`, `group`, существование и уникальность ID в `groups` и `publish`, требование подмножества при групповом доступе, отключение маршрута через `features.submit`, `Pending` при модерации, `Published` без неё или для доверенной группы и невозможность передать состояние из формы. Отдельно проверяются отсутствие публичного `Draft`, невозможность модерации пользовательской группой, явное подтверждение прямой публикации гостя, административное уведомление `pending` и уведомление только зарегистрированного автора о `result`.

Для `support` проверяется строгий единственный изменяемый ключ типа `ext.mail`, а допустимые `state` и `prio` читаются только из полных карт `config/node.php → support`. Отсутствующая, повреждённая или изменившая числовой контракт карта безопасно блокирует расширение; `STATE_*`, `PRIO_*` и второй массив значений в PHP отсутствуют. При включённой почте новое обращение уведомляет только подписанных модераторов `node-help`, ответ владельца предпочитает назначенного подписанного оператора и корректно возвращается к группе при отсутствии получателя, а ответ администратора уведомляет только владельца. Собственный ответ, изменение рабочей карточки и выключенная настройка не создают строку Mail; тело приватного ответа не попадает в очередь, а сбой почты не отменяет тикет или комментарий.

Профиль `help` проверяется точным эффективным составом: доступ только зарегистрированному пользователю, прямая запись `Published`, обязательный `CommentMode::Open`, выключенные рейтинг, избранное, опрос, главная, закрепление, модерация публикации, расписание, связи, дерево, структурированные ресурсы и четыре публичные интеграции. Редакторский `[attach]` использует каталог типа и контролируемую отдачу, не создавая строку `_node_assets`.

Для `_admins.modules` проверяются чистая установка и штатное обновление до `TEXT NOT NULL`, побайтовое сохранение прежнего списка, явная передача значения обоими `INSERT` администратора, запись списка длиннее 255 символов и отказ неизвестных ключей. План чтения администратора не получает новый индекс или дополнительный запрос.

Для административной конфигурации проверяются прежние строковые вызовы `setConfigFile()` с прежним строковым преобразованием и новый пакетный вызов для `config/node.php`, области `fields.node` в `config/fields.php` и правила типа в `config/uploads.php`. Новый тип получает точную копию действующего правила `uploads.all` через `setUploadRuleData()` и автоматически появляется на существующем экране загрузок. Пакет обязан без преобразования сохранить `string`, `int`, `bool`, `null` и вложенные массивы, а `float`, объект, ресурс, замыкание и смешанную форму аргументов — отклонить до записи. Также проверяются сохранность остальных областей полей и загрузок, отсутствие промежуточного `config/local.php`, однократная пересборка общего кеша, откат всех исходников при ошибке и запрет прямой записи `local.php` из Node.

Публичная и административная формы материала проверяются с активными штатными редакторами: `intro` и `body` создаются только через `getTplTextarea()` с `mod = <type>` и хранилищами `node.intro`, `node.body`. Проверяются выбор редактора из `$conf['editor']`, правила из `$conf['uploads'][<type>]`, место `<type>.attach`, встроенный `getFileManagerWindow()`, пределы `checkEditorTextRoom()` и отсутствие редактора, драйвера, JavaScript или маршрута загрузки Node.

Структурированные ресурсы проверяются через существующий `getFileManagerField()` с местом `<type>.attach`: multipart-файл обрабатывает общий `getUploadService()`, выбранный путь — `getUploadTakenFile()`, а несколько уникальных экземпляров поля создают несколько строк `_node_assets`. Файлы сохраняются в `uploads/<type>`, изображения редактора используют `thumb`; `node.asset`, `uploads/node`, `temp`, `public` и отдельный загрузчик отсутствуют. Модератор `node-<type>` получает штатные файловые действия без ослабления прав обычного пользователя.

Специфичные языковые константы Node проверяются по префиксу `_NODE_*` во всех шести локалях отдельно для публичной и административной области. Существующие глобальные константы общих действий переиспользуются и не получают дубликат с префиксом Node.

Для глобальных полей проверяются динамические области в `admin/modules/fields.php`, неограниченное количество полей в рамках общих пределов конфигурации, именованные значения, все зарегистрированные типы, сохранение значений `0` и `false` и единый путь формы, нормализации, валидации и вывода. Определения принимают только нативные типы: `req`, `multi`, `active` являются `bool`, `sort` — `int`, а `default` соответствует базовому типу; строковые `'0'`, `'1'` и `'10'` отклоняются. Позиционного формата, числовых типов, двойного чтения и отдельной админки Node нет.

Для `getFieldTypeList()` проверяются точные ключи `title`, `control`, `multi`, `options`, десять утверждённых типов, их элементы формы и допустимые параметры. Только `select` разрешает `multi = true`; неизвестный тип, параметр или попытка передать класс, callback, SQL, путь шаблона либо CSS отклоняется.

Подписи реестра используют существующие `_FIELDINPUT`, `_FIELDAREA`, `_FIELDSELECT`, `_FIELDDATE`, `_FIELDTIME`, `_EMAIL`, `_URL`; новые `_FIELD_BOOL`, `_FIELD_INT`, `_FIELD_DECIMAL` определены во всех шести административных языках. Публичная форма не требует административных констант типов и не загружает ради них административный язык.

Для `select.options.items` проверяются только `title`, `active`, `sort`, устойчивость сохраняемого ключа, порядок `sort` с ключом, отказ нового выбора отключённого варианта и сохранение его подписи для прежнего значения. Отдельный числовой ID или SQL-запрос вариантов отсутствует.

Имена полей и ключи вариантов одинаково проверяются по `^[a-z][a-z0-9_]{0,31}$`: принимаются границы длины 1 и 32, отклоняются пустое и более длинное значение, первый цифровой символ, верхний регистр, национальные символы и дефис. Чисто цифровой ключ не может превратиться в `int` при работе PHP с массивом.

Для `title`, `intro` и `select.items.*.title` проверяются Unicode-границы 255 и 1000, обязательность подписи, канонический пустой `intro`, простой текст, существующая константа, отказ неизвестной строки `_...` и отсутствие HTML на выходной границе. Литерал не требует языкового файла, а константа разрешается штатным механизмом.

Для параметров проверяются включительные `min`, `max`, подсчёт Unicode-символов, точные числовые и календарные границы и количество элементов множественного `select`. Одиночный `select` с границами и `bool` с любым параметром отклоняются. `decimal` требует целый `scale` от `1` до `18`, дополняет дробную часть до фиксированной длины и точно сравнивает отрицательные, положительные и граничные значения без `float`; отсутствие, ноль и значение `19` отклоняются. Значения с 65 цифрами принимаются, с 66 — отклоняются; знак и точка не считаются, конфигурация не повышает предел.

Проверяются жёсткие границы 256 полей в наборе, 256 вариантов `select`, 64 выбранных значений, 4096 символов `text`, 262144 символа `textarea`, 254 символа `email`, 2048 символов `url` и 1048576 байт итогового канонического JSON. Значение ровно на границе принимается, превышение отклоняется до SQL, а `options.max` не может увеличить предел.

Для `default` проверяются применение только при создании активного поля и отсутствии ввода, отсутствие подстановки при чтении и редактировании, типизированное значение, уникальные активные ключи множественного `select` и отказ отключённого варианта. `active = false` вместе с `req = true` отклоняется; обязательное поле требуется для `Pending` и `Published`, но не для `Draft` и `Disabled`. Пустые строка и массив отсутствуют, а `false`, `0`, `'0.00'` сохраняются.

При изменении материала проверяются полный набор активных полей, сохранение прежних неактивных значений вопреки скрытому POST, полная замена активных значений, удаление отсутствующего необязательного поля и сохранённого ключа без определения. Неизвестное имя формы игнорируется. `updateNodeStatus()` не меняет JSON и проверяет готовность по сохранённым значениям.

Канонизация проверяется по каждому типу: края и переносы `text`, окончания строк и сохранение отступов `textarea`, повторы и порядок `select`, закрытые входы `bool`, границы и ведущие знаки `int`, точка и запрет экспоненты `decimal`, реальные даты и обе HTML-формы `datetime`, регистр частей `email`. Для URL принимаются `http`, `https` и `/path`, сохраняется регистр пути и запроса, а `//host`, учётные данные, адрес без схемы и опасные схемы отклоняются; `filterWebUrl()` не вызывается. Проверка и фильтрация подтверждаются одним набором граничных фикстур.

Класс `Field` загружается без Composer и одинаково обслуживает Node и остальные целевые области. Проверяются точное имя класса и файла, отсутствие собственного конструктора и состояния, один глобальный экземпляр `$fld`, отсутствие `FieldManager`, `FieldService`, `FieldRegistry`, каталога `core/classes/field/` и специальных классов Node.

Отдельно проверяются точные сигнатуры шести публичных методов `Field`: `getFieldTypeList()`, `filterFieldList()`, `filterFieldValues()`, `checkFieldValues()`, `getFieldForm()` и `getFieldView()`. Проверка возвращает не более одного из кодов `required`, `type`, `format`, `choice`, `min`, `max` по устойчивому имени поля, обязательность отключается только для незавершённого черновика, а неизвестные имена удаляются без ошибки. Нормализация не скрывает неверное значение, форма не читает POST и локализует коды без HTML из проверки, а вывод получает явные `Parser` и имя модуля. Методы CRUD и записи конфигурации отсутствуют.

`getFieldView()` проверяется как массив по устойчивым именам в порядке `sort`, затем имя. Каждая запись содержит точный набор `name`, `type`, `label_text`, `hint_text`, `value`, `value_text`, `value_html`, `value_href`, `items`; имя продублировано внутри для перебора шаблоном. Неактивные, пустые, неизвестные поля и удалённые варианты отсутствуют, но `false`, `0` и существующие отключённые варианты выводятся. Только `textarea` получает безопасный `value_html` от `Parser`, только проверенные `url` и `email` получают `value_href`, а `select` возвращает выбранные `items` с `value` и `label_text`.

`filterFieldList()` на каждой неверной структуре бросает `InvalidArgumentException` с путём первой ошибки и не возвращает частичный набор. `NodeService` преобразует его в `NodeException::INVALID` с исходным `previous`, а `NodeQuery` журналирует повреждённую сохранённую конфигурацию и исключает тип. Пользовательский ответ не раскрывает техническое сообщение; классы `FieldException` и `FieldError` отсутствуют.

Для записи типов проверяются точные сигнатуры `addNodeType()`, `updateNodeType()`, `updateNodeTypeStatus()` и `deleteNodeType()`, административный контекст, уникальность и неизменность имени, создание только в отключённом состоянии с `version = 1`, полная повторная проверка перед включением и отсутствие обходного способа изменить `active`. Ключ `ext` устанавливается, заменяется или очищается только у отключённого типа без материалов; при наличии материала отказ не меняет базу и конфигурацию, а после физического удаления всех материалов смена снова разрешена без отдельного флага. Каждое изменение требует ожидаемую версию и увеличивает её ровно на один; устаревшая форма получает `NodeException::CONFLICT` без изменения базы или конфигурации. Удаление отклоняется при наличии материалов, согласованно очищает конфигурацию и строку типа и сохраняет файловое дерево.

Схема расширений проверяется только как часть фактического `setup/sql/table.sql` и штатного обновления SLAED. Отдельные `_node_extensions`, колонка версии, установщик, деинсталлятор и мигратор отсутствуют; несовместимая настройка отклоняется текущим расширением по версии формата `config/node.php`. Отключение и повторное включение типа сохраняют данные.

Для `NodeService` проверяются точные сигнатуры `addNode()`, `updateNode()`, все разрешённые и запрещённые переходы `updateNodeStatus()`, а также отдельное физическое удаление `deleteNode()`. Создание принимает отдельный `NodeStatus`, разрешает только `Draft`, `Pending` или `Published`, проверяет право и фиксирует материал сразу с версией `1` одной транзакцией; `Disabled` и `Deleted` отклоняются без записи. Остальные проверки подтверждают обязательную ожидаемую версию, увеличение версии ровно на один, возвращённый сохранённый `Node`, отказ устаревшей записи и полную фиксацию или откат основной записи, категорий, связей и ресурсов.

Для `final readonly NodeInput` проверяются точный конструктор, неизменяемость, свойство `comon` типа существующего `CommentMode`, последний массив `ext` и отсутствие системных полей. `cids`, `rels` и `assets` являются полными наборами, пустой массив очищает соответствующие связи, а `fields` содержит полный набор активных редактируемых полей. Неизвестные структурные ключи, повторения, чужие идентификаторы и неподдерживаемые вложенные значения отклоняются до SQL. Неизвестное имя дополнительного поля отбрасывается общим `Field` по NOD-113 и не является структурным ключом `NodeInput`. `pubdate` проверяется как значение `_nodes.published`, `aname` применяется только к анонимному автору, создание получает `uid` и `ip` из `NodeContext`, а изменение сохраняет исходного автора и IP. Стандартный тип принимает только пустой `ext`; зарегистрированный тип канонизирует его своим `NodeExtension` и хранит только в собственной схеме.

Для границы типа проверяется отсутствие универсальных настроек материала и невозможность переопределить режим, права, процесс, интеграции, ресурсы, расширение или пределы. Отключённые `categories`, `poll`, `home`, `pinned`, `related`, `tree` и `schedule` принимают только утверждённые пустые значения, а отключённые `comments` — только `CommentMode::Disabled`; каждый подделанный непустой вариант отклоняется сервисом без записи, даже если контроллер не показал соответствующее поле. Для включённых комментариев проверяются все три значения `Disabled`, `Moderated` и `Open` без сведения к логическому типу.

Матрица состояний проверяется полностью: каждая разрешённая пара проходит, каждая отсутствующая пара отклоняется, повтор текущего состояния не выполняет `UPDATE`, восстановление всегда даёт `Disabled`, а будущий `published` и наступивший `expires` не создают новых состояний.

Для ошибок проверяются все коды `NodeException`, сохранение исходного исключения хранения в `previous`, преобразование модулем в ожидаемый HTTP-статус и отсутствие текста исключения, SQL и внутренних деталей в публичном ответе. `NodeQuery::getNode()` должен возвращать одинаковый `null` для отсутствующего и закрытого материала.

Для всех типов, включая тип без категорий и расширения, проверяются запрет прямых URL оригинала и thumb, контролируемые `200/206/HEAD`, внешний `302` без локального редиректа, общий `404`, MIME и отсутствие серверного скачивания внешнего источника. Изменение features/ext не открывает каталог.

Для `asset` и `report` проверяется адрес конкретного типа, точное совпадение типа маршрута с материалом и ресурсом, общий `404` при несовпадении и отсутствие любого публичного поведения у `index.php?name=node`. Жалоба дополнительно требует `POST`, CSRF и ограничение частоты.

Для `getNodeAsset()` одинаково проверяются отсутствующий, чужой и недоступный ресурс. Для трёх ресурсных методов `NodeService` проверяются повторная авторизация внутри сервиса, атомарный единственный учёт разрешённого `GET download`, отсутствие учёта для `HEAD`, показа, отказа и повторного диапазона, идемпотентная жалоба, сохранение только первого `ruid`, а также явное полезное или отклонённое решение только главным администратором или модератором типа. Полезная зарегистрированная жалоба начисляет `report` и очищается с ним в одной транзакции; гость и отклонённая жалоба баллов не создают. `hits`, `reported`, `ruid`, `_nodes.version`, `_nodes.updated` и `_node_assets.updated` не получают побочных изменений сверх утверждённых колонок.

Для контролируемой отдачи проверяются прямой отказ ко всему `uploads/<type>`, состояние материала, `pread` основной категории, дополнительное ограничение расширения, недоступность редакторского файла и `thumb` в обход Node, а также смена режима без окна незащищённого доступа. Полный `GET`, `HEAD`, открытый, закрытый и суффиксный одиночные диапазоны дают правильные `200`, `206`, длину и границы; повреждённый и неудовлетворимый диапазоны дают `416`, а несколько корректных диапазонов — полный `200` без multipart.

Для HTTP-кеша проверяются `ETag`, `Last-Modified`, приоритет `If-None-Match`, запасной `If-Modified-Since`, совпадающий и несовпадающий `If-Range`, отсутствие тела у `HEAD` и `304`, а также повторная проверка прав до каждого `304`. Контролируемый ответ имеет `private, no-cache, must-revalidate, no-transform`, не удаляет cookie, не использует `cache_b` и не создаёт файл в `storage/cache`; прямой публичный ресурс остаётся под существующими правилами веб-сервера.

Для совместимости прежний двухаргументный `getFileStream()` остаётся вложением `application/octet-stream` без кеша. Проверяются безопасное имя, серверный MIME, принудительное скачивание SVG, HTML, XML, PDF и неизвестного формата, потоковое чтение большого файла ограниченными блоками и остановка после разрыва соединения. Callback `$start` выполняется ровно один раз перед телом полного ответа или диапазона с нуля и не выполняется для ошибки открытия, `HEAD`, `304`, `416` и ненулевого диапазона.

Для `attach` проверяются только `GET|HEAD`, положительный глобальный `id`, точное имя `key`, значения `thumb` отсутствует или `1`, правильные корень и уменьшенная копия, а также общий `404` для любого отказа. Набор атак включает `/`, `\\`, `..`, `%`, нулевой байт, двойное кодирование, drive letter, stream wrapper, alternate data stream, симлинк наружу, имя длиннее 255 байт, допустимо выглядящий `.php` и безопасное имя чужого материала. `file` в маршруте Node отсутствует и продолжает обрабатываться только глобальным маршрутизатором.

`Parser::getAttachList()` и `filterAttach()` проверяются одним набором допустимых и повреждённых тегов. `filterContent()` и `filterDoc()` сохраняют прежние вызовы с `nid = 0`, используют уже существующий корень `uploads/<mod>` как `uploads/<type>`, включают `nid` в память запроса и строят контролируемый URL только для сохранённого материала; дополнительные поля в поиск вложений не входят.

Для материала в нескольких категориях проверяются: дополнительная категория не обходит `pread` основной, закрытая дополнительная категория не появляется недоступному пользователю, а все публичные интеграции используют ту же общую проверку доступа.

Порядок интеграций проверяется зависимостями этапов: категории и `NodeContext` готовы до CRUD, контракт цели — до комментариев, рейтинга и избранного; правила баллов — до вознаграждаемых действий, уведомление выполняется только после успешной фиксации изменения, а RSS, sitemap и SEO используют окончательные публичные URL. Временная прямая ветка конкретного типа и повторная адаптация одной подсистемы не допускаются.

Для единой регистрации проверяется, что глобальная подсистема передаёт публичное имя типа и глобальный `_nodes.id`, а `NodeQuery` является единственным разрешителем динамического типа и доступа. `modul` хранит неизменяемое имя типа, `cid`, `mid` или `fid` — глобальный ID; отдельные реестры Node в комментариях, рейтинге, избранном, поиске, RSS, sitemap и блоках отсутствуют. Неизвестная, отключённая и недоступная цель даёт одинаковое отсутствие результата, а пакетное чтение не выполняет запрос на каждый ID.

Для `final readonly NodeTarget` проверяются точный файл, конструктор и порядок `NodeType`, `id`, `uid`, `title`, `CommentMode`, `comnum`, `score`, `ratings`, неизменяемость, отсутствие URL, содержимого и поведения. `getNodeTarget()` и `getNodeTargetList()` используют одинаковую проверку доступа; пакет принимает только `id => type`, не более `syncbatch`, сохраняет входной порядок, исключает несовпадения и использует не более двух SQL-запросов на смешанный набор. Полный `Node` и тяжёлые связанные данные не создаются.

Для `final NodeView` проверяются файл `core/classes/node/view.php`, конструктор с `Parser` и `Field` и единственный публичный `getNodeView(NodeType $type, Node|NodeTarget $node, string $mode): array`. Полный `Node` разрешает `list`, `view`, `card`, лёгкий `NodeTarget` — `card`, `block`, `search`; неизвестный режим, несовместимая пара и несовпадение типа дают `NodeException::INVALID`. Подготовщик не выполняет SQL, не вызывает `Template`, не читает запрос и не создаёт необработанный пользовательский HTML.

Каждый режим `NodeView` возвращает точный набор `id`, `type`, `mode`, `href`, `title`, `intro`, `intro_html`, `body_html`, `author`, `ahref`, `ctitle`, `chref`, `date`, `date_iso`, `mtime_iso`, `views`, `comnum`, `rating`, `ratings`, `fields`, `assets` без произвольных добавлений. Проверяются обычный экранируемый текст, HTML только в утверждённых `*_html`, однократное экранирование URL шаблоном, `null` рейтинга без голосов, одинаковая форма лёгкой цели, группировка ресурсов по роли и отсутствие `src`, `reported`, `ruid` и физического пути. Массив не сериализуется отдельно и не получает собственного кеша.

Проверки Point: класс S01 и подключение S04 — [points.md](points.md).

Для NOD-206 проверяются тип с категориями, тип с расширением и простой тип без обоих признаков: все три сохраняют серверную защиту, контролируемые URL и права новой загрузки. Активация при неподтверждённой защите отклоняется.

Счётчик `hits` увеличивается ровно один раз при разрешённом начале `download`; `HEAD`, `304`, `416`, отказ, отсутствующий файл, повторные диапазоны и обычный показ изображения его не меняют.

Для жалоб проверяются `POST` с CSRF, идемпотентная совместная установка `reported` и первого `ruid`, сохранение `ruid = 0` для гостя, неизменность первого автора при повторе, ограничение частоты и отсутствие `ruid` в данных публичного шаблона. Административный разбор требует явного `useful`: полезная жалоба зарегистрированного пользователя создаёт ему одно событие `report`, отклонённая и гостевая не начисляются; после решения и штатной замены ресурса `reported` и `ruid` очищаются вместе. Два параллельных решения блокируют и повторно проверяют ту же строку: только первое начисляет и очищает, второе завершается без изменений.

Для профилей проверяется создание независимой конфигурации без runtime-ссылки на профиль. Клонирование создаёт новое неизменяемое `name`, экспорт не содержит данных, секретов, абсолютных путей и файлов. Тип с ошибкой зависимости, поля, роли ресурса, каталога или расширения остаётся отключённым.

Экспорт типа проверяется как UTF-8 JSON `node-<name>.json` с точными верхнеуровневыми ключами `format`, `version`, `type` и точным составом определения. Импорт принимает не более 1 МиБ, всегда создаёт новый отключённый тип через общий путь создания и позволяет до записи заменить предложенное имя. Проверяются неизвестный ключ, неверные JSON, формат и версия, существующее имя, недопустимые настройки, поле, режим, роль ресурса и расширение; ни одна ошибка не оставляет строку, конфигурацию или каталог. PHP-сериализация, данные материалов, ресурсы, секреты, локальные пути и отдельный список зависимостей отсутствуют.

Списки принимают только `published`, `updated`, `title`, `views` и `rating`, применяют разрешённое типом значение по умолчанию и направления `asc|desc`, отвергают запрещённый типом ключ, произвольные имена SQL-колонок и выражения из конфигурации. Проверяются устойчивые дополнительные порядки, последние позиции материалов без оценок, безусловный приоритет `pinned`, `400` публичного запроса, перенаправление явно переданной стандартной сортировки на чистый URL и `noindex, follow` для нестандартной сортировки и `let`.

Для времени публикации проверяются материал до `published`, внутри разрешённого интервала и после `expires`; наступление срока не должно менять состояние и версию записи.

Эффективная конфигурация интеграций после объединения с `defaults` принимает точные ключи `search`, `rss`, `sitemap`, `blocks`, `seo`: первые четыре являются нативными `bool`, а последний допускает только `website`, `article`, `news`. Проверяется безопасное отключённое значение по умолчанию, допустимый пустой набор отличий типа, отказ неизвестного, отсутствующего в итоговом разделе или неверного ключа, отсутствие регистрации выключенного типа у потребителя и передача выбранного `seo` в существующий `setHead()` без отдельного генератора разметки.

Для разрешения типа проверяются фиксированный обработчик `modules/node/index.php`, отсутствие SQL Node для постороннего имени, `404` для отключённого зарегистрированного типа и отсутствие возврата к одноимённому старому модулю даже при его наличии на стенде.

Для административных маршрутов проверяются утверждённые сочетания `op` и HTTP-метода, неизменяемый ключ `type`, глобальный `id`, обязательные `version` и CSRF в теле записи, отказ `GET` для `status` и `delete`, `404` неизвестной операции и Post/Redirect/Get после успешного изменения. Операции `save`, `saveadd` и `saveedit` отсутствуют.

Административный `POST op=sync` проверяет CSRF, право модерации типа и точное расширение `sync`, не принимает URL из запроса и вызывает `updateNodeSync()` для сохранённого источника. `GET`, другой тип и другой обработчик получают отказ; успешное обновление и ответ без изменений завершаются Post/Redirect/Get, а ошибка сохраняет прежний текст и выводит только безопасное сообщение.

Два редактора получают одну версию материала и типа. Первый успешно сохраняет, второй получает `409` без изменения основной записи, связей, ресурсов и конфигурации. Ответ второго сохраняет его нормализованные значения, безопасно показывает актуальные отличия и не меняет ожидаемую версию без явного продолжения. Продолжение само ничего не записывает; следующий `POST` использует актуальную версию, а третье конкурентное изменение снова даёт `409`.

Проверяются оба выхода из конфликта: канонический `GET` загружает актуальные данные, а продолжение сохраняет пользовательский ввод только в форме. Для смены состояния и удаления требуется повторное открытие и подтверждение актуальной записи. Автоматическое слияние, запись без версии, серверный черновик и новый объект конфликта отсутствуют.

Для публичных маршрутов проверяются список, категория, пагинация, просмотр, добавление, ресурс, вложение и жалоба; закрытый набор `op`, допустимые HTTP-методы, `405` с `Allow`, положительные `cat`, `num` и `id`, точное совпадение типа и общий `404`. `attach` дополнительно принимает только безопасный `key` и необязательный `thumb=1`. `preview` проходит полную валидацию без SQL-записи, `submit` требует CSRF и права `workflow`, создаёт материал через `NodeService` и завершается безопасным GET после перенаправления. Публичного изменения существующей записи и операций `liste`, `send`, `loading`, `broken` нет.

### Состав выпуска

Приёмка охватывает все девять замен — `news`, `pages`, `faq`, `help`, `jokes`, `content`, `links`, `files`, `media` — и дополнительный `docs`. Каждый профиль проходит общий валидатор конструктора, создание отключённого типа, активацию, публичный сценарий с проверкой доступа и административную запись с проверкой сохранённых данных. Для `help` дополнительно обязательна приватная поддержка, для `content` — ручная и плановая синхронизация. Полные специальные сценарии остальных профилей дополняются вместе с их определениями; проверка трёх эталонов не закрывает приёмку десяти профилей.

Приёмка подтверждает отсутствие runtime-зависимости от таблиц и кода девяти заменяемых модулей. Импорт их старых данных, совместимость и fallback не тестируются, потому что не входят в реализацию Node. Эти модули могут присутствовать только на стенде и исключаются из целевой поставки. Остающиеся `account`, `forum`, `shop` проверяются с общими Point и Rating; обновление общих данных проверяется отдельно по `12-migration.md`.

### Производительность

Бюджет SQL, отсутствие N+1, массовые операции и кеш. Повторное чтение типа одним `NodeQuery` не выполняет SQL и повторную сборку, а новый HTTP-запрос не наследует память предыдущего. Настройки и поля читаются из общего `$conf` без отдельного файла кеша Node.

Для интеграций набор из `1200` ID обязан дать вызовы размером `500`, `500` и `200`; нулевые, отрицательные и повторные значения до разбиения удаляются. Проверяется отсутствие запроса на каждый материал, `OFFSET` и передачи более `limits.syncbatch` ID. Искусственная ошибка второй партии оставляет первую подтверждённой, не подтверждает вторую и позволяет продолжить с последнего сохранённого курсора без пропусков и повторной обработки первой партии.

Отдельно проверяется, что `syncbatch` не меняет `search.slimit`, `rss.max` и `mail.batch`. Генерация sitemap читает минимальные строки Node партиями по `500`, не удерживает весь набор Node в памяти и создаёт следующий XML-файл после `50000` URL.

Автоматическая проверка снимает `$db->qnum` до и после обработчика и закрепляет верхние границы: `0` для попадания списка в HTML-кеш, `3/7` для обычного/максимального списка без построения HTML-кеша, `4/8` при его построении с getNodeDeadline(), `5/6` для материала без/со связанными карточками, `2` для `[attach]`, чтения и `HEAD` ресурса, `3` для начала скачивания и жалобы, `3` для административного списка, `5` для формы изменения, `6/7` для смены состояния без/с изменением _node_publish и `2` Node-запроса для физического удаления. Изменение количества строк, категорий, связей и ресурсов внутри утверждённых пределов не увеличивает число пакетных запросов.

Профиль времени запускается с отключённым Xdebug и прогретой MariaDB серией повторов и проверяет `p95`: `150 ms` для чтения и модели, `50 ms` для файловой авторизации без потока, `300 ms` для административной записи без загрузки и не более `10 ms` в среднем на SQL. Эти значения отчётные и воспроизводимые, но не являются зависящим от нагрузки PHPUnit-гейтом.

HTML-кеш принимает только анонимный `GET` списка с пустым `op`, сортировкой типа по умолчанию и строгими параметрами `name`, `cat`, `num`. Проверяются разные ключи типа, категории и страницы, отказ кеша при `let`, нестандартных `order` или `dir`, повторном, лишнем или повреждённом параметре, а также отсутствие кеша для `view`, `add`, `asset`, `attach`, `report`, пользователя и администратора.

Успешные создание, изменение, смена состояния, удаление материала и изменение типа делают прежний HTML недостижимым через новое поколение `Cache`. Финальный addEpoch(true) после COMMIT не подавляется ранним административным вызовом; допускаются два увеличения в одном запросе. Guard запрещает чтение/запись HTML-кеша до завершения. Подтверждённый откат снимает guard, неизвестный исход сохраняет его до восстановления. Изменения `views`, `hits`, `reported` и `ruid` поколение не увеличивают. Материалы, списки и SQL-результаты не появляются в отдельном дисковом кеше Node.

## Малая фикстура MariaDB

`node_probe.php` создаёт одноразовую базу со случайным безопасным именем на настроенном сервере MariaDB. Рабочая база из `$conf['db']['name']` явно запрещена как цель создания, очистки и удаления; точное имя одноразовой базы сохраняется внутри процесса и удаляется в `finally` и обработчике завершения.

- DDL всех таблиц Node и его утверждённых расширений извлекается из фактического `setup/sql/table.sql`; в тестах нет второй копии схемы.
- Требуемые сценариями таблицы `users`, `categories`, `admins`, `comment`, `rating` и `favorites` также извлекаются из установочного SQL только по необходимости.
- Конфигурация, файловая область и кеш направляются во временный корень процесса, поэтому тест не меняет `config/*.php`, каталоги типов в `uploads` и `storage/cache` стенда.
- Один процесс создаёт схему один раз; отдельный сценарий использует транзакцию и откат либо полностью пересоздаёт принадлежащие ему строки.
- Невозможность создать одноразовую базу на стенде является явной ошибкой проверки, а не молчаливым пропуском.

Базовые данные содержат три доказательных типа `news`, `docs`, `files`, публичную, закрытую, дочернюю и языковую категории, анонимного и зарегистрированного автора, участника группы, модератора типа, управляющего Node и главного администратора. Сценарии переключают активность типа и создают материалы всех состояний, будущую публикацию, истёкший материал, главную и закреплённую запись, дополнительные категории, дерево `parent`, обычные связи и несколько ресурсов разных ролей.

Граничные наборы создаются только для использующего их сценария: максимальная страница, `limits.maxassets`, пределы категорий и связей, повреждённые поля и повторяющиеся идентификаторы. После сценария они не остаются в базе.

Для защиты от N+1 одна и та же выборка выполняется сначала с одним материалом, затем с максимальной страницей и максимальными допустимыми связанными наборами. `$db->qnum` обязан сохранить утверждённую границу; проверка не подменяется анализом текста SQL.

## Профиль большой базы

`php tools/node-profile.php` запускается явно и не входит в обычный PHPUnit или pre-commit. Инструмент создаёт собственную одноразовую базу и детерминированно наполняет её набором:

- `100000` материалов;
- `10` типов;
- `200` категорий;
- по `2` дополнительные категории и связи на материал;
- по `3` ресурса на материал.

Данные создаются пакетным SQL, а не циклом из сотен тысяч одиночных `INSERT`. Профиль прогревает одинаковые маршруты, сравнивает страницу из одного элемента с максимальной страницей, выводит количество SQL, общее и среднее SQL-время, `p50`, `p95` и планы основных запросов. Превышение числа SQL завершает инструмент ошибкой; время сравнивается с целями NOD-100 и записывается в отчёт. При загруженном Xdebug временные результаты не считаются приёмочными.

## Браузерная приёмка

Постоянный браузерный runner Node, новый npm-скрипт и тестовый файл в репозитории не создаются. Проверка выполняется существующими средствами проекта и правилами `.claude/skills/browser-debugging/SKILL.md`:

- `npm run browser:audit -- --url <url>` запускает чистую проверку страницы;
- `npm run browser:inspect -- --url <url>` собирает подробные CDP-сигналы;
- `npm run browser:attach` используется только для явно выбранной уже открытой вкладки;
- многошаговый Playwright-сценарий временно находится в `c:\tmp\`, запускается оттуда и удаляется после работы.

Учётные данные не записываются в документацию, сценарий или репозиторий. Пользователь сайта и администратор получают разные браузерные контексты и проходят разные формы входа по проектному навыку. Пользовательская форма выбирается как первая видимая после проверки скрытого `op=login`; административная отправка и ожидание `networkidle` выполняются совместно с пределом `40000 ms` для ALTCHA. Успех обоих входов подтверждается исчезновением соответствующего поля пароля, а не только адресом страницы.

Минимальный обязательный набор состоит из семи сценариев:

1. Гость открывает списки и материалы `news`, `docs`, `files`; проверяются разные представления, canonical, категория, пагинация и ключевой экран на узкой и широкой ширине.
2. Администратор создаёт отключённый тип `nodeprobe`, получает `404` на его публичном адресе, включает тип и получает рабочий пустой список.
3. Пользователь сайта открывает публичную форму `nodeprobe`, выполняет предпросмотр без записи и отправляет материал в состояние, определённое `workflow`.
4. Администратор видит материал в очереди, публикует его, после чего новый гостевой контекст сразу видит запись в списке; этим подтверждается инвалидация HTML-кеша.
5. Две административные страницы редактируют одну версию: первая сохраняет, вторая получает `409`, сохраняет свой ввод, показывает актуальные отличия, продолжает без записи и затем успешно сохраняет обычным новым `POST`.
6. Галерея, `[attach]`, скачивание и плеер получают рабочие контролируемые адреса; прямой адрес закрытого дерева запрещён, а ожидаемые `HEAD`, `Range` и скачивание не создают ошибок интерфейса.
7. Закрытый материал одинаково отсутствует для гостя и постороннего пользователя, доступен разрешённой группе и модератору своего типа и недоступен модератору другого типа.

Фикстура `news` создаётся только из утверждённого профиля: полный набор сортировок, режим `article`, все стандартные возможности кроме `tree`, интеграции поиска, RSS, sitemap и блоков, SEO `news`, роли `cover` и `gallery`, стандартный пользовательский `workflow` с модерацией и без начальных полей или расширения. Тест не собирает параллельную ручную конфигурацию этого типа.

Фикстура `docs` также создаётся из профиля: сортировка `title asc`, алфавитный фильтр, режим `docs`, категории, избранное, связи `parent` и `related`, поиск, sitemap, блоки и SEO `article`. Подтверждаются отсутствие публичной отправки, комментариев, рейтинга, опроса, структурированных ресурсов, начальных полей и расширения.

Фикстура `files` создаётся из профиля с режимом `files`, страницей до 25 строк, алфавитом, всеми сортировками, категориями, комментариями, рейтингом, избранным, главной, закреплением, расписанием, связями и пользовательской отправкой через модерацию. Проверяются обе роли: необязательная локальная `cover` и обязательная `download` от одного до десяти локальных или внешних ресурсов с жалобами и `hits`. Поля `release` и `site` проходят общий `Field`, а размер файла не дублируется в JSON. Расширение отсутствует.

Каждая страница проверяется на `console`, `pageerror`, неразрешённые ответы `4xx/5xx`, сломанные запросы и новые записи в `error_php.log`, `error_sql.log`, `error_site.log`. Ожидаемые `404`, `409` и запрет прямого файла указываются сценарием явно и не считаются общей сетевой ошибкой.

Перед началом сценарий требует локальный HTTPS-хост `slaed.loc`, разрешённый в `127.0.0.1`, отсутствие типа и каталога `nodeprobe` и наличие активных доказательных типов. Все созданные записи помечаются уникальным идентификатором запуска. Очистка удаляет через интерфейс только сохранённые ID текущего запуска, затем удаляет тип и, после проверки точного пути и отсутствия типа, созданный этим запуском каталог `uploads/nodeprobe`. Чужой существующий тип, каталог или материал автоматически не удаляется: проверка останавливается и сообщает точную помеху.

Временный Playwright-файл и созданные им сессии удаляются после проверки. Если оба backend после реальной попытки запуска недоступны, выбрана неверная вкладка или проблема не относится к браузеру, применяются условия остановки проектного навыка вместо ложного успешного отчёта.

## Приёмка завершённых технических контрактов

- Rating: уникальный nonce одной доставки и разные nonce при нулевом интервале; подмена значения с прежним nonce; граница суток и переполнение формы; каждая ошибка SQL/COMMIT; обновление остатка/сроков и повтор manifest. Аннулирование главному администратору, сохранение last, отсутствие строки цели, отрицательный доступ к журналу. Баланс и журнал Point неизменны во всех ветках.
- Point: getEventId возвращает ID/0/false без смешения; блокировка пользователя раньше события, конкурентная компенсация, отключённые новые начисления при отмене прежнего, исходный ключ без клиентского source. Прежний тест числовых наград заменяется проверкой 15 имён и отсутствия rate; голосование не требует Point даже косвенно через NodeService.
- Конфигурация: два писателя разных областей, устаревшая форма, исходные PHP/OPcache/local.php, остановка процесса на каждом шаге журнала, известный и неизвестный исход COMMIT, восстановление из административного маршрута невалидного типа. Сверить version БД и node.types, правило ratings, uploads и экспорт восьми свойств ввода плюс name.
- Кеш: ранний административный addEpoch не подавляет финальный force; авария после COMMIT оставляет обход кеша, восстановление занятого маркера не удаляет его; параллельный рендер не публикует старый снимок. Уже готовый кеш перестаёт отдаваться точно на published/expires, включая новую будущую запись и stale-ветку; один SQL срока на промахе, ноль на попадании.
- Файлы/категории: два процесса upload/deleteType/createType и assignment/deleteCategory; отсутствие инверсии lock, повторная проверка под lock, node-<name> для модератора, скрытый пользовательский файл, неизменность защиты. Прямые оригинал/thumbnail/preview запрещены у всех десяти профилей, контролируемые ответы проверяют права и владельца.
- Feed: полный Parser и извлечение attach с враждебными Markdown/BB/HTML/URL; транспорт resolve/get без DNS и HTTP наружу; private redirect и rebinding; одинаковые XML дают одинаковый body без зависимости от темы и rss.temp. Ошибка не очищает последнее тело content.
- Field: общий preflight всех строк до первого изменения, неоднозначные позиции/подписи, disabled/empty/0, расширение колонок, остановка между партиями, совпавший/чужой target hash, повтор после публикации конфигурации и все остающиеся формы без двойного формата.
- Интеграции: обычный и домашний bootstrap, язык node, admin/AJAX без физического старого модуля; смешанные типы с двумя разными расширениями; поиск с буквальными %/_; дерево без недоступного родителя, курсор sitemap, операции счётчиков. Опрос сохраняет собственный voting-limit и награду poll, auto_links — outs и visit; повтор не удваивает награду за тот же источник.

Эти проверки являются требованиями к будущей реализации. В текущей работе проверяется только документация; фиктивные PHP/HTTP-результаты не подставляются.
