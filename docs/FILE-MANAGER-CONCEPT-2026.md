# SLAED CMS 6.3 — File Manager / File Browser
## План реализации

**Статус:** решения закрыты, макеты утверждены, этапы 0, 0.5, 1, 2a, 2b, 3, 4, 5, 6 и 7 закрыты, следующий — этап 8  
**Объём одной сессии:** шапка, свой этап и разделы из его карты чтения — около 500–600 строк вместо всего документа  
**Целевая версия:** SLAED CMS 6.3 Phoenix  
**Принцип:** развить существующую подсистему `uploads`, не внедряя сторонний файловый менеджер.

Это не обсуждение. Каждое решение ниже принято и обосновано там, где названо;
возвращаться к ним — не работа, а переделка. Читать до конца перед первой правкой.

## Как работать над этим планом

**Один этап — одна сессия — один готовый к коммиту набор.** Этапы идут по
порядку §26 и каждый заканчивается работающим и проверенным куском. Не начинать
следующий, не закрыв предыдущий: порядок не произвольный, он объяснён в §26 у
каждого этапа.

Коммит делается **только по явной команде владельца** — `.rules/git.md` это
запрещает без неё, и план исключения не вводит. «Один коммит на этап» описывает
границу набора изменений, а не право закоммитить его самостоятельно. Работа
этапа заканчивается отчётом и предложением коммита с готовым сообщением.

**Перед первой правкой этапа прочитать:**

```text
.agents/SYSTEM-PREAMBLE.md            роль и рабочий процесс
.agents/skills/slaed/INDEX.md         выбрать рабочий скилл под задачу
.rules/*                              строгие правила, всегда обязательны
этот файл: шапку и свой этап          у каждого этапа есть карта чтения
разделы, названные в карте этапа      только их, а не документ целиком
```

**Документ целиком читать не нужно.** У каждого этапа в §26 стоит карта чтения:
какие разделы плана, какие файлы кода и какие тесты ему нужны. Разделы, в карту
не попавшие, к задаче отношения не имеют. Оглавление — ниже.

**Макеты открывать в браузере, а не читать как текст.** Это восемьсот строк HTML
каждый, и они написаны, чтобы на них смотреть:

```text
demo/filemanager-v2-rail.html      окно редактора
demo/filemanager-admin-2026.html   админка
```

В исходник заглядывать точечно — за именем класса или куском разметки. Макет —
рабочий образец: классы, разметка и поведение в нём такие, какими должны стать в
коде. Расхождение макета и кода — дефект кода, пока владелец не решил иначе.

**Оглавление:**

**Что считается закрытым этапом:**

```text
php -l на каждом изменённом PHP-файле
PHPUnit-тест на этапы с логикой: пути, права, дескриптор, конфликт версий
браузерная проверка на этапы с интерфейсом, со скриншотами всех состояний
storage/logs/error_php.log, error_sql.log, error_site.log — без новых записей
отчёт по .rules/report.md
```

Тест соразмерен риску этапа: правило путей и версии файла проверяются
модульно, раскладка и веер — глазами в браузере.

**Что кусается на каждом этапе:**

- Границу шаблона легко пробить незаметно. PHP отдаёт данные, флаги и адреса;
  имена CSS-классов и разметка живут в шаблонах. Это самое частое нарушение в
  этом проекте, и файловый браузер с его строками и плитками — первый кандидат.
- Тема одна на всех. Если компонента не хватает — он добавляется в тему под тем
  же именем, что во второй теме (§32), а не переопределяется в модуле.
- Языковые константы правятся сразу во всех шести локалях, иначе интерфейс
  разъезжается по языкам (`.rules/constants.md`).
- Изменяющее действие идёт только POST-ом с токеном. Ни одна новая ссылка не
  должна ничего менять (§17).
- Ключ шаблона может пропасть молча. `Template::getView()` раздаёт данные через
  `extract($data, EXTR_SKIP)`, поэтому ключи, чьи имена уже заняты локальными
  переменными самого рендерера — `path`, `file`, `data`, `real`, `lev`,
  `iscode`, — до шаблона не доходят и выводятся пустыми. Стоившая тишины строка
  `title="{{ path }}"` в строке и плитке уже поймана и переименована в
  `hint_text`; новые фрагменты этих имён не берут.

**Что уже сделано и на что можно опираться:**

```text
docs/EDITOR-UPLOADS-2026.md   закрыт: настройки решают, поле решает, гость изолирован
core/system.php               getEditorFileOwner()  — токен владельца на сессию гостя
core/system.php               getEditorFileJson()   — список только своих файлов, лимит guestfiles
core/system.php               checkEditorUploadAccess() — одно решение о праве загрузки
core/helpers.php              getEditorRoomData()   — ширина поля решает, можно ли embed
```

Гостевая изоляция и `guestfiles` работают. Прежний блокер «guest owner = 0»
снят, и каталог гостя показывает файлы его сессии — это больше не заглушка.

**Утверждённые макеты:**

```text
demo/filemanager-v2-rail.html      ToastUI, compact mode, боковой рельс
demo/filemanager-admin-2026.html   Админка, full mode, каталог и системные файлы
```

Оба построены на одной оболочке: навигация слева, работа в центре, свойства
справа, постоянная строка состояния внизу. Отличаются правами и корнем, а не
языком интерфейса.

**Три механизма общие для обоих экранов** и описаны один раз, в §9:

```text
sl-dial     веер действий на объекте
sl-modal    галерея предпросмотра

```

## 1. Цель

Создать единый файловый слой SLAED, который используется в трёх сценариях:

1. **Администратор → Загрузки → Каталог файлов** — полноценный файловый менеджер для `uploads/*`.
2. **ToastUI → Файловый менеджер** — компактный браузер разрешённых файлов модуля для загрузки, выбора и вставки в материал.
3. **Администратор → Загрузки → Системные файлы** — отдельная вкладка для просмотра и редактирования файлов SLAED внутри `BASE_DIR`.

Главная схема:

```text
                         FileManager
                             │
              ┌──────────────┼──────────────┐
              │              │              │
              ▼              ▼              ▼
        Uploads Admin     ToastUI       System Files
          FULL MODE      COMPACT MODE      FULL MODE
              │              │              │
         uploads/*       uploads/mod      BASE_DIR
```

## 2. Что уже есть в SLAED 6.3

### 2.1. `admin/modules/uploads.php`

Модуль уже является естественным владельцем будущего File Manager:

- выбор upload-директории;
- загрузка файла с компьютера;
- загрузка файла по URL;
- правила расширений;
- лимиты размеров и квот;
- ограничения изображений;
- количество файлов;
- основная директория;
- дополнительная директория `thumb`;
- файловые списки через HTMX;
- настройка шаблонов отображения файлов.

Поэтому новый отдельный `admin/modules/filemanager.php` **не создаётся**.

### 2.2. `core/classes/upload.php`

Класс `Upload` уже отвечает за безопасную публикацию новых файлов:

- проверка extension;
- проверка MIME;
- проверка изображений;
- quota;
- maxbytes;
- maxwidth/maxheight;
- collision-free naming;
- временный `.part`;
- lock;
- atomic publication;
- remote URL security;
- удаление файлов, созданных Upload service.

`Upload` остаётся специализированным сервисом загрузки и **не превращается в File Manager**.

### 2.3. ToastUI

У ToastUI уже реализована существенная часть интеграции:

```text
editorUpload
editorFiles
```

Редактор уже получает:

- module upload rule;
- CSRF token;
- extensions;
- maxquota;
- maxbytes;
- maxwidth;
- maxheight;
- maxfiles;
- список сохранённых файлов;
- drag & drop;
- upload;
- attachment/embed modes;
- собственное окно «Файловый менеджер».

Это сохраняется и развивается.

### 2.4. `Editor::getCode()`

Для системных текстовых файлов уже существует CodeMirror 6 через:

```php
Editor::getCode(...)
```

Отдельный code editor для File Manager не нужен.

## 3. Основные архитектурные решения

### Решение 1. Хозяин File Manager — `uploads`

UI интегрируется в:

```text
admin/modules/uploads.php
```

Главные вкладки:

```text
[ Каталог файлов ]
[ Системные файлы ]
[ Шаблоны ]
[ Конфигурация ]
[ Справка ]
```

### Решение 2. «Системные файлы» — отдельная вкладка

Системная файловая область **не добавляется** в selector:

```text
Директория: uploads/all
```

Upload files и system files имеют разные права, разные риски и разные политики.

### Решение 3. Один filesystem engine

Создаётся общий backend:

```text
FileManager
```

Он работает с разными контекстами:

```text
uploads
system
editor
```

### Решение 4. `Upload` и `FileManager` разделены

```text
FileManager
└── путь, имя, замок, чтение и управление существующим filesystem
    ничего не знает про Upload

Upload
└── принимает и безопасно публикует новые upload-файлы
    берёт у FileManager примитивы: имя, замок, канонический путь

Adapter (маршрут)
└── решает, чем является запрос, и зовёт нужный из двух
```

**Зависимость односторонняя: `Upload` → `FileManager`, и никогда обратно.**
Загрузка файла — это по-прежнему `Upload`, но зовёт его маршрут, а не файловый
слой. `FileManager` не содержит ни одного вызова `Upload`: иначе классы
замкнутся друг на друга, а автозагрузки в проекте нет и порядок подключения
станет ловушкой.

**Подключение.** Автозагрузчика нет: `getUploadService()`
(`core/system.php:4290`) подключает `upload.php` по первому требованию, а тесты
и инструменты подключают его напрямую — например `tests/Support/upload_probe.php:13`.
Поэтому `core/classes/upload.php` в своём начале сам подключает файловый слой:

```php
if (!class_exists('FileManager')) require_once __DIR__.'/filemanager.php';
```

Тот же приём уже применён к `Parser` в `tests/Support/*_probe.php`. Любой, кто
подключил `Upload`, получает `FileManager` вместе с ним, и ни один существующий
вызывающий не ломается.

### Решение 5. Общий backend, но не один универсальный HTTP endpoint

Админка использует HTMX/HTML. ToastUI использует JSON.

Объединяется **domain layer и модель файлов**, а не транспорт:

```text
                     FileManager
                         │
            ┌────────────┴────────────┐
            │                         │
        Admin adapter            Editor adapter
        HTMX / HTML                 JSON
```

### Решение 6. Никаких сторонних SPA/file-manager frameworks

Не добавлять:

- Vue;
- React;
- CodeIgniter;
- jQuery;
- jQuery UI;
- elFinder backend;
- eXtplorer backend;
- Tiny File Manager runtime.

UI:

```text
Bootstrap 5
Bootstrap Icons
HTMX
Vanilla JS
```

## 4. Компоненты

```text
core/classes/filemanager.php          новый класс, единственный новый файл ядра
admin/modules/uploads.php             хозяин интерфейса, новый модуль не создаётся

templates/admin/partials/
├── file-browser.html                 оболочка: панель, три колонки, подвал
├── file-browser-tree.html            дерево
├── file-browser-list.html            список и плитки
└── file-browser-editor.html          редактор исходника

templates/admin/fragments/
├── file-browser-row.html             строка списка
├── file-browser-tile.html            плитка
└── file-browser-props.html           свойства объекта
```

**Новых файлов JS и CSS не заводится — но у двух экранов разные дома.**

Админский браузер живёт в административной теме:

```text
templates/admin/assets/js/admin-ui.js       поведение
templates/admin/assets/css/theme.css        стили
```

Окно редактора живёт в плагине и в теме сайта, и трогать надо именно их:

```text
plugins/editors/toastui/assets/editor-upload.js       поведение окна
plugins/editors/toastui/driver.php                    данные и ключи шаблона
templates/<theme>/partials/editor-toastui-files.html  разметка окна
templates/<theme>/assets/editors/toastui/skin.css     стили окна, в каждой теме
```

Тем две — `lite` и `admin`, — и `skin.css` правится в обеих: редактор
открывается и на сайте, и в административной форме. Свой `file-browser.js` не
заводится ни там, ни там: он означал бы второе подключение и растаскивание общих
компонентов по файлам.

Крошки и панель инструментов собственных фрагментов не получают: панель — это
`sl-searchbox` с готовыми `sl-but-mini`, крошки — цепочка ссылок. Отдельный
фрагмент на три элемента дороже, чем он экономит.

ToastUI сохраняет собственный wrapper:

```text
templates/<theme>/partials/editor-toastui-files.html
```

но получает данные через тот же FileManager domain layer.

## 5. Ответственность `FileManager`

Имена методов подчиняются `.rules/global.md`: camelCase, глагол из разрешённого
набора плюс существительное, 6–24 символа. Тот же закон, по которому названы
`Upload::addUploadedFile()` и `Upload::deleteStoredFile()`.

Минимальный публичный контракт:

```text
getFileList()        перечислить директорию
getFileData()        один объект как дескриптор §7
getFileBody()        прочитать содержимое текстового файла
setFileBody()        записать содержимое, с проверкой версии §13
addFileEntry()       создать пустой файл
addDirectory()       создать директорию
deleteFileEntry()    удалить файл или директорию
updateFileName()     переименовать
addFileCopy()        скопировать
updateFilePath()     переместить
addFileArchive()     упаковать существующий файл в ZIP
addFilesArchive()    упаковать отмеченный набор в один ZIP
```

Дополнительно:

```text
getFileOwner()       владелец из managed-имени, единственный разбор в проекте
getCapabilities()    что разрешено в этом контексте, §14
checkFileAccess()    допустима ли операция над этим путём, §12
isFileEditable()     открывается ли файл в редакторе исходников
getCodeLanguage()    режим подсветки для CodeMirror, §11
```

`stat`, `read`, `write`, `list`, `create`, `rename`, `copy`, `move` как имена
методов не используются: ни одно из них не проходит правило, а половина ещё и
занята встроенными функциями PHP.

Upload выполняется через:

```text
Upload::addUploadedFile()
Upload::addUploadedFiles()
Upload::addRemoteFile()
```

а не собственной реализацией FileManager.

## 6. File context

Каждый запрос FileManager выполняется внутри заранее созданного контекста.

### Upload context

```text
mode     = uploads
root     = UPLOADS_DIR
access   = admin
editor   = false
```

Корень — всё хранилище, а не отдельный модуль: §8 и утверждённый макет показывают
дерево с корнем `uploads` и всеми модулями, а администратору §8 не оставляет
изъятий. Модуль здесь не корень, а первый сегмент пути: по нему берутся правила
загрузки (`getAdminUploadRule()`), потому что правила у каждого модуля свои.
Изоляция по модулю остаётся у контекста `editor` ниже, где она и нужна.

### ToastUI context

```text
mode     = editor
root     = UPLOADS_DIR/<module>
access   = module upload rules + owner
editor   = false
compact  = true
```

### System context

```text
mode     = system
root     = BASE_DIR
access   = isAdmin(true)
editor   = true
```

Клиент никогда не задаёт физический root. Он передаёт только относительный путь внутри уже выбранного context.

## 7. Нормализованная модель файла

FileManager должен возвращать единый descriptor:

```php
[
    'name'         => 'picture.webp',
    'path'         => 'news/picture.webp',
    'kind'         => 'image',
    'extension'    => 'webp',
    'size'         => 245760,
    'mtime'        => 1786082400,
    'url'          => 'uploads/news/picture.webp',
    'thumbnail'    => '',
    'width'        => 1280,
    'height'       => 720,
    'managed'      => true,
    'editable'     => false,
    'previewable'  => true,
    'capabilities' => [...],
]
```

Абсолютный серверный путь в дескрипторе **отсутствует**: клиент работает
относительным путём внутри context, и в JSON редактора абсолютного пути нет
никогда.

Исключение одно и оно явное: админский full mode дополнительно получает поле
`realpath` и показывает его в свойствах. Администратор полноправен, и знать
расположение файла ему нужно. Решение о выдаче принимает сервер по context, а не
клиент по запросу.

### Панель инструментов

Навигация, действия над директорией и переключатели вида — круглые `sl-but-mini`
одной группой слева, на плашке `sl-searchbox`:

```text
← ↑ ⟳ │ создать папку · загрузить │ крошки … фильтр · список ▤ ▦
```

Загрузка выделена заливкой как главное действие, остальные — `sl-is-muted`.
Прямоугольных кнопок в панели нет: они занимали место и спорили с крошками.

Действия над файлом живут в веере строки, действия над отмеченными — в
`sl-bulk-bar` (§9.1). В панели инструментов их нет.

### Строка возможностей

Под рабочей областью выводится, что разрешено в текущем контексте. Значения
приходят с сервера (§14), интерфейс их не вычисляет. Запрещённое остаётся на
месте приглушённым, чтобы пользователь видел границу прав, а не искал пропавшую
кнопку.

Метод запроса в подписи не упоминается. «Удаление · POST» ничего не говорит
администратору: POST — способ отправки, а не право, и требование «мутации только
POST» живёт в §17, а не в интерфейсе.

### Абсолютный путь в админском режиме

Текущая под-вкладка «Основная директория» печатает серверный путь в заголовке:

```text
Директория: C:/OSPanel/home/slaed.loc/public/uploads/all
```

Само по себе это не нарушение: администратор полноправен и скрывать от него
расположение файла незачем. Меняется место и роль. Путь перестаёт быть
заголовком раздела и становится справочным полем «Полный путь» в свойствах
выбранного объекта, рядом с относительным адресом.

Правило §7 остаётся в силе для остальных контекстов: в JSON редактора и в любом
интерфейсе не-администратора абсолютный путь не отдаётся никогда. Различие
делает context, а не клиент.

### Администратор полноправен

Администратору доступны все директории и все файлы без изъятий.

Поддерживаемые операции v1:

```text
browse
preview
upload
download
delete
compress
rename
move
mkdir
```

Ограничения снимаются, предупреждения остаются. Имена managed upload-файлов
создаёт Upload service, и они хранят владельца, а на сам файл уже могут
ссылаться опубликованные материалы. Поэтому rename и move не запрещены, но
интерфейс сообщает последствие рядом с кнопкой: ссылки в материалах не
обновляются автоматически, старый адрес перестанет открываться.

Автоматическое обновление ссылок остаётся вне первой версии (§29). Это разные
задачи: право на операцию у администратора есть уже сейчас, а переписывание
содержимого материалов — отдельный проект.


### Три способа вместо трёх радио

Сегодняшние радио `upload` / `attach` / `embed` неравноправны: `attach` — это не
источник файла, а форма вставки уже загруженного. Поэтому рельс делит окно так:

```text
Загрузить на сервер   → приёмник файла + «вставить как» (изображение | файл)
Ссылка на изображение → адрес + описание, доступна всегда
Встроить в текст      → приёмник файла, base64, лимит поля
Мои файлы             → каталог модуля
```

Поля адреса и описания больше не висят над всем содержимым: они принадлежат
своему разделу. Выбор «изображение или миниатюра/файл» живёт внутри загрузки и
внутри каталога, потому что относится к обоим.

### Разделы отражают права

`canupload` и `canlist` — одно серверное решение, `canembed` — свойство поля.
Недоступный раздел не исчезает: он гаснет, получает замок и подменяет описание
причиной. Если закрыт текущий раздел, окно открывается на первом доступном.

```text
автор,  поле с текстом  → все четыре раздела
автор,  поле-анонс      → «Встроить в текст» закрыт: поле не хранит base64
гость,  загрузка есть   → разделы открыты, каталог — файлы его сессии (§16)
гость,  загрузки нет    → живёт только «Ссылка на изображение»
```

### Compact view

Раздел «Мои файлы» по умолчанию компактный.

Показывать:

- preview/icon;
- filename;
- size;
- kind;
- mtime;
- select/insert;
- refresh;
- последние N файлов.

Не показывать:

- дерево всего `uploads`;
- system directories;
- rename;
- move;
- delete;
- raw filesystem paths.

Вместо «Нет информации» пустой каталог объясняет причину: ещё ничего не
загружено, либо фильтр ничего не нашёл.

### Expanded view

Существующая кнопка expand разворачивает окно и одновременно переводит «Мои
файлы» в расширенный браузер:

- filter текущей директории;
- больше файлов;
- list/grid;
- preview;
- pagination;
- file metadata из дескриптора §7.

ToastUI остаётся внутри разрешённого module root. Набор действий над файлом
решает контекст (§14): автору доступны вставка и скачивание, администратору —
ещё архивирование и удаление.

## 9.1. Три механизма, общие для обоих экранов

Описаны здесь один раз. Админский полный режим (§8) использует их же.

### Веер действий — `sl-dial`

Действия принадлежат объекту, а не списку. Под каждым файлом раскрывается веер
из системного компонента темы: `sl-dial` + `sl-dial-toggle` + `sl-dial-item`,
каждый пункт — `sl-but-mini` с иконкой и `title`. Раскрытие по наведению даёт
CSS, закрытие чужих вееров — тот же обработчик, что в `plugins/system/slaed.js`.

```text
редактор, автор       вставить изображением · вставить вложением · скачать
редактор, админ       + сжать в ZIP · удалить
админка               открыть/редактировать · предпросмотр · скачать ·
                      переименовать · переместить · сжать · удалить
```

Пункт «вставить изображением» не рисуется для не-картинок, «сжать» — для
директорий. Ширина плашки веера считается темой через `--sl-dial-count` по
`:last-child`, поэтому скрытые правами пункты остаются в разметке и ломают счёт:
переменную задавать явно по числу видимых пунктов.

Удаление помечается `data-sl-confirm` и открывает системную модалку `#sl-confirm`,
а не `window.confirm`.

### Галерея предпросмотра — `sl-modal`

Нажатие на миниатюру открывает `dialog.sl-modal.sl-modal-wide`: снимок,
свойства из дескриптора §7 справа, стрелки, клавиши ← →, счётчик позиции и те же
действия, что в веере. Список закольцован.

Перебираются только просматриваемые объекты: директории, архивы и документы в
галерею не попадают, и счётчик считает от их числа, а не от длины списка.

### Отметки и массовые действия — чекбоксы и `sl-bulk-bar`

Отметка — обычный `input[type=checkbox]` из `base.css`: первой колонкой списка
(`sl-col-check` в админке) и в углу плитки. В шапке — «отметить все» с
промежуточным состоянием при частичном выборе.

Отметки хранятся одним набором на список, поэтому плитка и строка одного файла
всегда показывают одно состояние. Панель `sl-bulk-bar` со счётчиком `sl-bulk-count`
появляется, когда отмечен хотя бы один объект, и скрывается, когда снята
последняя отметка. Смена директории или контекста отметки сбрасывает — иначе
действие уйдёт не туда.

Отметка и «текущий объект» — разные вещи. Текущий тот, чьи свойства показаны
справа; он меняется нажатием на строку или плитку и не зависит от отметок.

Действия панели говорят числом: при одной отметке «вставить изображением», при
нескольких — «вставить изображениями».

## 12. System Files security boundary

Это отдельная политика от Upload.

### Обязательные правила

1. Root всегда определяется сервером.
2. Browser передаёт только относительный path.
3. Все пути нормализуются.
4. `..` не может выйти за root.
5. Запрещены absolute paths.
6. Запрещены stream wrappers: `php://`, `file://`, `data://` и т.п.
7. Проверяется symlink escape.
8. Mutating operations — только POST.
9. Все mutating requests — CSRF protected.
10. Никакого shell execution.
11. Никакого chmod/chown в v1.
12. Никакого произвольного archive extraction в v1.

### Hidden/protected paths

**Спрятать из списка — не значит защитить.** Путь, убранный из перечисления,
по-прежнему открывается по прямому запросу: его можно прочитать, скачать,
переписать и удалить, зная имя. Скрытие — это удобство, а защита — это отказ,
и они задаются раздельно.

Политика централизована и отвечает на каждую операцию отдельно:

```text
путь                    список  чтение  скачивание  запись  удаление
.git/                   нет     нет     нет         нет     нет
.env                    нет     нет     нет         нет     нет
config/*.php            да      да      да          да      подтверждение
storage/sessions/       нет     нет     нет         нет     нет
storage/logs/*.log      да      да      да          нет     да
*.part, lock-файлы      нет     нет     нет         нет     нет
```

Пять столбцов таблицы — не весь набор операций. Переименование, копирование и
перемещение трогают **два** пути сразу, и каждый проверяется своей стороной:

```text
операция          источник           назначение
переименование    write + delete     write
копирование       read               write
перемещение       write + delete     write
создание файла    —                  write
создание папки    —                  write
```

Читается так: переместить можно только то, что разрешено менять и удалять, и
только туда, куда разрешено писать. Копирование источник не меняет, поэтому ему
довольно чтения. Проверяются оба пути, а не один: иначе закрытый `.env`
копируется в открытую директорию и читается оттуда свободно.

Решение принимает один метод — `checkFileAccess()` (§5), — и каждый маршрут
спрашивает его перед действием, а не после того, как путь уже открыт. Для
операций с двумя путями он вызывается дважды, по разу на сторону. Проверки не
размазываются по контроллерам.

Тест обязан бить не по списку, а по прямому обращению: запросить закрытый путь
на чтение, на скачивание, на запись и на удаление и получить отказ на каждом.
Проверки «его нет в перечислении» недостаточно — она проходит и тогда, когда
защиты нет вовсе.

### Critical files

Супер-администратору доступны все операции и над этими файлами:

```text
index.php
admin.php
setup.php
.htaccess
config/*
core/*
```

Запрета нет, но список остаётся: он помечает пути, для которых удаление,
переименование и перенос требуют явного подтверждения в интерфейсе, а сама
операция пишется в audit log (§24). Ошибка здесь останавливает сайт, поэтому
случайного клика быть не должно.

Список ведётся централизованно в system policy. Не размазывать эти проверки
по controller.

## 13. Безопасное сохранение исходников

Обычный:

```php
file_put_contents($file, $text)
```

для System File Editor недостаточен.

При `open` сервер отдаёт version/hash. При `save` browser возвращает version.

### Сверка версии происходит под замком, а не рядом с ним

Сравнить версию и потом заменить файл — это две операции, и между ними успевает
вклиниться второй запрос: оба читают одну версию, оба считают её актуальной, оба
пишут, и правка того, кто пришёл первым, исчезает без следа. Проверка версии без
замка не защищает ни от чего.

Поэтому весь участок идёт под исключительной блокировкой назначения:

```text
взять замок назначения (LOCK_EX)
 ↓
прочитать текущее содержимое и посчитать версию
 ↓
сравнить с версией, пришедшей от клиента
 ├─ разошлись → отпустить замок, ответить 409, ничего не писать
 └─ совпали   → записать временный файл в той же директории
                 ↓
                заменить назначение одним переименованием
                 ↓
                посчитать новую версию и вернуть её
 ↓
отпустить замок
```

**Замок общий на проект.** Протокол лежит в `FileManager` публичной парой:

```text
FileManager::getPathLock()      взять исключительный замок пути
FileManager::deletePathLock()   отпустить его
```

Второго протокола в проекте нет, и заводить его нельзя не только из-за дубля:
**два независимых замка не сериализуют участников между собой**. Если `Upload`
публикует файл под своим замком, а `FileManager` пишет под своим, они спокойно
столкнутся на одном пути. Поэтому `Upload` берёт ту же пару — при публикации
(`core/classes/upload.php:570`) и при удалении своего файла (`:154`), — а
временный `.part` и одно переименование идут под ней.

### Ключ замка — директория, а не файл

Замок берётся на `dirname()` временного файла, а имя файла-замка — `sha1()`
этого канонического пути (`core/classes/filemanager.php:157`). Ключ менять
нельзя: новый писатель встанет в другую очередь и сериализации не будет вовсе.

Директория, а не файл, выбрана не из удобства: `Upload` под этим замком **ищет
свободное имя** в каталоге, и замок отдельного файла ему бесполезен — файла ещё
нет. Один ключ на всех означает, что публикация и правка в одном каталоге ждут
друг друга. Цена известна и принимается: две правки разных файлов одной
директории тоже сериализуются.

### Кто обязан брать замок

```text
запись содержимого файла        да, этап 4
создание файла и директории     да, этап 5
переименование                  да, этап 5
копирование                     да, этап 5
перемещение                     да, этап 5, два замка
удаление                        да, этап 5
загрузка через Upload           да, уже берёт
чтение, перечисление, скачивание нет
```

Операция этапа 5 без замка — незакрытая работа: она делает ровно то, ради чего
протокол и заводился.

### Две директории и порядок захвата

Перемещение и копирование между каталогами трогают два ключа, и два процесса,
взявшие их в разном порядке, встанут насмерть. Поэтому ключи **сортируются и
берутся в лексикографическом порядке**, а при совпадении берётся один замок:

```text
$keys = array_unique([$srcdir, $dstdir]);
sort($keys);
берём по очереди, отпускаем в обратном порядке
```

Это правило обязательно к соблюдению во всех операциях с двумя путями, и тест
этапа 5 проверяет именно его: перемещение A→B и одновременное B→A не образуют
взаимной блокировки.

### Переименование поверх существующего файла

`rename()` в PHP на Windows перезаписывает существующий файл — проверено на
стенде проекта, старое содержимое заменяется, временный файл исчезает. Отдельная
ветка «сначала unlink, потом rename» не нужна и вредна: она открывает окно, в
котором файла нет вообще.

Тест обязан проверять именно замену существующего файла, а не запись в пустоту.

### Чужие процессы

Замок держат только писатели, которые его берут: `FileManager` и `Upload`. Правка
файла по FTP, редактором на диске или другой программой замка не берёт — и не
может быть им остановлена.

Гарантия формулируется без преувеличения:

```text
два писателя через приложение   сериализуются полностью, потери правки нет
правка мимо приложения          обнаруживается best-effort сверкой версии
```

«Best-effort» здесь буквально: между повторным чтением версии под замком и
переименованием остаётся окно, и внешняя программа, попавшая в него, будет
перезаписана без предупреждения. Закрыть это окно средствами приложения нельзя —
можно только не обещать того, чего оно не делает.

Практический вывод для системной области: правка файлов мимо интерфейса во время
работы с ним — не поддерживаемый сценарий, а не защищённый.

Сохранение:

1. validate path (§12);
2. validate writable;
3. take the destination lock;
4. re-read and compare version;
5. create temp in same directory;
6. write complete content;
7. flush/close;
8. preserve permissions where applicable;
9. atomic rename/replace;
10. release the lock and return new version.

Пустой файл должен сохраняться корректно.

## 16. Ownership upload-файлов — сделано

Реформа владельца закрыта вместе с `docs/EDITOR-UPLOADS-2026.md`. Действующая модель:

```text
authenticated user → id пользователя строкой
guest              → непрозрачный токен сессии, hash_hmac от session_id
moderator/admin    → null, потому что владельца у файла нет, а не как скрытый флаг
```

Токен гостя выводится из сессии, но никогда не равен её идентификатору: сегмент
попадает в публичное имя файла и ничего не должен подтверждать, будучи прочитан
из URL. Сравнение владельца — строковое: приведение к числу обнуляет каждый
токен и роднит одного гостя с другим.

Реализация лежит в `getEditorFileOwner()` и `getEditorFileJson()` (`core/system.php`).

**Имя файла — собственность `FileManager`.** Разбирать имя и знать его формат —
работа файлового слоя, а не службы загрузки, поэтому там лежат и шаблон, и длина
соли:

```text
FileManager::SALTLEN            public const, длина соли, filemanager.php:20
FileManager::getFileOwner()     разбор владельца из имени, :149
FileManager::checkFileName()    соответствует ли имя managed-формату, :143
```

Разбор в проекте один. Генератор имени берёт длину из `FileManager::SALTLEN`
(`core/classes/upload.php:178`), `Upload::deleteStoredFile()` спрашивает
`checkFileName()` (`:149`), а `getEditorFileJson()` — `getFileOwner()`
(`core/system.php:4409`). Второй регулярки не заводить ни при каких условиях:
именно с двух копий одного формата этот перенос и начинался.

Зависимость `Upload` → `FileManager` идёт на константу, на чистую проверку строки
и на замок, поэтому Решение 4 §3 не нарушается: сервис загрузки по-прежнему не
читает и не перечисляет файловую систему.

Клиент имя файла не разбирает вообще — принадлежность приходит в дескрипторе (§7).

## 17. HTTP / routing

### ToastUI

Сохраняем существующий contract:

```text
index.php?go=4&op=editorUpload&mod=...
index.php?go=4&op=editorFiles&mod=...
```

Они становятся adapters над общим FileManager/Upload layer.

Два действия §14 — удаление и упаковка у модератора модуля — своих адресов здесь не
имели, и этап 7 их дописал. Существующий контракт не менялся: это отдельные op той
же точки, POST-ом и с токеном, как всякое изменяющее действие (§12, п. 8–9):

```text
index.php?go=4&op=editorDelete&mod=...    удалить файл или отмеченный набор
index.php?go=4&op=editorArchive&mod=...   упаковать файл или отмеченный набор
```

Оба принимают либо один путь в `file`, либо набор в `mark[]`, спрашивают право у
capabilities дескриптора каждого пути, журналируют по записи на путь и отвечают,
сколько из скольких удалось — тем же правилом, что и админские маршруты ниже.

### Admin read operations

Читающие маршруты живут в `go=5` рядом с существующими фрагментами HTMX:

```text
getAdminFileList      каталог целиком: дерево, список, свойства; крошки — hx-swap-oob
getAdminFileData      панель свойств одного объекта
getAdminFilePreview   байты изображения для предпросмотра, §20
```

Дерево отдельного маршрута не имеет: оно приходит вместе со списком как хребет
открытого пути.

### Скачивание

Прямая ссылка на файл годится только внутри `uploads/*`, который отдаётся
веб-сервером как статика. Для системной области она непригодна: `index.php`
по ссылке будет **исполнен**, а не отдан, `.htaccess` веб-сервер закроет, а
шаблон вернётся клиенту в обход всякой проверки прав.

Поэтому скачивание системного файла — отдельный маршрут `go=5`, а не ссылка:

```text
getAdminFileDownload
```

Он обязан:

```text
проверить isAdmin(true) заново, а не полагаться на то, что список уже открывался
проверить путь заново через checkFileAccess(), §12
отдать Content-Type: application/octet-stream и никогда угаданный по расширению
отдать Content-Disposition: attachment с безопасным именем
отдать Content-Length и завершиться exit после readfile()
```

`Content-Type` не выводится из расширения намеренно: `text/html` или
`image/svg+xml`, отданные из административной области, исполняются в её же
источнике и превращают просмотр файла в XSS. Активные типы — HTML, SVG, JS —
скачиваются, но не показываются в браузере: предпросмотр для них не строится
(§20).

Существующая функция `stream()` (`core/system.php:4418`) для этого не берётся:
её никто не вызывает, имя не проходит правило именования, заголовки устарели
(`application/force-download`, пустой `Content-Range`), пути она не проверяет и
не завершает вывод. Она либо переписывается под новый контракт, либо удаляется
как мёртвая — решается на этапе уборки.

### Admin write operations

Не использовать GET.

Выполнять POST через `admin.php?name=uploads`:

```text
op=fmupload     принять загруженный файл
op=fmcreate     создать пустой файл
op=fmmkdir      создать директорию
op=fmrename     переименовать
op=fmcopy       скопировать
op=fmmove       переместить
op=fmdelete     удалить
op=fmcompress   упаковать файл в ZIP
op=fmpack       упаковать отмеченный набор в один ZIP
op=fmsave       сохранить содержимое из редактора
```

Изменяющий маршрут принимает либо один путь в `file`, либо отмеченный набор в
`mark[]`, и это один и тот же маршрут: набор — не вторая операция, а то же
действие над несколькими путями. Каждый путь набора проверяется и журналируется
отдельно, а ответ называет, сколько из скольких удалось.

Каждая операция §5, меняющая файловую систему, имеет ровно один маршрут в этом
списке. Операция без маршрута — незакрытая работа, а не «сделаем позже».

Все через `checkAdminPost(...)` или эквивалентный scoped CSRF contract.

### Важная миграция

Текущее удаление в `getAdminUploadFiles()` выполняется через GET/HTMX GET.
При переходе на File Manager delete/compress должны стать POST-actions.

Версия — `sha1()` байтов на диске; в интерфейсе показаны её первые шесть знаков,

записать `.part`, заменить одним `rename()`. Конфликт отвечает 409, не пишет
ничего и возвращает страницу с предупреждением, текстом автора и уже новой
версией — решение перезаписать чужую правку остаётся за администратором.

Разделитель строк берётся у файла на диске: браузер отправляет форму с CRLF, и
без этого каждое сохранение переписывало бы все строки LF-файла. Права
переносятся на временный файл до подмены. Пустой файл сохраняется, двоичный не
открывается вовсе, а `NUL` в теле запись отклоняет.

Журнал (§24) — `Logger::addFile()` в `storage/logs/error_file.log`: администратор,
операция, путь, назначение, время и результат. Тело файла и токен из дампа
запроса выброшены перед записью: `Logger` дописывает в запись весь `$_POST`, а
§24 содержимое в журнале запрещает.

### Языковые константы

Собственный префикс `_FM_*` не вводится: `.rules/constants.md` требует, чтобы
префикс точно совпадал с namespace модуля или конфигурации, а namespace у
файлового менеджера свой не появляется — он живёт внутри уже существующих.
Строки распределяются по областям, которым принадлежат:

```text
админский браузер   admin/lang/{locale}.php     префикс _UPLOADS_*
                    namespace config/uploads.php → $conf['uploads']

окно редактора      lang/{locale}.php           префикс _EDITOR_*
                    namespace config/global.php → $conf['editor']
```

Оба префикса точно совпадают с namespace своей конфигурации, как требует
`.rules/constants.md`.

**Существующие `_E*` не переименовываются и переиспользуются как есть** —
`_EUPLOAD`, `_EIMGURL`, `_EMODEEMBED` и ещё семь десятков подписей редактора
работают и трогать их этот план не будет. Но расширять `_E*` новыми именами
нельзя: правило про точный префикс исключений не знает, а `_E*` под него не
подходит. Всё новое заводится как `_EDITOR_*`.

Административный браузер получает `_UPLOADS_*` — префикс своего
конфигурационного namespace.

Существующие константы переиспользуются, дублировать их запрещено: `_DELETE`,
`_UPDATE`, `_CLOSE`, `_DESCRIPTION`, `_ERROR_SIZE`, `_ERROR_FILE` и остальные
уже есть.

Исключение из деления на две области — подписи, которые называют общее понятие
интерфейса, а не файловый менеджер: `_RETRY` и `_FRESET` заводятся в
`lang/{locale}.php` без префикса и служат обоим экранам. `lang/{locale}.php`
подключается и в админке (`core/security.php:754`), а `.rules/constants.md`
запрещает держать одну константу в двух областях. Имена состояний, принятые на
этапе 1, перечислены в его разделе §26.

Каждая новая константа заводится сразу в шести локалях: `de`, `en`, `fr`, `pl`,
`ru`, `uk`.

## 28. Acceptance criteria

File Manager считается готовым, когда:

- один domain layer используется Admin и ToastUI;
- зависимость классов односторонняя: `Upload` знает про `FileManager`, обратного
  вызова нет ни одного;
- протокол замка в проекте один, и оба писателя берут его на одном ключе;
- разбор managed-имени в проекте один, и обе прежние регулярки сняты;
- каждая операция §5, меняющая файловую систему, имеет ровно один маршрут §17,
  проверку `checkFileAccess()` и запись в audit log;
- Upload service не дублирован;
- System Files имеет отдельную вкладку;
- System Files доступен только super-admin;
- absolute server path не покидает сервер ни на одном маршруте, кроме одного:
  админский full mode получает поле `realpath` в дескрипторе и показывает его в
  свойствах (§7). В JSON редактора и в любом ответе не-администратору его нет;
- path traversal и symlink escape закрыты;
- system edit использует существующий `Editor::getCode()`;
- save имеет conflict detection, и сверка версии идёт под замком, а не рядом с ним;
- save заменяет существующий файл одним переименованием, без окна отсутствия файла;
- mutating actions не работают через GET;
- ToastUI не видит чужие upload roots/files;
- текущие module upload rules остаются authoritative;
- существующая загрузка файлов не ломается;
- текущая ToastUI интеграция не заменяется новым editor subsystem;
- нет jQuery/Vue/React/стороннего File Manager runtime.

- FTP;

## 31. Состояния процесса и ошибок

Список состояний закрыт здесь, чтобы каждый экран не решал заново. Оба макета
их показывают: под пояснениями стоит ряд кнопок, который переключает состояние
на живой странице. Реализация переносит готовое, а не придумывает заново.

### Загрузка

```text
идёт        полоса выполнения на файл, имя, размер, отмена
несколько   очередь: файлы грузятся по одному, видно который из скольких
удалась     файл появляется в каталоге, каталог не перезагружается целиком
не удалась  причина у файла, остальные файлы очереди продолжают грузиться
```

Причина берётся с сервера и не сочиняется на клиенте. `Upload` уже отвечает
разными ошибками: тип, размер, размеры изображения, квота, число файлов за раз.

### Каталог

```text
грузится    скелетон на месте плиток, не пустой экран и не «загрузка…»
пуст        объяснение почему: ещё ничего не загружено
фильтр пуст «ничего не найдено», с кнопкой сбросить фильтр
не удался   текст ошибки и «повторить», список не подменяется пустотой
```

Пустой каталог и пустой результат фильтра — разные состояния и разные тексты.

### Действие над файлом

```text
удаление       подтверждение через #sl-confirm, затем строка исчезает
архивирование  индикатор на строке, по завершении список обновляется
переименование поле прямо в строке, Enter применяет, Esc отменяет
конфликт       имя занято — сообщение у поля, а не общий алерт
```

Ни одно изменяющее действие не выполняется без ответа сервера: строка не
исчезает «оптимистично», пока запрос не подтверждён.

## 32. Выравнивание тем — **сделано**

Макеты собраны на системных компонентах, и при сборке нашлись расхождения между
`templates/lite` и `templates/admin`. Все они закрыты правкой тем, а не
переопределением в макете:

| Класс | Что было | Где не хватало |
| --- | --- | --- |
| `sl-but-mini` | браузер рисовал вторую рамку поверх круглой заливки | `admin` |
| `sl-but-mini.sl-is-muted` | белый глиф на светлой заливке не читался | `admin` |
| `sl-but-mini[disabled]` | недоступная кнопка не отличалась от доступной | `admin` |
| `sl-bulk-bar` | панель массовых действий существовала только в `lite` | `admin` |
| `sl-bulk-count` | счётчик отмеченных не имел общего имени | обе |
| `sl-modal-wide`, `sl-modal-image` | галерее негде было взять ширину и снимок | `admin` |
| `tr[aria-selected]` | выбранная строка не отличалась от наведённой | `admin` |

**Правило на будущее:** если компонента не хватает в одной теме, он добавляется в
неё под тем же именем, что в другой. Локальное переопределение в модуле или
макете — не решение, а отложенный дубль.

## 33. Клавиатура и доступность

```text
Esc            закрывает галерею, затем окно
← →            перебор в галерее
Enter          применяет действие в фокусе
Tab            не выходит за пределы открытой модалки
```

Фокус при открытии окна уходит на первый управляющий элемент, при закрытии
возвращается на кнопку, которая окно открыла. Строка состояния — `aria-live`,
чтобы результат действия читался озвучкой, а не только глазами.

Каждая кнопка-иконка несёт `title` и `aria-label`: в веере и в панели
инструментов подписи нет, и без них действие не назвать.
