## Зачем до 8.0

Сайт узнаёт об обновлениях только кодом, который уже стоит у него. Установка 8.0 без проверки останется слепой
навсегда: исправление безопасности 8.0.1 дойдёт лишь до тех, кто сам зайдёт на slaed.net. Обновлятор — единственное,
что нельзя догнать позже; всё прочее на клиенте (отчёты об ошибках, коннекторы, MCP) потом привезёт он сам.

## Решения

Владелец, 2026-10-15; шаг их не пересматривает.

- **Полный цикл до 8.0:** проверка, скачивание, проверка подписи, установка по кнопке, автооткат.
- **Подпись — это «добро» на выпуск.** Манифест подписывается Ed25519 офлайн на машине владельца. Без подписи сайт
  ничего не примет, откуда бы ни пришёл файл.
- **Два ключа:** основной подписывает выпуски, ключ восстановления (сейф, бумага и флешка) только меняет ключи.
- **Мастер — slaed.net, обычный модуль `master`.** Код открыт в репозитории (форку он нужен для своего мастера), но в
  архив выпуска не входит (`modules/master export-ignore` в `.gitattributes`), так что на сайты не попадает. На
  slaed.net владелец заливает его по SFTP; обновлятор его не трогает, потому что файлов модуля нет в `files.json`.
- **Клиент — в ядре,** не отключаемый модуль: страница панели `admin/modules/update.php` «Обновления».
- **Единый вход:** API — ветка `public/index.php` для пути `/api/`, до загрузки ядра. Отдельного `public/api.php` нет.
  `admin.php` и `setup.php` остаются отдельными файлами.
- **Шаги 1–2 коннектора (`docs/2027-CONNECTOR.md`) делаются здесь,** до 8.0, плюс ограничение запросов по IP.
  Клиентские ключи, MCP и прочие сервисы — после 8.0.
- **Ответ файлом:** у `setApiReply()` третий режим `file` рядом с `envelope` и `jsonrpc`; отдаёт `getFileStream()`.
  Режим объявляет действие ключом `reply` (`envelope` по умолчанию, `file`, `jsonrpc`) — владелец, 2026-10-15, шаг 2;
  ключ дописан в `.rules/api.md`, так режим виден в `system/schema` до вызова.
- **Источник архива — только slaed.net** (владелец, 2026-10-15, по аудиту): сайт скачивает архив через
  `master/file`, к GitHub не обращается и редиректов не выполняет (`.rules/api.md`, `ApiHttp`). GitHub Releases —
  для людей: страница выпуска и ручное скачивание для «Загрузить архив». Зеркало на GitHub возможно позже выпуском
  8.x вместе с исключением в `.rules/api.md`, если трафик slaed.net станет проблемой по статистике мастера; в 8.0
  его нет. Манифест — только с мастера (пауза и доля выкатки иначе не работают); недоступен мастер — проверка
  повторится завтра.
- **На slaed.net без поддомена:** архивы лежат в `storage/update/master/`, вне веб-корня, отдаются через API.
- **Публикация на slaed.net — только SFTP** (системный OpenSSH `sftp`, вход по SSH-ключу). FTP не используется.
- **Сведения о клиентах — в базе мастера;** артефакты (архивы, манифесты, подписи) — файлами.
- **Статистика по минимуму:** сайт шлёт только перечисленное в `master/check`, текст ошибок не шлёт никогда; мастер
  не пишет IP в свою базу. Страница «Обновления» перечисляет, что и куда уходит, и даёт выключатель.
- **Домен сайта сообщается мастеру по умолчанию,** клиент может выключить (владелец, 2026-10-15): для поддержки,
  личных оповещений и картины живых установок. Выключил — мастер стирает домен этого сайта при следующей проверке.
  Раз домен собирается, на slaed.net нужна короткая заметка о приватности службы обновлений.
- **Источник меняется только кодом (форком),** не настройкой: в панели нет поля «адрес сервера» или «ключ».
- **`public/update.php` в релиз не входит** (владелец: это его внутренний инструмент). Шаги базы 8.x, ручной
  путь и аварийный откат на него не опираются.
- **Версия — константа в коде** (`SL_VERSION` в `core/version.php`, строго `X.Y.Z`), кодовое имя — отдельная
  константа `SL_CODENAME` (владелец, 2026-10-15; имена короче 13 символов по `.rules/global.md` — владелец,
  2026-10-16, шаг 3). `$conf['version']` ядро собирает из обеих при загрузке
  (`8.0.0 <имя>`), так что десять мест чтения не меняются, а `modules/presentation/index.php` по-прежнему делит строку
  на номер и имя. Ключ `version` убирается из `config/global.php` в репозитории до релиза, а
  `admin/modules/config.php` перестаёт записывать его при каждом сохранении общих настроек. Установка не
  перезаписывает `config/`, а файлы, залитые вручную, сразу несут свою версию.
- **Сроки хранения — настройки модуля `master`** (молчащие сайты, дневные итоги); срок жизни манифеста —
  параметр `tools/release.php build`, потому что он внутри подписи.
- **Размер выпуска:** видео и архив Феникса владелец убирает из дерева до релиза.
- **Изменённые на сайте файлы** останавливают установку до явной отметки «перезаписать»; языки и темы `admin` и
  `lite` заменяются без останова (раздел «Настройки, языки и темы при обновлении»).
- **Дамп базы порциями и восстановление из него пишутся здесь** (шаг 8): сейчас `Backup::addDatabaseBackup()`
  снимает дамп за один проход в одной транзакции, а восстановления нет вовсе. На обратимость шагов базы не
  полагаемся.
- **Настройки, языки и темы — одним шагом** (владелец: так проще управлять), без второго слоя: `config/` остаётся
  одним слоем и поставкой в git, как сейчас; установка дописывает в файлы сайта недостающие опции, не меняя
  существующих; языковые файлы переписываются целиком из пакета; темы `admin` и `lite` тоже приходят из
  пакета целиком, сторонние темы не трогаются. Ручной путь по FTP — на совести владельца сайта: залитый поверх
  `config/` затирает настройки (владелец, 2026-10-15). Раздел «Настройки, языки и темы при обновлении».
- **Установка по шагам,** каждый в своём запросе, с прогрессом; оборванную можно продолжить или откатить.
- **Пока идёт установка, планировщик молчит.**
- **Файлы меняет отдельный исполнитель без ядра** (`core/apply.php`), переименованиями, а не копированием; место
  проверяется расчётом пикового расхода до «Скачать» и до «Установить» и заново перед каждой пачкой. Раздел
  «Установка».
- **Исполнитель — из нового пакета** (владелец, 2026-10-15): установку ведёт `core/apply.php` проверенной подписью
  новой версии, а не установленный, как `update-core.php` у WordPress. Ошибку установщика исправляет следующий
  выпуск, а не тот же сломанный код. Аварийный `core/rescue.php` — установленный.
- **После установки сайт проверяет себя,** а «Проверить установку» показывает всё, что сделает установка, ничего не
  применяя (владелец, 2026-10-15).
- **Первый выпуск после 8.0 — пустой 8.0.1** (владелец, 2026-10-15): меняется только версия; сначала beta, потом
  stable. Он проверяет всю цепочку на настоящих сайтах, пока их мало и ошибка дешёвая.
- **Репетиция — скрипт перед каждым выпуском** (владелец, 2026-10-15), а не разовый шаг: без зелёной репетиции того
  же подписанного архива `release.php publish` не публикует.
- **Время ежедневной проверки у каждого сайта своё** — из `sid`, без общего пика.
- **Два архива на выпуск:** полный (установка с нуля и сайты старше прошлой версии) и дельта от прошлой версии.
- **`public/update.php` и `storage/update/sql/table_update6_3.sql` — `export-ignore`:** в архив не попадают, на
  стенде и в репозитории остаются.
- **Аварийный откат** — по одноразовому коду, показанному перед установкой, или, если код потерян, по пустому файлу
  `storage/update/client/rescue.now`, положенному по FTP: доступ к FTP уже доказывает владельца.
- **«Вернуть предыдущую версию»** после удачной установки: бэкап последней установки хранится до следующей, кнопка
  возвращает файлы, `config/` и базу, предупреждая, что изменения базы и настроек с момента установки пропадут.
- **Оповещения от мастера** — общие (всем или по диапазону версий) и личные (одному сайту по `sid`); каждое
  подписано офлайн-ключом, как выпуск; только простой текст ru/en, ссылки лишь на slaed.net и github.com/SLAED-CMS.
  Раздел «Оповещения».
- **Репозиторий — `github.com/SLAED-CMS/SLAED`** (владелец, 2026-10-15): имя вшивается в код 8.0 навсегда — адреса
  страниц выпусков и разрешённых ссылок оповещений.
- **Поддерживается только последняя версия:** исправления выходят только новым выпуском, старые ветки не
  сопровождаются; `min` лишь не даёт перепрыгнуть через несовместимое.
- **«Проверить целостность»** на странице «Обновления»: хеши поставочных файлов против `files.json` и лишние PHP-файлы
  в папках ядра — детектор взлома.
- **Сорванная установка сообщается мастеру** числами: версия и номер шага, на котором случился откат.
- **Автоустановка исправлений безопасности — после 8.0.** Идеи после релиза — `docs/2027-IDEAS.md`.
- **Отказ от выпуска** — пауза на мастере; назад сайты не откатываются, исправление идёт следующей версией.
  Пауза отзывает предложение и у тех, кто его уже увидел: ответ `master/check` без манифеста или с манифестом ниже
  найденной версии сбрасывает найденную версию в `state.json`, и плашка гаснет. «Загрузить архив» сначала заново
  спрашивает мастера и принимает архив только под манифест, который мастер подаёт сейчас; мастер недоступен —
  ручная загрузка закрыта с объяснением. Так выпуск на паузе не поставить и архивом, скачанным с GitHub. Ручную
  паузу владелец отмечает и на странице выпуска GitHub (`gh release edit`); автопауза GitHub не трогает — доступа
  к нему у сервера нет. Чтобы сайтам ниже приостановленного выпуска снова подавался предыдущий, владелец
  переподписывает его манифест (`sign.php --refresh`): иначе сайт, видевший более свежий манифест, отклонит старый
  по `time`.
- **Договор между версиями замораживается в 8.0.0 как версия 1** (по аудиту, 2026-10-15): схема `apply.lock`,
  раскладка бэкапа установки и вход порционного дампа `Backup`. Новый исполнитель пишет их так, чтобы их понял
  спасатель 8.0.0. Раздел «Установка».
- **Автопауза выкатки** (владелец, 2026-10-15): мастер сам ставит выпуск на паузу, когда сорванных установок у него
  больше порога, и пишет владельцу письмо. Снять паузу может только владелец.
- **`storage/geoip/` — в пакете и в обновлениях** (владелец, 2026-10-15): базы едут в полном архиве и, когда
  меняются, в дельте; отдельного пакета данных нет.
- **Сайт без `sodium` проверяет подпись своим классом `Signature`** (владелец, 2026-10-15, шаг 0; свой класс вместо
  `paragonie/sodium_compat` — владелец, 2026-10-16): из всей библиотеки нужна была одна проверка Ed25519, а везла
  она 78 файлов и 758 КБ. `core/classes/signature.php` — перенос `crypto_sign_open` из TweetNaCl (общественное
  достояние) под 64-битный PHP 8.4, около 200 строк, с отказами libsodium: S не меньше L, неканонический ключ, точки
  малого порядка у ключа и у R. `Update::isSignValid()` грузит его только тогда, когда расширения нет; на 32-битном
  PHP он отвечает «подпись неверна». Подписывают выпуски `tools/sign.php` и церемония ключей по-прежнему только
  настоящим `sodium`.
- **Сайт без `zip` распаковывает через `PharData`** (владелец, 2026-10-15, шаг 0): `Update` сам читает центральный
  каталог архива — сырые имена, режим записи, размеры — и применяет к нему все отказы раздела «Что сайт отклоняет»;
  содержимое берёт `ZipArchive`, а без него — поток `phar://` каждой записи. Отказы одни для обоих чтецов, поэтому
  каталог свой и при `ZipArchive`; по именам `PharData` их не проверить: записи `../x` и `/x` он молча
  пропускает, у симлинка теряет признак, на обратном слеше бросает исключение посреди обхода. `PharData` нужны
  `phar` и `zlib`; нет ни `zip`, ни этой пары — установка из панели закрыта, как было.
- **Журнал nginx slaed.net без строки запроса — делается** (владелец, 2026-10-15, шаг 0): доступ к настройке
  журнала у владельца есть; шаг 4 пишет образец `log_format`, заметка о приватности держит обещание «IP не связан с
  доменом».
- **Файлы, которые пишет сам сайт, архив не затирает** (владелец, 2026-10-15, шаг 0): `public/sitemap.xml` пишет
  задача `sitemap`, в git он лежал с адресами стенда — уходит из git в `.gitignore`. `public/robots.txt` пишут
  задача `sitemap` (строка `Sitemap:`) и файловый менеджер — в `files.json` он помечен как файл сайта, как файлы
  `config/`: кладётся, только если его нет, в «Проверить целостность» и в список изменённых не попадает, правило
  «нет в новом списке — удалить» его не касается.
- **В архив едет всё дерево** (владелец, 2026-10-15, шаг 0): сверх `export-ignore`, уже названных в этом разделе,
  ничего не исключается — `public/demo/`, `tests/`, `docs/` и `uploads/presentation/` поставляются.
- **Задачи мастера знает ядро, а в планировщик их пишет сам мастер** (владелец, 2026-10-16, шаг 4): имена
  `masterclean` и `masterwatch` стоят в карте `getSchedulerJob()` и в `addSchedulerSystemJob()`, обработчик
  `addMasterTask()` грузит `modules/master/common.php` и без активного модуля отвечает «Отключено». В поставочном
  `config/scheduler.php` их нет — иначе у каждого сайта висели бы две мёртвые задачи, а шаг 7 дописывал бы их при
  каждом обновлении; строки задач добавляет сохранение «Настроек» мастера. `config/master.php` пишет только мастер,
  в git его нет.
- **Разделы, которые сайт создаёт и удаляет сам, слияние берёт целиком** (владелец, 2026-10-16, шаг 7): карты по
  имени `modules.modules`, `node.types`, `scheduler.jobs` и наборы полей — не списки, и `array_is_list()` их не
  отличает. Раздел типа Node — `node.types.<тип>`, `fields.node.<тип>`, `uploads.<тип>`, `ratings['node.<тип>']` —
  есть на сайте — не сливается, нет — не добавляется никогда: удалённый тип не возвращается, отличия типа от
  `defaults` не дописываются, имя типа остаётся свободным для нового. Набор полей `fields.<набор>` есть на сайте — не
  сливается (удалённое поле не возвращается), нет — добавляется целиком. Всё прочее, `modules.modules` и
  `scheduler.jobs` тоже, сливается рекурсивно: новый модуль и новая задача выпуска дописываются, новое поле
  записи — в каждую запись. Новый тип Node до сайтов доходит только PHP-шагом версии: без строки `_node_types` он
  не тип.

## Обзор

```
ВЛАДЕЛЕЦ (своя машина)            МАСТЕР slaed.net (модуль master)        GitHub
──────────────────────            ────────────────────────────────        ──────
release.php build v8.0.1          storage/update/master/                  Release v8.0.1
sign.php  ← пароль ключа            inbox/   ← SFTP                       (архив)
release.php publish ──SFTP──────►   8.0.1/   архив, манифесты, подписи
                     ──gh──────────────────────────────────────────────►  (для людей)
                                  Панель → Мастер:
                                    Выпуски · Сайты · Статистика · Оповещения · Ключи · Настройки · Журнал

КЛИЕНТ (каждый сайт 8.x)
  планировщик updatecheck, раз в сутки
    GET https://slaed.net/api/v1/master/check?sid=…&ch=stable&v=8.0.0&…
    ← манифест + подпись + новые заявления о ключах + оповещения
    → проверка подписи, свежести, версии → плашка «Доступна 8.0.1»
  Панель → Обновления:
    Скачать (slaed.net) или Загрузить архив вручную
    → размер и SHA-256 → распаковка в stage → сверка списка файлов
    → Установить: закрыть сайт → бэкап → файлы → шаги базы → открыть
       ошибка → автооткат
```

## Единый вход

- `public/index.php` после заглушки установки (раздел «Установка»; она стоит первой, раньше и лёгкого пути, потому
  что тот грузит `core/stream.php`) и лёгкого пути `uploads/` смотрит путь: начало `/api/` → определяет `API_FILE`,
  грузит лёгкое ядро (без темы, шаблонов и сессии) и отдаёт запрос `ApiRouter::getResponse()`; иначе — сайт, как
  сейчас.
- Правила сервера не меняются: всё, что не файл, уже приходит в `index.php` на Apache и nginx; заголовок
  `Authorization` уже пробрасывается в `public/.htaccess`. Имя `api` уже зарезервировано в `Route::TYPES`.
- Простая форма `api.php?r=…` не нужна: ЧПУ обязательны, `/api/v1/…` работает на любом сайте 8.0.
- Проверки, порядок, конверт ответа и коды — `.rules/api.md`. Здесь строятся проверки без клиентов
  (`checkApiRoute`, `checkApiMaint`, `checkApiCors`, `checkApiFlood`, `checkApiSize`, `filterApiInput`) и сервис
  `system` с `ping` и `schema`. Ключи клиентов (`checkApiAuth` для `key`) — после 8.0 по плану коннектора.
- Машинные точки `go=` в `index.php` (запуск планировщика) переедут в `/api/` после 8.0; здесь не трогаются.

## Мастер: модуль `master`

Есть в репозитории, нет в архиве выпуска (`export-ignore`); на slaed.net приходит по SFTP и ставится через «Модули»
(`modules/master/sql/table.sql`). Проверку подписи и формат манифеста он берёт из класса ядра `Update`, своей копии
нет.

```
modules/master/
  api.php       объявление сервиса: check, file (оба auth public, GET)
  common.php    обработчики
  admin/        панель модуля, вкладки через getTplAdminTabs()
  sql/table.sql _master_site, _master_stat, _master_release, _master_note
  lang/         шесть языков
```

**`master/check`** — сайт присылает: `sid` (идентификатор установки, 32 строчных шестнадцатеричных символа — тип
`hex` у `ApiInput`), `ch` (канал), `kseq`, `v` (версия), `php` (`X.Y.Z`), `db` (`mysql` или `mariadb`) и `dbv`
(`X.Y.Z`), `ext` (биты: 1 — `sodium`, 2 — `zip`, 4 — `phar` с `zlib`), `ep` и `es` (число ошибок PHP и базы с прошлой
проверки), `host` (домен сайта, тип `host`: строчные метки punycode с точкой и буквенной зоной, так что `localhost` и
IP отклоняются с 422; пустой или не присланный — мастер стирает сохранённый), `fv` и `fs` (версия и номер шага
последней сорвавшейся установки, один раз; не присланный `fv` — параметр со значением `null`, срыв в строке сайта
остаётся до следующего). Обязательны только `sid` и `v`. Мастер обновляет строку сайта и отвечает
`{manifest, keys, notes}`: манифест `{body, sig}` или `null`, заявления `{kseq, body, sig, psig}`, оповещения
`{id, body, sig}`; `body` везде — подписанные байты в base64:
- манифест, который сейчас подаётся этому каналу и этому сайту, его байты в base64 и подпись. Доля выкатки —
  `crc32(sid.'|'.версия) % 100 < доля`: у каждого выпуска своя первая когорта, а не одни и те же сайты каждый раз;
- заявления о ключах с `kseq` выше присланного;
- действующие оповещения для этого сайта: общие под его версию и личные на его `sid`;
- ничего, если подавать нечего.

Заявления о ключах мастер читает прямо из `inbox/keys/` по порядку `kseq` до первого, не прошедшего проверку: подпись
и есть доказательство, приёма они не требуют, вкладка «Ключи» только показывает. Ключами в силе — заводскими ядра и
этими заявлениями — мастер проверяет выпуски и оповещения при приёме.

**`master/file?v=8.0.1&kind=full|delta`** — архив выпуска из `storage/update/master/8.0.1/` через
`getFileStream()` в режиме кэша `private`: докачка, HEAD, ETag. Выпуск на паузе или не принятый отвечает 404. Действие
только читает (`.rules/api.md`: `public` — только чтение): скачивания не считаются и у сайта не отмечаются; установку
видно по версии в следующей `master/check`.

Версия становится частью путей (`master/<версия>/`, `step/<версия>.sql`), поэтому `v` везде — строго `X.Y.Z`
(`^\d+\.\d+\.\d+$`, тип `ApiInput`), `kind` — только `full` или `delta`; суффиксов вида `-beta` нет, канал задаёт
`channel` манифеста.

**Панель «Мастер»:**
- **Выпуски:** список `inbox/` → «Принять» (проверка обеих подписей и SHA-256 архива тем же кодом, что у клиента;
  перенос в `<версия>/`) → «В beta», «В stable», «Пауза», «Доля %». Перевод в stable подаёт уже подписанный
  stable-манифест того же архива. Пауза помечена, кто её поставил: владелец или автопауза с цифрами срабатывания.
- **Сайты:** домен (если сообщён), идентификатор, версия, канал, PHP, база, расширения, ошибки, первый и последний
  визит; поиск по домену; молчащие. Наружу список не выводится и не выгружается.
- **Статистика:** по дням — версии, каналы, PHP, базы, доля без `sodium`/`zip`, сумма ошибок по версии (сигнал
  остановить выкатку), сорванные установки по версии и шагу.
- **Оповещения:** принять из `inbox/` (проверка подписи), список действующих, «Снять»; личное помечено `sid`
  адресата. На вкладке «Сайты» у строки сайта — подсказка, как отправить ему личное (`sid` для `release.php note`).
- **Ключи:** отпечатки, `kseq`, заявления — только чтение.
- **Настройки:** сроки хранения, порог автопаузы.
- **Журнал:** записи `admin.log` этого модуля (`checkAdminPost()` уже пишет каждое действие панели); отдельной
  таблицы аудита нет.

**Таблицы** (домены колонок — `docs/NODE.md`, «Schema conventions»):

| Таблица | Что хранит | Ключ |
| --- | --- | --- |
| `_master_site` | последнее состояние сайта: `sid`, домен (пусто — не сообщён), версия, канал, PHP, база, расширения, ошибки, первый и последний визит, последний срыв установки (версия, шаг, время) | PK `sid` |
| `_master_stat` | дневной итог: день, канал, версия, PHP, база → число сайтов, сумма ошибок, сорванные установки | PK по всем измерениям |
| `_master_release` | версия, состояние (ждёт, beta, stable, пауза), кто поставил паузу (владелец или автопауза), доля, время приёма и смены | PK версия |
| `_master_note` | id, адресат (`sid` или пусто), диапазон версий, уровень, срок, состояние, подписанные байты и подпись | PK id |

Задача планировщика `masterclean` раз в сутки подводит дневной итог и удаляет сайты, молчащие дольше срока;
устаревшие итоги удаляет тоже. Сроки — настройки модуля (вкладка «Настройки», `config/master.php`): молчащие
сайты 180 дней, итоги 730 дней по умолчанию. Регистрация — «Решения», задачи мастера (шаг 4); после пункта 4
`docs/2027-CORE.md` задачи переедут в `modules/master/scheduler.php`.

**Автопауза.** Задача `masterwatch` раз в час, регистрируется так же, как `masterclean`. По каждому выпуску в beta
или stable она считает с момента его приёма сорванные установки (сайты с последним срывом на этой версии, которые
всё ещё сообщают прежнюю версию) и удачные (сайты, которые сообщают эту версию); сайт, сорвавшийся и потом
поставивший выпуск, считается только удачей. Если сорванных не меньше 5 и их доля от суммы выше порога (по
умолчанию 5 %), выпуск уходит в паузу с пометкой «автопауза», владельцу уходит письмо на `adminmail` slaed.net с
версией, цифрами и самыми частыми шагами срыва, а в `admin.log` ложится запись. Минимум в 5 срывов защищает от
ложной паузы на малой выборке. Сама задача паузу не снимает. Решение принимает задача планировщика, а не
`master/check`: публичный запрос только записывает присланное (`.rules/api.md`).

## Клиент: «Обновления» в ядре

- **Класс `Update`** (`core/classes/update.php`): запрос к мастеру, проверка подписи и свежести, ключи, скачивание,
  распаковка, сверка, установка, откат. Одна функция внешнего запроса к единственному хосту `slaed.net`: только
  HTTPS, без редиректов, ответ ограничен по размеру; после 8.0 она уходит на `ApiHttp` коннектора вместе с
  `getSchedulerFetch()`.
- **Задача `updatecheck`**, раз в сутки, в своё для сайта время: минута суток из `crc32(sid)`, так что сайты одного
  хостинга не приходят к мастеру разом; при выключенной проверке — только кнопка «Проверить». Расписание задачи —
  строка cron в `config/scheduler.php`, поэтому идентификатор и строку с его минутой создаёт `setup.php`.
- **Плашка** на главной панели и в «Обновлениях»: «Доступна 8.0.1», красная при флаге `security`. Весь текст —
  языковые константы; из ответа берутся только номер версии и флаги. Ссылка на описание собирается из номера по
  постоянному шаблону `https://github.com/SLAED-CMS/SLAED/releases/tag/v<версия>`.
- **Оповещения** — плашки на главной панели и в «Обновлениях» по уровню (info, warn, danger); «Скрыть» запоминается
  на сайте и мастеру не сообщается. На «Обзоре» виден `sid` сайта с кнопкой «Скопировать»: его владелец сайта
  называет, когда пишет в поддержку, — так мастер может ответить личным оповещением.
- **Страница панели «Обновления»** (`admin/modules/update.php`) — модуль панели ядра, как «Планировщик» и
  «Безопасность»: всегда есть, не отключается. Вкладки:
  - «Обзор»: версия, последняя проверка, найденная версия, «Проверить», «Скачать», «Загрузить архив», «Проверить
    установку», «Установить», «Вернуть предыдущую версию», «Применить шаги базы» для ручного пути, «Проверить
    целостность»;
  - «Настройки»: канал stable/beta, выключатель проверки со списком «что отправляется и куда», хранить ли бэкап
    последней установки для возврата, «Сообщать домен мастеру (для поддержки и личных оповещений)»;
  - «Журнал»: установки и возвраты (из `admin.log`).
- **Настройки** — `config/update.php`. Файл уже занят: `$conf['update']` держит отметки возможностей (`fields`,
  `points`, `ratings`, `node`), которые пишет `setup.php` и читают десять мест в ядре и панели; обновлятор их не
  трогает. Свои ключи он кладёт рядом, без пересечения имён: `update.check` — `upcheck` (1), `channel` (`stable`),
  `keepbak` (1), `upsite` (1); `update.steps` — отметки выполненных шагов базы. Файла нет в поставке, поэтому
  слияние его не касается; `setup.php` пишет его целиком и засевает обе группы. Нет ключа — читается значение в
  скобках. Всё, что касается самого сайта, решает сайт и работает без
  мастера; мастер решает только политику выпусков, и она приходит в подписанном манифесте: `min`, `php`, `security`, а
  пауза и доля выкатки — тем, какой манифест он подаёт.
- **Идентификатор установки** — 32 случайных символа, создаёт `setup.php`; рядом хранится SHA-256 `homeurl`: сайт,
  скопированный на другой адрес, сам получает новый идентификатор. Новый идентификатор (копия сайта, потерянный
  `state.json`) переписывает и минуту в строке расписания `updatecheck`.
- **Домен** — хост `homeurl` в нижнем регистре (IDN в punycode), без пути; `localhost`, адрес IP и зоны `.local`,
  `.test`, `.localhost` не отправляются никогда, так стенды не засоряют мастер.
- **Счётчики ошибок** — только числа, считаются в момент проверки по журналам `Logger` (каналы PHP и базы) с
  прошлой проверки, без текста.
- **Без `sodium`** подпись проверяет свой класс `Signature`, **без `zip`** архив читает `PharData` под своим
  разбором центрального каталога («Решения»); «Обзор» называет, каким путём идёт сайт. Нет ни `zip`, ни пары
  `phar` и `zlib` — установка из панели закрыта, страница объясняет ручной путь.

## Выпуск: что делает владелец

```
1. Подготовка   тесты зелёные, VERSIONS.md, UPGRADING.md, версия в коде, шаг базы, если менялась схема
2. Тег          git tag v8.0.1   (только локально; наружу его отправляет publish)
3. Сборка       php tools/release.php build v8.0.1
                  проверки: тег есть, дерево чистое, версия в коде = 8.0.1 и выше прошлой,
                            нет симлинков и лишних верхних папок,
                            полный архив не вырос больше чем на 20 % против прошлого выпуска
                  git archive тега → slaed-8.0.1.zip (+ files.json внутри)
                  дельта по двум files.json → slaed-8.0.1-from-8.0.0.zip
                  manifest-beta.json и manifest-stable.json
4. ДОБРО        php tools/sign.php 8.0.1   → показывает версию, хеш, коммит → «y» → пароль ключа
                  → подписи обоих манифестов; пока они не опубликованы, их никто не видит
5. Репетиция    php tools/rehearse.php v8.0.1
                  прошлый выпуск начисто на копию стенда → обновление полным архивом и дельтой
                  с настоящими подписями → самопроверка → «Вернуть предыдущую версию»
                  → отчёт с хешем архива; для 8.0.0 — установка начисто и самопроверка
6. Публикация   php tools/release.php publish v8.0.1
                  отказ: нет зелёной репетиции этого хеша или в архиве тестовые заводские ключи
                  git push тега → gh release create (оба архива, для людей) → SFTP в inbox/ через .part и rename
                  → скачивает обратно с обоих мест и сверяет хеш
7. Пульт        Мастер → Выпуски: Принять → В beta → (через несколько дней) В stable
```

- Утилиты — только командная строка (`PHP_SAPI === 'cli'`), лежат вне веб-корня, ездят в поставке без секретов:
  форку они нужны для своего мастера.
- Подпись — отдельная команда с паролем; сборка и публикация ключей не касаются. Подписывать в CI или на сервере
  нельзя.
- `sign.php --refresh` раз в месяц переподписывает поданные манифесты (срок жизни 45 дней); `sign.php --keys` —
  церемония: создать ключи, заявление о смене ключа. Истёкший манифест сайт просто не принимает: обновление не
  предлагается, сайт не ломается. Вкладка «Выпуски» мастера предупреждает за 10 дней до `expires` поданного манифеста.
- Публикация отказывает, если отпечатки вшитых заводских ключей совпадают с тестовыми или расходятся с README:
  выпуск с тестовым основным ключом и тестовым ключом восстановления потом не исправить ничем. Сборка с тестовыми
  ключами разрешена — на ней идёт вся разработка до шага 11 — и подписывается тестовым ключом.
- Сборка отказывает и при росте полного архива больше чем на 20 % против прошлого выпуска, пока владелец не
  подтвердит размер (`--max`); для первого выпуска `--max` обязателен. Так в архив не попадут случайные медиа. Дельту
  это не касается: неизменный файл, например база `storage/geoip/`, в неё не входит.
- Красная репетиция номер версии не сжигает: тег ещё нигде не опубликован, подписи нигде не поданы. Локальный тег
  удаляется, ошибка исправляется, сборка, подпись и репетиция повторяются под тем же номером.
- `tools/rehearse.php` идёт мимо мастера: отдаёт `Update` архив и его уже подписанный манифест так же, как
  «Загрузить архив», без обхода проверки подписи. Путь через настоящий мастер проверяет разовая генеральная
  репетиция (шаг 10).
- Настройки публикации — `tools/.env` (gitignored): `SLAED_SFTP=user@slaed.net:22`, `SLAED_SFTP_PATH=…`.
- На машине владельца нужны PHP CLI с `sodium`, `git`, `gh`, `sftp`; как включается `sodium` в OSPanel —
  `.rules/global.md`, «Toolchain».

## Оповещения

```
твоя машина:  php tools/release.php note --level warn --ver "<8.0.2" --until 2026-12-31   (всем ниже 8.0.2)
              php tools/release.php note --level info --sid <sid>                          (одному сайту)
              → текст ru и en → sign.php (пароль) → publish → inbox/ мастера
мастер:       «Мастер → Оповещения»: принять (проверка подписи), снять
клиент:       в ответе master/check — свои оповещения → проверка подписи → плашка
```

- Подписанные байты: тег `SLAED-NOTE-v1\n`, id, уровень, диапазон версий, `sid` адресата (или пусто), срок,
  текст ru и en. `sid` внутри подписи — личное нельзя переслать другому сайту.
- `release.php note` пишет `storage/release/notes/<id>.json` (`id` — время записи, текст спрашивается до строки с
  одной точкой), `sign.php --note <id>` подписывает, `release.php publish --note=<id>` кладёт пару в `inbox/notes/`;
  заявление о ключах так же уходит в `inbox/keys/` через `publish --keys=<kseq>`. Каждый файл после SFTP скачивается
  обратно и сверяется по SHA-256.
- Только простой текст, экранируется при выводе, до 1000 символов на язык; ссылка показывается, только если ведёт на
  `https://slaed.net/` или `https://github.com/SLAED-CMS/`, иначе выводится как текст. Язык панели не ru — en.
- Сайт отклоняет: неверную подпись, чужой `sid`, версию вне диапазона, истёкший срок; повтор id не показывается
  второй раз.
- Снятое мастером исчезает с сайтов при следующей проверке; истёкшее — само.
- Обратного канала нет: сайт ничего мастеру не пишет, кроме обычной проверки.

## Подпись и ключи

- Ed25519 (`sodium_crypto_sign_detached()`), подпись отдельная, над точными байтами файла с префиксом типа
  (`SLAED-UPDATE-MANIFEST-v1\n`, `SLAED-KEYCHANGE-v1\n`). Сначала проверка, потом разбор тех же байтов
  (`JSON_THROW_ON_ERROR`), без перекодирования. Ключи и подписи — строгий base64, ровно 32 и 64 байта.
- Выпуск проверяется только текущим основным ключом. Заявление о ключе — только ключом восстановления и с `kseq`
  выше сохранённого; замена самого ключа восстановления требует ещё подписи основного.
- Заводские публичные ключи вшиты в ядро; доверенные ключи, `kseq` и отозванные — `storage/update/client/keys.json`,
  пишет только обработчик заявлений; пакет с этим путём отклоняется.
- Подписанное сообщение — тег типа и следом байты файла как есть; сам файл тега не несёт, манифест остаётся чистым
  JSON. Подпись лежит рядом файлом `<имя>.sig` — строгий base64 64 байт.
- Файл ключа — JSON `slaed-key`: роль, публичный ключ, соль и параметры Argon2id, `secretbox` с seed 32 байт; пароль
  не короче 10 символов. Новый ключ восстановления один раз показывает seed для бумаги, `--keys new … --seed`
  восстанавливает файл с бумаги. Путь основного ключа — `--key=` или `SLAED_KEY` в `tools/.env`.
- Заявление о ключах — `{type: keychange, kseq, primary, recovery, time}`; у владельца
  `storage/release/keys/<kseq>.json` с `.sig` (ключ восстановления в силе) и `.psig` (основной в силе, только при
  замене ключа восстановления). Заменённые ключи уходят в `revoked` и вернуться не могут. Ключи в силе инструменты
  считают так же, как сайт: заводские ключи ядра и все заявления по порядку (`Update::getKeyChain()`).
- Тестовые заводские ключи — `tests/Fixtures/update/primary.key` и `recovery.key`, пароль `slaed-test`; это не
  секрет: `publish` отказывает, пока вшитый ключ совпадает с одним из них.
- Закрытые ключи никогда не попадают в репозиторий, на сервер и в CI. Основной — файл, зашифрованный паролем, на
  флешке или в менеджере паролей; восстановления — бумага и отдельная флешка в сейфе. Отпечатки публикуются также
  в README репозитория.

## Манифест и пакет

Манифест (JSON): `type` (`release`), `version`, `channel`, `min` (с какой версии можно обновиться), `php`
(наименьшая версия PHP), `security` (флаг), `full` и `delta` — по архиву: `size`, `usize` (объём после
распаковки), `sha256`, у дельты ещё `from` (версия, от которой она); `commit`, `time`, `expires` (`time` + срок, по
умолчанию 45 дней, `release.php build --expires`), `kid`. Свободного текста и адресов в манифесте нет: адрес архива
сайт строит сам — `https://slaed.net/api/v1/master/file?v=<версия>&kind=full|delta`. `version` и `from` — строго
`X.Y.Z`.

`release.php build` пишет `kid` пустым, а `time` и `expires` — заготовкой срока; `sign.php` ставит `kid`, `time` и
`expires` с тем же сроком в момент подписи (и при `--refresh`). `min` по умолчанию — первый выпуск с обновлятором
(самый младший тег, у которого есть `core/version.php`), `php` — из `require.php` в `composer.json` тега. Выход сборки —
`storage/release/<версия>/` (gitignored): оба архива, `files.json`, оба манифеста; пересборка под тем же номером
сначала стирает эту папку вместе со старыми подписями.

Полный архив — дерево тега плюс `storage/update/files.json`. Дельта — только файлы, которых нет в `files.json`
версии `from` или чей хеш в нём другой (сравнение двух списков, а не `git diff`: переименования и `export-ignore`
учитываются сами), плюс все файлы настроек `config/` целиком, изменились они или нет (владелец, 2026-10-16, шаг 7:
слияние читает поставку целиком — по `node.php` оно узнаёт типы Node, иначе дельта с одним `uploads.php` вернула
бы сайту правило удалённого типа), и тот же полный `files.json` новой версии; удалять сайт решает по
спискам, а не по архиву. Сайт ровно на версии `from` берёт дельту, остальные — полный архив; оба подписаны одним
манифестом. Медиа и стенды, не нужные сайту, не входят ни в один архив (`export-ignore`).

`files.json` — список всех поставляемых файлов с SHA-256: `{"version", "files": {путь: {"sha256", "size", "site"}}}`,
`site: true` только у файлов сайта (`Update::isSiteFile()`), сам `files.json` в списке не значится. Этот файл
есть уже в архиве 8.0.0, поэтому сайт всегда знает, что именно у него стоит:
- файлы, которых нет в новом списке, удаляются;
- файлы, чей хеш на диске не совпадает со старым списком, изменены на сайте — до установки показывается их список.

Файлы `config/` в `files.json` помечены как настройки и следуют только строке `config/` таблицы раздела
«Настройки, языки и темы»: «Проверить целостность» их не сверяет, в список изменённых они не попадают, а правило
«нет в новом списке — удалить» их не касается. Файл настроек удаляет только PHP-шаг версии, иначе вместе с ним
пропали бы данные сайта. Так же помечен `public/robots.txt`: его дописывает сайт, и пакет кладёт его, только если
файла нет.

Сайт без `files.json` (поставлен из git, а не из архива) обновляется из панели с предупреждением: старые файлы не
удаляются, изменённые не распознаются.

Версия сайта — константа `SL_VERSION` в `core/version.php` (его читает и заглушка точек входа без ядра);
`$conf['version']` ядро собирает из неё и `SL_CODENAME` при загрузке.
`config/global.php` версию больше не хранит: установка не перезаписывает настройки сайта.

## Настройки, языки и темы при обновлении

Установка не трогает то, что сайт сохранил сам, а новое приходит само. Во время работы ничего не меняется:
`getConfig()` читает только `config/`, `getLang()` — только `lang/`; второго слоя нет.

| Файл | Не менялся на сайте (хеш = старый `files.json`) | Менялся на сайте |
| --- | --- | --- |
| `config/<имя>.php` | всегда считается сайтовым | дописываются недостающие опции |
| `public/robots.txt` | всегда считается сайтовым | кладётся, только если его нет |
| `lang/`, `admin/lang/`, `modules/<модуль>/lang/` и `modules/<модуль>/admin/lang/` поставочных модулей | заменяется целиком | заменяется целиком, прежний файл — в бэкапе установки |
| `templates/admin`, `templates/lite` | заменяется | заменяется, прежний файл — в бэкапе установки |
| сторонние темы `templates/<другое имя>` | не трогаются | не трогаются |
| остальной код | заменяется | останов до отметки «перезаписать» |

- **Настройки:** для каждого файла настроек пакета установщик сравнивает массив, который возвращает файл сайта, с
  массивом пакета и добавляет недостающие ключи на любой глубине со значением поставки: в ассоциативный массив
  сливается рекурсивно, список (`array_is_list()` значения поставки) — целое значение и не сливается, а разделы,
  которые сайт создаёт и удаляет сам, — по «Решениям»: раздел типа Node и набор полей есть на сайте — целиком
  его, раздел типа, которого на сайте нет, не добавляется. Файлы
  устроены по-разному — `global.php` держит опции на первом уровне (`getConfig()` склеивает файлы плоским
  `array_merge`), `scheduler.php` кладёт задачи на третий (`scheduler.jobs.*`), — и правило одно для всех.
  Существующее не меняется. Пишет `setConfigFile()` (журнал, откат): строкой — обычные файлы, формой с замыканием —
  `node`, `fields`, `uploads` и `ratings`, которые строкой он не принимает. Файла на сайте нет — копируется целиком.
- `config/system.php`, `header.php` и `chmod.php` — код, а не настройки (`getConfig()` их пропускает,
  `setConfigFile()` не пишет): они идут строкой таблицы «остальной код».
- **Переименование, смена смысла, удаление опции** — PHP-шаг версии (`storage/update/step/<версия>.php`) через
  `setConfigFile()`.
- **Языки** (владелец, 2026-10-15): поставляемые `lang/<код>.php` переписываются целиком из пакета, как код; так
  исправления формулировок мастера доходят до всех сайтов сами. Правки админа в этих файлах при обновлении теряются
  (прежний файл лежит в бэкапе установки); страница «Языки» об этом предупреждает.
- **Темы** (владелец, 2026-10-15; дочерних тем нет): `admin` и `lite` переписываются из пакета целиком, как код и
  языки; правки в них при обновлении теряются (прежние файлы — в бэкапе установки), раздел «Шаблоны» об этом
  предупреждает. Сторонние темы установщик не трогает; если ядро новой версии ждёт фрагмент, которого в сторонней
  теме нет, это забота её автора.
- После установки удаляется `config/local.php` (собранный кэш конфигурации `getConfig()`), кэш собирается заново.
- **Ручной путь** (FTP): залитый целиком `config/` затирает настройки сайта поставкой, без `config/` новые опции не
  дописываются. Поэтому новая опция в коде всегда читается с запасным значением (`$conf['раздел']['опция'] ?? …`):
  сайт без неё работает так, как до её появления. Справка ведёт на «Загрузить архив» в панели, ручной путь —
  запасной.

## Шаги базы между выпусками

Шаг версии — файл в `storage/update/step/` (`8.0.1.sql`, при необходимости `8.0.1.php` для данных); выполняется по
порядку версий одной функцией `Update`, отметка выполненного — `update.steps` в `config/update.php`; `setup.php`
отмечает все шаги своей версии выполненными. Отметку получает каждая версия, и та, у которой файла шага нет, —
иначе «Применить шаги базы» висела бы вечно. Сначала выполняются шаги базы и PHP-шаги, потом слияние `config/`:
PHP-шаг, переименовавший опцию, должен успеть до того, как слияние допишет её под новым именем со значением поставки.

**Лёгкий режим `UPDATE_FILE`.** Новое ядро на старой схеме может упасть при загрузке, если читает новую колонку,
поэтому шаги базы никогда не выполняются полной загрузкой. Режим устроен как `API_FILE`: ядро без темы, без сессии
посетителя, без модулей, блоков, `Point` и `Rating` и без прочих запросов загрузки к таблицам, которые меняют шаги;
администратор проверяется одним запросом к таблице администраторов (`isAdmin()`), а её схема меняется только
совместимо. Если кука администратора истекла, режим показывает свою форму входа: логин и пароль сверяются с той же
таблицей, кука ставится того же вида, что у обычного входа, — полное ядро для входа не нужно. Так устроен экран
«Database Update Required» у WordPress.

Кто запускает: установка из панели — сама, на шаге 6, в этом режиме. Ручной путь (файлы залиты по FTP или из git):
пока `SL_VERSION` выше последней отметки, сайт закрыт так же, как при `apply.lock`. Заглушка всех точек входа
сравнивает их до ядра — номер версии лежит в маленьком `core/version.php`, который читают и заглушка, и ядро, —
и отвечает 503 всем, включая `/api/` и псевдо-cron; планировщик молчит, потому что новый код на старой схеме не
должен ни показывать страницы, ни писать в таблицы. Проходит только лёгкий режим администратора в `public/admin.php`:
он показывает «Применить шаги базы» с тем же бэкапом базы перед ними, снятым уже на закрытом сайте; после шагов сайт
открывается сам.
`public/update.php` в этом не участвует и в релиз не входит.

## Установка

Установка идёт шагами, каждый — отдельный короткий запрос: бэкап базы порциями, файлы пачками, шаги базы по одному.
Ход пишется в `apply.lock`, страница показывает прогресс; запрос, оборванный таймаутом хостинга, продолжается со
следующей пачки. Пока лежит `apply.lock`, планировщик не запускает ни одной задачи, ни по cron, ни псевдо-cron.
`apply.lock` создаётся атомарно (`fopen(…, 'x')`): вторая установка и двойной клик получают отказ.

**Дамп порциями — новый режим `Backup`** (шаг 8). Сейчас `Backup::addDatabaseBackup()` снимает дамп за один проход
внутри `START TRANSACTION WITH CONSISTENT SNAPSHOT`, а его «состояние сессии» — это `sql_mode` и `time_zone`
соединения, не ход дампа. Новый режим пишет дамп по таблице и смещению, запрос на порцию, ход — в `apply.lock`; сайт
закрыт, поэтому согласованность держит закрытие, а не снимок, и режим не требует InnoDB (полный дамп `Backup`
отказывает на любом другом движке). Восстановление пишется заново: тоже порциями, с распаковкой того сжатия, которым
снят дамп, и без ядра, чтобы его мог вызвать `core/rescue.php`.

Вход порционного режима (шаг 8, договор v1, `Backup::FORMAT` = 1) — статические методы `Backup` на `PDO` в режиме
`ERRMODE_EXCEPTION`; ни `Database`, ни функций ядра они не зовут, файл класса грузится сам при определённом
`FUNC_FILE`. Один вызов — одна часть; состояние — массив, который вызывающий хранит между запросами (`apply.lock`).
- `getSiteTables($pdo, $prefix)` — список таблиц сайта по правилу ниже; `checkDumpAccess($pdo, $tabs)` — каких прав
  не хватает: `SELECT`, `INSERT`, `CREATE`, `DROP` на схему, на MySQL при внешних ключах ещё `REFERENCES`; имя базы
  в правах читается как шаблон LIKE (`user\_db`, `user\_%` хостингов). Права выводятся из `SHOW GRANTS`, без записи в
  базу, поэтому годятся и для «Проверить установку».
- `getDumpState($dir, $prefix, $tabs, $pack)` открывает дамп в пустой папке (`gz`, без `zlib` — `none`);
  `addDumpPart($pdo, $state)` пишет следующую часть `000001.sql.gz`: одна часть — не больше одной таблицы и около
  4 МБ SQL, первая часть таблицы начинается с `DROP TABLE IF EXISTS` и `SHOW CREATE TABLE`, строки — `INSERT` до
  1 МБ. Таблица с одним целым ключом читается по ключу (`last`), прочие — по смещению (`skip`), упорядоченно по
  ключу или по всем колонкам. Часть пишется во временное имя и переименовывается; место проверяется перед каждой.
  Последняя часть пишет индекс `dump.json` — формат, префикс, сжатие, список таблиц, части с таблицей, числом строк,
  размером и SHA-256, итог строк; с ним дамп готов, без него — нет.
- `getRestoreState($dir)` проверяет индекс; `addRestorePart($pdo, $state)` сверяет хеш части, распаковывает и
  выполняет её. Часть 0 сначала удаляет все таблицы префикса по тому же правилу: таблицы списка вернут их части, а
  прочие созданы после фиксации и не возвращаются — заодно освобождаются имена ограничений, которые шаг мог
  перенести на новую таблицу. В состоянии `head` — часть, с которой начинается текущая таблица: вызывающий, не
  знающий, дошёл ли результат последнего вызова, продолжает с `head`, и таблица пересоздаётся без дублей.
- Состояние или индекс чужого формата, индекс, где у таблицы списка нет частей или они идут не подряд (часть 0
  удалила бы её навсегда), повреждённая часть, законченный дамп в папке, префикс вне грамматики, соединение без
  исключений — отказ с именем причины.

Охват — только таблицы сайта: на хостинге одна база часто общая для нескольких программ, а `Backup` по умолчанию
берёт всю базу (`include` = `*`). Таблицы называются `{prefix}_<имя>`, а префикс может сам содержать `_`
(`checkSetupPrefix()`), поэтому совпадения по `{prefix}_%` мало: при префиксе `ab` оно захватит и установку с
префиксом `ab_x`. Список таблиц сайта фиксируется на предпроверке и лежит в `apply.lock`: таблицы `{prefix}_%`,
кроме принадлежащих более длинному префиксу — того, у которого в базе есть своя `<префикс>_admins`. Дамп берёт
только этот список. Восстановление удаляет только таблицы, которые появились после фиксации списка, то есть созданы
шагами этой установки, — иначе такая таблица уронила бы следующую попытку на `CREATE TABLE`. Чужие таблицы не
трогаются ни дампом, ни восстановлением.

**Файлы меняет не ядро.** Пока файлы меняются пачками, ядро на диске — смесь старого и нового, и грузить его нельзя.
Поэтому `core/apply.php` — отдельный исполнитель: он ведёт все запросы установки и сам решает, грузить ли ядро. В
фазе «бэкап базы» он грузит старое, ещё целое ядро; в фазе «файлы» не грузит ни ядро, ни базу, а берёт следующую
пачку из `apply.lock` и двигает файлы; в фазе «новым ядром» грузит новое в лёгком режиме `UPDATE_FILE` (раздел
«Шаги базы между выпусками») — оно выполняет шаги базы и сливает `config/`. Запрос страницы прогресса несёт токен
этой установки, в `apply.lock` лежит его хеш: сессии без ядра нет, страницу прогресса исполнитель отдаёт сам.
`core/apply.php` заменяется последним в фазе «файлы», `core/rescue.php` — только на шаге 8.

**Исполнитель берётся из нового пакета.** Перед фазой «файлы» `core/apply.php` из `stage/` копируется в
`storage/update/client/run/apply.php` и сверяется с хешем из `files.json` нового пакета; точки входа подключают эту
копию, а не установленный файл. Копия нужна потому, что сам `stage/` при установке разъезжается переименованиями.
Договор между заглушкой старой версии и исполнителем новой — один `require` без аргументов; всё остальное
исполнитель читает из `apply.lock`, у которого есть номер формата: исполнитель отказывает на формате, которого не
знает. `core/rescue.php` остаётся установленным до шага 8 включительно — он должен работать, даже если новый пакет
плох, в том числе при сбое на шагах 6–7, когда точки входа уже новые. После установки `run/` удаляется.

**Заглушка всех точек входа.** Ядро грузят три файла: `public/index.php` (с веткой `/api/`), `public/admin.php` и
`public/setup.php`. Каждый первой инструкцией, до ядра, смотрит `apply.lock` и, пока он лежит, разбирает запрос
сам, в таком порядке: форма кода отката или лежащий `rescue.now` — установленный `core/rescue.php`, мимо нового
исполнителя, чтобы откат работал и при плохом пакете; запрос с верным токеном установки — исполнитель
`run/apply.php`; всё прочее — статический 503 с `Retry-After`, без ядра (для `/api/` — без HTML). Так сайт закрыт
всё время, пока лежит `apply.lock`, и `$conf['close']` для этого не нужен: он сам требует ядра, а заход
администратора в `admin.php` при смешанном ядре кончился бы фаталом или исполнением смешанного кода. Эта инструкция
остаётся первой и в каждой новой версии точек входа: после их замены аварийный путь держится на новой заглушке,
которая до шага 8 отдаёт откат ещё старому `core/rescue.php`. Без `apply.lock` та же заглушка закрывает сайт, пока
версия в `core/version.php` выше последней отметки шагов (ручной путь, раздел «Шаги базы между выпусками»).

**Договор между версиями, версия 1.** Исполнитель приходит из нового пакета, а старая версия на сайте остаётся в
двух местах: в фазе «бэкап базы» исполнитель вызывает `Backup` старого ядра, а при сбое на шагах 5–8 откатывает

**Файлы переезжают, а не копируются.** Старый файл переименовывается в папку бэкапа, новый — из `stage/` на его
место; удаляемый файл тоже уезжает в бэкап. Откат — те же переименования обратно. Переименование внутри одного диска
не занимает места и не может оборваться на полпути файла. Если `stage/` или `storage/backup/` лежат на другом диске,
чем дерево сайта (сравнение `stat()['dev']`), переименование невозможно — тогда копирование, и расчёт места ниже это
учитывает.

**Расчёт места.** Все величины известны заранее: `size` и `usize` — из подписанного манифеста, остальное считается
по диску и базе.

| Обозначение | Что | Откуда |
| --- | --- | --- |
| Z | архив | `size` манифеста |
| U | распакованный пакет в `stage/` | `usize` манифеста |
| D | дамп базы | сумма `data_length` таблиц сайта из `information_schema` × 1,2 (без сжатия, с запасом) |
| B | старые файлы, которые уедут в бэкап | сумма `filesize()` перезаписываемых и удаляемых файлов |
| N | новые файлы | сумма размеров файлов в `stage/` |
| P | бэкап прошлой установки | размер папки; удаляется в начале новой установки |
| R | запас | 10 % от нужного, не меньше 50 МБ |

- **«Скачать»:** свободно ≥ Z + U + R. Архив удаляется сразу после распаковки.
- **«Установить»** (`stage/` уже лежит): свободно + P ≥ D + R, если всё на одном диске; на разных дисках —
  свободно + P ≥ D + B + N + R.
- Страница показывает расчёт словами: «Нужно 140 МБ, свободно 900 МБ; бэкап прошлой установки 60 МБ будет удалён».
  Не хватает — кнопка не нажимается, а страница говорит, сколько освободить.
- **Расчёт может ошибиться** (квота хостинга меньше, чем видит `disk_free_space()`; дамп больше оценки). Поэтому перед
  каждой пачкой файлов и каждой порцией дампа место проверяется снова, а любая неудавшаяся или неполная запись —
  ошибка: установка останавливается и откатывается. Откат — переименования и не требует места; восстановление базы
  требует места только на сервере базы.
- `disk_free_space()` выключен на хостинге — расчёт показывается без «свободно», установка требует явной отметки
  «место проверено вручную», а проверки по ходу заменяет только обработка ошибок записи.
- После удачной установки бэкап занимает B + D; страница показывает его размер рядом с `keepbak`.

1. **Предпроверка, сайт ещё открыт:** подпись и хеш уже сверены; PHP не ниже `php` манифеста; версия сайта не ниже
   `min`; запись разрешена для каждого файла и папки назначения; место — по расчёту выше; список изменённых на сайте
   файлов — администратор отмечает «перезаписать» явно; opcache: если он включён, `validate_timestamps` = 0, а
   `opcache_reset()` запрещён `opcache.restrict_api`, установка из панели закрыта с объяснением — иначе «новое ядро»
   шага 6 исполнило бы старый байткод; права базы: `Backup` доказывает видимость объектов и находит таблицы префикса
   сайта заранее, а не на шаге 4, когда сайт уже закрыт.
2. **Код отката** показывается один раз до начала.
3. **Закрыть:** атомарно создаётся `apply.lock` с хешами токена и кода отката, исполнитель копируется в `run/`;
   с этого момента заглушка отвечает 503 всем, кроме запросов установки и отката; бэкап прошлой установки удаляется.
4. **Бэкап базы:** новый режим `Backup` порциями, старым ядром, пока оно ещё целое.
5. **Файлы** (`run/apply.php`, без ядра): пачками, переименованиями — старый в бэкап, новый из `stage/`; удаляемые

6. **Новым ядром в лёгком режиме:** `config/` без `local.php` копируется в бэкап установки; шаги базы и PHP-шаги по

7. **Очистка:** `config/local.php` и кэши; `stage/` остаётся до шага 8.
8. **Открыть:** если `core/rescue.php` есть в пакете (в дельте его нет, когда он не менялся), он встаёт на место
   переименованием, а прежний уезжает в бэкап установки; затем удаляются `stage/` и `run/`, снимается
   `apply.lock`, записывается итог. Бэкап остаётся до следующей установки.
9. **Самопроверка:** сайт запрашивает у себя `/` и `/api/v1/system/ping`. Ошибка 5xx или нет ответа — страница

   администратор. Хостинг не даёт сайту обратиться к себе — страница просит открыть сайт и нажать «Всё в порядке» или
   «Вернуть предыдущую версию».

**«Проверить установку»** выполняет предпроверку шага 1 над уже распакованным `stage/` и показывает, какие файлы
заменятся, добавятся и удалятся, какие изменены на сайте, какие опции `config/` допишутся, какие шаги базы
выполнятся и сколько нужно места. Ничего не закрывает, не пишет и не двигает.

Ошибка на шагах 3–4 — файлы и база ещё не тронуты: неполный дамп удаляется, `apply.lock` снимается, сайт
открывается. Ошибка на шагах 5–8 — автоматический откат: файлы обратными переименованиями, `config/` из бэкапа
установки (вместе с отметками шагов `update.steps`, иначе повторная установка пропустила бы шаг на вернувшейся
старой схеме), база из дампа, `apply.lock` снимается и сайт открывается; версия и номер шага сбоя пишутся в
`state.json` и уходят мастеру со следующей проверкой.

Любой откат — автоматический, аварийный и «Вернуть предыдущую версию» — заканчивается сбросом кэшей:
`opcache_reset()` (иначе при `validate_timestamps` = 0 PHP исполнял бы новый байткод поверх старых файлов),
удаление `config/local.php` (новое ядро могло успеть пересобрать его со списками ресурсов новой темы) и кэшей
страниц и ресурсов.

Если ядро после сбоя не грузится или исполнитель сломан,
откат запускается заглушкой точки входа до загрузки ядра: пока лежит `apply.lock`, она отдаёт `core/rescue.php` —
одну страницу с полем «Код отката»; верный код или лежащий
`storage/update/client/rescue.now` (положен по FTP) возвращает файлы, `config/` и базу из бэкапа. Код одноразовый,
на сервере только его хеш; файл `rescue.now` после отката удаляется.
Установка не трогает `core/rescue.php` до шага 8, поэтому на всём протяжении установки откатывает старый,
проверенный спасатель; базу он восстанавливает сам, читая `config/db.php` напрямую, порциями — запрос на порцию.
Установка никогда не запускается сама.

«Вернуть предыдущую версию» на странице «Обновления» доступна, пока лежит бэкап последней установки (`keepbak` = 0
удаляет его сразу после удачной установки): тем же откатом возвращает файлы, `config/` и базу, предупредив, что
изменения базы и настроек с момента установки пропадут. Следующая установка заменяет этот бэкап своим.

## Что сайт отклоняет

До распаковки: неверная подпись манифеста или архива; выпуск, подписанный ключом восстановления; чужой канал
(`stable`-сайт берёт только `stable`, `beta`-сайт — `beta` и `stable`); версия не выше установленной; `time` старше
уже виденного; размер или SHA-256 не совпали; архив больше подписанного размера (скачивание обрывается).
При распаковке — по своему разбору центрального каталога, до того как чтец (`ZipArchive` или `PharData`) откроет
хоть одну запись: абсолютный путь, `..`, обратный слеш, буква диска, симлинк, путь вне поставляемых верхних папок,
путь под `storage/update/client/` или `master/`, распакованный объём больше подписанного `usize`; и по ходу —
запись, отдавшая байтов больше объявленного в каталоге. Файлам ставится 0644, папкам 0755.

## Статистика и приватность

- Отправляется только перечисленное в `master/check`; текст ошибок и пути — нет; домен — пока клиент не выключил.
- Мастер не пишет IP в свою базу, только считает по нему частоту (`checkApiFlood`: счётчик в файловом кэше под
  хешем адреса, с коротким сроком). IPv6 считается по префиксу /64, иначе случайными адресами одного узла можно
  засыпать `_master_site` случайными `sid`. Предел рассчитан на сотни сайтов за одним адресом хостинга, которые
  приходят в разные минуты.
- `master/check` несёт данные в строке запроса, а журнал веб-сервера пишет её рядом с IP. Поэтому для
  `/api/v1/master/` журнал доступа slaed.net ведётся без строки запроса (свой `log_format` nginx с путём вместо
  `$request_uri`), иначе обещание «IP не связан с доменом» не держится. Доступ к настройке журнала на slaed.net
  у владельца есть (шаг 0).
- Домен — заявление сайта, а не доказательство: под случайным `sid` можно прислать чужой. Вкладка «Сайты» служит
  поддержке, а не учёту.
- Страница «Обновления» перечисляет, что и куда уходит (только slaed.net), у проверки и у домена свои
  выключатели. На slaed.net — короткая заметка о приватности службы обновлений (что, зачем, сколько
  хранится, как удалить); в `docs/` — заметка о DSGVO для владельцев сайтов.
- Список доменов с версиями — цель для атакующего: панель мастера держать под сильным паролем и, пока нет второго
  фактора (`docs/2027-CORE.md`, п. 2), ограничить `admin.php` slaed.net по IP на хостинге.

## Безопасность

- Взлом slaed.net даёт только придержать или переключить уже подписанное. Взлом аккаунта GitHub задевает только
  людей, скачивающих архив руками: «Загрузить архив» сверяет его с подписанным манифестом, ручной путь по FTP — на
  совести владельца сайта. Двухфакторный вход на обоих обязателен.
- Внешние запросы клиента — только HTTPS, только к `slaed.net`, без редиректов (`.rules/api.md`, `ApiHttp`); ответ
  ограничен по размеру.
- Действия панели — через `checkAdminPost()`; установка, откат, пауза, перевод канала — в `admin.log`.
- Публичные действия мастера ограничены по IP (`checkApiFlood`) до любого запроса к базе; `v` и `kind` проверяет
  `ApiInput` до обработчика, так что версия не может стать путём вне `storage/update/master/`.
- Выпуск с тестовыми заводскими ключами невозможен: `release.php publish` отказывает (раздел «Выпуск»).

## Справка в панели

Каждая новая страница панели выходит со своей подробной справкой, и справка входит в «готово» того шага, который
строит страницу или её часть. Справка — для администратора сайта и для владельца на мастере: что значит каждая
кнопка, каждое состояние и каждый отказ и что делать дальше. Пишется по образцу `admin/info/scheduler/ru.md`: только
действующее устройство, без истории изменений. `docs/UPDATE.md` (шаг 11) — другая справка, для того, кто выпускает и
дорабатывает; панельная справка на неё не ссылается вместо объяснения.

**`admin/info/update/ru.md` — страница «Обновления»:**
- что делает раздел, откуда приходят выпуски, что такое подпись и почему сайт не примет чужой архив — простыми
  словами; каналы `stable` и `beta`;
- вкладка «Обзор»: каждое поле, каждая кнопка («Проверить», «Скачать», «Загрузить архив», «Проверить установку»,
  «Установить», «Вернуть предыдущую версию», «Применить шаги базы», «Проверить целостность»), когда она доступна и
  почему бывает закрыта; плашки выпуска и оповещений, красная плашка исправления безопасности;
- установка по шагам: что происходит на каждом из девяти шагов, что сайт всё это время закрыт, сколько это длится,
  что делать, если закрылся браузер или оборвался запрос (установка продолжается с места обрыва), расчёт места словами
  и как его читать, отметка «перезаписать» для изменённых файлов, самопроверка после установки;
- откаты: автоматический; аварийный по коду отката и по файлу `storage/update/client/rescue.now`, положенному по FTP,
  — где взять код, куда положить файл, что увидишь; «Вернуть предыдущую версию» — что вернётся и что пропадёт
  (изменения базы и настроек с момента установки);
- ручной путь: «Загрузить архив»; заливка файлов по FTP, закрытый сайт и лёгкий режим «Применить шаги базы», вход в
  нём; что нельзя заливать поверх (`config/`);
- таблица отказов: каждое сообщение страницы (подпись, свежесть, канал, версия, место, права на файлы, opcache, нет
  ни `zip`, ни `phar` с `zlib`, права базы, мастер недоступен, выпуск на паузе, изменённые файлы) → причина → что
  сделать; что значит запасной путь без `sodium` или без `zip`;
- «Проверить целостность»: как читать результат, что значит изменённый поставочный файл и лишний PHP-файл в ядре;
- вкладка «Настройки» и приватность: что отправляется на slaed.net и зачем, выключатели проверки и домена, где
  виден `sid` и зачем его называть в поддержке; вкладка «Журнал».

**`modules/master/admin/info/ru.md` — модуль «Мастер» на slaed.net:**
- путь выпуска по шагам с командами владельца (`release.php build`, `sign.php`, `rehearse.php`, `publish`) и что
  после каждого видно на вкладке «Выпуски»: `inbox/` → «Принять» → beta → stable, доля выкатки, пауза;
- автопауза: когда срабатывает, что приходит в письме, как разобраться и снять паузу; переподпись предыдущего
  выпуска после паузы; пометка паузы на GitHub;
- вкладки «Сайты», «Статистика», «Оповещения» (как отправить общее и личное, срок, снятие), «Ключи» (что значат
  отпечатки и `kseq`, когда менять ключи), «Настройки» (сроки, порог автопаузы), «Журнал»;
- `--refresh` и истекающий манифест: что будет, если пропустить, и где об этом предупреждение;
- приватность: что мастер хранит, что не хранит, журнал nginx без строки запроса.

**Правки существующей справки:** `admin/info/scheduler/ru.md` — задача `updatecheck` в таблице системных заданий и
молчание планировщика во время установки и при отставшей схеме; `admin/info/lang/ru.md` — языковые файлы поставки
переписываются при обновлении целиком; `admin/info/template/ru.md` — темы `admin` и `lite` переписываются при
обновлении целиком, сторонние не трогаются.

## Тесты

- **Подпись и ключи:** верная проходит; подделанный манифест, подделанный архив, подпись ключом восстановления,
  чужой канал, старая или равная версия, старый `time` отклоняются; заявление ключа с большим `kseq` принимается, с
  меньшим или подписанное основным — нет; замена ключа восстановления — только с двумя подписями.
- **Распаковка:** `..`, симлинк, абсолютный путь, лишняя верхняя папка, путь под `client/`, zip-бомба — каждый
  отказ одинаково через `ZipArchive` и через `PharData`; дерево, распакованное обоими чтецами, совпадает побайтно.
- **Запасная подпись:** с `Signature` при выключенном расширении верная подпись проходит, подделанный манифест
  и чужой ключ отклоняются, а при расширении класс не грузится; `Signature` проходит векторы RFC 8032 и отвечает как
  libsodium на свежих подписях, перевёрнутых битах, точках малого порядка, неканонических ключах и S больше L.
- **Файлы сайта:** `public/robots.txt` со строкой `Sitemap:` после обновления цел, на сайте без него появляется;
  `public/sitemap.xml` нет в `files.json`.
- **Аварийный откат:** по верному коду и по `rescue.now` откатывает без ядра, неверный код не принимается; откат
  работает и при сломанном `run/apply.php`.
- **Договор v1:** спасатель 8.0.0 откатывает установку, которую вёл исполнитель более новой версии (`apply.lock` v1
  с добавочными полями); исполнитель новой версии снимает дамп через вход v1 старого `Backup`; новый спасатель
  восстанавливает дамп, снятый старым `Backup`.
- **Пауза:** после паузы ответ без манифеста гасит плашку; «Загрузить архив» с архивом выпуска на паузе отклонён;
  без мастера ручная загрузка закрыта; переподписанный предыдущий манифест принимается сайтом, видевшим
  приостановленный.
- **Версия и настройки обновлятора:** `$conf['version']` = номер и кодовое имя, презентация показывает оба;
  сохранение общих настроек не возвращает `version` в `config/global.php`;
  `update.check` и `update.steps` пишутся, а отметки возможностей в `config/update.php` остаются как были.
- **`config/` в `files.json`:** отредактированный конфиг не считается взломом и изменённым файлом; конфиг, пропавший
  из нового списка, не удаляется.
- **Целостность:** изменённый поставочный файл и лишний PHP-файл в `core/` найдены, чистая установка чиста.
- **Сорванная установка:** после отката следующая проверка несёт `fail` один раз, мастер считает его в итоге.
- **Домен:** `localhost`, IP и `.local`/`.test`/`.localhost` не уходят; `upsite` = 0 стирает домен на мастере.
- **Возврат:** «Вернуть предыдущую версию» восстанавливает файлы и базу прошлой версии и пропадает после следующей
  установки.
- **Место:** расчёт Z + U и D (+ B + N на разных дисках) с запасом; не хватает — кнопка закрыта; место кончилось
  посреди пачки или дампа — откат без лишнего места; без `disk_free_space()` нужна явная отметка.
- **Исполнитель из пакета:** установку ведёт `run/apply.php` нового пакета, а не установленный `core/apply.php`
  (подложенная в установленный файл ошибка не мешает); копия с чужим хешем и `apply.lock` неизвестного формата
  отклоняются; `run/` удалён после установки.
- **Самопроверка и пробный прогон:** 500 на `/` после установки даёт предложение отката; «Проверить установку» не
  меняет ни одного файла, ни `config/`, ни базы и называет тот же список, что потом применяет установка.
