# SLAED CMS: отказ загрузки файлов без PHP Fileinfo

## Назначение документа

Этот документ передаёт Opus 5 подтверждённую проблему, её причину и план исправления. На этом этапе код исправлять не требуется: сначала следует проверить описанные точки и реализовать минимальное безопасное изменение с тестами.

## Проблема

На production-сайте `https://slaed.net/index.php?name=files&op=add` любые загружаемые файлы отклоняются сообщением «Недопустимый формат файла!». Ошибка воспроизводится не только в модуле `files`, но и в `forum`, поэтому она не связана с настройками одного модуля или конкретным PNG-файлом.

Продовый журнал `storage/logs/error_file.log` фиксирует для реальных запросов:

```text
op: editorUpload
path: files | forum
result: unsupported
```

Тот же корректный PNG размером 168×130 успешно проходит локальную загрузку через тот же обработчик. Клиентский JavaScript отправляет файл корректно; проблема находится на серверной стороне.

## Подтверждённая причина

Production работает на PHP 8.4.22 через FPM/FastCGI. В опубликованном `phpinfo()` указан параметр сборки:

```text
--disable-fileinfo
```

Следовательно, расширение Fileinfo выключено при компиляции PHP. Его нельзя включить директивой в `php.ini`; для этого потребуется другая сборка PHP или пересборка текущей.

SLAED фактически считает Fileinfo обязательным:

- `composer.json:16` содержит зависимость `ext-fileinfo`;
- `core/classes/upload.php:216` отклоняет локальную загрузку с кодом `unsupported`, если MIME reader недоступен;
- `core/classes/upload.php:255-263` возвращает `null`, если класс `finfo` отсутствует или объект нельзя создать;
- `core/classes/upload.php:124` по той же причине блокирует загрузку по удалённой ссылке;
- `core/system.php:4270` преобразует `unsupported` в общий текст `_ERROR_FILE`, поэтому инфраструктурная ошибка выглядит как неверный формат файла.

Проверка Fileinfo выполняется в `checkUploadInput()` раньше проверки ошибки PHP, источника и размера файла. Поэтому при недоступном Fileinfo все попытки получают один и тот же код независимо от реальной причины отказа.

## Цели исправления

1. Разрешить безопасную загрузку поддерживаемых файлов на PHP-сборках без Fileinfo, когда тип можно надёжно проверить другим способом.
2. Сохранить fail-closed поведение для форматов, для которых надёжного валидатора нет.
3. Не доверять расширению имени и значению `$_FILES['type']` как доказательству типа содержимого.
4. Показывать пользователю инфраструктурную ошибку отдельно от ошибки формата.
5. Сохранить одинаковую серверную политику для локальных файлов и загрузки по URL.

## Рекомендуемое решение

### 1. Ввести проверку типа с контролируемым fallback

Fileinfo оставить основным MIME reader, но не делать его безусловным предварительным требованием для всех файлов.

Для изображений использовать существующую проверку фактического изображения:

1. Проверить расширение по allowlist модуля и внутренней таблице поддерживаемых типов.
2. Определить реальный тип через `getimagesize()` или `exif_imagetype()`.
3. Сопоставить полученный `IMAGETYPE_*` с разрешённым расширением и MIME-политикой.
4. Выполнить существующее декодирование соответствующей функцией GD (`imagecreatefrompng()`, `imagecreatefromjpeg()` и т. п.).
5. Проверить ограничения размеров изображения.

Такой путь допустим только для форматов, которые распознаются и декодируются сервером. Отсутствие Fileinfo не должно ослаблять проверку.

### 2. Не делать универсальный fallback по сигнатурам

Для ZIP, RAR и других не-графических форматов применять отдельные валидаторы:

- ZIP: `ZipArchive::open()` и проверка результата;
- RAR: расширение RAR или отдельный проверенный parser, если поддержка действительно требуется;
- прочие типы: конкретный валидатор либо отказ `unsupported`.

Не использовать самописную универсальную таблицу первых байтов как замену Fileinfo: короткие сигнатуры не обеспечивают полноценную валидацию контейнера и могут создать ложное чувство безопасности.

### 3. Исправить порядок предварительных проверок

В `core/classes/upload.php::checkUploadInput()` сначала проверить:

1. структуру `$_FILES`;
2. код ошибки PHP;
3. наличие и корректность временного файла;
4. лимит размера;
5. политику расширения;
6. доступный валидатор содержимого.

Это обеспечит точные коды ошибок даже при отсутствии Fileinfo. Перемещение проверок не должно приводить к записи файла до завершения всей валидации.

### 4. Разделить пользовательские сообщения

Код `unsupported` нельзя объединять с `extension`, `mime` и `image` в `core/system.php::getUploadFailText()`.

Добавить отдельное локализованное сообщение по смыслу: «Проверка этого типа файла недоступна на сервере». Если потребуется новая языковая константа, добавить её синхронно во все шесть локалей: `de`, `en`, `fr`, `pl`, `ru`, `uk`.

Не раскрывать посетителю внутренние сведения о PHP, расширениях или путях сервера. Подробная техническая причина должна оставаться в журнале.

### 5. Добавить диагностику окружения

Проверку Fileinfo добавить в системный монитор и, если соответствующая проверка существует, в установщик:

```php
extension_loaded('fileinfo') && class_exists('finfo')
```

Нужно различать:

- расширение отсутствует;
- класс доступен, но `new finfo(FILEINFO_MIME_TYPE)` завершается ошибкой;
- Fileinfo работает штатно.

Если fallback реализован полностью, Fileinfo следует обозначить как рекомендуемую возможность, а не как безусловное требование приложения. Тогда зависимость `ext-fileinfo` в `composer.json` потребуется пересмотреть осознанно. Не удалять её до появления и тестирования безопасных валидаторов для всей заявленной политики загрузки.

## План реализации для Opus 5

### Этап 1. Зафиксировать текущие контракты

- Изучить целиком `core/classes/upload.php`, включая таблицу типов, локальную загрузку, remote upload, MIME-проверку, проверку изображений и результат ошибок.
- Найти все вызовы публичных методов класса загрузки и все потребители кодов ошибок.
- Проверить конфигурации разрешённых типов всех модулей.
- Проверить существующие PHPUnit-тесты загрузки и test doubles для `is_uploaded_file()`/`move_uploaded_file()`.
- Не менять публичные маршруты и JSON-контракт редактора.

### Этап 2. Добавить тесты, воспроизводящие production

Создать тестовый сценарий, в котором MIME reader недоступен, без зависимости от реального набора расширений локального PHP. Для этого использовать существующий тестовый seam либо минимально внедрить управляемую зависимость; не добавлять глобальные флаги и production-only обходы.

Обязательные случаи:

- валидные PNG/JPEG/GIF проходят через безопасный image fallback;
- расширение изображения не соответствует фактическому типу — отказ;
- повреждённое изображение — отказ;
- PHP/HTML, переименованный в `.png`, — отказ;
- превышение размера возвращает `size`, а не `unsupported`;
- запрещённое расширение возвращает `extension`;
- не-графический тип без Fileinfo и без отдельного валидатора возвращает `unsupported`;
- при доступном Fileinfo текущий штатный путь сохраняется;
- remote upload следует той же политике и удаляет временный `.part` после отказа.

### Этап 3. Реализовать минимальный fallback

- Убрать безусловный ранний отказ по отсутствию `finfo` из общего входного валидатора.
- Выбирать валидатор после проверки входа, размера и расширения.
- Для поддерживаемых изображений использовать фактический тип изображения и декодирование GD.
- Для остальных форматов сохранять отказ, если Fileinfo и специализированный валидатор недоступны.
- Не принимать `$_FILES['type']` и HTTP `Content-Type` как доверенные значения.
- Не записывать файл в конечный каталог до полного завершения проверок.

### Этап 4. Улучшить диагностику и сообщение

- Добавить отдельное отображение `unsupported` в `getUploadFailText()`.
- Синхронно обновить все шесть языковых файлов при добавлении константы.
- Добавить в `error_file.log` безопасное поле с причиной capability failure, например `fileinfo_missing`, `fileinfo_init_failed` или `validator_missing`, без путей и чувствительных данных.
- Добавить состояние Fileinfo в системный монитор.

### Этап 5. Пересмотреть Composer-требование

После завершения fallback определить заявленный уровень совместимости:

- если произвольные разрешённые файлы по-прежнему требуют Fileinfo, оставить `ext-fileinfo` обязательным;
- если все разрешённые форматы имеют безопасные независимые валидаторы, перенести Fileinfo из обязательного требования в рекомендацию Composer с понятным описанием ограничения.

Не менять `composer.json` раньше этого решения.

## Матрица проверки

| Поток | Условие | Ожидаемый результат | Источник подтверждения |
|---|---|---|---|
| Local upload | Fileinfo включён, валидный PNG | Успех | JSON, файл в `uploads/`, журнал |
| Local upload | Fileinfo выключен, валидный PNG, GD включён | Успех через fallback | JSON, файл, журнал |
| Local upload | Fileinfo выключен, PHP переименован в PNG | Отказ | JSON и `error_file.log` |
| Local upload | Файл больше лимита | `size` | JSON и журнал |
| Local upload | Неподдерживаемое расширение | `extension` | JSON и журнал |
| Local upload | Неизвестный бинарный тип без валидатора | `unsupported` | JSON и журнал |
| Remote upload | Валидное изображение | Та же политика, что локально | JSON, файл, журнал |
| Remote upload | Отказ после скачивания | Нет конечного файла и `.part` | Файловая система и журнал |

## Обязательная верификация

1. `php -l` для каждого изменённого PHP-файла.
2. PHPUnit-тесты класса загрузки и всех связанных upload-тестов.
3. PHPStan для изменённой области.
4. `php-cs-fixer --dry-run` для изменённых файлов.
5. Реальная HTTP-загрузка через редактор локально с включённым Fileinfo.
6. Реальная HTTP-загрузка в контролируемом окружении без Fileinfo или эквивалентный изолированный integration test.
7. Проверка результата в `uploads/` и отсутствия временных файлов после отказа.
8. Проверка `storage/logs/error_file.log`, `error_php.log`, `error_site.log` и `error_sql.log`.
9. Проверка одинакового поведения модулей `files` и `forum`.

## Критерии приёмки

- Валидные изображения загружаются при отсутствии Fileinfo, если GD поддерживает их формат.
- Поддельные и повреждённые изображения не принимаются.
- Неизвестные форматы не проходят без надёжного валидатора.
- Пользователь больше не получает сообщение о неверном формате при инфраструктурной ошибке.
- Лог однозначно показывает причину `unsupported`.
- Работа окружений с доступным Fileinfo не ухудшается.
- Локальная и удалённая загрузка используют одну политику безопасности.
- Все связанные автоматические и HTTP-проверки проходят.

## Альтернативное оперативное решение

Самое короткое инфраструктурное исправление production — установить штатную сборку PHP 8.4 с Fileinfo или пересобрать текущую без `--disable-fileinfo`, затем перезапустить FPM pool. Через `/www/server/php/84/etc/php.ini` включить отсутствующее при компиляции расширение нельзя.

Даже после исправления PHP рекомендуется реализовать понятную диагностику `unsupported`, чтобы аналогичная конфигурационная проблема не маскировалась сообщением о формате файла.

## Безопасность production

Публичный `https://slaed.net/info.php` раскрывает версию PHP, Server API, пути конфигурации, параметры компиляции и список отключённых функций. После завершения диагностики файл следует удалить либо закрыть авторизацией или ограничением по IP.

## Пример:

```php
if (function_exists('finfo_open')) {
    $finfo = finfo_open(FILEINFO_MIME_TYPE);
    $mime = finfo_file($finfo, $uploaded_file_path);
    finfo_close($finfo);
} elseif (function_exists('mime_content_type')) {
    $mime = mime_content_type($uploaded_file_path);
} else {
    // FALLBACK: Wenn Fileinfo komplett deaktiviert ist
    $extension = strtolower(pathinfo($uploaded_file_name, PATHINFO_EXTENSION));
    
    // Einfache Mime-Erkennung per Erweiterung für die gängigsten Typen
    $mimes = [
        'png'  => 'image/png',
        'jpg'  => 'image/jpeg',
        'jpeg' => 'image/jpeg',
        'gif'  => 'image/gif',
        'zip'  => 'application/zip',
        'pdf'  => 'application/pdf'
    ];
    
    $mime = isset($mimes[$extension]) ? $mimes[$extension] : 'application/octet-stream';
    
    // Zusätzlicher Schutz für Bilder ohne Fileinfo:
    if (in_array($extension, ['png', 'jpg', 'jpeg', 'gif'])) {
        // getimagesize() benötigt kein Fileinfo und validiert, ob es ein echtes Bild ist
        $img_info = @getimagesize($uploaded_file_path);
        if (!$img_info) {
            $mime = 'unsupported'; // Datei ist manipuliert oder kein echtes Bild
        }
    }
}
```
