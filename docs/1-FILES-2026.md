# Files 2026

Work plan for one way of delivering uploaded files across the site. Today Node closes its upload folders and
serves files through a route that checks the rights of the material; every other module links its files directly
in open folders. The plan gives the forum, private messages and comments the same controlled delivery, brings the
migrated Node texts onto that route, and retires `uploads/archive/`.

## What exists today

| Area | Folder | Delivery | Who may read |
| --- | --- | --- | --- |
| Node materials | `uploads/<type>/`, closed | `op=attach` for `[attach]`, `op=asset` for resources | the reader of the material |
| Comments of Node | the folder of the type | `op=attach` with the id of the material | the reader of the material: published comments, all for a moderator |
| Forum posts and signatures | `uploads/forum/`, open | direct link | anyone with the address |
| Private messages, profile comments, own block | `uploads/account/`, open | direct link | anyone with the address |
| Site messages and newsletters | `uploads/all/`, open | direct link | anyone with the address |
| Polls and their comments | `uploads/voting/`, open | direct link | anyone with the address |
| Avatars, presentation | `uploads/avatars/`, `uploads/presentation/`, open | direct link | public by nature |
| Migrated direct links | `uploads/archive/<module>/`, open | direct link | anyone with the address |

How it works for Node:

- `Parser::filterAttach()` turns `[attach=name …]` into `index.php?name=<type>&op=attach&id=<nid>&key=<name>` when
  it is given a material id (`int $nid` of `Parser::filterContent()`); without one it writes `uploads/<mod>/<name>`.
- `NodeService::getNodeFile()` grants a name only when it is a managed name (`FileManager::checkFileName()`) with an
  allowed extension, and only when the text of the readable material or one of its published comments carries it.
  Its preview branch (id 0) grants the visitor's own uploads that no material holds yet.
- A closed folder holds the guard files of `FileManager::getGuardFiles()`. Apache and LiteSpeed follow `.htaccess`;
  nginx needs the shared rule in UPGRADING.md, "Web Server Rule for Node Upload Directories".

### Defects the plan closes

1. **Private files are public.** An attachment of a private message, or of a post in a forum category closed to
   the reader, is served to anyone who has its address. Only the random part of the name protects it, and some
   names have none.
2. **Two concepts for one job.** `uploads/archive/` exists only because migrated texts addressed files directly.
   It is a second, open place beside the closed type folder.
3. **Raw HTML cannot use the route.** The route grants only names that `Parser::getAttachList()` finds in
   `[attach]` tags, so 184 addresses inside `[usehtml]` cannot leave the archive as they are.
4. **An attachment is not an inline image.** The image templates of `config/filetype.php` render `[attach]` as a
   thumbnail (`[tsrc]`, `max-width:[twidth]px`) that links to the full image. A screenshot a text showed at full
   width would become a thumbnail.
5. **Comments of other targets link directly.** A comment of a poll or a profile renders `[attach]` as a direct
   link into the folder of that module.
6. **Nothing reports unused files.** The migration left 414 files nothing references. No screen tells an
   administrator which files of a folder are no longer used.
7. **A signature resolves against two folders.** The forum renders a signature with the module `forum`, a
   private message with the module of its page, `account`; an `[attach]` of one signature exists in only one of the
   two folders and is broken on the other page.
8. **The shipped tree carries old folders.** `uploads/jokes/`, `uploads/media/` and `uploads/pages/` are tracked,
   though no shipped type or module uses them.
9. **Node types share the upload root with modules.** A type folder `uploads/<type>/` sits beside `avatars`, `all`,
   `archive`, `forum`, `account` and `presentation`. `NodeService::checkNewName()` guards the collision with several
   separate checks (module names, `$base['uploads']`, a case-insensitive scan of `UPLOADS_DIR`), the nginx rule
   depends on a `.htaccess` in every type folder, and the path `'uploads/'.$mod` is built in several places.

## Design

### Node under one root

The folder follows the owner: the owner `node` keeps its types in `uploads/node/<type>/`, the way `forum` keeps
`uploads/forum/`. One function names the folder of an owner and every caller that builds `'uploads/'.$mod` or
`UPLOADS_DIR.'/'.$name` for a type today asks it instead: `Parser::filterAttach()`, `getUploadRuleData()` and
`getUploadPlaceRule()` in `core/system.php`, `getNodeAssetPath()` in `modules/node/index.php`, the methods of
`NodeService` that build a type path (`checkNewName()`, `setTypeRoot()`, `checkTypeGuard()`, `setTypeWrite()`,
`updateNodeTypeStatus()`, `deleteNodeType()`, `checkNodeFiles()`, `setNodeWrite()`, `getNodeFile()`), the uploads
screen of the administration (`admin/modules/uploads.php`, which lists `UPLOADS_DIR`), `tools/upload-route-check.php`
and the test probes (`route_web.php`, `install_probe.php`). That function becomes the **folder** answer of the `node`
adapter in batch 4.

Batch 1 runs before the tree is split, so `uploads/node/` first sits beside the other owners and keeps the guard
files of `FileManager::getGuardFiles()`. Batch 2 of 0-PRIVATE-DATA-2026.md then puts the document root on `public/`
and leaves the whole `uploads/` at the project level, one root, `UPLOADS_DIR`, for every owner. A public owner is
served at its old address by the light path of the front controller, which knows the public folders from one list;
a closed owner is read only by its route, never by URL. Each later batch of this plan closes its owner by taking its
folder off that list, with no folder move: the forum in batch 5, the private messages in batch 6, the poll comments
in batch 7. With the root on
`public/` no upload exists for the web server; with the root on the project the rewrite sends any request for one
into `public/`, where the light path answers it, and a refusal becomes 410 by item 1 of 2-PROD-FINDINGS-2026.md. No
nginx rule names an upload folder. Inside `uploads/node/` a type can collide only with
another type, so `checkNewName()` drops its scan of the upload root; the refusal of a module name, which the route
of a type would shadow, and of a key of `config/uploads.php`, the namespace a type shares with `dir`, `width` and
`all`, stay. A constant `NODE_DIR` names the root of the types, and `FileManager::getPathLock()` takes
`uploads/node/<type>` as the root of an upload area, so a write of one type never waits for another type.

No public address changes: direct access to a type folder is already refused, and texts reach their files through
`go=file` and `op=asset` by name. Batch 0 confirmed that no stored row carries the folder path ("Inventory of
batch 0").

### One route, one owner per file

A new class `FileAccess` (`core/classes/access.php`, the file name of the naming rule) owns the delivery decision and nothing else. It receives
one adapter per owner as closures, the way `getRatingService()` builds `Rating`. Its factory is `getFileService()` in
`core/system.php`. An owner is named by a closed value:

- `node` — the existing check, `NodeService::getNodeFile()`, as batch 3 leaves it;
- `forum` — a post: the reader of its category and topic, from the stored row;
- `privat` — a private message: its sender or its recipient; its folder is `uploads/account/`;
- `comment` — a comment of a target that is not a Node type: the reader of that target, published comments only; its
  target is the id of the comment, its folder the one the comment form uploads into (`uploads/voting/` for a poll,
  `uploads/profile/` for a profile);
- `profile` — the texts of an account outside its messages, its folder `uploads/profile/`: the signature to whoever
  may open the profile, the own block to its owner alone (decision "The profile folder");
- `public` — avatars, presentation, `uploads/all/` and the other folders on the public list of the light path; no
  route and no rights check, the address `uploads/<folder>/<name>` that `getUploadUrl()` answers, as today.

The own block of an account (`getUserBlock()`), which only its owner sees, is a text of the owner `profile`.

Each adapter answers two questions from stored rows only, never from the request:

- **grant**: may the reader receive this name of this target — the text of the target must carry the name, whatever
  its form: the rights check, not a random part, protects a closed folder. The name is a bare file name of a type the
  upload service supports, and the file exists in the folder; the upload rule of the folder decides what may be
  uploaded, previewed and newly bound, never whether a stored text serves a name it carries (decision "The rule
  governs the upload"). A Node text carries a name in an `[attach]` or,
  inside its `[usehtml]` blocks, as the `go=file` address of the same material ("Existing texts");
- **folder**: which folder holds the files of this owner.

The route is one endpoint for every owner, Node included, `index.php?go=file&own=<owner>&id=<target>&key=<name>` with
an optional `thumb=1`; the type of a Node material is read from its row. A Node preview has no material yet and names
its type instead: `index.php?go=file&own=node&name=<type>&key=<name>&preview=1`; the forum has the same preview with
`name=forum` (decision "A preview of the forum"), and `FileAccess::PREVIEW` lists the owners that have one. The query
is exactly one of the two forms, the route answers through `getFileStream()`, and every refusal is the same 404.

### The parser asks, it does not build

`Parser::filterContent()` takes a file context instead of `int $nid`: the owner and the target id. `filterAttach()`
asks `FileAccess` for the address of a name. A closed owner, Node included, answers `go=file`, a public owner answers
the direct link. The cache key of the parser carries the context.

### Closing a folder

A folder closes by leaving the public list of the light path (batch 2 of 0-PRIVATE-DATA-2026.md); every folder
already lies outside `public/`, so nothing moves. Before an owner is switched to the route, the
self-check of batch 3 of 0-PRIVATE-DATA-2026.md confirms the folder is out of reach; it judges the body against a
marker rather than the status code, and answers `closed`, `open` or `unknown`. Only `closed` switches an owner on.
That batch also moves `NodeService::checkTypeGuard()` onto the check and watches the closed upload root on its
schedule; this plan does not repeat it. The guard files of `FileManager::getGuardFiles()` go with batch 2 of that
plan; a closed folder carries none.

### Caches

Every page is rendered live, so no route of this plan meets a stored page. The parser cache never stores a text
that carries an `[attach]`: `Parser::filterAttach()` marks the parse as varying and `filterContent()` skips the write.
The address of a file is therefore built anew on every render, `config/filetype.php` is already part of the parser
key (`getConfigHash()`), and no batch of this plan raises the key. A converted text is a new text and a new key.

### Retired addresses

Production still runs the release with open module folders, and outside links point at `uploads/<module>/<name>`.
After 8.0 no upload is under the document root, so the request reaches the light path instead of the server, and
the light path refuses a closed folder.
No record maps an old address to its new route (decided 2026-10-05): item 1 of 2-PROD-FINDINGS-2026.md answers 410
for any missing file under `uploads/`, `uploads/archive/` included once batch 8 retires it.

### Existing texts

A text that addresses a file of its own owner's folder directly is rewritten to `[attach]` with the name unchanged.
The rewrite is a change of stored texts and runs in `update.php` for a 6.2 site and once on the stand; it renames
and moves no file. On a 6.2 site the file already sits in the folder of its 6.2 module and reaches its owner with the
folder move of UPGRADING.md (`uploads/news/` to `uploads/node/news/`, `uploads/pages/` to `uploads/node/docs/`), so
no archive exists there; on the stand an `uploads/archive/<module>/` address becomes `[attach]` of the type that
module became. `update.php` therefore stops renaming attachment names into managed names (`getMigrateNames()`) and
stops moving files. A name without a random part keeps working, because the grant asks whether the text carries the
name, not what form it has; a new name a writer binds still passes the owner check of the writer
(`checkNodeFiles()`, and its counterparts of batches 5 and 6). A direct address that names a file which does not
exist stays as it is; an address into the folder of another owner is the matter of batch 8.

Inside `[usehtml]` the raw HTML stays: `update.php` rewrites the `src` of an image of the own folder into the
`go=file` address of the same material, and `NodeService::getNodeFile()` grants a name that such an address of
the material carries, as it grants a name of an `[attach]`.

### Inline images

`[attach]` gains a form that renders the full image inline instead of a thumbnail. The grammar
(`Parser::ATTACH`, `ATTSIZE`, `ATTREL`) requires `align` and `title` and allows `width`, `height` and `rel`. The image
templates of `config/filetype.php` use `[rel]` but not `[width]` and `[height]`, and for an image `filterAttach()`
overwrites both with the size of the file (`getimagesize()`), so an explicit width cannot carry the choice. The
grammar gains one optional segment, such as `size=full`, that selects a full-size image template. The converted
`[img]` addresses use it, so the migrated texts look as they did. Batch 2 fixes the form, and the editor offers it
beside the thumbnail when an attachment is inserted (decided in batch 0).

### Unused files

An administration report lists, per folder, the files that no text, comment, resource or avatar references. It
deletes nothing on its own: the administrator removes the files the report shows. The scan uses the same reference
readers the route uses, so the report and the route never disagree about what is used.
