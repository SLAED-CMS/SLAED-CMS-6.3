# Mail Delivery

Status date: 2026-07-27. Approved, not started. Outgoing mail has two separate
defects: it can only leave the server through PHP `mail()`, and it leaves inside
the request that triggered it. This plan fixes both in one subsystem — one
class, one config section, one drain task, one admin view — without touching the
26 existing call sites.

The two halves ship in order: **transport first, queue second.** The transport
is useful on its own, changes nothing for an installation that does not
configure it, and is what finally gives the queue a real delivery result and a
real error string to record.

### Decisions made during execution

- **`addQueue()` is not in batch 1.** In stage 1 it *delivers*, so it cannot exist
  before a transport does. It arrives in batch 2 together with PHP Mail, the
  default transport, which is also what makes that batch a self-contained
  comparison against today's `addMail()`. Batch 1 is exactly what its row
  promises: pure functions over a message.
- **The wiring is in batch 1, not batch 6.** `require_once` at
  `core/system.php:130` and `$mailer = new Mail($db, $conf)` after the database
  exists, per the stage's second bullet. Batch 5 (`mailtest`) needs the global to
  exist, so it could not wait for the migration batch. Batch 6 moved the
  construction itself — see its entry below.
- **`$db` is stored and unused until stage 2.** The constructor takes it as the
  plan specifies, so the wiring line never has to change again; the transport
  half genuinely works with no database.
- **Composition methods are private, and the tests reach them by reflection.**
  The plan makes the header builder and the address sanitiser private, and stage
  2 makes sending private for the same reason: nothing outside the class may
  compose or deliver a message.
- **The header block carries `To:`, and an empty recipient means the transport
  writes its own.** The plan never mentions the header, but two of the three
  transports need it: Sendmail is started with `-t`, which reads its recipients
  from the message, and an SMTP message without `To` is malformed. PHP `mail()`
  is the exception — it writes `To` itself and a second one would duplicate it,
  so that transport passes an empty recipient. Deciding this in the batch that
  owns header assembly is what keeps assembly in one place instead of splitting
  it across batches 3 and 4.
- **`ext-mbstring` needs no further work.** The plan asks for the requirement to
  be stated in `composer.json`, the README and the installer. All three already
  do: `composer.json require` lists `ext-mbstring`, `README.md:53` names it, and
  `setup/index.php:34-36` refuses an install without it beside the PHP version
  test. No batch has to add this.
- **Priority needs no clamping.** Measured across the 26 call sites: the last
  argument is only ever `1` or `3`, so `X-Priority` cannot receive a value
  outside the meaningful range. The `$pr ?: 3` default that `addMail()` applies
  moves to `addQueue()` in batch 2.
- **Charset is a class constant, not `_CHARSET`.** All six `lang/*.php` define
  `_CHARSET` as `utf-8`, but it is a request-scoped language constant and the
  stage 2 drain runs in the scheduler. `Mail::CHARSET = 'UTF-8'` removes that
  dependency; the emitted `Content-Type` differs only in the case of the token,
  which is case-insensitive per RFC 2045.

- **The send path is `setDelivery()`, and it exists from batch 2.** `addQueue()`
  resolves and validates the message; `setDelivery()` encodes the subject and the
  body and hands both to a transport. That boundary is where stage 2 splits: the
  drain calls `setDelivery()` and never `addQueue()`, so keeping composition
  inside `addQueue()` now would only mean moving it later. The `match` on
  `$conf['mail']['transport']` the design describes replaces its single call in
  batch 3, when a second arm exists — a `match` with nothing but a default arm
  would be a pass-through, which is what the naming rules ask to avoid.
- **Transports are named as a family.** `addPhpMail()` here, `addSendMail()` and
  `addSmtpMail()` in batches 3 and 4, so the `match` reads as one dispatch table
  rather than three unrelated names.
- **`title` length is not validated yet.** The plan validates it at enqueue
  because the column is `VARCHAR(255)`; that column arrives in stage 2, and
  refusing a long subject today would reject messages `addMail()` sends. It moves
  in with the table, in the same batch that can no longer store them.
- **`kind` is accepted unvalidated and only logged.** Nothing reads it before the
  queue exists, and refusing a message because a call site forgot its `kind`
  would fail a password reset over a bookkeeping field. The 26 call sites each
  name one in batch 6, which is where a missing one becomes visible.
- **An unresolvable sender aborts the send.** If neither `mail.frommail` nor the
  caller's address validates there is no `From` to send under, and `From: <>`
  is worse than a recorded failure — the plan's own rule is that a value failing
  validation aborts rather than being silently cleaned.
- **The envelope fallback is attempted once per object, not per message.** The
  plan asks for the fallback to be *recorded* once; attempting it once follows
  from the measurement in the facts above. A transport failing for its own
  reasons — the 26 s connect this box produces — would otherwise cost two
  attempts for every message, and the fallback only ever answers one question:
  does this host accept the fifth parameter. So the retry runs once, a successful
  one drops `-f` for the rest of the run, and a failed one is not repeated. In
  stage 1 the object lives for one request, in stage 2 for one drain run.
- **No test enters `mail()`.** A positive delivery test would open a real SMTP
  connection from this box and take the measured 26 s to fail. The tests cover
  what happens before a transport is entered and the pure helpers around it; the
  transport itself is covered by the stage's own verification list, which needs a
  host that can actually deliver and the `mailtest` operation from batch 5.
- **`tests/bootstrap.php` gained a `getAgent()` mock** beside the `getIp()` one it
  already carried, because the client block calls both.
- **The `match` arrives in batch 3, as batch 2 promised, and its `default` arm is
  PHP Mail.** An unset, empty or unrecognised `mail.transport` therefore delivers
  the way the installation already does, which is the stage's compatibility claim.
  No value is rejected at delivery time for being unknown; batch 5 owns the
  selector that decides which values an administrator can produce at all.
- **The subject moved into `getHeaders()` rather than being prepended by the
  transport.** `mail()` takes the subject as its own parameter, but a message
  piped to `sendmail -t` has to carry it inside the block, and so will the SMTP
  `DATA` in batch 4. The builder already had exactly this shape for `To:` — an
  empty argument means the transport supplies it — so the second case reuses the
  rule instead of splitting assembly across three methods, which is what batch 1
  decided to avoid. The eleven batch-1 header tests were updated for the added
  argument; none of their assertions changed.
- **The recorded failure text is bounded, in `setError()` and nowhere else.**
  This is the first transport that captures a foreign process's output, and
  `sendmail` stderr is unbounded input: without a limit a misconfigured binary
  writes kilobytes into `getError()` and into every `Logger` line. The cut is
  `mb_substr()` at 255 characters, counted in characters so a multibyte response
  is not split mid-character, which is the rule the plan already fixes for the
  stage 2 `error` column — applying it once, in the single place every failure
  passes through, is what keeps stage 2 from having to add it per transport.
- **`-t`, not a recipient argument.** The binary reads its recipient from the
  `To:` header the block now carries, so no address is ever passed as a command
  argument. `-i` accompanies it so a lone `.` cannot end the message early, and
  `-f<sender>` is a separate array element, never interpolated. The address
  cannot reach the argument list at all, and the array form means no shell parses
  what does.
- **The configured path is validated, and a value carrying arguments simply is
  not a file.** `mail.sendmail` is run through the header sanitiser first, so no
  control character reaches `is_file()` — which throws a `ValueError` on a NUL
  byte in PHP 8 — and is then required to be an existing executable file. An
  administrator who types `/usr/sbin/sendmail -OQueueDirectory=/tmp` gets a
  refusal with a stated reason rather than a command line, which is the whole
  point of the path-only rule.
- **The capability probe stays private and is a delivery guard, not a UI
  feature.** `function_exists('proc_open')` is false when the function is in
  `disable_functions`, so the transport refuses with its own message instead of
  failing at the pipe. Reporting that absence next to the control it disables is
  batch 5's work and needs no new public surface here.
- **No test starts a real binary**, for the same reason batch 2 entered no
  `mail()`: there is no sendmail on this box, and the usual shim — a `.cmd` that
  ignores its arguments — cannot be spawned by an argument-array `proc_open()`
  at all, because `CreateProcess` does not run batch files without a shell, and a
  shell is exactly what this transport refuses to involve. The tests cover the
  two guards, the transport selection (the assertion is the sendmail message, not
  the PHP Mail one) and the error bound; the pipe itself belongs to the stage's
  verification list on a host that has an MTA.

- **The failure path closes the connection, and there is exactly one of them.**
  `setSmtpFail()` records the phase and the code and drops the socket, so the
  stage's "the socket is closed on every failure path" criterion is one place
  rather than a rule to remember at each of the eleven call sites. `RSET` was the
  alternative and was rejected: a dialogue that failed mid-step has no verified
  state, and reusing it to save one handshake per failure trades a measurable
  cost against an unbounded one. Recording the phase first means stage 2's
  classification table — transport-wide, campaign-wide, recipient, message-wide —
  still has everything it needs to decide what the failure meant.
- **`phase` and `code` are recorded but not published.** Both land in the
  `Logger` context now and are what stage 2 writes into the `phase` and `code`
  columns. They stay private because `setResult()` lives inside the class, so
  filling those columns needs no public surface the plan's list does not name.
- **The connection is kept, and reopened only when the relay dropped it.**
  `checkSmtpLink()` returns the socket it already holds unless `feof()` says the
  peer is gone, which is what makes the stage 2 drain one handshake per run
  rather than per message. `__destruct()` says `QUIT` and closes, because in
  stage 1 the object dies with the request and a relay should not be left holding
  a session for it.
- **`AUTH PLAIN` is preferred over `AUTH LOGIN` when a relay advertises both** —
  one command against three round trips, same credentials, same protection. The
  mechanism is read out of the capability list the last `EHLO` returned and never
  assumed: a relay offering only `CRAM-MD5` and `GSSAPI` gets a stated refusal
  rather than a guess that teaches it to rate-limit us.
- **The second `EHLO` after STARTTLS is not optional**, and the mechanism list is
  read from it. The capabilities a relay advertises before encryption are not the
  ones that count, and several providers only offer `AUTH` on the encrypted side.
- **Both credentials pass the header filter.** They only ever reach the wire
  base64-encoded, so this buys nothing against protocol injection — what it buys
  is that a NUL cannot reach the `AUTH PLAIN` framing, where it would silently
  shift the user/password boundary. Neither value, nor its encoded form, is
  passed to a failure message at any level.
- **The EHLO name comes from `gethostname()` when it looks like a host name.**
  The plan's config block has no key for it and adding one to a shipped default
  would be a setting nobody can answer better than the system can; a name that
  does not match the host-name shape degrades to `localhost` rather than being
  sent as-is.
- **Continuation is bounded at 100 lines.** Following a multi-line reply is
  required; following it forever is a relay's choice about how long our run
  lasts. The cap is a refusal with its own reason, not a silent truncation.
- **TLS verification is on and has no switch.** `verify_peer`, `verify_peer_name`
  and SNI through the stream context, `STREAM_CRYPTO_METHOD_TLS_CLIENT` rather
  than the `ANY` constant that still admits SSLv3. The plan's reasoning is
  followed literally: an option to disable verification exists mainly to make a
  broken configuration look like it works.
- **The warning capture became two methods, and all five sites use them.** Batch
  2 and batch 3 each carried their own copy of the set-handler/restore pattern,
  and the SMTP transport needs it three more times — connect, the TLS handshake
  and every write. `setWarnCatch()`/`getWarnText()` replace all five, which is
  the consolidation `.rules/global.md` requires of a new helper. It touches the
  two earlier transports, which is wider than this batch's stated scope; the
  behaviour is identical and their tests are unchanged, and the alternative was
  shipping a fifth copy of the same four lines.
- **No test reaches a relay**, for the third batch running. The dialogue is
  driven over a `stream_socket_pair()` standing in for the server: the class
  writes commands into one end and the test preloads the answers into the other,
  which is what makes the eight named hazards testable against real socket
  semantics — multi-line replies, an unexpected code, dot-stuffing, CRLF, the
  read timeout, the closed socket — without a network. The pair is available on
  this Windows host; a host where it is not skips those tests rather than
  failing them.
- **The black-holed-port test asserts the bound, not the wording.** A connect to
  a dead local port answers with the operating system's own message, which is
  localised, so the assertion is that the attempt ends well inside its timeout
  and that the socket is gone afterwards.

- **The shipped `config/mail.php` carries every key, the tab exposes only the delivery ones.**
  The stage asks for the file with every limit at its listed default, and the
  queue keys are in it — but a row for `batch` or `keep` on the mail tab would be
  a control for machinery that does not exist until stage 2. The file is
  complete, the screen is not, and stage 2 adds the rows in the batch that gives
  them meaning. A regression test asserts the whole key set and both defaults, so
  the file cannot quietly drift from the plan between now and then.
- **The shipped file is written in the order a save would write it.**
  `setConfigFile()` `ksort()`s before export, so a file shipped in the plan's
  reading order would be reordered by the first save and every installation would
  differ from the repository after one click. Shipping it sorted is what makes the
  "a fresh install and an upgraded install produce the same config keys"
  criterion hold on the bytes and not only on the key set.
- **`save()` writes the delivery keys and hands the stored section back as the
  base.** `setConfigFile('mail.php', $new, $conf['mail'])` merges over what is
  already there, which is how the queue keys, and the password when the field is
  left empty, survive a save that never mentions them. This is the mechanism
  `config/oauth.php` already uses, not a new one.
- **The password field is `type="password"`, renders empty and is never read
  back.** An empty submission is simply absent from the array handed to
  `setConfigFile()`, so the stored value comes through the merge. Nothing has to
  compare the posted value against the stored one, which is the usual place this
  goes wrong.
- **Header-bound values are stored as typed and sanitised at the boundary.**
  `fromname`, `host`, `user`, `pass` and the Sendmail path are read with the
  `raw` filter and trimmed; `text` would run `filterHtml()` over them and turn a
  sender name of `Иван & Co` into `Иван &amp; Co` inside a MIME header. `Mail`
  already strips control characters from every value that reaches a header, which
  is the boundary the plan puts them at, and `setConfigFile()` writes through
  `var_export()`, so nothing typed here can reshape the file.
- **The two addresses are validated on save and refuse the save.** `frommail` and
  `replyto` are the only two fields where a wrong value is silent — the message
  simply stops being delivered — so an address that fails
  `FILTER_VALIDATE_EMAIL` redirects with a stated reason instead of being stored,
  which is the same shape the SEO template validation in this module already has.
  The rejected value is not echoed back into the message.
- **The transport and the encryption selector accept only their listed values.**
  Anything else falls back to `php` and `none` rather than being stored, so the
  `match` in `setDelivery()` never has to interpret a value the panel produced.
- **The test send is a fourth `case`, and it reads the stored settings.** The
  button is a submit inside the shared config form, named `op` like the form's
  own hidden field, so the browser posts the clicked value last and the module
  routes to `mailtest`. It therefore does not save first, and the hint on the row
  says so: settings are saved, then tested. Making the button save as well was
  rejected as improvisation — the plan describes an operation that validates the
  token, defaults the recipient and sends.
- **The value-driven row hook is `data-sl-show-when` plus `data-sl-show-value`,
  next to the tab hook it complements.** `setFieldShows()` sits beside
  `initTabGroup()` in `plugins/system/slaed.js`, keyed on a control's name within
  the same form and re-applied on `change`. A row is written visible and is only
  ever *hidden* by the script, which is what makes it progressive in the sense
  the plan asks for.
- **The capability probes report beside the control and do not remove it.**
  A missing `openssl` puts a warning next to the encryption selector and a
  disabled `proc_open` one next to the Sendmail path; neither control is
  disabled, because a disabled field posts nothing and the first save would
  silently reset the value it was hiding. Both transports already refuse with
  their own stated reason at send time, so nothing here can be a surprise later.
- **Nothing was added for the SMTP `AUTH` mechanism.** The class reads it from
  what the relay advertises, so an installation has no mechanism to choose and
  the tab offers no control for one.

- **The upgrade statement went into `table_update6_3.sql`, not into a new file.**
  The stage asks for "a new `setup/sql/table_update*.sql`", but 6.3 is the version
  this work ships in — `config/global.php` reads `6.3.0 Phoenix` and
  `setup/index.php` offers exactly one path into it, 6.2 → 6.3. A new file would
  need a 6.3 → 6.4 branch and a release that does not exist, and the only
  installation reaching this code through the installer would then get the table
  on a fresh install and not on an upgrade — which is the one divergence the
  stage's own "same schema either way" criterion forbids. The statement is a
  `CREATE TABLE IF NOT EXISTS` in the batch M style that file already uses, with
  the primary key alone in the create and every secondary index added through
  `addidx`, so a half-applied upgrade gains only what it is missing.
- **A claimed row is moved behind the lock window, and that is what makes the
  claim exclusive.** The obvious predicate — `locked IS NULL` — was measured and
  discarded: with 100 000 pending rows `EXPLAIN` picked `KEY locked` over
  `hold_status_prio_ntime` and added a filesort over 99 267 rows, and the claim
  took **202 ms**. Written against the index the plan designed —
  `hold = 0 AND status = 0 AND ntime <= NOW()` and nothing else — the same claim
  is a range read of 25 rows with no filesort and takes **1.9 ms**. Exclusivity
  then comes from the claim itself setting `ntime` to now plus the lock window,
  so a claimed row is not due for anyone else, and a run that dies hands its rows
  back when the window passes rather than through a sweep. `deleteClaim()` stays
  and still clears `locked`/`lockid` behind `KEY locked`, but it is bookkeeping
  now, not the mechanism.
- **A released row is due again immediately.** A run stopped by its budget or by
  the rate cap sets `ntime = NOW()` on what it did not send, otherwise the claim's
  own window would keep the rest of the batch waiting fifteen minutes for no
  reason.
- **The drain job is `priority = 2`, as the plan's prose says and not as its code
  block says.** The block lists `1`; the paragraph under it explains at length why
  `2` is correct — the scheduler runs one due job per trigger and breaks ties by
  name, so an equal priority would sort `maildrain` ahead of `newsletter`. The
  block is corrected here to match the reasoning.
- **`updateQueue()` returns counts rather than a status.** `addMailTask()` maps
  them to what the scheduler stores: a run that refused everything it tried is
  `failed` — a broken transport is what an administrator has to be told about —
  and anything else is `success` with the counts in the job's `extra`. An empty
  queue is **not** `idle`, which is the shape `updateNewsletter()` uses:
  `deleteSchedulerLock()` counts every status but `success` as a failure
  (`core/system.php:382-389`), and the scheduler screen shows that counter
  (`admin/modules/scheduler.php:48`). A job that runs every five minutes and
  reports `idle` on a healthy installation would show thousands of failures and
  a last-success date that never moves. The newsletter job never showed this
  because it ships disabled and runs hourly.
- **Retention is keyed on `time`, the creation stamp**, because the table has no
  column for the moment a row was accepted and the plan's schema does not add
  one. For a queue that drains within minutes the two differ by minutes, and a
  row that stayed pending for days is not accepted and is not pruned at all.
- **The test send reports what the run did, not what the queue accepted.** The
  rate window and the time budget can both end a drain before the test message
  leaves, so success is claimed only when the run actually sent something;
  otherwise the row is in the queue and `_MAIL_TESTWAIT` says so instead of the
  button implying a delivery nobody observed.
- **The rate window lives in the scheduler job state**, as the plan requires, and
  is read and written through `getSchedulerState()`/`setSchedulerState()` behind a
  `function_exists()` guard, because the class also runs in tests that never load
  the procedural core. It is persisted after every batch, so a run that is killed
  loses at most one batch of accounting rather than the whole window.
- **CLI raises the budget and the batch, and nothing else changes.** A run under
  `php_sapi_name() === 'cli'` asks for `set_time_limit(0)`, takes the job's lock
  window minus a minute as its budget and multiplies the configured batch by ten;
  a run inside a web request takes 60% of `max_execution_time`, or two minutes
  where that is unlimited, which is what keeps a pseudo-cron drain inside the
  request that started it.
- **The test send queues and then drains, instead of sending directly.** Making
  sending private is what the stage asks for, and a button that only stored a row
  would stop proving anything — the plan's own reason for having it is that the
  administrator sees the transport's exact words. `mailtest()` therefore calls
  `addQueue()` and then `updateQueue()`, and reports `getError()` when the run
  refused anything. Verified in a browser: with `transport = php` on a box with no
  MTA the button answers `php mail() refused the message: mail(): Failed to
  connect to mailserver at "localhost" port 25`, which is the same diagnostic as
  before the queue existed.
- **The six queue settings arrive on the mail tab now**, which is what batch 5
  promised when it shipped the file complete and the screen short: `batch`,
  `rate`, `tries`, `backoff`, `keep` and `keepbulk` each have a row and are
  validated on save. `verify` and `dnsttl` are still absent by the same rule —
  the verification ladder they govern arrives in stage 3.
- **A row that refers to a body that is gone fails without retrying.**
  `setResult()` gained a fourth argument for that: an attempt cap exists for
  failures that might improve, and a deleted source row is not one of them.

### Defects found and fixed inside the batch

- **A UTF-8 aware pattern in the header sanitiser dropped the whole value.**
  `preg_replace('/[\x00-\x1F\x7F]+/u', ...)` returns `null` on a malformed byte,
  and the `?? ''` fallback then discarded the entire subject or display name —
  a message from a caller holding a single non-UTF-8 byte would have gone out
  with `From: <addr>` and no subject at all. The character class is ASCII, so the
  modifier bought nothing; the match is now bytewise and a malformed byte
  degrades to the substitution character `mb_encode_mimeheader()` already emits.
  Both regression tests were confirmed to fail against the old pattern before the
  fix was restored.
- **A masked address copied whatever an injection appended behind it.** Masking
  the local part of the raw value left the rest intact, so the rejected recipient
  `user@slaed.net\r\nBcc: victim@example.com` reached `error_site.log` as
  `u***@slaed.net Bcc: victim@example.com` — the log format itself was never at
  risk, `Logger` strips control characters, but the address the injection named
  was written out in full and the mask bought nothing. `getMaskedMail()` now
  validates first and logs a bare `***` for anything that fails, so only an
  address that is real is ever partially readable. Observed in the log during the
  batch, not predicted.
- **A rejected address is no longer put in the log at all.** Once the mask
  validates first, the address of a *rejected* message could only ever render as
  `***`, so the field carried no information and only invited the next reader to
  widen it again. The two rejection entries now carry `kind` alone; `Logger`
  already records the URL, the IP and the request, which is what identifies the
  call. The masked form stays where it means something: a delivery failure for an
  address that is real.
- **The envelope check now reads the shell rule rather than assuming it.**
  `mail()` passes the fifth parameter through `escapeshellcmd()`, which does not
  escape a space, so an address containing one would split into extra arguments
  for the local MTA — the classic fifth-parameter vector. Measured on PHP 8.4.1:
  `filter_var()` **rejects** every form carrying a space, including the quoted
  `"a b"@example.com`, and escapes `;` and `"` in the exotic forms it does accept
  (`"a;b"@example.com`). The gate the plan asks for — attempt `-f` only for an
  address that passes validation — is therefore sufficient here, and no second
  pattern of our own is added. Worth re-checking if the sanitiser is ever
  loosened.

- **An unchecked `fwrite()` could have reported an unsent message as accepted.**
  Measured in batch 3 against a process that exits before reading its input: the
  write returns `false` while the exit status can still be `0`, so the transport
  would have answered success for a message no binary ever saw — and on a system
  that raises `EPIPE` the same path emits a warning, which inside a pseudo-cron
  request leaks into the response body exactly as the suppressed `mail()`
  warning would. The write is now compared against the message length and
  wrapped in the same warning handler the PHP Mail transport already uses, with
  a short write reported as its own failure separately from a non-zero status.
- **A `sendmail` stderr of exactly `"0"` was discarded.** `?: ''` on the captured
  output treats the string `"0"` as empty, so that one response would have been
  dropped from the recorded reason. The capture now tests `=== false` — the only
  value `stream_get_contents()` uses to signal failure — and keeps every other
  string as it came.
- **`stream_socket_client()`'s error string can be `null`, and handing it to a
  typed helper would have been a `TypeError`.** The reference argument stays
  unset when the failure happens before a connection is attempted at all, and
  `filterHeader(string $text)` is a user function, so a coercive `null` throws
  rather than degrading — a connect failure would have become a fatal error
  inside the very path that exists to report one. Caught while writing, before
  the first run: the value is defaulted at the call, and the captured warning is
  the fallback text when the relay gives no reason of its own.
- **The reuse claim was asserted rather than assumed.** The connection surviving
  between messages is what the whole stage 2 drain design rests on, and nothing
  proved it: a second `addQueue()` now has to reach the relay over the socket the
  first one opened, with no `EHLO` and no `QUIT` in between. Removing the reuse
  branch makes it fail.
- **Two comment lines exceeded the 180-character limit** `.rules/global.md` sets
  for PHP. Both were shortened into two lines each, which is the form the rest of
  the file already uses, rather than being wrapped.
- **Four of the SMTP guards were confirmed to fail their tests when removed.**
  Dropping the dot-stuffing lets `aBodyLineBeginningWithADotIsStuffed` see a bare
  `.` line in the middle of a body; returning after the first reply line breaks
  four tests including both `AUTH` dialogues, which is what a desynchronised
  reader looks like from the outside; hard-coding the mechanism instead of
  reading the capability list makes `anUnadvertisedMechanismIsNeverAttempted`
  hang until the read timeout; and removing the close from `setSmtpFail()` leaves
  `everyFailurePathClosesTheSocket` holding an open stream. Each was restored
  immediately after the run.
- **Both sendmail guards were confirmed to fail their tests when removed.**
  Dropping the path validation makes the two guard tests report
  `the sendmail binary could not be started` instead of the expected refusal,
  and PHPUnit additionally flags the `CreateProcess` warning `proc_open()`
  raises — which is the second thing the guard prevents, since that warning
  would otherwise reach the response body.

- **The test send would have written the SMTP password into the site log.**
  `Logger` records every posted field with its failure entry
  (`core/classes/logger.php:106`), and the test button submits the shared config
  form, so a password typed into the field travelled with the request that then
  recorded a delivery failure. Today it survives only because
  `Logger::filterArray()` keeps the first 50 keys and the field sits past that
  bound (`core/classes/logger.php:155`) — a positional accident, not a
  protection. `mailtest()` now drops the field from the request before any
  transport can run; the send reads the stored configuration and never that
  field. Confirmed by posting the operation directly with the field present: the
  password appears in `error_site.log` without the guard and does not with it.
  **The general defect is untouched and belongs to its own batch** — any POST
  under 50 fields still records every value, which includes the admin login form.

- **`$mailer` is constructed in `core/security.php`, not in `core/system.php`.**
  Two of the 26 sites are `addHackReport()` and `addWarnReport()`, and they are
  reached from the request scan inside `core/security.php` itself — the flood
  check at `:76-78` and the GET/POST/COOKIE/FILES sweep from `:274` — which all
  run while that file is still being included. The batch-1 wiring created the
  object *after* the include returned, so a migrated security notice would have
  called a method on `null` and turned a blocked attack into a fatal error. The
  construction moved to `core/security.php:54`, immediately after `$db` and
  `PREFIX_DB`, which is what this plan's **Code** section already describes:
  "because `$db` is only created at `core/security.php:49`, the object is
  constructed after that line". The `require_once` stays at
  `core/system.php:130`, so the class is loaded before the file that uses it.
- **`kind` names the originating feature, one value per module.** `account`,
  `admins`, `contact`, `forum`, `help`, `money`, `order`, `privat`, `recommend`,
  `security`, `shop`, `newsletter`, and `test` for the batch-5 send. The one
  site that is not a module is `addAdminMail()`, which serves two purposes with
  one message: it passes `comment` or `content` depending on its own `$iscmt`
  flag, so the stage-2 admin filter and the per-`kind` retention can tell a
  comment notice from a new-content notice without re-deriving it.
- **`addAdminMail()` keeps the `_admins.modules` rewrite for now.** The removal
  table lists it, but its replacement — "the admin module normaliser, where a
  write belongs" — is not work any stage in this plan schedules, and this batch
  is a call-site migration. It is left in place and recorded as a blocker.
- **The newsletter body is parsed once per batch, not once per recipient.**
  `$prs->filterContent()` sat inside the `foreach`, so it re-parsed the same
  body for every address in the slice. The migrated line hoists it; the value is
  identical for every recipient, which is also why stage 3 can store it once

- **`CONTRIBUTING.md` needed a different naming example, not a deletion.** Its
  verb-prefix table illustrated `add` with `addMail()`'s signature; the example

  `$mailer->addQueue()` would not serve — the table lists functions, not methods.

### Deviations from the plan

- **`filterText()` is not applied to the subject or the addresses.** Today
  `addMail()` runs the recipient, the sender and the subject through
  `filterText()` (`core/security.php:1016-1018`), which HTML-escapes,
  `strip_tags`, `urldecode`s and censors them. That is an *input* filter: it
  turns `Иван & Co` into `Иван &amp; Co` in a MIME subject line, corrupts a
  local part containing `&`, and depends on `isAdmin()` and the request-scoped
  `$conf`, none of which exist in the stage 2 drain. `Mail` replaces it with the
  sanitiser the plan specifies — control characters stripped from header text,
  `FILTER_VALIDATE_EMAIL` for addresses. This changes subject bytes for subjects
  containing `& < > " '` or a `%xx` sequence, and the plan's own criterion is
  that byte parity is *not* the test.
- **The `From` display name is no longer wrapped in quotes when it is encoded.**
  RFC 2047 §5 forbids an encoded word inside a quoted string, so today's
  `From: "=?utf-8?b?..?=" <addr>` is not decoded by a conforming client. A
  non-ASCII name is now emitted as a bare encoded word; a plain-ASCII name is
  emitted as a proper quoted string with `"` and `\` escaped, which today's code
  did not do and which a site name containing a comma or a dot requires.
- **`Reply-To` loses its redundant display name.** Today it is
  `"addr" <addr>`; it is now `<addr>`. Same address, same meaning, one form.
- **A pure-ASCII subject is no longer base64-encoded.** `mb_encode_mimeheader()`
  encodes only what needs encoding. Legal either way, and it keeps ASCII
  subjects readable in raw sources and logs.
- **The header block is returned without a trailing line break.** Each transport
  supplies its own separator — `mail()` wants headers with no trailing newline,
  SMTP `DATA` wants a blank line before the body. Batch 2 onward relies on this.
- **`mail()` is handed CRLF headers where `addMail()` used bare LF.** The stage's
  own criterion separates the two: header composition and semantics are
  unchanged, encoding and line handling deliberately are not. CRLF is what SMTP
  requires and what PHP's own documentation asks for on Windows; a local MTA
  reached through `sendmail_path` accepts both.
- **The result of `mail()` is now read.** `addMail()` discarded it, so a refused
  message was invisible; `addQueue()` returns `false`, `getError()` carries the
  captured warning text and `Logger::addSite()` records the failure with the
  transport and the masked recipient.

- **"All rows are usable with the script disabled" cannot hold on this screen,
  and not because of the new hook.** `.sl-tab-panel { display: none }` with only
  the first panel visible (`templates/admin/assets/css/theme.css:3780-3786`)
  means that without JavaScript the config module shows tab 0 and nothing else —
  the mail tab is as unreachable as the SEO and cache tabs already were.
  Measured in a browser with scripts blocked: the SMTP row and the `sitename`
  input are equally invisible. The new hook is progressive on its own terms, the
  screen around it is not, and fixing the tab mechanism is outside this batch.
- **The `mtemp` template stays on the mail tab and keeps its own POST name.**
  It belongs to `config/global.php`, not to `config/mail.php`, and the plan
  leaves it where it is. It is therefore the one row on the tab that is not part
  of the mail section.

## Facts (measured 2026-07-27)

- There is exactly **one** real send point: `mail()` inside `addMail()`
  (`core/security.php:1047`). Everything else routes through it, so both the
  transport and the queue can be introduced behind that single function.
- `addMail()` **ignores the result** of `mail()` and suppresses its warnings
  with a local error handler (`core/security.php:1044-1048`). A refused or

## Problems this causes

1. **No choice of transport.** Delivery is whatever `mail()` resolves to. There
   is no way to point the installation at an authenticated SMTP relay, which is
   what most hosting now requires for mail to arrive at all.
2. **Requests wait for delivery.** A comment costs 26.6 s here; on production
   the per-message cost is lower but still multiplied by the recipient count.
3. **Failures are silent.** The return value is discarded, warnings suppressed;
   nobody learns that a password reset never left the server.
4. **Two mechanisms.** The newsletter has its own ad-hoc queue, everything else
   has none.
5. **No retry.** A temporary outage loses every message sent during it.
6. **Unusable throughput.** Four messages per hour means a mailing to the
   current subscriber list runs for nearly two days.
7. **No visibility.** There is no way to see what is pending, what failed and
   why.

## Naming

The subsystem is called **mail**, everywhere, with no second vocabulary layered
on top:

- table `{prefix}_mail`, singular, like `{prefix}_comment` and
  `{prefix}_message`;
- class `Mail` in `core/classes/mail.php`, singular, like every existing service
  class (`Cache`, `Parser`, `Editor`, `Template`, `Logger`, `Geoip`, `Captcha`,
  `Oauth`);
- config section `$conf['mail']` from `config/mail.php`;
- the word *queue* survives only inside method names, where it is the noun the
  verb acts on (`addQueue()`, `updateQueue()`, `deleteQueue()`).

`.rules/global.md` required class names of 8-24 characters, which `Mail` and
five of the eight classes already in `core/classes/` did not meet. The rule now
reads 4-24, so the short name is compliant rather than excepted. `Pdo` stays the
one name below the floor.

There is **no** separate queue class. An earlier draft called it `MailQueue`;
that name is gone. Queue mechanics and transport live in the same `Mail` object
because they are the same subsystem, and splitting them would produce exactly
the layering this project does not want.

## Self-sufficiency

SLAED CMS must work immediately after the files are copied to a server. No
Composer install, no package manager, no SDK, no framework, no third-party
library. Mail is part of the standard distribution and is written entirely
against PHP itself.

This is not an aspiration to be introduced by this plan — it is the current
state, and the plan must not be the thing that breaks it:

- `composer.json` declares no runtime **package** at all — only the platform:
  `php >=8.4`, `ext-mbstring`, `ext-pdo`, `ext-json`. Extensions are not
  packages, and declaring them is what the self-sufficiency rule asks for;
- `php-cs-fixer`, `phpstan` and `phpunit` sit in `require-dev`, and
  `autoload-dev` maps only `Tests\`. The runtime never loads anything from
  `vendor/`;
- `/vendor/`, `node_modules/` and `/composer.phar` are in `.gitignore` and are
  not part of what ships;
- classes are loaded by explicit `require_once` in `core/system.php`, so there
  is no autoloader to accidentally reach into a package;
- front-end dependencies (`altcha`, `editors`, `highlightjs`, `htmx`,
  `tablesort`) are vendored under `plugins/`, not fetched from a CDN.

Therefore, for this subsystem:

- **forbidden** — PHPMailer, Symfony Mailer or any equivalent; a new entry in
  `composer.json require`; anything that makes `composer install` a
  precondition for sending mail; provider SDKs; loading code or configuration
  from an external host; making delivery depend on a third-party API;
- **written here** — PHP `mail()`, Sendmail, SMTP, SMTP AUTH, STARTTLS and
  implicit SSL, MIME header assembly, UTF-8 subject and body encoding, SMTP
  response parsing, timeouts, error logging.

Hosted senders — Brevo, Mailgun, Amazon SES, Postmark, Resend and the rest — are
reached through the SMTP credentials every one of them publishes. That is the
integration, and it needs no code specific to any of them. A provider that only
offers an HTTP API is out of scope by this principle, not by oversight.

### Reuse before writing

Self-sufficiency is not an argument for hand-writing what already exists. It
rules out packages, not solutions. Two sources are already available and both
must be exhausted before a line of new code:

**PHP's own functions.** These are bundled, tested by millions of installations,
and are exactly the places where hand-rolled code grows subtle bugs:

- `mb_encode_mimeheader()` — RFC-2047 subject encoding including correct folding
  of long headers. The current `'=?'._CHARSET.'?b?'.base64_encode(...).'?='` at
  `core/security.php:1018` does not fold, so a long non-ASCII subject already
  produces an over-length header line. Do not reimplement this;
- `filter_var($val, FILTER_VALIDATE_EMAIL)` — address validation, already used
  in `core/classes/oauth.php:267`. No regular expression of our own;
- `stream_socket_client()`, `stream_set_timeout()`,
  `stream_socket_enable_crypto()` — the whole SMTP socket layer, including
  STARTTLS and implicit SSL, with certificate verification handled by the
  stream context rather than by us;
- `proc_open()` with a pipe set — the Sendmail transport, giving a readable exit
  status that a `popen()` call would hide;
- `random_bytes()` / `bin2hex()` — `lockid`;
- `base64_encode()`, `quoted_printable_encode()` — body encoding.

**SLAED's own helpers.** Consolidation matters more here than anywhere, because
a second mechanism for an existing job is the definition of the zoo this project
avoids:

- `Logger::addSite()` for failures — not a new log file;
- `setConfigFile()` for writes to `config/mail.php` — not a bespoke writer;
- `getSiteToken()` / `checkSiteToken()` for the test send — not a new token;
- `getRandomString()` (`core/system.php:3546`) where a readable random string is
  needed;
- the existing admin form fragments — `input`, `select`, `textarea`,
  `label-hint`, `alert`, `getTplRadioGroup()` — for every row of the mail tab.
  No new fragment and no CSS class from PHP;
- the existing scheduler job mechanics — lock, heartbeat, manual trigger — for
  the drain;
- the value-driven row visibility hook belongs **next to** the existing
  `data-sl-tab-show` implementation in `plugins/system/slaed.js:679-681`, in the
  same style and the same file, not in a new script. **Taken in stage 1 batch 5:**
  `setFieldShows()` sits immediately above `setTabs()` (`:765`) and is registered
  in the same two places (`:1339`, `:1358`).

What genuinely has no ready-made counterpart is the SMTP conversation itself:
PHP ships a socket layer but no SMTP client. That, and only that, is written
from scratch — which is also why its response parsing, timeouts and failure
paths get their own tests.

### PHP extensions this relies on

Extensions are not libraries and are allowed by the principle above, but each one
is a real assumption and none of them may be silent.

**`mbstring` — a hard requirement, declared.** The plan uses
`mb_encode_mimeheader()` for subject encoding and folding. That is not a new
dependency: the codebase already calls `mb_strtolower()`, `mb_substr()`,
`mb_strlen()` and `mb_strpos()` unconditionally across eight files, so an
installation without `mbstring` is already broken well before it sends mail.
Writing a private MIME-folding fallback only for this subsystem would therefore
buy nothing while adding exactly the kind of hand-rolled code this plan avoids.
The honest resolution is to state the requirement: `ext-mbstring` in
`composer.json`, in the README requirements, and in the installer check beside
the PHP version test.

**`openssl` — optional, probed.** SMTP with STARTTLS or implicit SSL needs it;
`stream_socket_enable_crypto()` does not exist without it. Unencrypted SMTP,
Sendmail and PHP `mail()` remain fully available. The mail tab reports its
absence next to the encryption selector instead of offering a choice that will
fail.

**`proc_open` — optional, probed.** The Sendmail transport cannot run without it,
and shared hosting routinely lists it in `disable_functions`. The mail tab
reports Sendmail as unavailable rather than letting the transport fail at send
time, and the other two transports are unaffected.

Both optional checks are capability probes, never a hard failure at boot. Missing
`mbstring` is different in kind: it is a stated requirement, and the installer
refuses rather than degrading, exactly as it does for the PHP version.

Derived from all 36 tables in `setup/sql/table.sql`, not assumed:

  `ENGINE={engine} DEFAULT CHARSET={charset} COLLATE={collate}`.

## Target design

### Transports

Three transports, all inside `Mail`, each one private method:

- **PHP Mail** — the current `mail()` call, kept as the default so an
  installation that upgrades and configures nothing keeps behaving exactly as
  before;
- **Sendmail** — a pipe to the configured binary through `proc_open()`, so the
  exit status is readable. `mail.sendmail` holds **the path only**; every
  argument (`-t`, `-i`, `-f<sender>`) is supplied by the class and the command is
  passed to `proc_open()` as an **array**, so no shell is involved. A config
  value that carried arguments would be a config value that carries a command,
  and an administrator with panel access would gain shell execution. The path is
  validated as an existing executable file before use, `proc_open()` itself is
  probed, and a non-zero exit status is a delivery failure with the process
  stderr recorded;
- **SMTP** — a raw socket dialogue supporting plain, STARTTLS and implicit SSL,
  with optional `AUTH`.

No interface, no adapter, no abstract base, no per-transport class. A transport
is chosen by one `match` on `$conf['mail']['transport']` and handled by one
private method. The extension point that an interface would have provided is
already there: adding a fourth transport is adding a fourth arm and a fourth
method.

The SMTP method must handle, explicitly:

- connection with a timeout on both connect and every read, so a dead relay
  cannot hang a request;
- `EHLO` with a fallback to `HELO`, and re-`EHLO` after a successful STARTTLS;
- **multi-line replies** — SMTP continuation lines use `250-` and only the final
  line uses `250 `; reading a single line is the classic way this breaks;
- STARTTLS via `stream_socket_enable_crypto()`, and implicit SSL via the
  `ssl://` scheme, with certificate verification left on;
- `AUTH LOGIN` and `AUTH PLAIN`, chosen from the advertised mechanisms rather
  than assumed;
- `QUIT` and socket close on every exit path, including failures;
- one connection reused for a whole drain run, which is what makes the queue
  fast rather than merely asynchronous.

### The SMTP hazards, named

Writing the client ourselves is the decision this project has taken, and the
argument against it is real: a protocol bug affects every message, silently.
That risk is only acceptable because the failure modes are few and enumerable
rather than open-ended. Each of these is an implementation requirement with a
test, not a note:

- **Dot-stuffing.** A body line beginning with `.` must be sent as `..`, and the
  terminating `.` on its own line must be the only bare one. Normally this is the
  most common defect in hand-written clients; here the base64 body cannot produce
  such a line, so the rule applies only to the terminating sequence. It is still
  implemented and tested, because the transport must stay correct if a future
  message part is not base64.
- **Line length.** RFC 5321 caps a line at 1000 octets including CRLF. This is
  the live defect, not a hypothetical: `base64_encode()` returns a single
  unwrapped line, so a 5 KB message is one 6720-octet line today. Wrap at 76 with
  `chunk_split()` and fold headers through `mb_encode_mimeheader()`.
- **Line endings.** Every line terminates with CRLF on the wire, regardless of
  what the stored body uses. A lone LF is not a line ending in SMTP.
- **Multi-line replies.** `250-` continues, `250 ` ends. Reading one line and
  moving on desynchronises the whole dialogue.
- **TLS verification stays on.** `stream_socket_enable_crypto()` with peer and
  peer-name verification enabled through the stream context; an option to
  disable it is not offered, because it exists mainly to make a broken
  configuration look like it works.
- **Timeouts on every read**, not only on connect, so one unresponsive relay
  cannot occupy a worker indefinitely.
- **Header injection.** Recipient, sender, sender name and Reply-To are rejected
  on any `\r` or `\n` before they reach a header or the `MAIL FROM`/`RCPT TO`
  envelope.
- **Unexpected codes.** Any reply outside the expected set aborts with the
  server's own text preserved, rather than being treated as success.

If this list ever stops being enumerable, the decision to write the client
ourselves should be revisited — that is the honest condition under which a
vendored library becomes the better trade.

### Header injection

Making the sender name, sender address and Reply-To configurable turns header
assembly into a security boundary that did not exist before. Every value that
reaches a header — recipient, sender, sender name, Reply-To, subject — is
stripped of `\r` and `\n` before use, and a value that still fails validation
aborts the send rather than being silently cleaned. The subject is protected by
its base64 MIME encoding, but the addresses are not, and the SMTP envelope
(`MAIL FROM`, `RCPT TO`) is not.

Campaign policy is a different question from delivery, so it lives in

"Empty" applies to a specific subset, not to the file. `transport` defaults to
`php`; the fields that inherit site data (`fromname`, `frommail`, `replyto`) and
the SMTP credentials (`host`, `user`, `pass`) ship empty; everything else — the
Sendmail path, the port, the timeout and every delivery, queue and campaign
limit — ships with the explicit values listed above.

The compatibility claim is about **stage 1 and the transport only**: with
`transport = php` the messages go out the same way they do today, synchronously,
and nothing changes until an administrator selects a different transport.

Stage 2 changes delivery deliberately and without waiting to be asked — that is
the point of it. `addQueue()` starts storing rather than sending, the drain job
ships enabled, and mail becomes asynchronous on every installation that takes the
upgrade. That is a behaviour change, it is intended, and it belongs in the
release notes rather than being softened here.

The queue keys live here rather than beside `newsletter.count`, because they
govern this subsystem and not the newsletter.

The SMTP password is stored in `config/mail.php` like the database password in
`config/db.php` and the master secret in `config/security.php` — the same
mechanism, no new architecture. These are PHP files returning an array, so
fetching one over HTTP produces no output. The password is never rendered into
the admin HTML and an empty password field never overwrites the stored value.

### Storage

```

```

`KEY lockid` is not optional: the claim is a conditional `UPDATE` followed by a
`SELECT ... WHERE lockid = ?`, and without the index that read scans the table on
every batch. `KEY kind_ref_status` serves the campaign queries — progress,
failure rate, the circuit breaker — which filter by `kind` and `ref` and would
otherwise scan. Both were missing from an earlier revision.

Naming decisions, against the standards above:

- `title`, not `subject` — every other table calls it `title`;
- `time`, not `created` — every other table calls the creation stamp `time`;
- `ntime`, not `next` — keeps the `etime`/`ltime`/`endtime` family and avoids the
  SQL keyword entirely;
- `status`, not `state` — `status` is the project word for this;
- `lockid CHAR(32)`, not `BINARY(16)` — the schema stores random identifiers as
  hex and has no binary column anywhere;
- `error` is kept: single word, lowercase, and non-reserved in both MySQL 8 and
  MariaDB. It is backticked in DDL like every other column.

`ntime` is `NOT NULL` and defaults to the queue time. A nullable `ntime` would
force the claim query into `ntime IS NULL OR ntime <= NOW()`, and that `OR`
destroys range access on `hold_status_prio_ntime`. With the column always set, the
claim is one clean range scan.

`prio` keeps a bulk mailing from delaying a password reset: the drain orders by
`prio`, then `ntime`, then `id`. `kind` drives the admin filter and cleanup.
`locked` carries its own index so releasing stale claims is not a table scan.

`status`: `0` pending, `1` **accepted**, `2` failed.

### Say accepted, not delivered

A successful transport call means a relay took the message. It does not mean a
mailbox received it, and without an inbound channel we cannot know that. The
vocabulary is fixed so the admin screens do not promise more than the system
knows:

| Term | Meaning |
|---|---|
| **accepted** | the transport handed the message over without error |
| **failed** | the transport refused it, synchronously |
| **bounced** | a permanent per-recipient verdict, from `RCPT TO` or an inbound bounce |
| **delivered** | unknown to this system; the word is not used in the UI or in counters |

`status = 1` is therefore "accepted". The mailing counter beside it counts
acceptances, and the rate the circuit breaker watches is a **hard-failure** rate,
not a bounce rate, because at that moment only some of the failures are known to
be per-recipient.

### Two fields are bounded, and the bound matters

`title` and `error` are `VARCHAR(255)`, and both can be overrun by real input:
a long subject, or a multi-line SMTP response concatenated into one string. Under
strict SQL mode an oversized write **fails**, which for `error` means the row
that just failed to send also fails to record why — and stays claimed until the
lock expires.

- `title` length is validated at enqueue, where the caller can still be told;
- `error` is truncated to fit, counted in characters rather than bytes so a
  multibyte response is not cut mid-character, with control characters stripped;
- the full server response goes to `Logger`, which has no such limit;
- recording a failure must never itself be able to fail — that path is tested.

The table follows the `{engine}` placeholder like every other table. The queue
requires a transactional engine so a job can join the caller's transaction; this
installation is InnoDB throughout and the migration must keep it that way.

### Why `ref` exists

A queue row per recipient is correct for transactional mail, where every message
differs. For a mailing it is not: one newsletter to 100 000 subscribers with a
50 KB HTML body would write that same body 100 000 times — about **5 GB** for a
single send, and again for the next one.

So the body is stored **once**:

- `ref = 0` — the row is self-contained, `body` holds the message. This is every
  transactional mail and the default;
- `ref > 0` with `kind = 'newsletter'` — `body` is empty and the drain reads the
  message from `_newsletter.body` for that id, rendering it once per batch
  rather than once per row.

One column, one branch in the drain, no second table and no join in the claim
query. `ref` is a plain `INT UNSIGNED NOT NULL DEFAULT 0`, matching how `pid`,
`lid` and `mid` are declared elsewhere in the schema.

The resolution is keyed on `kind`, so adding a second bulk source later is a
second arm, not a redesign. A missing or deleted `ref` target fails the row into
`failed` with a stated reason instead of sending an empty message.

### What is built when, and where

The message body is composed **by the caller**, and the IP and browser block is
appended by `Mail` at `addQueue()` time when the call passes `client => true` —
inside the originating request, where that data is meaningful. From stage 2 that
body is what goes into the queue row, and the drain must never append its own
request data, otherwise every notification would carry the scheduler's IP.

The **headers are built inside `Mail`, at send time**. `title` carries the raw
subject and the transport encodes it and assembles the header block from
`$conf['mail']` and the caller's `sender` and `prio`. Storing an encoded subject
would inflate it by roughly a third and silently truncate at 255 bytes.

### Base64 stays — it is a deliverability decision, not an accident

`addMail()` sends the body as `Content-Transfer-Encoding: base64` with
`base64_encode($message)`, and encodes the `From` display name as an RFC 2047
"B" word (`core/security.php:1038-1039`). That is kept, deliberately, and the new
transports keep it:

- the body is 8-bit safe end to end, so no intermediate MTA can mangle UTF-8;
- there is no quoted-printable soft-break behaviour to get wrong;
- the base64 alphabet is `A-Za-z0-9+/=`, so a body line **can never begin with a
  dot**. Dot-stuffing, the single most common defect in hand-written SMTP
  clients, cannot corrupt the body at all;
- once wrapped, line length is bounded by construction rather than by inspection.

Those last two points matter for the decision to write the SMTP client
ourselves: they remove two of the eight named hazards from the body path
entirely, leaving them only for the terminating sequence. The encoding choice
therefore makes the hand-written client materially safer, not riskier.

**What is missing today is the wrapping.** `base64_encode()` does not insert line
breaks — it returns one line. A 5 KB HTML message becomes a single 6720-octet
line, measured. RFC 2045 recommends 76 characters and RFC 5321 caps a line at
1000 octets, so the current output already violates the transport limit; PHP
`mail()` and a local MTA tolerate it, and a raw SMTP dialogue will not. The fix is
`chunk_split(base64_encode($body), 76, "\r\n")`, which the project already does
correctly for keys in `core/classes/oauth.php:194`.

The same gap exists in the headers. The hand-built encoded word
`'=?'._CHARSET.'?b?'.base64_encode($conf['sitename']).'?='` produces 112
characters for a realistic site name, against the RFC 2047 limit of 75 per
encoded word. `mb_encode_mimeheader($name, 'UTF-8', 'B')` emits the **same B
encoding** and folds it across lines correctly, which is why it replaces the
hand-built version: the scheme is unchanged, only the conformance improves.

### Identity: From, Reply-To and the envelope sender

`addMail()`'s second argument, `$smail`, currently serves as `From`, `Reply-To`
**and** `Return-Path` at once (`core/security.php:1039-1041`). Adding configured
identity fields makes that ambiguous, and guessing here breaks SPF and DMARC
alignment, so the resolution order is fixed:

| Field | Source | Fallback |
|---|---|---|
| `From` address | `mail.frommail` | the caller's `sender` |
| `From` display name | `mail.fromname` | `$conf['sitename']` |
| `Reply-To` | `mail.replyto` | the caller's `sender` |
| Envelope sender | whatever `From` resolved to | — |

The envelope sender always follows the resolved `From`, never the caller's
argument independently, so the address the receiving side authenticates is the
address the message claims. `mail.frommail` therefore exists precisely so an
installation can align outgoing mail with a domain it is authorised to send for,
while a module that wants replies to reach it keeps doing so through `Reply-To`.

### Return-Path is not ours to write

`addMail()` emits a literal `Return-Path:` header today
(`core/security.php:1041`). That is wrong: `Return-Path` is written by the
**receiving** MTA from the envelope sender, and a self-supplied one is either
ignored or treated as a forgery signal. It is removed, and the envelope sender is
set through the mechanism each transport actually provides:

- **SMTP** — `MAIL FROM:<sender>` in the dialogue;
- **Sendmail** — the `-f` argument, passed as its own array element, never
  interpolated into a string;
- **PHP `mail()`** — the fifth parameter as `-f<sender>`, attempted only when the
  address passes validation. Hosts commonly refuse it through
  `mail.force_extra_parameters` or a restricted `sendmail_path`, so a rejection
  is expected and non-fatal: the message is sent without it and the fallback is
  recorded once, not per message.

No transport writes `Return-Path` as a header under any circumstances.

### No legacy surface

The old contract is not preserved. There is no compatibility wrapper, no
pass-through alias and no transitional signature — the mechanism is replaced
whole, and every caller moves to it once. This follows `.rules/global.md`
directly: a legacy helper is renamed and its call sites migrated rather than
wrapped, and a chosen full migration gets the new contract without a fallback
layer.

**`addMail()` is deleted.** It cannot survive as a facade even if one wanted it
to, because its signature cannot express what the queue needs:

- there is no `kind`, and it is not derivable — only the call site knows whether
  it is sending a password reset or a newsletter, and `kind` drives priority,
  retention and every admin filter;
- `$id = 0|1` is a magic integer meaning "append the visitor's IP and browser";
- `$smail` conflates `From`, `Reply-To` and the envelope sender, which the
  identity table above now separates;
- `$pr` carries `$pr ?: 3` defaulting inside the function.

Adding a seventh parameter for `kind` would be exactly the crutch this
consolidation removes. The 26 call sites migrate instead, once, in stage 1 —
before the queue exists — so stage 2 changes only what happens inside the object.

**The service is a global instance, like `$db` and `$tpl`.** `core/system.php`
creates `$mailer = new Mail($db, $conf)` and call sites use it directly:

```php
$mailer->addQueue([
    'kind'   => 'account',
    'email'  => $addr,
    'title'  => $subj,
    'body'   => $text,
    'sender' => $conf['adminmail'],
    'prio'   => 1,
    'client' => true,
]);
```

The name is `$mailer` rather than `$mail` because `$mail` is already a local
variable holding an email address across `modules/account`, `modules/order`,
`modules/money` and others — a global of that name would shadow them.

`client => true` replaces the magic `$id`: it asks for the originating IP and
browser block by name instead of by integer.

**The return value means what it says.** In stage 1 `addQueue()` delivers
directly and returns the transport result. In stage 2 it returns **accepted into
the queue**, and no caller can learn the delivery outcome synchronously by
design — the outcome lives in the queue row, the log and the admin view. Because
the migration already happened in stage 1, that change touches no call site.

### Code

One class, `Mail` in `core/classes/mail.php`, reached through the global
`$mailer` the way `$db`, `$tpl` and `$prs` already work. `core/system.php`
requires the file between `$conf = getConfig()` (line 126) and
`require_once core/security.php` (line 130). Because `$db` is only created at
`core/security.php:49`, the object is constructed after that line, and the
transport half works with no database at all.

Public surface:

- `addQueue()` — accept one message; called inside the caller's transaction
- `getError()` — description of the last failure
- `getBatch()` — claim a batch under a lock
- `setResult()` — record success or failure, increment `tries`
- `updateQueue()` — full drain run, called by the scheduler task
- `deleteQueue()` — prune rows past the retention window
- `getList()` — admin listing with `kind`/`status` filters
- `getStats()` — pending, accepted and failed counts
- `checkAddress()` — the verification ladder for one address, always failing open

Private: one method per transport, the header builder, the address sanitiser and
the SMTP dialogue helpers. Sending is private from stage 2 onward — once a queue
exists there is no legitimate reason for anything outside the class to deliver a
message directly, and leaving a public send method would be the crutch through
which a caller quietly goes around the queue.

This is a large class — the SMTP dialogue alone is the bulk of it — and that is
the accepted trade for having one place where mail leaves the system. What it
must not become is a hierarchy.

**Audience expansion is one concept, not three.** `addAdminMail()` and
`updateNewsletter()` do the same job — resolve a set of recipients and enqueue a
message for each — and after this work they are two implementations of that one
shape, both ending in `$mailer->addQueue()`. Neither sends anything itself, and
neither keeps a private delivery path. `addAdminMail()` also loses the
`_admins.modules` rewrite it performs today (`core/system.php:3728-3730`): a
mail function has no business normalising admin records, and that write moves to
the code that owns admin modules.

### Errors

- every failure produces a `Logger::addSite()` entry with the transport, the
  phase, the code, the queue row id and the recipient **masked** — `a***@dom.tld`
  — because a log is read by more people than a queue row and a full address list
  is exactly the kind of thing that should not accumulate in a file with a long
  retention. The unmasked address stays in the queue row, which the admin view
  already gates;
- the SMTP password, the `AUTH` payload and anything that could contain them are
  never logged, at any level;
- server responses are stripped of control characters before being logged or
  stored, so a hostile relay cannot inject line breaks into the log format;
- nothing is suppressed without being recorded. The PHP-mail transport keeps an
  error handler around `mail()`, but that handler now **captures** the warning
  text instead of discarding it — an unhandled warning inside a pseudo-cron
  request would leak into the response body, so removing it is not an option;
- `getError()` holds the last message for the caller and for the test send;
- from stage 2 the same string is what lands in the `error` column.

### Delivery

- Claiming a batch is **atomic**: a single conditional `UPDATE` stamps `locked`
  and `lockid` on the rows it takes and moves their `ntime` behind the lock
  window, and only then are they read back by `lockid`. Two concurrent runs
  therefore cannot claim the same row — the second one no longer finds them due.
  The predicate is `hold = 0 AND status = 0 AND ntime <= NOW()` and nothing else,
  because that is exactly what `hold_status_prio_ntime` leads with; a marker
  column in it was measured to cost the index and a filesort (see **Progress**).
- A stale claim — a run that died before recording a result — becomes due again
  when the lock window passes, and `deleteClaim()` clears the `locked`/`lockid`
  markers it left behind; `KEY locked` backs that sweep.
- A temporary failure increments `tries`, stores `error` and sets `ntime` to the
  backoff deadline; the row is skipped until then.
- After the attempt cap the row becomes failed and is left for the admin view.
- Delivery is **at-least-once**: if a run dies after the transport succeeded but
  before the row is marked accepted, that message is sent again. Exactly-once is not
  achievable here and is not attempted.
- A delivery failure never rolls back the business transaction that queued it —
  the comment, order or registration is already committed.
- An SMTP drain opens one connection per run, not one per message.

### Scheduler

The drain runs as a system job beside the existing `cachegc`, `dbbackup`,
`filescan`, `newsletter` and `sitemap` jobs, reusing the same lock, heartbeat
and manual-trigger mechanics. Pruning runs in the same task.

The job is part of the design, not an implementation choice, so it is written
down here in the shape `config/scheduler.php` already uses:

```
'maildrain' => [
    'title'        => 'Mail delivery',
    'type'         => 'system',
    'active'       => '1',
    'system'       => 'maildrain',
    'schedule'     => '*/5 * * * *',
    'priority'     => '2',
    'lock_timeout' => '900',
    'manual'       => '1',
    'settings'     => [],
],
```

`priority` is `2`, deliberately **below** the newsletter producer's `1`, and the
two are not expected to run in the same tick. The scheduler runs **one** due job
per trigger (`getSchedulerNextJob()`, `core/system.php:517-522`) and breaks
priority ties by job name (`core/system.php:302`) — with an equal priority
`maildrain` would sort ahead of `newsletter` alphabetically, which is the
opposite of what the wording in an earlier revision claimed. Since the drain runs
every five minutes and expansion is itself a scheduled, resumable job, nothing
depends on the two sharing a tick.

The upgrade step inserts the job **and enables it**; a queue behind an inactive
job is a site with no mail, and `newsletter.active = '0'` in the shipped config
shows how easily that happens.

### The rate limit has to outlive one run

`mail.rate` as "messages per minute" means nothing if the window lives in a
variable: two runs a minute apart, or two racing pseudo-cron triggers, each stay
under the cap and together double it.

- the scheduler lock already excludes concurrent runs of the same job, and that
  is a precondition, not the mechanism;
- the limiter state — the window start and the count spent in it — is persisted
  with the scheduler job state, so a new run resumes the current window instead
  of opening its own;
- a manual trigger from the admin uses the same limiter. An operator pressing
  the button is not a reason to exceed a provider's cap;
- the drain stops on the cap the same way it stops on the time budget: it
  finishes the row in hand and leaves the rest claimed-free for the next run.

### Queued in an AJAX request, drained when?

`addSchedulerTrigger()` is emitted while a full page is built
(`core/system.php:2046`, inside `setHead()`). `addComment()` answers a fragment
and never calls `setHead()` (`core/user.php:265-308`), so **a comment
notification queued over HTMX does not start a drain**. On a quiet site it waits
for the next visitor to load a whole page.

The contract, stated rather than left to chance:

- with a real OS cron the question does not arise, and that stays the
  recommendation for any site that can have one;
- under pseudo-cron the fragment response carries the scheduler trigger as a
  response header that the shared script acts on, so an HTMX write wakes the
  drain exactly as a page load would;
- where neither is available the honest SLA is written into the admin: **mail is
  sent no earlier than the next scheduler-triggering request**, and the queue
  view says how long ago the drain last ran.

Two things follow from how the scheduler actually runs here, and they are part
of the design, not of the risk list:

- the job ships with `active => '1'` in `config/scheduler.php`, and the upgrade
  step enables it on existing installations. A queue behind a disabled job is a
  site with no outgoing mail;
- under pseudo-cron the drain executes inside a web request. `mail.batch` must
  therefore be chosen against `max_execution_time`, the job's `lock_timeout` and
  `scheduler.cron_timeout = 600`. The per-message cost is exactly the number
  that still has to be measured properly, so `mail.batch` ships at a
  deliberately low 25 and is raised only against a real figure from a host with
  a working transport. A reused SMTP connection raises the real ceiling
  considerably, but the default does not assume it. The drain also stops early
  when it approaches the time budget rather than being killed mid-row.

### Two axes of scale

SLAED is sized along two independent dimensions, and they pull in opposite
directions. The design has to satisfy both.

**Many users per installation.** 11 845 accounts here, 100 000 and above
expected. Because a mailing targets the whole user table, one send is one row per
account, and everything in the queue is multiplied by that number: storage,
drain time, retention.

**Many installations.** 100 000 hosts, each configured by someone else, most of
them never touched after install. This is the harder constraint, because it means
**no per-host tuning is available**. A setting that has to be raised for the
system to work is a setting that will not be raised on the overwhelming majority
of sites. Consequences that are part of the design, not of the risk list:

- every default must be correct on the weakest plausible host — modest
  `max_execution_time`, no shell, no CLI cron, shared hosting limits. That is why
  the transport defaults to PHP `mail()` and `mail.batch` to 25;
- **pseudo-cron is the primary mode for a large share of installations**, not a
  fallback for small ones. CLI cron is a capability some hosts have, and the
  drain must be excellent without it;
- **every capability is probed, never assumed.** `openssl` for TLS is one;
  `proc_open()` is another and is routinely listed in `disable_functions` on
  shared hosting, so the Sendmail transport checks for it and reports its absence
  in the mail tab exactly like a missing `openssl`. `set_time_limit(0)` may be
  refused, so the CLI drain treats it as best-effort and still honours its own
  time budget;
- **diagnosis has to be self-service.** Nobody can support 100 000 hosts
  individually. The test send with the verbatim server response is what turns a
  support request into a setting the administrator can fix themselves;
- **migrations run 100 000 times.** The upgrade SQL has to be idempotent and
  re-runnable, tolerate a partially applied prior state, and behave on both MySQL
  and MariaDB — which is what the existing `addcol`/`addidx` procedure helpers in
  `table_update6_3.sql` already exist for. A DDL that fails halfway on one engine
  variant is not one bug, it is 100 000 of them.

### Draining at scale

Pseudo-cron is the mode most installations will run in, and the arithmetic of a
large user table under it is unforgiving. A mailing to 100 000 subscribers at
`mail.batch = 25` is 4000 drain runs; on the hourly schedule the newsletter job
uses today that is **166 days**, and even at one run per minute it is close to
three. `docs/PERFORMANCE.md` already recommends `pseudo = 0` with a real OS cron
for exactly this reason.

The drain is therefore built to be time-boxed rather than count-boxed, and to
behave differently depending on how it was started:

- it loops on batches until either the queue is empty or its time budget is
  spent, instead of sending a fixed count and exiting;
- the budget comes from the context: under pseudo-cron it is a fraction of
  `max_execution_time`, and the run ends politely well inside it; started from
  CLI cron it is the job's `lock_timeout`, with `set_time_limit(0)` and a much
  larger effective batch;
- one SMTP connection spans the whole run, not one batch, and is re-opened only
  if the server drops it;
- `mail.rate` caps messages per minute. Every hosted provider enforces a
  send rate — Amazon SES defaults to 14/s, others publish their own — and
  exceeding it produces throttling responses that look like random failures and
  burn the retry budget. The cap is a first-class setting, not something to
  discover in production;
- progress is written per batch, so a run killed mid-mailing resumes from where
  it stopped rather than restarting.

At 100 000 recipients the queue also stops being small: retention has to be
applied per `kind`, because keeping 30 days of delivered newsletter rows means
millions of rows for no operational value, while the same window for
transactional mail is what makes "did the password reset go out" answerable.
`deleteQueue()` therefore prunes with `kind` in the predicate, and the shipped
default keeps bulk rows far shorter than transactional ones.

### Above 10 000 users the list itself is the risk

Measured on this installation, 2026-07-27. Registrations span **2005 to 2024**,
and last-visit distribution across 11 845 accounts is:

| Last visit | Accounts |
|---|---|
| within 1 year | 9 |
| 1-3 years | 45 |
| 3-5 years | 57 |
| **older than 5 years** | **11 734** |
| never | 0 |

One syntactically invalid address. So the "mass mail" audience — the one the
selector offers first — sends **11 734 messages to addresses last used more than
five years ago**. A list of that age typically hard-bounces at tens of percent,
while major providers begin throttling above roughly 5% and blacklist well before
20%. The domain would be blocked long before a bounce-processing mechanism had
anything to process.

That reorders the problem. Above 10 000 users the protection that matters is
**before and during** the send, not after it, and none of it needs an inbound
channel.

The design rule is that the system **measures rather than assumes**. Installations
differ too much for the engine to guess who should receive mail: a shop has
customers who order without ever logging in, a subscription site has readers who
never register, a freshly migrated database may have no usage history at all.
Any rule of the form "these accounts are probably dead" is a guess about someone
else's project. What travels between projects is observed delivery behaviour.

1. **A canary batch.** A mailing does not start at full size. The first
   `newsletter.canary` messages are sent and their failure rate is measured, and the
   campaign then parks in `held` — it **never** releases the rest by itself, at
   any measured rate. `newsletter.abort` decides whether the operator is shown a report
   or a refusal. Audiences smaller than `newsletter.canarymin` skip the canary, because
   sampling a list you could send whole is not sampling.
2. **A circuit breaker in the drain.** The drain tracks the rate of **permanent
   recipient-scoped** failures over a rolling window and aborts the mailing when
   it crosses `newsletter.abort`, marking it in the admin view. It counts only what the
   outcome taxonomy below classifies as a recipient verdict — a rejected sender
   or a refused body is not evidence about the list, and treating it as such would
   let one bad message abort a mailing that is otherwise fine.

   The window is defined so two implementations behave the same: the last
   `newsletter.breakwin` results for that campaign, evaluated only once at least that
   many results exist, counted per campaign and reset with it. Below that number
   there is no rate and no abort — a run of three failures out of four says
   nothing.

   It is `newsletter.breakwin` and not `newsletter.canary` because the canary can be switched
   off. Tying the window to a setting whose documented value `0` disables a
   different feature would leave the breaker dividing by zero on exactly the
   installations that chose to send without sampling first — the ones it most
   needs to protect.
3. **Suppression from observed outcomes.** A permanent `RCPT TO` verdict — and
   only that — increments the address in `{prefix}_maildead`. At `newsletter.bouncemax`
   the address stops entering **bulk** audiences. Transactional mail is never
   suppressed: a password reset must still be attempted even for an address that
   failed a newsletter, which is what makes a wrong suppression cheap and a
   missing one expensive.
4. **Ramping.** `mail.rate` already caps throughput; at this size the first
   mailing from a domain with no sending history must ramp rather than burst.
5. **Audience hygiene at queue time.** Addresses are validated with
   `filter_var(..., FILTER_VALIDATE_EMAIL)` and suppressed addresses are skipped
   before a row is written. Both are facts about the address, not opinions about
   the user.

### Verify by whatever means are available, then send

The governing rule, and the one that makes this work across 100 000 unlike
hosts: **use every verification the environment offers, and when none is
available, send anyway.** No check may become a precondition for delivery,
because a check that can fail closed will eventually stop mail on someone's
server. Every step below is optional, and every one of them degrades to "send
it".

The methods, in the order they become available:

1. **Syntax** — `filter_var(..., FILTER_VALIDATE_EMAIL)`. Always available, free,
   applied at queue time. Measured on the user table here: 1 address of 11 845.
2. **Recorded outcomes** — the `bounce` counter from previous sends. Available
   from the second mailing onward, free, and the reason the next mailing is
   always cleaner than the last.
3. **Domain resolution** — `checkdnsrr($domain, 'MX')`, falling back to an `A`
   record because RFC 5321 permits implicit MX. Available wherever outbound DNS
   works, which is nearly everywhere. This one is worth its own paragraph below.
4. **The `RCPT TO` verdict** — only obtainable during the send itself, and only
   when the receiving side does recipient verification rather than accepting
   everything for later bouncing.
5. **An inbound bounce channel** — mailbox polling or VERP. Rarely available,
   opt-in, separate plan.

**Domain resolution is the cheapest large win and it is measured.** Of 11 845
addresses on this installation there are only **864 distinct domains**, and
**330 of them (38%) no longer resolve at all** — no MX, no A. Behind them sit
**902 addresses, 7.6% of the list**, eliminated before a single SMTP connection
is opened. That figure alone sits above the ~5% mark where providers begin
throttling, so on an aged list this check can be the difference between a
completed mailing and a damaged domain.

The cost scales with **distinct domains, not addresses** — 864 lookups took 152
seconds here, sequentially and uncached — so it grows far more slowly than the
list. Verdicts are cached per domain through the existing `Cache` service with a
TTL (`mail.dnsttl`), never re-resolved per mailing, and the TTL is what lets a
domain that comes back be reused without any manual reset.

Three limits stated so nobody over-reads the result:

- a resolving domain proves the domain accepts mail, **not** that the mailbox
  exists — this removes dead providers, not dead people;
- a DNS timeout or a resolver failure is **not** a dead domain. It marks nothing,
  suppresses nothing, and the address is sent to. Fail open, always;
- where DNS is unavailable or `mail.verify` is off, the step is skipped entirely
  and the mailing proceeds on the remaining evidence.

### The campaign is a state machine, and it needs storing

`pending / accepted / failed` describes a **message**. A mailing is a longer-lived
thing that can be held after a canary, released by an operator, aborted by the
breaker or resumed, and none of that fits in a per-row status or in a bare
`fails` counter. `{prefix}_newsletter` therefore carries the campaign state:

```
  `status` TINYINT UNSIGNED NOT NULL DEFAULT 0,
  `audit`  VARCHAR(100) NOT NULL DEFAULT '',   -- audience criterion, not addresses
  `apar`   VARCHAR(100) NOT NULL DEFAULT '',   -- its parameter: group id, days, client set
  `cursor` INT UNSIGNED NOT NULL DEFAULT 0,    -- last source id expanded, 0 = not started
  `expect` INT UNSIGNED NOT NULL DEFAULT 0,    -- audience size counted once when preparing began
  `total`  INT UNSIGNED NOT NULL DEFAULT 0,    -- rows written so far
  `fails`  INT UNSIGNED NOT NULL DEFAULT 0,
  `note`   VARCHAR(255) NOT NULL DEFAULT '',   -- why it stopped
```

`status` values are fixed so two implementations cannot disagree: `0` draft,
`1` preparing, `2` queued, `3` canary, `4` held, `5` running, `6` done,
`7` aborted.

`cursor` holds the last source-table id the producer expanded, and the producer
always orders its source by that table's primary key ascending — `_users.id` for
every user-derived audience. An audience assembled from more than one source runs
its sources in a fixed declared order and encodes which one is current in `apar`,
so a single ascending `cursor` remains meaningful.

**Progress needs both numbers stored, not one.** `expect` is written once, on
entry to `preparing`, from a `COUNT` over the criterion; `total` counts the rows
actually written. Progress is `total` of `expect`. Neither is recomputed later:
the audience is live data and a user registering mid-expansion would otherwise
move the denominator under a restart, making progress jump backwards or a
finished campaign look unfinished. `expect` is an estimate frozen at the start
and is allowed to differ from the final `total` — the campaign completes when the
cursor is exhausted, never when the two numbers agree.

| # | Transition | Who performs it |
|---|---|---|
| 1 | draft → preparing | the operator, on save. Writes the criterion, nothing else |
| 2 | preparing → preparing | the producer job, one batch per run, advancing `cursor` |
| 3 | preparing → queued | the producer, when the cursor is exhausted. All rows exist with `hold = 1` |
| 4 | queued → canary | the producer, in the same transaction as 3, when `newsletter.canary > 0 AND expect > 0 AND expect >= newsletter.canarymin`: it marks the canary slice `camp = 1, hold = 0` |
| 5 | queued → running | the producer, in the same transaction as 3, otherwise — `newsletter.canary = 0`, or `expect = 0`, or `expect < newsletter.canarymin`: it clears `hold` on everything |
| 6 | canary → held | the drain, once every canary row has a result |
| 7 | held → running | the operator, explicitly. Clears `hold` on the rest |
| 8 | preparing/canary/running → aborted | the operator, or the drain on crossing `newsletter.abort`. Sets `hold = 1` |
| 9 | aborted → running | the operator, after deciding to continue anyway |
| 10 | running → done | the drain, when nothing is left to claim |

Rows 3-5 happen together so a campaign is never observably `queued` with nothing
claimable and no canary — the drain would see an audience it must not touch and
no instruction about it.

The condition on row 4 is three tests, not one. `canarymin` alone is not enough:
`newsletter.canary = 0` is the documented way to switch the canary off, and an
audience of 100 000 would otherwise enter `canary` with a slice of zero rows and
sit in a state nothing can ever finish. `expect > 0` guards the same dead end
from the other side — an audience that expanded to nothing. All three read the
**frozen `expect`**, never a fresh count of a live audience, so a restart cannot
send the campaign down a different branch than the one it started on.

An earlier revision listed `draft → queued` performed by the operator on save,
which is the synchronous expansion this design replaces; that transition no
longer exists.

`held` is the answer to a contradiction in an earlier revision, which said both
"continue automatically below the threshold" and "the canary must not release the
audience by itself". **The canary never releases.** It always parks in `held` and
waits for a human, and `newsletter.abort` decides whether the operator is looking at a
report or at a refusal. Automatic release is the one behaviour that would let a
bad list drain unattended at three in the morning.

**The queue has to honour the state, or the state is decoration.** Campaign
states live on `_newsletter`, but the drain claims from `_mail`, so without a
per-row marker it would happily send the whole audience of a campaign sitting in
`held`. `camp` and `hold` in the `_mail` DDL above carry it — they are part of
the table from the start, not added later, because the claim index leads with
`hold` and an index cannot reference a column that does not exist yet.

The claim predicate gains `hold = 0`, and `hold` is the only thing the state
machine touches on `_mail`: expansion writes the main audience with `hold = 1`
and the canary slice with `camp = 1, hold = 0`. `hold` joins the claim index as
its leading column, so a held campaign costs the drain nothing.

**`ref` alone does not identify a campaign's rows.** It is a plain integer and
means nothing outside its `kind`, so a release keyed on `ref` would also unhold
any transactional row that happens to carry the same number. Every campaign-wide
update carries the full predicate:

```sql
UPDATE {prefix}_mail SET hold = 0
 WHERE kind = 'newsletter' AND ref = :id AND camp = 2 AND status = 0
```

`camp = 2` keeps the release off the canary slice, which was already released and
already has results; `status = 0` keeps it off rows that are finished. Abort is
the same predicate with `hold = 1`. `kind_ref_status` covers it.

That is deliberately a flag rather than a join against `_newsletter` on every
claim — the claim runs constantly and must stay a single-table range scan.

### Expanding the audience is a job, not a click

Writing one row per recipient is fine at 164 and impossible at 100 000: an
`INSERT` loop of that size inside the admin request that pressed "save" will hit
the execution limit, and there is no way to resume it because nothing recorded
how far it got.

Expansion is therefore work the scheduler does, with its own state:

- `draft → preparing` happens on the operator's action and writes nothing but the
  criterion;
- the producer job expands in batches ordered by the source primary key ascending,
  recording the last id reached in `_newsletter.cursor`, so a killed run resumes
  instead of restarting or duplicating;
- when the cursor is exhausted the campaign moves to `queued` and, in the same
  transaction, to `canary` or `running` — transitions 3-5 above;
- the admin list shows `preparing` with its progress, because a mailing that
  looks queued but is still materialising is exactly the state an operator would
  otherwise interpret as broken.

States therefore read: `draft` → `preparing` → `queued` → `canary` → `held` →
`running` → `done`, with `aborted` reachable from `preparing`, `canary` and
`running`.

### The audience is a criterion, not a list

Dropping `_newsletter.mails` leaves nowhere to record who a mailing was for, so
`audit` and `apar` replace it: `all`, `subs`, `group`, `active`, `money`,
`order`, `shop` and the parameter each needs — a group id, a number of days, a
client set. The rows are expanded by the producer job **during `preparing`**, in
resumable batches; reaching `queued` is what marks the expansion finished, not
what starts it.

That also removes the last reason for the audience `<select>` to carry addresses.

### The message body must stop changing under the queue

Queue rows for a mailing hold `ref` and an empty `body`, so the text is read from
`_newsletter` at send time — and `admin/modules/newsletter.php:239-260` lets an
administrator edit or delete that row while the queue is draining. Recipients
would then receive a body nobody approved, or the remaining rows would fail
because their source disappeared.

**Once a campaign leaves `draft` it is immutable, `done` included.** Title, body
and audience are frozen: the admin screen refuses the edit and offers to abort,
or to clone into a new campaign for a resend. An earlier revision exempted `done`,
which is wrong — delivered rows keep `ref` pointing at that body for as long as
retention holds them, so editing a finished campaign rewrites the record of what
was actually sent, and re-running the same id would mix two texts under one
history.

Deleting a campaign that still has queue rows is refused for the same reason.
This is cheaper than snapshotting the body per campaign and it keeps one copy of
the text, which is why `ref` exists in the first place.

### What an SMTP failure actually says

Treating every `5xx` as evidence about the recipient is wrong: a rejection can
come from `AUTH`, `MAIL FROM`, `RCPT TO`, after `DATA`, from a content filter, or
from the relay's opinion of our sender reputation. Only one of those is about the
address.

Each attempt is classified before anything is recorded:

| Phase | Permanent verdict means |
|---|---|
| connect, `EHLO`, `AUTH` | **transport-wide** — the configuration is broken. Abort the run, do not touch any row's counter, raise it in the admin |
| `MAIL FROM` | **campaign-wide** — the sender is refused. Abort the mailing, suppress nothing |
| `RCPT TO` | **recipient** — the only case that may increment suppression |
| after `DATA`, content or policy | **message-wide** — the body is refused. Fail the row, suppress nothing; every recipient would otherwise be blamed for one bad body |

`4xx` at any phase is temporary: retry with backoff, never suppress.

The row stores the phase and the code alongside `error`, because "550" without
its phase cannot be interpreted later — and the circuit breaker counts only the
recipient-scoped permanent failures, so a broken relay trips the transport alarm
instead of quietly marking ten thousand addresses dead.

### Recording failures so the next send is cleaner

Verification is only half of it; what makes the list improve over time is that
every verdict is kept.

- **Per address — a suppression registry keyed by the address**, not a column on
  `_users`. Bulk audiences include shop, order and money clients whose addresses
  need not exist in `_users` at all, so a `_users.bounce` column cannot hold a
  verdict for half the people it is supposed to protect. One small table keyed by
  the normalised address, carrying the failure count, the last phase and code,
  and when it was last seen:

```
CREATE TABLE `{prefix}_maildead` (
  `id`    INT UNSIGNED NOT NULL AUTO_INCREMENT,
  `email` VARCHAR(255) COLLATE utf8mb4_bin NOT NULL DEFAULT '',
  `fails` TINYINT UNSIGNED NOT NULL DEFAULT 0,
  `phase` VARCHAR(10) NOT NULL DEFAULT '',
  `code`  VARCHAR(20) NOT NULL DEFAULT '',
  `time`  DATETIME NOT NULL DEFAULT CURRENT_TIMESTAMP,
  PRIMARY KEY (`id`),
  UNIQUE KEY `email` (`email`)
) ENGINE={engine} DEFAULT CHARSET={charset} COLLATE={collate};
```

  It is incremented **only** by a permanent `RCPT TO` verdict, per the taxonomy
  above. At `newsletter.bouncemax` the address stops entering bulk audiences.
  Transactional mail ignores the registry entirely.

  **"Normalised" is a contract, not an adjective.** A lookup that disagrees with
  the unique index either misses suppressions or collides them, so one function
  produces the stored form and every read goes through it: trim surrounding
  whitespace; reject the address outright if it contains any control character;
  lowercase the **domain** only; leave the **local part** byte-for-byte, since
  case is significant there by RFC even where most providers ignore it.

  **A non-ASCII domain is converted to punycode, not stored as it arrived.** An
  earlier revision claimed the opposite and got the consequence backwards: under
  a binary collation `почта.рф` and `xn--80a1acny.xn--p1ai` are two different
  keys for one mailbox, which is precisely the double spelling it claimed to
  prevent. `idn_to_ascii()` produces the canonical form. It needs `ext-intl`,
  which this plan does **not** add to the requirements — so it is probed like
  `openssl` and `proc_open`: present, it canonicalises; absent, a non-ASCII
  domain is refused at the normaliser with a stated reason rather than stored in
  a form that will not match itself later.

  The column's collation must match that rule. `{collate}` is case-insensitive on
  this installation, which would fold local parts the normaliser deliberately
  keeps distinct, so `email` is declared with a binary collation and the
  case-folding lives entirely in the normaliser where it can be reasoned about.
- **Per domain — cached, and only cached.** A dead-domain verdict skips the
  address **for the current run** and is cached with `mail.dnsttl`; it never
  increments the permanent registry. DNS is a statement about right now: a domain
  that fails to resolve today may resolve next week, the TTL would expire but a
  permanent counter would not. When the TTL lapses and the domain resolves again,
  the negative verdict is simply gone.
- **Per mailing** — `{prefix}_newsletter` gains `fails INT UNSIGNED NOT NULL
  DEFAULT 0` beside the existing `send` counter, so a mailing carries both what
  it delivered and what it lost.

Where an operator actually sees it, so the record is not write-only:

- **`newsletter` home** — the mailing list already shows `send`; it gains the
  failure count and rate beside it, which is the first place anyone looks after a
  campaign;
- **`newsletter&op=add`** — each audience option shows its count and the failure
  rate it produced last time, so the next choice is informed by the previous
  result rather than by a rule of thumb;
- **the queue view** — filtered by `status = failed`, with the `error` string, for
  the question "which addresses, and why".

That closes the loop the requirement asks for: a mailing records what failed, the
next mailing skips it, and the operator can see how much was skipped and why.

The counter is a running total rather than a flag on purpose: one failure can be
a transient misclassification, several are a pattern. An administrator can clear
it, and the domain cache expires on its own, so nothing becomes permanently
unreachable through an old verdict.

**Audience choice stays with the operator.** An activity window — "users seen in
the last N" — is offered as one more selectable audience beside the existing
ones, because on a list like the one measured above it is the difference between
11 845 recipients and 111. It is **not** the default and not the protection: only
the site owner knows whether dormant accounts on their project are dead weight or
their actual customers. The engine's job is to show the count next to every
option, add the hard-failure rate observed for that audience once there is send
history, and then do what it is told.

Only after those does an inbound channel add value, and it stays a separate,
opt-in plan: polling a mailbox needs one configured per installation, and VERP
with a catch-all needs MX control that shared hosting often does not give. Both
are improvements on top of the four above, not substitutes for them.

### How much is actually invisible

"Asynchronous bounces cannot be read without an inbound mailbox" is true but
narrower than it sounds, and the boundary is worth stating because it decides how
much the inbound plan is even worth.

**What determines the split is the transport topology, not the queue.** Sending
straight to the recipient's MX makes most dead-address verdicts synchronous: the
receiving server answers `RCPT TO` with `550 5.1.1` when the mailbox is gone, and
a dead domain fails at resolution before a connection exists. Sending through a
relay — a provider or the host's smarthost — moves that verdict past our
horizon, because the relay accepts everything at `RCPT` and bounces later to the
envelope sender. Most installations will use a relay, since hosts routinely block
outbound port 25 and direct sending needs PTR, SPF and IP reputation to work at
all. Direct-to-MX is therefore out of scope, but the reason is worth recording:
it is the difference between seeing a bounce and not.

**What stays invisible even so** is a genuinely narrower set than "bounces":
mailboxes that exist but are full, content or policy rejections issued after
`DATA` was accepted, and silent discards. Those cannot be inferred from the
dialogue at all.

**What is still knowable without any inbound mail** is the send history itself.
After one mailing every address carries a real outcome, and that signal is
project-agnostic in a way no usage heuristic is. The risky send is therefore the
first one on an unmeasured list, which is exactly what the canary batch and the
circuit breaker cover.

Usage signals — `lastvis`, a click back to the site — indicate liveness rather
than death, and only sometimes: an address can be perfectly deliverable while its
owner has not logged in for years, which is the normal state of a shop customer
or a newsletter reader. They are inputs an operator may choose to filter on, not
evidence the engine should act on by itself.

The conclusion is not "ignore the problem". It is that the synchronous half plus
the canary and the breaker carry the reputation risk without assuming anything
about the project, and the inbound channel refines an already-safe system rather
than rescuing an unsafe one.

### Where each setting lives

Three screens exist today and between them they hold five settings, split along a
line that stops making sense once a queue exists.

| Screen | Holds now |
|---|---|
| `config` → Почта (`_MAILOPT`, tab 6) | `mtemp` |
| `newsletter&op=config` | `newsletter.active`, `newsletter.count` |
| `newsletter&op=add` | mailing title, audience, body |

Two problems are visible without adding anything:

- **`newsletter.active` duplicates `scheduler.jobs.newsletter.active`.** The same
  mailing is gated twice, in two files, on two screens, and `updateNewsletter()`
  checks only the first (`core/system.php:3754`). One of them has to go, and the
  scheduler flag is the one that belongs to a scheduled job.
- **`newsletter.count` is not a newsletter setting.** It is how many messages one
  drain run sends. Once the queue carries every kind of mail, that number governs
  password resets too. It becomes `mail.batch` and disappears from the newsletter
  screen.

The line that does make sense: **`$conf['mail']` is *how mail is delivered*,
`$conf['newsletter']` is *how a campaign is run*.**

**`config` → Почта** — everything about delivery, for every message the system
sends:

- transport, sender identity, SMTP, Sendmail path;
- test send;
- queue mechanics — `batch`, `rate`, `tries`, `backoff`, `keep`, `keepbulk`,
  `verify`, `dnsttl`;
- the existing `mtemp`, left where it is.

It also gains the `checkPerms(CONFIG_DIR.'/mail.php')` writability notice that
`newsletter&op=config` already shows for its own file
(`admin/modules/newsletter.php:268`) — same helper, same purpose.

**`newsletter&op=config`** — campaign policy only, which is what the screen is
actually for:

- canary batch size, and the audience size below which the canary is skipped;
- how many results the circuit breaker evaluates over;
- hard-failure rate that aborts a mailing;
- failures before an address stops entering bulk audiences.

That is the whole of `config/newsletter.php`: `canary`, `canarymin`, `breakwin`,
`abort`, `bouncemax`. It loses `active` to the scheduler job and `count` to
`mail.batch`, so the file stops being a mixture and holds only campaign policy —
which is exactly the line the section above draws.

Each field is validated on save rather than trusted:

- `canary` and `canarymin` — non-negative integers; `canary = 0` is valid and
  means "no canary";
- `breakwin` and `bouncemax` — **positive** integers. A `breakwin` of `0` would
  divide by zero in the breaker, and a `bouncemax` of `0` would suppress every
  address on its first result;
- `abort` — an integer percentage in `1..100`.

An earlier revision called all three of `canary`, `canarymin` and `breakwin`
non-negative and then refused `0` for `breakwin` two sentences later.

**`newsletter&op=add`** — unchanged in shape. The audience selector keeps its
`_NLWHERE` row and its per-option counts; what changes is that every option
becomes a criterion rather than a list of addresses, and each one shows the
hard-failure rate observed for it last time next to the count.

### Admin

Two different screens, deliberately kept apart.

**Settings — `admin.php?name=config`, tab «Почта» (`_MAILOPT`, index 6).** No
new admin module. The tab today holds only `mtemp`; it gains, in this order:

1. transport selector;
2. sender identity — name, address, Reply-To;
3. SMTP settings — host, port, encryption, auth, user, password, timeout;
4. Sendmail path;
5. test send;
6. the existing `mtemp` template, left where it is.

SMTP rows are shown only when the transport is SMTP, and the Sendmail path only
when it is Sendmail. The existing `data-sl-tab-show` hook keys off the tab index
and cannot express that, so a small value-driven counterpart is added to the
shared admin script, named under the `sl-*` convention. It is progressive: with
the script unavailable every row is simply visible.

The password field renders empty regardless of what is stored, and `save()`
treats an empty submission as "keep the current value".

**Test send** is a fourth operation in the module's `switch ($op)` — `mailtest`,
lowercase and within the 4-12 character limit for admin handlers. It validates
`checkSiteToken()`, defaults the recipient to `$conf['adminmail']`, sends
through the configured transport and reports either success or the exact
`getError()` string. It is the only place in the panel that proves the settings
work before real mail depends on them.

**Every action is POST and every action checks the token.** Test send, retry,
delete, releasing a held campaign, aborting and resuming are all state-changing,
so none of them is reachable by a link:

| Action | Method | Token |
|---|---|---|
| test send | POST | `checkSiteToken()` |
| retry a failed row | POST | `checkSiteToken()` |
| delete queue rows | POST | `checkSiteToken()` |
| release a held campaign | POST | `checkSiteToken()` |
| abort a running campaign | POST | `checkSiteToken()` |
| resume an aborted campaign | POST | `checkSiteToken()` |

This is written out because the existing comment action links show how easily a
state change ends up as a `GET` with a token in the query string
(`core/system.php:5627-5658`), which is the pattern being removed there and must
not be reintroduced here.

**Queue state** lives in `admin/modules/newsletter.php`, not in the config tab:
list with filters by `kind` and `status`, the failure reason, retry and delete
actions, the campaign state with its `preparing` progress, and the
pending/accepted/failed counts from `getStats()`. Configuration and
operational state are different questions and belong on different screens.
Result query, count query, pager URL, selected filter state and highlighting
stay consistent, per the admin list-filter parity rule in `.rules/global.md`.

New user-visible text lands in all six locales at once
(`de`, `en`, `fr`, `pl`, `ru`, `uk`), in `admin/lang/*.php` where `_MAILOPT`
already lives.

## Verification

### Transport (stage 1)

- PHP Mail delivers with no configuration at all, on a freshly upgraded
  installation;
- Sendmail delivers through the configured path, and a wrong path fails loudly
  rather than silently;
- SMTP delivers plain, with STARTTLS and with implicit SSL;
- SMTP delivers with `AUTH LOGIN` and with `AUTH PLAIN`;
- a multi-line `EHLO` response is parsed correctly, and a relay that answers
  with continuation lines does not break the dialogue;
- a dead host and a black-holed port both fail on the timeout instead of hanging
  the request;
- the socket is closed on every failure path;
- a recipient, sender name or Reply-To containing `\r\n` is rejected and never
  reaches a header or an SMTP envelope;

  subject encoding, header folding and line endings are brought to MIME and SMTP

  a long non-ASCII subject changes those bytes on purpose, and the current
  unfolded output is a defect, not a baseline;
- `From`, `Reply-To` and the envelope sender resolve exactly as the identity
  table specifies, with and without the config fields set;
- no message carries a `Return-Path` header written by us;
- `mail.sendmail` containing arguments or shell metacharacters is refused, and
  no transport ever builds a shell command string;
- every failure appears in `storage/logs/error_site.log` with the transport and
  the response.

  `body`, and no row ever carries the scheduler's;
- `title` holds the raw subject and the delivered message carries a correctly
  encoded one;
- a request that sends mail returns without waiting for delivery;
- a queued message is delivered by the drain task;
- a failing address increments `tries`, stores a non-empty `error`, retries,
  then lands in failed;
- two concurrent drain runs never send one row twice;
- a run killed mid-batch releases its claim after the lock timeout;
- a delivery failure leaves the originating comment, order or registration
  intact;
- pruning removes only rows past the retention window, and applies the shorter
  bulk window to `newsletter` rows only.

### Scale (stage 2 and 3)

Measured against a synthetic list, not assumed:

- 100 000 queued newsletter rows occupy the size of 100 000 short rows plus
  **one** body — `ref` is set, `body` is empty, and total table growth is
  compared against the same mailing with inline bodies;
- a drain run resolves the shared body once per batch, not once per row;
- a `ref` pointing at a deleted newsletter fails the row with a stated reason
  and never sends an empty message;
- a CLI drain run empties a 100 000 row queue in bounded wall-clock time, with
  one SMTP connection, and resumes correctly after being killed halfway;
- `mail.rate` is respected: the drain does not exceed the configured messages
  per minute even when the queue is deep and the relay is fast;
- a throttling reply from the relay is retried with backoff rather than counted
  as a permanent failure;
- `EXPLAIN` on the claim query still shows range access with 100 000 pending
  rows, not a scan;
- an invalid or suppressed address never produces a queue row, and every audience
  option reports a count matching the rows it would create;
- the canary batch runs first, parks the campaign in `held` and **never** releases
  the rest on its own, whatever the measured rate;
- a campaign in any state but `draft` cannot have its title, body or audience
  edited — `done` included — and cannot be deleted while queue rows remain;
  a resend is a clone into a new campaign id;
- the producer resumes from `cursor` after being killed mid-expansion, producing
  neither duplicate nor missing rows;
- a campaign in `held` has no claimable rows: the drain leaves it alone until an
  operator releases it;
- a permanent rejection at `RCPT TO` increments the suppression registry; a
  permanent rejection after `DATA`, at `MAIL FROM` or at `AUTH` does not, and the
  last of those aborts the run and raises a transport alarm instead;
- a dead-domain verdict skips the address for that run and leaves the registry
  untouched, and the address is tried again once the cache entry expires;
- an address that exists in no `_users` row — a shop or order client — is
  suppressed and un-suppressed exactly like a registered one;
- the rate limit holds across two consecutive runs and across a manual trigger,
  not only within one run;
- a comment queued over HTMX starts a drain without waiting for the next full
  page load;
- an oversized subject is refused at enqueue, and a multi-line SMTP response is
  stored truncated without failing the write that records it;
- a dead domain is resolved once and skipped for every address behind it, and the
  verdict survives into the next mailing through the cache;
- **a DNS failure sends the message.** With the resolver unreachable, `mail.verify`
  off, or the domain simply not answering, nothing is suppressed and nothing is
  counted — verified by breaking resolution deliberately and confirming the
  mailing still completes;
- a mailing whose hard-failure rate crosses the threshold is aborted, not
  completed, and says so in the admin view;
- a permanent rejection **at `RCPT TO`** marks the address and excludes it from
  the next bulk audience, while a transactional message to the same address is
  still attempted;
- a permanent rejection at `AUTH`, `MAIL FROM` or after `DATA` marks **no**
  address, per the outcome taxonomy;
- a `4xx` at any phase is retried and never increments the suppression counter.

### Tests

Added with the stage that introduces the behaviour, not at the end:

- header assembly — a known message produces the expected header block on each
  transport;
- address sanitising — `\r`/`\n` in any address field aborts the send;
- SMTP reply parsing — multi-line and single-line responses, and an unexpected
  code;
- dot-stuffing — a non-base64 body whose line begins with `.` arrives intact and
  is not truncated;
- line length — a 5 KB message produces base64 lines of at most 76 octets, not
  one 6720-octet line as today;
- header folding — a long site name and a long non-ASCII subject fold across
  lines with every encoded word inside the 75-character limit, still using B
  encoding;
- line endings — a body stored with bare LF goes on the wire as CRLF;
- claim atomicity — two `getBatch()` calls never return the same row;
- backoff — a failed attempt moves `ntime` forward and the row is skipped until
  then;
- attempt cap — the row lands in failed and stops being claimed;
- subject encoding — a non-ASCII `title` round-trips through the drain;
- retention — `deleteQueue()` removes only rows past the window.

## Open decisions

Everything below is deliberately unresolved. Each has a placeholder that lets
implementation start, and each needs a real answer before the stage that depends
on it is called done. They are listed here so a session that only reads this file
knows what has not been settled.

### Canary sampling — settled

The canary measures the audience, so it must not be the head of it. The first
`newsletter.canary` rows by `id` are the oldest accounts on an aged list and the
newest on a growing one, and either way they are not the mailing.

- the slice is drawn **at random** across the expanded audience;
- it is spread across recipient domains rather than concentrated: a hundred
  addresses that all resolve to one provider measure that provider, not the list;
- the rate is computed over the canary as a whole, with the slice size as the
  denominator, and a single failure in a hundred is a rate of one percent rather
  than a signal;
- below `newsletter.canarymin` there is no canary and no measurement, by design.

### Bulk-mailing thresholds — settled

| Setting | Value | Why this number |
|---|---|---|
| `newsletter.canary` | `100` | At a true failure rate of 10%, a hundred messages estimates it to roughly ±6% — enough to tell a normal list from a catastrophic one. Fifty would decide on noise |
| `newsletter.canarymin` | `500` | Below that the canary is a large fraction of the audience and stops being a sample; the mailing simply runs |
| `newsletter.breakwin` | `100` | The denominator the breaker divides by. Kept separate from `canary` because that one may legitimately be `0`, which would leave the breaker without a window on exactly the installations that chose to send unsampled |
| `newsletter.abort` | `10` | Providers throttle around 5% and blacklist well before 20%. Ten sits above ordinary noise and below irreversible damage, and does not fire on a merely mediocre list — a threshold that cries wolf gets raised by the operator, which is worse than a sane default |
| `newsletter.bouncemax` | `2` | One `5xx` can be a misclassification: some servers answer 550 on a temporary policy or overload. Two is a pattern. The cost is asymmetric — a wrongly suppressed address still receives transactional mail, while an unsuppressed dead one damages reputation on every send |
| `mail.dnsttl` | `604800` | One week, so a revived domain becomes usable again without any manual reset |

**Activity window** is offered as a free-form field in days beside the existing
audience options, not as a fixed set. A shop may reasonably want five years and a
news site ninety days; the engine shows the resulting recipient count as the
number is typed and does not pick for anyone. On the installation measured above
that reads 9 recipients at 365 days, 54 at 1095 and 111 at 1825.

### Numbers that need a measurement, not an opinion

- **Per-message cost on a working transport.** The 26.7 s figure in the facts
  above is a connect timeout on a host with no transport configured, not a
  delivery cost. `mail.batch = 25` and `mail.rate = 60` are placeholders sized
  for safety and must be revisited against a real measurement, following
  `docs/PERFORMANCE.md`.
- **Comment submit latency, before and after.** Same reason — the baseline has to
  be re-established before any before/after claim is made.
- **Retention windows.** `keep = 30` and `keepbulk = 3` are guesses about how
  long anyone looks back; the queue's real growth rate will say more.

### Architecture, still open

- **The inbound bounce channel**, when that separate plan starts: mailbox polling
  or VERP with a catch-all. Both need infrastructure the administrator provides,
  and the choice determines whether it is usable on shared hosting at all. Not
  needed for any stage here.

## Risks

- An SMTP relay whose dialect the hand-written dialogue does not survive; the
  test send is what surfaces that before real mail depends on it, and the named
  hazard list above is what keeps the risk enumerable.
- Silent body corruption from dot-stuffing or line-length handling — the failure
  mode that does not announce itself, which is why both are tested rather than
  reviewed.
- A mailing sized for the current 164 subscribers being run against a list three
  orders of magnitude larger; the scale checks exist to stop that being
  discovered in production.
- Provider throttling misread as delivery failure, burning the attempt cap on
  messages that were never rejected.
- A blocking socket without a timeout turning one bad relay into a hung site;
  every read and the connect itself carry one.
- The SMTP password reaching a backup, a dump or a page source.
- Rows claimed by a run that dies before recording a result; the lock timeout
  and `KEY locked` release them.
- Retry storms against a permanently broken address; the attempt cap prevents
  them.
- The newsletter conversion losing addresses still pending in the CSV column.
- A batch size tuned for CLI cron overrunning the request budget under
  pseudo-cron.
- Queue growth on installations that never prune.

## Out of scope

- APIs of individual mail providers.
- Incoming mail, mailboxes, webhooks and unsubscribe links.
- **Asynchronous** bounce processing, which needs one of those inbound channels.
  The synchronous half — `5xx` classification, the `bounce` suppression counter
  and the mailing circuit breaker — is **in** scope and ships in stage 3, because
  it needs no infrastructure the administrator has to provide.
- Open and click statistics.
- Composer dependencies, third-party libraries and provider SDKs — see
  **Self-sufficiency** above; the SMTP client is written against the protocol.
- Providers reachable only through an HTTP API, for the same reason.
- Attachments, CC and BCC, until existing code needs them.
- Templating of message bodies beyond the existing `$conf['mtemp']`.
- Reworking who receives admin notifications (`admins.smail`).
